# 构建镜像

构建容器镜像既是技术活，也是一门艺术。你需要让镜像保持小巧、专注，以提升安全性，但同时也得权衡潜在的取舍，比如缓存带来的影响。在本系列内容中，我们将深入探讨镜像的奥秘、构建方式以及最佳实践。

## 介绍

学习如何构建精简高效的生产级 Docker 镜像，这对于减少生产环境的开销、提升部署效率至关重要。

## 一、理解镜像层

### 说明

正如你在什么是镜像？中学到的，容器镜像由多个层组成。这些层中的每一层一旦创建就不可更改。但这到底意味着什么？这些层又是如何被用来创建容器可使用的文件系统的呢？

### 镜像层

镜像中的每一层都包含一组文件系统变更——包括新增、删除或修改操作。我们来看一个理论中的镜像：

1. 第一层添加了基本命令以及一个包管理器，比如 apt。
2. 第二层安装 Python 运行环境和用于依赖管理的 pip。
3. 第三层会复制应用程序特定的 requirements.txt 文件。
4. 第四层安装该应用程序的特定依赖项。
5. 第五层复制了应用的实际源代码。

这一特性十分有益，因为它支持在不同镜像之间复用层。例如，假设你想开发另一个 Python 应用程序，借助分层机制，你可以使用同一个 Python 基础层。这会加快构建速度，并减少分发镜像所需的存储量与带宽。

**层允许你通过复用他人的基础层来扩展其镜像，这样你只需添加应用所需的数据。**

### 堆叠层

分层功能借助内容可寻址存储和联合文件系统得以实现。虽然这会涉及一些技术细节，但具体的工作原理如下：

1. 每一层下载完成后，都会被解压到主机文件系统中属于它自己的目录里。
2. 当你从镜像运行容器时，会创建一个联合文件系统，其中各层相互堆叠，形成一个全新的统一视图。
3. 容器启动时，其根目录会通过 chroot 被设置为这个统一目录的位置。

创建联合文件系统时，除了镜像层之外，还会为运行中的容器专门创建一个目录。这使得容器可以对文件系统进行修改，同时又能让原始镜像层保持不变。这样就可以基于同一个基础镜像运行多个容器。

### 实操

在这份实操指南中，你将使用docker container commit命令手动创建新的镜像层。请注意，你几乎不会通过这种方式创建镜像，因为通常你会使用 Dockerfile。但这样做能让你更轻松地理解整个工作原理。

#### 创建基础镜像

1. 安装并配置好Docker Desktop

2. 在终端中，运行以下命令启动一个新的容器

`docker run --name=base-container -ti ubuntu`
**使用一个正在运行的容器创建镜像副本**
镜像下载完成且容器启动后，你应该会看到一个新的 shell 提示符。这是在容器内部运行的环境。其显示效果与以下内容类似（容器 ID 会有所不同）：

root@d8c5ca119fcd:/#

3. 在容器内，运行以下命令来安装 Node.js：


`apt update && apt install -y nodejs`

该命令运行时，会在容器内下载并安装 Node。在联合文件系统的语境下，这些文件系统的更改会发生在该容器独有的目录内。

4. 运行以下命令验证 Node 是否已安装：


`node -e 'console.log("Hello world!")'`

5. 既然你已经安装了 Node，就可以将所做的更改保存为新的镜像层，从该镜像层可以启动新的容器或构建新的镜像。要完成此操作，你需要使用docker container commit命令。在新终端中运行以下命令：


`docker container commit -m "Add node" base-container node-base`

6. 使用 docker image history 命令查看镜像的层


`docker image history node-base`

7. 要证明你的镜像已安装 Node，你可以使用这个新镜像启动一个新的容器：


 docker run node-base node -e "console.log('Hello again')"

 完成这一步后，你应该会在终端中看到“Hello again”的输出，这表明Node已安装成功且可以正常运行。

8. 既然你已经完成了基础镜像的创建，就可以删除那个容器了：

`docker rm -f base-container`

**基础镜像作为构建其他镜像的基础。任何镜像都可作为基础镜像使用。不过，有一些镜像是专门设计作为构建模块的，为应用程序提供基础或起点。**

在这个示例中，你可能不会部署这个node-base镜像，因为它目前还不能实际执行任何操作。但它可以作为你进行其他构建的基础。

#### 对比commit构建和build构建

| 特性 | docker commit（从容器创建） | Dockerfile（通过 docker build 创建） |
| ---- | ---- | ---- |
| 构建方式 | 手动、命令式。在容器内手动执行命令后"拍照"保存。 | 自动、声明式。通过代码(Dockerfile)描述构建步骤。 |
| 可重复性 | 低。构建过程依赖人工操作，无法保证每次得到完全一致的结果。 | 高。只要Dockerfile不变，构建结果就是确定的。 |
| 可追溯性 | 差，形成"黑箱镜像"。无法从镜像本身得知是如何构建的，docker history 也看不到详细过程。 | 好。Dockerfile本身就是一份完美的构建文档，所有步骤都清晰可见。 |
| 版本控制 | 不支持。无法纳入Git等版本控制系统。 | 支持。Dockerfile是文本文件，非常适合进行版本管理。 |
| 镜像体积 | 易臃肿。会原样保留容器内的所有改动，包括临时文件、缓存等无用数据。 | 可优化。可以通过多阶段构建等技巧，精确控制最终镜像的内容和大小。 |
| 自动化(CI/CD) | 困难。手动过程难以集成到自动化流水线。 | 原生支持。是CI/CD流程的标准做法。 |

#### 构建应用镜像

既然你已经有了基础镜像，就可以对其进行扩展来构建其他镜像。

1. 使用新创建的 node-base 镜像启动一个新容器：

`docker run --name=app-container -ti node-base`

2. 在此容器内，运行以下命令以创建一个 Node 程序：


`echo 'console.log("Hello from an app")' > app.js`

要运行这个 Node 程序，你可以使用以下命令，并查看屏幕上打印的信息：
`node app.js`

3. 在另一个终端中，运行以下命令将此容器的更改保存为新镜像：


`docker container commit -c "CMD node app.js" -m "Add app" app-container sample-app`
该命令不仅会创建一个名为 sample-app 的新镜像，还会向镜像中添加额外配置，以设置容器启动时的默认命令。在本例中，你将把它设置为自动运行 node app.js。
4. 在容器外的终端中，运行以下命令以查看更新后的层：


`docker image history sample-app`

5. 最后，使用全新的镜像启动一个新容器。由于你指定了默认命令，可以使用以下命令：


`docker run sample-app`

6. 既然你已经用完了容器，你可以使用以下命令将其删除：


`docker rm -f app-container`

## 二、 编写Dockerfile文件

### 说明

Dockerfile 是一种基于文本的文档，用于创建容器镜像。它向镜像构建器提供要运行的命令、要复制的文件、启动命令等相关指令。

Dockerfile 是一种基于文本的文档，用于创建容器镜像。它向镜像构建器提供要运行的命令、要复制的文件、启动命令等相关指令。
举个例子：
```dockerfile
FROM python:3.13
WORKDIR /usr/local/app

# Install the application dependencies
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# Copy in the source code
COPY src ./src
EXPOSE 8080

# Setup an app user so the container doesn't run as the root user
RUN useradd app
USER app

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```

### 常用指令

Dockerfile中的一些常见的指令；

1. FROM <image> - 该指令指定了构建所基于的基础镜像。**如果本地没有对应的镜像，则会自动去Docker Hub上拉取**
2. WORKDIR <path> - 该指令指定“工作目录”，即镜像中用于复制文件和执行命令的路径。**创建镜像的本质是容器的快照，所以需要运行一个临时的容器，这里的WORKDIR指定后续构建镜像的工作目录是镜像内部文件系统里的一个逻辑路径，不是数组及磁盘存在的位置**
*WORKDIR /app等价于：这个虚拟磁盘里面，有一个文件夹叫/app，并且设置虚拟机开机默认就 cd 进到这个文件夹。*
3. COPY <host-path> <image-path> - 该指令告知构建器从主机复制文件并将其放入容器镜像中。
4. RUN <command> - 该指令告知构建器运行指定的命令。
5. ENV <name> <value> - 该指令用于设置运行中的容器将使用的环境变量。
6. EXPOSE <port-number> - 该指令在镜像上设置配置，指明该镜像希望暴露的端口。
7. USER <user-or-uid> - 此指令为所有后续指令设置默认用户。
8. CMD ["<command>", "<arg1>"] - 该指令设置使用此镜像的容器默认运行的命令。

>构建完成之后镜像被 Docker 保存在 Docker 守护进程管理的私有存储区域：
>Linux：/var/lib/docker（overlay2 分层存储）
>Windows/macOS (Docker Desktop)：藏在 WSL2 虚拟机内部(可以在Docker Desktop中查看存放镜像的位置)，你不能直接点开浏览。
>不要手动修改这个文件夹，交给 docker 命令管理。查看镜像：docker images；导出镜像为 tar 文件：docker save。
### 基础步骤

1. Determine your base image 确定基础镜像
2. Install application dependencies 安装应用程序依赖项
3. Copy in any relevant source code and/or binaries
复制所有相关的源代码和/或二进制文件
4. Configure the final image 配置最终图像

## 三、 构建、标记、发布镜像

### 说明

本小节会学习以下内容：
1. 构建镜像 - 基于Dockerfile构建镜像的过程

2. 给镜像打标签——即为图片命名的过程，这一过程也决定了镜像的分发范围

3. 发布镜像——通过容器注册表分发或共享新创建镜像的过程

### 构建镜像

大多数情况下，镜像是通过 Dockerfile 构建的。也可以使用之前所讲的docker commit一步一步手动构建镜像，最基本的 docker build 命令可能如下所示：


`docker build .`

命令末尾的.指定了构建上下文的路径或URL。构建工具会在该位置找到Dockerfile及其他被引用的文件。

*当你运行构建时，构建器会在需要时拉取基础镜像，然后执行 Dockerfile 中指定的指令。*


使用之前的命令，该镜像将没有名称，但输出会提供镜像的 ID。
比如：sha256:9924dfd9350407b3df01d1a0e1033b1e543523ce7d5d5e2c83a724480ebe8f00
然后运行只能通过指定ID：
`docker run sha256:9924dfd9350407b3df01d1a0e1033b1e543523ce7d5d5e2c83a724480ebe8f00`

这个名字肯定不好记，这就是打标签发挥作用的地方。

### 给镜像打标签

为镜像添加标签是为镜像赋予一个易于记忆的名称的方法。不过，镜像的名称有其固定结构。完整的镜像名称格式如下：


`[HOST[:PORT_NUMBER]/]PATH[:TAG]`

- HOST：镜像所在的可选注册表主机名。如果未指定主机，默认使用 Docker 的公共注册表 docker.io。
- PORT_NUMBER：如果提供了主机名，则为注册表端口号
- PATH：镜像的路径，由以斜杠分隔的组件组成。对于 Docker Hub 而言，格式遵循[NAMESPACE/]REPOSITORY，其中命名空间可以是用户名或组织名。若未指定命名空间，则使用library，这是 Docker 官方镜像的命名空间。
- TAG：一种自定义的、人类可读的标识符，通常用于标识镜像的不同版本或变体。如果未指定标签，默认使用latest。

#### 构建过程中打标签
要在构建过程中为镜像打标签，请添加 -t 或 --tag 标志：

`docker build -t my-username/my-image .`

#### 构建之后打标签
如果你已经构建了一个镜像，可以使用 docker image tag 命令为该镜像添加另一个标签：


docker image tag my-username/my-image another-username/another-image:v1

### 发布镜像

构建并标记好镜像后，你就可以将其推送到镜像仓库了。为此，请使用docker push命令：


`docker push my-username/my-image`

几秒钟内，你镜像的所有分层都会被推送至镜像仓库。

**在将镜像推送到仓库之前，你需要先完成身份验证。要完成这一步，只需使用 docker login 命令即可。如果本机只有一个账户，且已经通过Docker Desktop登录，在每次推送会自动完成身份认证，无需手动login，多用户或者也可以使用token进行认证提交。**

## 四、使用构建缓存

### 说明

**在构建镜像的过程有缓存机制**

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN yarn install --production
CMD ["node", "./src/index.js"]
```

当你运行 docker build 命令来创建新镜像时，Docker 会执行 Dockerfile 中的每条指令，按指定顺序为每个命令创建一个镜像层。**对于每条指令，Docker 会检查是否可以复用之前构建中的对应指令。**如果发现之前已经执行过类似的指令，Docker 就无需重新执行，而是使用缓存的结果。通过这种方式，你的构建过程会变得更快、更高效，还能节省宝贵的时间和资源。

**逻辑查找范围**：限定在当前构建的父镜像链（历史记录）上，并非扫描整个 Daemon 的所有无关镜像。
物理存储复用：属于整个 Docker Daemon 全局共享，只要层哈希一致，物理磁盘上的层数据只会存一份。

1. 缓存查找逻辑(命中规则)
Docker 的缓存命中不是在整个 Daemon 里“模糊搜索”拥有相同命令的层，而是严格遵循祖先链（Parent Chain）匹配：

- 执行第 N 条指令时，Docker 会先找到上一步（第 N-1 步）命中的那个缓存镜像 ID。

- 然后，它只会在该缓存镜像的子层列表中，查找有没有哪个子层的指令哈希值与当前第 N 条指令完全一致。

- 举例：你构建镜像 A（基于 Ubuntu）和镜像 B（基于 Alpine）。即使两者都有 RUN echo hello 这条完全相同的命令，它们之间不会互相命中缓存，因为它们的父层（Ubuntu vs Alpine）不同，在缓存树中分属不同分支。

2.  物理磁盘存储（全局共享）
一旦某个层被创建（无论属于哪个镜像），它的内容就是只读的，并存储在 Daemon 的存储驱动目录（如 /var/lib/docker/overlay2）下。如果两个完全不同的镜像恰好拥有完全相同的层哈希（比如都从同一个基础镜像 alpine:3.18 开始），物理磁盘上只会保存一份数据，其他镜像通过硬链接或指针复用，这叫存储复用（Storage Sharing）。

**如果镜像 A 和镜像 B 拥有完全相同的父链历史（例如它们都是从同一个中间层 ID 为 abc123 的状态继续构建），且执行相同的 RUN apt-get install，那么哈希一致，物理复用。后续如果构建命令不同，那么将只复用完全相同的镜像层，后续的部分需要重新占用物理磁盘。**

有效利用构建缓存可通过复用之前构建的结果并跳过不必要的工作，从而实现更快的构建。为了最大化缓存利用率、避免耗费资源和时间的重建，了解缓存失效的机制至关重要。以下是几种可能导致缓存失效的情况示例：
1. 对RUN指令的命令所做的任何更改都会使该层失效。如果你的Dockerfile中对RUN命令有任何修改，Docker会检测到该更改并使构建缓存失效。
2. 使用 COPY 或 ADD 指令复制到镜像中的文件所发生的任何更改。Docker 会监控项目目录内文件的所有改动。无论是内容变更还是权限等属性的更改，Docker 都会将这些修改视为使缓存失效的触发条件。
3. 一旦某一层失效，所有后续的层也会随之失效。如果包括基础镜像或中间层在内的任一先前层因修改而失效，Docker 会确保依赖于它的后续层也一并失效。这能保证构建过程保持同步，并避免出现不一致的情况。


**在编写或编辑 Dockerfile 时，要留意不必要的缓存未命中情况，以确保构建过程尽可能快速高效地运行。**

### 实操

1. 安装并配置好Docker Desktop

2. 打开终端并克隆github的业务源代码
`git clone https://github.com/dockersamples/todo-list-app`

3. 进入项目目录
`cd todo-list-app`
查看Dockerfile文件
```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN yarn install --production
EXPOSE 3000
CMD ["node", "./src/index.js"]
```

4. 在当前文件夹下根据Dockerfile构建镜像：
`docker build .`

第一行显示整个构建过程耗时 20.0 秒。首次构建可能需要一些时间，因为它会安装依赖项。

5.  现在，在不修改源代码或 Dockerfile 的情况下重新运行docker build命令，如下所示：
`docker build .`

由于缓存机制，只要命令和上下文保持不变，初始构建后的后续构建速度会更快。Docker 会缓存构建过程中生成的中间层。当你在未对 Dockerfile 或源代码进行任何更改的情况下重新构建镜像时，Docker 可以复用缓存的层，从而显著加快构建过程。

借助缓存层，后续的构建仅用1.0秒就完成了。无需重复安装依赖这类耗时步骤。**每一次Dockerfile操作都是一个镜像层，如果一旦有相同父级，那么当前镜像层就可以被复用，遇到RUN、COPY命令可能导致后续的镜像不同，那么就不能复用了。**

**因此，在编写Dockerfile的时候，可以尝试刻意确保依赖缓存仅在确实需要时才失效。对于基于 Node 的应用程序，依赖项定义在 package.json 文件中。如果该文件发生变化，你需要重新安装依赖项；但如果文件未更改，则使用缓存的依赖项。因此，首先仅复制该文件，然后安装依赖项，最后复制其他所有文件。这样一来，只有当 package.json 文件发生变化时，你才需要重新构建 yarn 依赖项。**

## 五、多阶段构建

### 说明

在传统构建中，所有构建指令都在单个构建容器中按顺序执行：下载依赖项、编译代码以及打包应用程序。所有这些步骤最终都会进入最终的镜像中。这种方法可行，但会导致镜像体积庞大，增加不必要的负担，同时也会提升安全风险。而多阶段构建正是为解决这一问题而生。

多阶段构建会在你的 Dockerfile 中引入多个阶段，每个阶段都有特定的用途。可以将其理解为能在多个不同环境中并行执行构建的不同部分。通过将构建环境与最终运行环境分离开，你可以显著减小镜像体积并缩小攻击面。这对于存在大量构建依赖项的应用程序尤为有益。

**多阶段构建适用于所有类型的应用程序。**

- 对于 JavaScript、Ruby 或 Python 这类解释型语言，你可以在一个阶段完成代码的构建和压缩，再将可直接用于生产环境的文件复制到更小的运行时镜像中。这能优化你的部署镜像。
- 对于C、Go或Rust这类编译型语言，多阶段构建允许你在一个阶段完成编译，然后将编译后的二进制文件复制到最终的运行时镜像中。无需将整个编译器打包进最终镜像。



下面是一个使用伪代码表示的多阶段构建结构的简化示例。请注意其中包含多个 `FROM` 语句以及一个新的 `AS <stage-name>` 语法。此外，第二阶段中的 `COPY` 语句通过 `--from` 指令从前一阶段复制内容。

```dockerfile
# Stage 1: Build Environment
FROM builder-image AS build-stage 
# Install build tools (e.g., Maven, Gradle)
# Copy source code
# Build commands (e.g., compile, package)

# Stage 2: Runtime environment
FROM runtime-image AS final-stage  
#  Copy application artifacts from the build stage (e.g., JAR file)
COPY --from=build-stage /path/in/build/stage /path/to/place/in/final/stage
# Define runtime configuration (e.g., CMD, ENTRYPOINT) 
```
