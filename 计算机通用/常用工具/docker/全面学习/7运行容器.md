# 运行容器

**容器 = 用镜像 “启动” 出来的东西**
但它包含两部分：
1. 运行中的进程（你理解的那一半）
2. 容器实例对象（Docker 保存的配置、读写层、挂载信息），Docker对象会持续保存。


## 一、 发布和暴露端口

### 说明

如果你一直跟随到目前的指南，就会明白容器为应用程序的每个组件提供了独立的进程。每个组件——React 前端、Python 接口和 Postgres 数据库——都在各自的沙箱环境中运行，与宿主机上的其他所有内容完全隔离。这种隔离特性对安全性和依赖管理非常有利，但同时也意味着你无法直接访问它们。比如，你无法在浏览器中访问这个网页应用。

这就是端口发布派上用场的地方。

### 发布端口


发布端口可通过设置转发规则实现一定程度的网络隔离突破。例如，你可以指定将主机端口 8080 上的请求转发到容器端口 80。发布端口需在容器创建阶段，通过 -p（或 --publish）参数结合 docker run 命令完成，语法如下：

`docker run -d -p HOST_PORT:CONTAINER_PORT nginx`

1. HOST_PORT：你希望接收流量的主机机器上的端口号

2. CONTAINER_PORT：容器内监听连接的端口号

**相当于做了一个端口映射**

例如，要将容器的80端口发布到主机的8080端口：

`docker run -d -p 8080:80 nginx`

现在，发送到你主机 8080 端口的所有流量都会被转发到容器内的 80 端口。

### 指定主机+发布端口(就是运行容器接收流量的端口)

默认情况下，发布的端口会监听所有主机接口（0.0.0.0 / ::）。你可以通过在发布字符串中先指定 IP 来绑定到单个地址：


`docker run -d -p 127.0.0.1:8080:80 nginx`

完整格式为 HOST_IP:HOST_PORT:CONTAINER_PORT。

1. HOST_IP：可选参数。要绑定的主机地址。使用 127.0.0.1 可将端口限制在本地机器，或指定特定网卡的 IP 地址，仅允许该网卡接收流量。

2. HOST_PORT / CONTAINER_PORT：与HOST_PORT:CONTAINER_PORT中的含义相同。


### 临时端口

**通过不指定主机端口进行映射而直接运行，主机会临时绑定对应的端口到对应的Docker端口上，可以通过`docker ps`查看**

比如：
`docker run -p 80 nginx`

随后使用`docker ps`即可查看所选端口。

### 指定发布端口

创建容器镜像时，EXPOSE 指令用于指明打包后的应用将使用指定端口。这些端口默认不会被发布。

使用-P或--publish-all标志，你可以将所有暴露的端口自动发布到临时端口。在开发或测试环境中避免端口冲突时，这一功能非常实用。

`docker run -P nginx`

## 二、覆盖容器默认设置

### 说明

Docker 容器启动时，会执行一个应用程序或命令。容器从其镜像的配置中获取该可执行文件（脚本或文件）。容器自带的默认设置通常能正常工作，但你可以根据需要进行修改。这些调整能让容器内的程序完全按照你的期望运行。

例如，如果你有一个监听标准端口的现有数据库容器，且想要运行同一个数据库容器的新实例，那么你可能需要更改新容器的监听端口设置，以避免与现有容器冲突。有时，如果程序需要更多资源来处理繁重的工作负载，你可能希望增加容器可用的内存；或者设置环境变量，以提供程序正常运行所需的特定配置细节。

docker run 命令提供了一种强大的方式来覆盖这些默认设置，并根据你的需求定制容器的行为。该命令包含多个标志，可让你实时自定义容器的行为。
### 覆盖网络端口

有时你可能希望为开发和测试目的使用独立的数据库实例。在同一端口运行这些数据库实例可能会发生冲突。你可以在 docker run 中使用 -p 选项将容器端口映射到主机端口，这样就能运行容器的多个实例而不会产生任何冲突。
`docker run -d -p HOST_PORT:CONTAINER_PORT postgres`

### 设置环境变量
此选项在容器内设置一个环境变量 foo，其值为 bar。
`docker run -e foo=bar postgres env`

**.env 文件是一种便捷的方式，可用于为你的 Docker 容器设置环境变量，避免在命令行中出现大量 -e 标志。要使用 .env 文件，可在 docker run 命令中传入 --env-file 选项。**


`docker run --env-file .env postgres env`

### 限制容器资源消耗

你可以将--memory和--cpus参数与docker run命令配合使用，以限制容器可使用的CPU和内存资源。例如，你可以为Python API容器设置内存上限，防止其占用宿主机上过多资源。具体命令如下：
`docker run -e POSTGRES_PASSWORD=secret --memory="512m" --cpus="0.5" postgres`

此命令将容器内存使用限制为 512 兆字节，并将 CPU 配额定义为 0.5，即半个核心。

*你可以使用docker stats命令来监控正在运行的容器的实时资源使用情况。这能帮助你了解分配的资源是否充足，或是否需要进行调整。*

## 三、持久化容器数据

容器启动时，会使用镜像提供的文件和配置。每个容器都能创建、修改和删除文件，且操作不会影响其他任何容器。当容器被删除时，这些文件的更改也会随之被删除。

虽然容器的这种临时特性有很大优势，但在需要持久化数据时却会带来一个挑战。例如，重启数据库容器时，你肯定不希望以空数据库开始运行。那么，该如何实现文件的持久化呢？

### 容器卷(volumes)

卷是一种存储机制，能够让数据在单个容器的生命周期之外持久化。可以将其理解为从容器内部到容器外部创建一个快捷方式或符号链接。

举个例子，假设你创建了一个名为 log-data 的卷。

**在主机上创建一个名为log-data的数据卷，由Docker engine/Daemon进行管理**
`docker volume create log-data`

使用以下命令启动容器时，卷将在/logs路径下挂载（或附加）到容器中：

`docker run -d -p 80:80 -v log-data:/logs docker/welcome-to-doc`

如果log-data卷不存在，Docker 会自动为你创建它。

容器运行时，其写入/logs文件夹的所有文件都会保存在此卷中，位于容器外部。如果删除容器并使用同一卷启动新容器，这些文件仍会保留。

**你可以将同一个卷挂载到多个容器上，以在容器之间共享文件。这在日志聚合、数据管道或其他事件驱动型应用等场景中可能会很有用。**


### 管理卷

卷拥有独立于容器的生命周期，且根据所使用的数据类型和应用程序，卷的大小可能会变得相当大。以下命令有助于管理卷：

1. `docker volume ls - 列出所有卷`
2. `docker volume rm <volume-name-or-id> - 删除卷（仅当卷未附加到任何容器时生效）`
3. `docker volume prune - 删除所有未使用（未挂载）的卷`

**如果是有容器有对某个卷的引用，那么应该先取消对卷的绑定关系/销毁容器，然后再进行rm进行删除卷，具体命令如下：**
```bash
# 1.查看卷
docker volume ls
# 2.查看哪个容器在用 mydata 卷
docker ps -a --filter volume=mydata
# 3.销毁引用该卷的容器
docker rm -f 容器ID
# 4.删除卷
docker volume rm mydata
```

## 四、与容器共享主机文件

**通过第三节所将的卷挂载的方式就可以实现共享文件，也是容器进行数据持久化的主要方式**


### 说明

每个容器都具备运行所需的全部组件，无需依赖宿主机上任何预先安装的依赖项。由于容器是隔离运行的，它们对宿主机及其他容器的影响微乎其微。这种隔离性带来了一大优势：容器能最大程度减少与宿主机及其他容器的冲突。不过，这种隔离性也意味着容器默认无法直接访问宿主机上的数据。

设想这样一个场景：你有一个 Web 应用容器，它需要访问存储在宿主机系统文件中的配置设置。该文件可能包含数据库凭证或API密钥等敏感数据。将此类敏感信息直接存储在容器镜像中会带来安全风险，尤其是在镜像共享的过程中。为解决这一问题，Docker 提供了多种存储方案，能够在容器的隔离性与宿主机的数据之间搭建起桥梁。

Docker 提供两种主要的存储选项，用于持久化数据以及在宿主机与容器之间共享文件：卷和绑定挂载。

### 卷和绑定挂载

详见第三节

### 在主机和容器之间共享文件

与 docker run 命令一起使用的 -v（或 --volume）和 --mount 标志都能让你在本地计算机（主机）与 Docker 容器之间共享文件或目录。不过，二者在行为和使用方式上存在一些关键差异。

-v 标志对于基本的卷或绑定挂载操作来说更简单便捷。使用 -v 或 --volume 时，如果主机位置不存在，系统会自动创建一个目录。

想象一下，你是一名项目开发人员。你的开发机器上有一个存放代码的源目录。当你编译或构建代码时，生成的产物（编译后的代码、可执行文件、镜像等）会保存在源目录下的一个独立子目录中。在接下来的示例中，这个子目录为/HOST/PATH。现在你希望这些构建产物能在运行应用程序的 Docker 容器中被访问到，同时还希望容器能在你重新构建代码时，自动获取最新的构建产物。
`docker run -v /HOST/PATH:/CONTAINER/PATH -it nginx`

--mount 标志提供更高级的功能和精细化控制，适用于复杂的挂载场景或生产环境部署。默认情况下，若你使用 --mount 绑定挂载 Docker 主机上尚不存在的文件或目录，docker run 命令不会自动为你创建该文件或目录，而是会生成一条错误信息。
`docker run --mount type=bind,source=/HOST/PATH,target=/CONTAINER/PATH,readonly nginx`

**Docker 推荐使用 --mount 语法而非 -v。该语法能更好地控制挂载过程，还可避免因目录缺失引发的各类潜在问题。**

### Docker 访问主机文件的权限设置

使用绑定挂载时，确保 Docker 拥有访问主机目录的必要权限至关重要。要授予读写权限，你可以在创建容器时，配合 :ro 或 :rw 标志使用 -v 标志（只读）或 --mount 标志（读写）。例如，以下命令授予读写访问权限。
`docker run -v HOST-DIRECTORY:/CONTAINER-DIRECTORY:rw nginx`

只读绑定挂载允许容器读取主机上的挂载文件，但无法更改或删除这些文件。读写绑定挂载则允许容器修改或删除挂载的文件，且这些更改或删除操作也会反映到主机系统上。只读绑定挂载可确保主机上的文件不会被容器意外修改或删除。`



Docker 的 **Volume（数据卷）** 和 **Bind Mount（绑定挂载）** 是两种将宿主机数据与容器共享的常用方式，它们的核心区别在于 **谁负责管理数据**。

简单来说，**Volume 是由 Docker 全权管理的存储区域**，而 **Bind Mount 则直接映射了宿主机上的一个具体文件或目录**。

对比表格：
| 特性 | Volume (数据卷) | Bind Mount (绑定挂载) |
| :--- | :--- | :--- |
| **管理方** | 由 **Docker 守护进程 (daemon) 管理** | 由 **用户 (宿主机文件系统) 直接管理** |
| **存储位置** | Docker 管理的目录，默认在 `/var/lib/docker/volumes/` | 宿主机上的 **任意路径**，由用户指定 |
| **生命周期** | **独立于容器**。删除容器不会自动删除 Volume，数据持久化 | **依赖宿主机目录**。容器删除后，宿主机目录仍在，但数据管理混乱 |
| **可移植性** | **高**。只需通过卷名即可挂载，易于在不同主机间备份和迁移 | **低**。依赖于宿主机特定的绝对路径，跨平台（如Win/Linux）可能因路径格式不同而失效 |
| **安全性** | **高**。由Docker管理，非Docker进程无法随意修改，降低了安全风险 | **较低**。Docker和非Docker进程都可修改，可能带来安全风险 |
| **初始化** | 挂载空卷时，Docker会自动将**容器镜像内该路径的内容复制**到卷中 | 挂载会**覆盖**容器内的目标目录，镜像内的原内容被隐藏 |
| **典型场景** | **生产环境**，适合数据库、应用状态等需要持久化存储的重要数据 | **开发、测试环境**，适合代码热加载、注入配置文件等需要频繁修改宿主机文件的场景 |

### 如何选择：Volume vs Bind Mount

#### 📦 推荐使用 Volume 的场景
- **生产环境中的数据持久化**：例如数据库（MySQL、PostgreSQL）的数据文件。Volume 能确保数据在容器更新或意外删除后依然安全。
- **需要在多个容器之间安全、方便地共享数据**。
- **需要备份、迁移或通过 Docker CLI 命令（如 `docker volume ls`）管理数据**。
- **对存储性能有要求**：Volume 直接写入宿主机文件系统，性能优于写入容器可写层。

#### 🔗 推荐使用 Bind Mount 的场景
- **本地开发环境**：将代码目录挂载到容器中，代码的任何修改都能在容器内实时生效，实现“热加载”。
- **向容器注入配置文件**：例如，将宿主机上的 `nginx.conf` 或 `my.conf` 挂载到容器内，方便随时调整配置。
- **需要容器访问宿主机上的特定资源**：例如挂载宿主机的 Docker 套接字 (`/var/run/docker.sock`)，以便在容器内控制宿主机的 Docker。

### ⚠️ 注意事项
1.  **关于 `-v` 和 `--mount`**：Docker 提供了 `-v` (或 `--volume`) 和 `--mount` 两种挂载语法。`-v` 更简洁，适合基础操作；`--mount` 更明确，参数更清晰，是官方推荐的方式。
2.  **路径问题**：使用 Bind Mount 时，若指定的宿主机目录不存在，`-v` 会自动创建，但 `--mount` 会报错。为确保行为一致，建议提前创建好目录。
3.  **权限问题**：Bind Mount 会直接使用宿主机文件的 UID/GID。如果容器内运行的用户（如UID 1000）没有相应权限，可能会导致“Permission denied”错误。需要确保权限匹配，或通过容器运行参数（如 `--user`）进行调整。

## 五、多容器应用(compose)

### 说明

启动单容器应用十分简单。例如，一个执行特定数据处理任务的 Python 脚本可在包含其所有依赖项的容器内运行。同样，一个为带有小型 API 端点的静态网站提供服务的 Node.js 应用，也能将其所有必要的库和依赖项高效地容器化。然而，随着应用规模不断扩大，将它们作为独立容器进行管理会变得愈发困难。


想象一下，这个数据处理 Python 脚本需要连接数据库。突然之间，你不仅要管理这个脚本，还要在同一个容器里管理数据库服务器。如果脚本需要用户登录，你还得配置一套身份验证机制，这会进一步增大容器的体积。

**容器的一个最佳实践是每个容器只做一件事，并把这件事做好。虽然这条规则有例外情况，但应避免让一个容器承担多项任务的倾向。**

**虽然docker run是启动容器的便捷工具，但使用它来管理不断扩展的应用栈会变得很困难。原因如下：**
1. 想象一下，为开发、测试和生产环境运行多条带有不同配置的 docker run 命令。这不仅容易出错，还非常耗时。
2. 应用程序之间往往相互依赖。随着应用栈规模扩大，按特定顺序手动启动容器并管理网络连接会变得十分困难。
3. 每个应用都需要其专属的docker run命令，这使得单个服务的扩展变得困难。扩展整个应用则可能导致资源被浪费在那些无需扩容的组件上。
4. 为每个应用程序持久化数据需要在每个docker run命令中单独进行卷挂载或配置，这会形成一种分散的数据管理方式。
5. 通过单独的 docker run 命令为每个应用设置环境变量既繁琐又容易出错。


**接下来引入Docker Compose：**

Docker Compose 在一个名为 compose.yml 的单个 YAML 文件中定义整个多容器应用。该文件为所有容器、它们的依赖项、环境变量，甚至卷和网络指定配置。借助 Docker Compose：

1. 你无需运行多条 `docker run` 命令。你只需在一个 YAML 文件中定义整个多容器应用即可。这能集中配置内容并简化管理。
2. 你可以按特定顺序运行容器，并轻松管理网络连接。
3. 你可以在多容器设置中直接对单个服务进行扩容或缩容。这使得资源分配能够根据实时需求高效进行。
4. 你可以轻松实现持久卷。
5. 在 Docker Compose 文件中一次性设置环境变量很简单。

借助 Docker Compose 运行多容器架构，你可以构建以模块化、可扩展性和一致性为核心的复杂应用。

### 实操

#### 手动多docker run创建

1. 获取github源码
`git clone https://github.com/dockersamples/nginx-node-redis`

2. 进入项目目录

`cd nginx-node-redis`

3. 构建镜像

`cd ./nginx`
`docker build -t nginx .`

`cd ./web`
`docker build -t web .`

4. 构建容器通信网络

`docker network create sample-app`

5. 行以下命令启动 Redis 容器，该命令会将其连接到之前创建的网络并创建一个网络别名（对 DNS 查找很有用）：
`docker run -d  --name redis --network sample-app --network-alias redis redis`

6. 启动两个web容器

```bash
docker run -d --name web1 -h web1 --network sample-app --network-alias web1 web
docker run -d --name web2 -h web2 --network sample-app --network-alias web2 web
```

7. 运行Ngix容器

`docker run -d --name nginx --network sample-app  -p 80:80 nginx`

8. 验证容器是否启动成功

`docker ps`

9. 可以在Docker Desktop里面查看具体的运行的容器及其配置等等。

#### 使用yml文件进行Docker Compose 简化部署

Docker Compose 提供了一种结构化且高效的方式来管理多容器部署。如前所述，使用 Docker Compose 时，你无需运行多个 `docker run` 命令。你只需在一个名为 `compose.yml` 的 YAML 文件中定义整个多容器应用即可。下面我们来看看它的工作原理。

导航到项目目录的根目录。在该目录内，你会找到一个名为 compose.yml 的文件。这个 YAML 文件是所有核心配置所在之处，它定义了构成你的应用程序的所有服务及其配置。每个服务都会指定自身的镜像、端口、卷、网络以及实现其功能所需的其他所有设置。

1. 使用docker compose up命令启动应用程序：


`docker compose up -d --build`

2. 查看 Docker Desktop 仪表板，你可以看到容器，并深入了解它们的配置。

3. 或者，你也可以使用 Docker Desktop 仪表板，选中应用程序堆栈后点击删除按钮来移除容器。
