# 项目过程与决策记录

把项目中的重要转折写成可以核查的过程链，让后来的人回答：发现了什么、当时知道什么、为何这样选、实际发生了什么、还欠什么验证。

## 适用边界

- 明确请求建立或更新项目过程记录时使用；工作中出现影响目标、方案、数据、评价口径、交付或风险的重要问题与决策时使用。
- 日常命令、普通提交和可从代码直接看出的细节留在现有工具中；只记录会改变后续判断的事件。
- 本 Skill 不替代项目的 issue tracker、ADR、实验 run card、变更日志或最终报告。先检查这些载体，选择现有记录的补充位置和链接关系。
- 项目事实、目录、权限、提交规则以该项目的指令与现有约定为准。本包不指定所有项目必须使用 `process/`。

## 执行流程

1. **确定记录目的。** 判断本次是即时记录、补充旧问题的后续结果，还是事后回溯。确认读者需要追查的问题和本次覆盖范围。若用户只要求建议，先给出结构与示例，不创建文件。
2. **核查现状与证据。** 阅读适用的 `AGENTS.md` 和现有导航；查找相关 issue、ADR、需求、方案、实验记录、提交及当前工作区状态。只读取当前任务需要的材料，不为建立过程记录而重做整项研究。区分来源中的事实、作者推断和待确认事项。
3. **选择记录位置。** 优先扩展现有过程目录或问题页。没有合适载体时，按项目规模建立简短入口、时间线和按主题组织的问题页；用户指定的位置优先。一个持续演进的问题保留一个稳定入口，子问题和跨主题问题用链接连接，避免复制整段内容。
4. **写出问题与决策链。** 使用 [记录格式](references/record-format.md) 中适合本事件的字段。至少交代触发、影响、证据、选项、决定及理由、结果或待验证项；没有决策时明确写“待决定”，不要补造一个。决定被取代时保留原判断与日期，再追加新证据和新决定。
5. **标明时间与证据状态。** 即时记录写清发生日期；事后回溯标明依据文件和可确认的时间范围。缺少来源时写“无法确认”。将结果链接到原始产物，引用具体版本、run、issue 或提交；不要把实验观察、模型分数、合成标签或草稿建议写成业务事实。
6. **更新导航并核验。** 将新页接入上级主题、时间线或已有索引，检查父子及相关问题的双向链接。核对相对路径、关键数字、状态和来源；保留项目已有未提交改动。按项目规则提交，仅暂存本次目标文件。

## 记录深度

简单事件用数段即可；复杂争议可分父问题和子问题。优先补全“为何选择”与“后来怎样”，不以统一篇幅或固定七节作为完成标准。记录应能让读者沿链接找到原始证据；原始指标、日志和长篇方案留在各自正式产物中。

## 完成检查

- 读者能追到“问题 → 当时证据 → 选项与理由 → 行动 → 结果/待验证”的路径。
- 已决定、建议、假设、已验证与未知事项没有混写；事后还原没有冒充当时记录。
- 新问题、父问题、相关决定和原始证据均可从项目入口找到，链接可用。
- 更新范围和提交方式符合项目约束，没有覆盖用户既有改动或复制敏感原始材料。
