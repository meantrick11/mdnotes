# 必备能力

## 1. 基础能力|方法论

基础能力包括很多，如果是能够在日常生活工作中起到作用的能力都算作基础能力的话，那么你能够想到所有的优秀品质都算，比如坚持、明确目标、睿智、创造力等等，但是不能所有都谈论，此处只列举个人比较重视的能力或者应该叫方法论

### 1.1 解决问题/矛盾驱动(最强心智)

我们本质所作的事情目的都是为了解决某些已经存在或者自己幻想的问题，包括大大小小的考试，应届面试、做题、学习等等，学习的目的是为了扩展视野、了解更过的知识、方法论，然后落实到具体问题之上。

**解决问题的能力太过宽泛**，你可以理解为任何大大小小的问题，包括生活鸡毛蒜皮或者公司/企业甚至国家所遇到的问题，对应，你能够解决的问题越大，那么在社会中的价值就越大，对应的回报就越大，如果觉得自己的价值被低估，那么先梳理一下自己能够解决的能力边界在哪里。

*思之困则学必勤。 -- 王夫之*

### 1.2 学会学习

既然我们的目标是解决某一类/个问题，那么我们极大概率是对于这个问题是不会的，(如果你已经能够解决了，那么这个问题也不会让你焦头烂额了)

既然这个问题是自己不会的，那么就需要通过**学习**去让自己会解决此类问题，学习的方式有很多种，挑自己喜欢的就行(视频、看书、网络资源、AI搜索、和其他人交流等等)，但是再次强调，我们的目的是**为了解决某一类问题**，带着目的性地学习，其学习的内容也有很多(比如基础概念、实操例子、方法论等等)，咱没那么多时间和精力学会所有，所以还是挑最能满足解决某一类问题的部分进行学习

*教育的伟大目标不是知识，而是行动。 -- 赫伯特·斯宾塞*

### 1.3 实践和总结

最重要的，既然当前已经学会了解决某一类问题，但是问题还没有解决，我们就需要运用所学进行问题的解决，在解决问题过程中还可能遇到其他小问题，你需要判断是否重要并值得解决，自然又回到了1.1，1.2的具体操作中。

当某一个问题彻底解决之后，你已经有了能够解决它的能力了，那么你需要整合并总结你所学+实操过程，形成自己的经验，如此，你的能力越来越系统，并且复用程度也更高，以后面对同样的问题，你有自己的方法论，自然迎刃而解了。

随着自己的方法论积累，那么自己能够解决的问题就越多或者越大，那么你就能够在社会上获得对应的报酬。

*通过实践而发现真理，又通过实践而证实真理和发展真理。 -- 毛泽东*

### 1.4 其他

当然除了上述心智以外，还有很多其他的优质能力，比如坚持、拆分目标、保持主线、适当娱乐等等无论是优质能力还是方法论。我觉得上述三条心智应该是比较通用，而不是那么偏颇某一点的特别心智方法。


### 1.5 判断

尤其是对当今大模型的发展带来的巨大冲击前提下，如果只从高维角度来讲，比如设计一个产品、从想法到落地等等这种，但是对基础的模型产生的代码的影响没有具体的判断力，针对具体的模块设计及为什么没有了解，那么最后代码只能是AI产生的杂乱代码，这个判断力来自于**基础积累**，比如你对项目的理解，模块相互之间的连接等等，这些理解跟上之后才能对AI产生的代码产生约束和判断，那么以小的岗位向上延申，只有有了基础的判断能力之后，向上学习培养更高层级的判断力和经验，才能让AI工具实现迭代，并对其有所掌控。而不是**AI代替大脑，成为yes工程师**。

**长期积累的经验，尤其是注重学到什么(横向扩充技术栈+纵向向上学习必要的拆解，然后积累)，而不是始终CURD,逐渐培养自己上层基础，自然会形成自己的判断力**

*脚踏实地，心向远方* 


### 1.6 输出能力

+自己的思考+自己的产出+总结，形成能够复用的经验+向上汇报的能力


## 2. 领域能力

对于不同的领域，对应都有不同的专业素养要求，对应的能力边界决定了你能够解决某一领域的具体问题

这里只讲作为开发者/软件相关的能力要求

### 业务能力

对于某一类业务的了解程度，比如业务流程图、业务架构图，对某一类业务的来龙去脉的了解程度影响着你是否只能做基础开发抑或是挑大梁当项目管理，架构师等等领导型职位，一般这种职位处理对应的管理能力之外，还需要对某一类业务有着深刻的理解。比如基础的业务流程、项目涉及到的功能，功能时序图是怎么样的？当然一个项目可能会有n多个功能，但是对于大致的流程，甚至你需要明确对对应的流程，及其各个边界等等内容。

**深入某一个行业/公司，了解其是做什么的？怎么做的？流程是怎么样的？这也是为什么强调要扎根，并且还要深耕，不能飘的原因，一旦嫖了，理解就不深刻，无法有自己独到的见解，或者见解十分肤浅**

### 技术了解

对应开发岗位，自不当然需要了解大量的技术，但是技术日新月异，如掌握第一节的具体心智论，以问题驱动学习，自然就不会纠结技术本身了，而是为了解决问题，大概率能够融合到对应的业务当中去。

但是对于某一些技术则需要**精度**，比如对拿手编程语言底层深入理解。

以及对应领域技术的**广度**，对于很多技术可以停留在是什么?怎么用的程度上?不需要过度深入，遇到某个特别的技术也不会一无所知。


### 路径展开

上面所说的都太过宽泛，不够具体：这里需要组件培养每个阶段不同层级的能力要求

**这些具体的能力要求暂时还没有接触到，比如逐渐完善，让自己具备对应的能力，先对标，然后学习超越**

普通开发 → 中级开发 → 高级开发 → 资深开发/技术专家 → 架构师/高级专家(业务、技术、出方案、文档等等) → 首席架构师/CTO

### 技术学习指南

#### 技术广度

在学习学习过程中不断扩展自己的知识地图，比如基础语言就有python、java、go等等，接口框架FastAPI、spring、Gin等等，但是知晓他们的定位，了解其作用，如果有实现学习一下如何使用，那么就是扩展技术广度，面对某些特定技术能够进行快速分类，知道其解决的问题，了解其作用，判断是否需要学习等等都需要技术广度来支撑，同时，技术广度也是高适配(什么项目都能简单上手)+成为架构师（分析系统是否需要某类技术）的基础素养

#### 技术深度

除了积累技术广度之外，还需要对于某一个领域的相关技术深入学习，对于每个技术我分为以下层次：

| 深度 | FastAPI 示例 | Spring 示例 |
| ---- | ---- | ---- |
| L1 知道用途 | 知道如何定义接口 | 知道 Controller、Service |
| L2 能够使用 | 实现路由、依赖注入、数据库操作 | 开发 Controller、Service、Mapper |
| L3 理解机制 | 请求匹配、依赖解析、ASGI 执行、事件循环 | Bean 注册、实例化、依赖注入、请求分发 |
| L4 工程级掌握 | 定位异步阻塞、生命周期、连接池问题 | 定位循环依赖、事务代理、Bean 初始化问题 |
| L5 底层与设计 | 阅读 Starlette、FastAPI、Uvicorn 等源码 | 阅读 Spring IoC、AOP 等源码 |


对于大部分技术，在广度积累时，需要达到L1->L2的层级，对于专精/常用的技术/框架学习需要达到L3->L4，甚至L5的层级


**对于某个技术，优先判断其作用及分类，然后根据重要程度学习到不同层级，并不是所有技术都需要完全学习到L3或者L5**
