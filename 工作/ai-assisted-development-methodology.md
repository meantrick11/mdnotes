# AI 辅助开发：把掌控感建立在可验证的工程判断上

拿到一个需求，把它交给 AI，几分钟后收到一批代码，这已经成为一种常见的开发方式。真正困难的问题随之出现：我凭什么接受这些代码？

如果判断依据只有“能运行”“页面看起来正常”“AI 说测试通过了”，那么代码虽然完成了，开发者对系统的理解却可能没有增长。下次出现问题，我们仍然只能把错误交回 AI，等待下一轮修改。

我希望建立的是一种可以长期复用的工作方式：在 AI 开始实现之前，形成对需求、关键路径和风险的理解；实现过程中，根据证据判断它是否偏离目标；交付之前，对照最初的标准确认结果。

**可以把大量编码工作交给 AI，但要保留定义问题、判断取舍和接受结果的能力。**

本文面向准备入职、刚接手小模块，以及希望系统改善 AI 协作方式的开发者。文中的流程是结合工程原则与公开一手资料形成的实践建议，并非某一套统一的“全球 AI 编程标准”。资料核对日期为 2026 年 9 月 24 日。

## 一、理解模型的局限，也理解 Agent 的工作方式

把大语言模型理解为“根据上下文预测后续 token 的概率模型”，是一个有帮助的起点。它提醒我们：语言流畅、代码完整、解释自信，都不能单独作为正确性的证明。

但这个描述不足以涵盖整个编程 Agent。实际使用的系统还包含工具、文件读取、命令执行、反馈循环和权限控制。它可以检查仓库、运行测试，并依据结果继续修改。因此，我们需要评价完整工作过程：它读取了什么、基于什么作出决定、执行了什么、最终得到了什么证据。

Anthropic 在介绍 Agent 时，将模型与工具、环境反馈和控制流程放在一起讨论。这有助于解释为什么同一个模型，在不同工具和反馈条件下，实际表现也会不同。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

上下文的作用，是减少需要猜测的部分。但上下文无法保证正确性；即使需求完整，也仍可能出现逻辑错误、错误 API 用法或遗漏的异常路径。

因此，我会把 AI 的代码当作需要验证的实现，把 AI 的解释当作需要核对的说明。对于它提出的更好方案，同样依据证据评估。

## 二、把“掌控感”变成五个可以回答的问题

主观上的熟悉感很容易产生。听完一段合理的解释，我们可能觉得自己懂了，却仍然无法指出哪里会出错。

我用五个问题检查自己的理解：

1. **目标：** 谁在什么场景下遇到了什么问题？完成后，外部可观察的行为有什么变化？
2. **路径：** 请求从哪里进入，经过哪些模块，在哪里读写数据，又影响哪些下游？
3. **约束：** 无论正常、异常还是重复请求，哪些规则都必须成立？
4. **风险：** 哪些情况最可能使方案失效？哪些后果最难恢复？
5. **证据：** 用什么测试、运行结果或检查，可以证明实现符合要求？

这里不要求开发者在动手前想清每一行代码。对于陌生模块，完全可以先让 AI 帮助探索，再逐步建立理解。

关键是把“已经确认的事实”“当前假设”“尚未解决的问题”分开。发现未知项并建立验证路径，本身就是掌控能力的一部分。

## 三、从一个小模块开始，先建立最小可用的系统地图

假设刚入职时接到一个任务：**允许用户取消尚未处理的预约。**

第一步可以让 AI 只做探索，找出接口入口、身份信息来源、预约状态定义、数据访问层、现有错误处理和相关测试。每个结论应附上实际文件、符号或调用关系，无法确认的部分明确标注。

开发者随后亲自走通一条主链路：

`用户操作 → 请求接口 → 身份与权限判断 → 业务状态校验 → 数据更新 → 返回结果`

读代码时，重点追问：身份从哪里来？业务规则在哪一层？写入是否原子化？失败如何暴露给调用方？现有调用者依赖什么返回格式？

“可能涉及哪些文件”是探索结果，不宜完全靠猜。AI 可以提出候选修改范围，但应先检查仓库中已有的实现方式。一个看似局部的按钮，可能连接着状态机、消息通知和定时任务。

对于入职后的第一项任务，还值得核对团队已有的完成要求：测试怎么运行、谁负责评审、接口如何兼容、什么情况下允许发布。这样建立的理解能直接服务于交付。

## 四、编码前：把一句需求写成可验收的约定

“实现预约取消功能”留下了许多空白。这些空白如果没有被主动发现，就可能由 AI 在编码过程中自行填补。

为了说明方法，先为这个示例作出以下业务约定。它们是教学假设，真实项目应以产品规则为准：

| 维度 | 本例约定 |
|---|---|
| 操作主体 | 已登录的预约创建者 |
| 允许状态 | 仅待处理状态可以首次取消 |
| 成功结果 | 状态变为已取消，记录取消时间 |
| 重复操作 | 本人重复取消返回已取消结果，不重复产生副作用 |
| 非法操作 | 他人无法取消；已完成预约无法取消 |
| 并发冲突 | 取消与开始处理竞争时，只允许一个状态转换成功 |
| 本次范围 | 接口、必要的业务及数据更新逻辑、测试 |
| 暂不涉及 | 退款、通知系统重构、批量取消 |

这张表定义了后续判断的依据。比如，第一次取消成功，只能证明正常路径可用，无法证明权限和并发行为正确。

我会尤其关注“不变量”：系统始终必须守住的业务规则。这个例子中，无权限的请求不得改变预约；一个预约不能同时完成互相冲突的状态转换；重复取消不能重复产生业务副作用。

OpenAI 的实践指南建议任务包含目标、上下文、约束和完成条件。这四项可以作为任务说明的基础骨架。[Best practices](https://learn.chatgpt.com/guides/best-practices)

### 用问题暴露遗漏

梳理边界时，可以沿着几个方向追问：

- 输入：缺字段、空值、超长内容或非法格式会怎样？
- 身份：未登录、无权限、跨用户或跨租户会怎样？
- 状态：对象不存在、已经完成、已经取消会怎样？
- 时间：重复请求、请求乱序、并发修改会怎样？
- 依赖：数据库或外部服务失败，会不会留下部分成功的数据？
- 兼容：旧客户端、旧数据和其他调用方能否继续工作？

这些是发现问题的入口，应按任务风险选择。一个展示文案修改没有必要机械地讨论全部分布式故障。

对于当前无法确定的问题，先记录其影响。会改变业务语义或数据安全的问题应在相关实现前确认；低风险、可逆的实现细节，可以遵循项目惯例推进，并留下假设说明。

## 五、把需求、方案和执行计划分开

这三类信息解决不同问题：

| 内容 | 回答的问题 | 预约取消示例 |
|---|---|---|
| 需求规格 | 必须得到什么结果？ | 只有创建者能取消待处理预约 |
| 技术方案 | 准备用什么机制保证结果？ | 使用包含所有者和预期状态条件的原子更新，并按项目约定处理未更新结果 |
| 执行计划 | 按什么顺序实现和验证？ | 确认状态定义，修改业务和数据逻辑，接入接口，验证关键场景 |

“先查询，再判断，再更新”看起来合理，但如果查询和更新之间状态被其他请求改变，就可能违反业务约束。是否使用条件更新、锁或其他机制，要结合已有架构和数据库行为判断，不能仅凭代码表面顺序接受方案。

规格保留需要守住的行为，技术方案允许根据仓库证据调整，执行计划则应拆到每一步都有明确产出和验证方法。

类似 `to-spec` 的工作流，可以承担把讨论整理成规格的作用。但一份排版完整的文档也可能忠实地记录错误假设。转换完成后，仍要检查业务矛盾、遗漏的异常路径，以及无法验证的描述。

## 六、实现中：用可审查的增量控制偏差

AI 可以快速生成大量代码，但团队的理解和审查能力有边界。每轮变更应足够小，让开发者能够说明它解决什么问题、改变哪些行为、如何验证。

对于预约取消，可以先完成状态更新及关键业务验证，再接入接口，最后验证用户链路。具体拆分顺序服从现有结构，重点是每一步能提供反馈。

每轮检查三个方面：

**范围。** 修改是否仍然服务于目标？如果一个小功能引入了新框架、重写公共组件或改动大量无关文件，应要求解释必要性。

**机制。** 实现是否真正维护业务规则？例如，前端隐藏按钮无法代替服务端授权；先查状态再写入，也不自动等于并发安全。

**证据。** AI 是否执行了适用的检查？它报告的“通过”对应什么命令、环境和测试范围？未执行的项目有没有明确列出？

当 AI 的实现偏离初始预期时，先比较原因。如果它发现了原计划遗漏的依赖，可以更新方案；如果只是顺手扩大重构范围，就应收回变更。掌控过程需要容纳基于证据的修正。

一个值得及时打断的信号是：AI 反复修改，却说不清当前错误的原因。这时应回到复现、日志、调用链和最小失败案例，避免继续叠加补丁。

## 七、验收：把需求和证据一一对应

AI 既写实现又写测试时，可能把同一个误解带入两者。代码通过了自己定义的断言，也可能没有满足业务需求。

降低这种风险的一种方法，是在实现前确定关键验收案例，并保留已有回归测试。新增测试应验证外部行为和不变量；必要时再验证关键内部机制。

| 要求 | 合适的验证方式示例 |
|---|---|
| 本人可以取消待处理预约 | 检查返回值、持久化状态和取消时间 |
| 他人无法取消 | 使用另一身份调用，确认拒绝且数据不变 |
| 已完成预约不能取消 | 验证错误行为及原状态保持 |
| 重复取消不重复产生副作用 | 重复请求，检查副作用记录或调用次数 |
| 取消与开始处理不能同时成功 | 在真实数据库语义下构造并发竞争，检查结果和最终状态 |
| 不破坏原有预约流程 | 运行相关回归测试和必要的集成检查 |

纯粹 mock 掉数据库的方法调用测试，通常不足以验证数据库并发行为。相反，一个简单的格式转换函数，也未必需要昂贵的端到端测试。验证方式应匹配风险所在的层次。

对于缺陷修复，尽可能让回归测试在修复前因目标缺陷失败，在修复后通过。这能帮助确认测试捕捉到了真正的问题。

测试结果要保留实际边界：“相关单元测试通过，但没有可用的集成环境”，比笼统的“全部验证完成”更有价值。测试提供的是特定条件下的证据，并不等于穷尽所有错误。

## 八、审查大量代码：先看结构，再深读关键路径

面对几千行变更，不必给每一行分配相同的注意力，但全部变更范围都需要被理解和归类。AI 的总结可以帮助定位，实际 diff 才能显示完整修改。

我会按以下顺序审查：

1. 看文件清单和整体范围，寻找无关修改、意外配置变化和新增依赖。
2. 对照需求，检查接口、数据结构和模块职责是否合理。
3. 深读权限、状态转换、事务、并发、异常处理和数据迁移等关键路径。
4. 检查测试是否覆盖目标行为，是否删除、跳过或弱化了原有断言。
5. 核对运行证据，以及仍然没有验证的风险。

生成文件和机械性修改可以通过生成流程、工具检查等方式处理；关键业务逻辑则需要逐行理解。若一个变更大到无法解释其关键行为，就应拆分、简化，或请熟悉模块的人共同评审。

GitHub 对 Copilot Agent 的责任使用说明明确要求人类审查和测试生成的变更。AI 审查可以增加发现问题的机会，但不能直接替代接受代码的责任。[Responsible use of GitHub Copilot agents](https://docs.github.com/en/copilot/responsible-use/agents)

即便使用第二个 Agent 或另一种模型，也应让它依据原始需求和实际 diff 审查。多个模型可能共享盲点，彼此同意不能单独构成正确性证据。

## 九、Skills、Grilling 和规格文档，应该各司其职

这些工具的价值，在于把容易遗漏的工程动作变得可重复。工具名称和组合可以变化，但需要承担的工作相对稳定。

| 工具或实践 | 适合承担的工作 | 需要防止的误用 |
|---|---|---|
| Brainstorming / Grilling | 追问目标、反例、范围和取舍，暴露假设 | 为了提问而提问，迟迟不作决定 |
| Spec / to-spec | 固化已确认的行为、边界和验收条件 | 把未确认假设写成事实 |
| 执行计划 | 拆分依赖和步骤，为每一步安排验证 | 罗列文件，却没有可观察的完成条件 |
| Skills | 复用经过实践的操作流程和检查方法 | 安装很多技能，却不知道何时适用 |
| 项目规则文件 | 记录稳定的仓库约定、命令和限制 | 堆积过时、重复或互相冲突的规则 |
| 测试与 CI | 执行可自动化的行为和质量检查 | 把“绿灯”理解为需求一定正确 |
| 代码审查 | 检查需求符合性、实现风险和可维护性 | 只读生成说明，不看实际变更 |

适合固化成规则的是反复出现的经验。例如，“取消预约曾发生并发覆盖”可以沉淀为状态更新检查项和回归测试；某次任务临时采用的参数，不一定值得进入全局规则。

重要约束还应尽可能由系统执行。例如，数据库唯一约束可以阻止某类重复数据，权限隔离可以限制 Agent 的操作范围，CI 可以阻止未通过检查的代码合入。自然语言提示之外，还需要这些实际机制。

## 十、经验不足时，让 AI 帮你发现未知，同时训练判断力

有经验的开发者通常积累了更多故障案例，因此更容易想到并发、兼容、状态转换和失败恢复等问题。这些经验会进入任务描述、方案选择和审查重点。

不过，资历本身也不能保证判断正确。熟悉的模式可能不适合新系统，经验仍需要用当前代码和运行证据校准。

对于初学者，我更愿意采用这样的学习循环：

**先作预测 → 查看实现 → 亲自运行 → 制造失败 → 解释差异 → 记录经验。**

例如，在让 AI 实现取消功能前，先写下自己预期涉及的层次和三个失败场景。实现后，比较哪些预期正确、哪些遗漏了；再亲自构造重复请求或并发冲突，观察实际行为。

有选择地手写代码也有价值。可以亲手实现一次事务处理、条件更新或错误传播，再与 AI 的方案比较。手写的目的，是暴露自己对执行过程的误解，并建立能够独立调试的能力。

学习是否发生，可以用一个简单的问题检验：离开 AI 的解释后，我能否讲清这个功能如何工作、最可能在哪里失败，以及如何定位失败？

## 十一、一份可直接复用的任务说明

下面的模板可按任务复杂度删减。小修复可能只需要几行；涉及权限、资金、跨服务状态或数据迁移时，则应补充更具体的验证与恢复安排。

```text
任务目标
- 谁在什么场景下遇到什么问题？
- 完成后，哪些可观察行为应当改变？

事实与上下文
- 相关需求、代码入口、相似实现、接口契约：
- 当前分支或版本、复现步骤、实际错误：
- 已确认事实、临时假设、待确认问题分别是什么？

范围与约束
- 本次需要实现：
- 本次不涉及：
- 必须保持的兼容行为和业务不变量：
- 应遵循的项目约定：

探索与方案
- 先读取相关实现，列出关键调用链和候选修改范围。
- 用文件、符号或运行结果支持结论，标注无法确认的部分。
- 对影响业务语义的重要歧义先澄清。
- 对存在明显取舍的方案，说明选择理由和风险。

验收标准
- 正常场景及预期结果：
- 权限、状态和输入边界：
- 按需补充重复、并发、依赖失败和兼容场景：
- 需要运行的检查或测试：

实施要求
- 按可审查、可验证的增量推进。
- 不顺带扩展无关功能或重构。
- 发现原方案不成立时，说明证据并更新计划。
- 不以跳过测试、弱化断言或吞掉错误来制造通过结果。

交付证据
- 修改了什么，为什么修改？
- 各项验收条件分别对应哪些实现和验证结果？
- 实际运行了什么检查，哪些未运行，原因是什么？
- 还有哪些风险，是否需要恢复措施或后续验证？
```

这份模板的作用，是帮助双方形成一致的工作约定。它无法替代开发者阅读代码、追问证据和判断结果。

## 十二、让每次任务留下可复用的经验

一次功能完成后，可以留下很短的复盘：最初漏掉了什么边界，哪项假设被推翻，AI 在哪里偏离，什么证据最终帮助作出了判断。

适合复用的部分再进入测试、项目规则或 Skill。这样，下次遇到相似任务时，起点会更高。

交付效率也应按完整过程衡量：需求澄清、生成、调试、审查、返工和上线后的维护都算在内。代码生成得快，只解决了其中一个环节。

我希望自己逐渐能够对一次变更作出具体说明：**我知道它解决什么问题，理解关键路径，清楚哪些证据支持它，也知道哪些地方仍然存在不确定性。** 当这件事能够做到，AI 带来的产出才更容易转化为可维护的工程成果。
