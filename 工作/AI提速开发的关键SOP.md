> AI 辅助开发的本质，是开发者掌控关键决策和交付质量，而不是亲自编写或审查所有代码。

掌控来自两端：开发前对问题和边界的判断，开发后对结果和风险的判断。

AI提速：
**不要尝试所有的代码一个一个阅读，了解项目业务层、不懂得技术作用，其次就是主要控制层链路，底层代码不用过多深究（和调用包一个道理），然后尝试让AI快速迭代开发，可以见mdnotes的具体工作流**

## 1. 开发前：掌控「做什么、怎么做」

关注：需求、边界、关键决策、变更范围。

怎么做：

* 明确业务目标、输入输出、功能边界和验收标准。

* 不确定时用 `grill-with-docs` 让 AI 提问，暴露自己遗漏的关键问题。

* 让 AI 阅读现有代码，输出实现方案、修改范围和影响分析。

* 你确认关键方案，而不是让 AI 自行决定所有架构和业务规则。

**注重上层问题，而不再需要单个函数、类等等问题，ai效率远远高于手敲代码**

## 2. 开发中：掌控「AI 有没有失控」

关注：偏离需求、错误假设、过度修改和不可验证的实现。

可能出现的问题：

* AI 对需求理解错误，自己补充了业务规则。

* 修改范围扩大，影响无关模块。

* 代码能运行，但核心业务逻辑错误。

* 测试覆盖不足，异常路径、权限或数据一致性有问题。

* AI 反复修补表面错误，却没有定位根因。

怎么做：

* 分阶段、小切片实施，而不是一次性生成全部代码。

* 每个阶段检查实现是否仍符合规格。

* 通过测试、运行结果和日志获得反馈。

* 重点审查高风险代码和关键决策，不要求逐行审查所有代码。

## 3. 开发后：掌控「能不能交付」

关注：功能正确、没有破坏现有系统、实际可用。

验收重点：

* 功能验收： 核心需求和边界条件是否满足？

* 回归验收： 旧功能、接口和数据是否受到影响？

* 运行验收： 异常、超时、依赖失败等场景能否正确处理？

* 变更审查： Diff 是否合理？是否存在无关修改和明显维护风险？

不是把所有代码重新看一遍，而是结合测试证据、实际运行结果和重点代码审查作出自己的判断。

## 4. 底层通用理念

无论使用什么 AI 编程工具，核心准则基本可以归纳为：

|理念|具体要求|
| --- | --- |
|明确性|需求和验收标准可理解、可验证|
|边界性|明确做什么、不做什么|
|可控性|修改范围、关键决策和影响可追踪|
|可验证性|通过测试和运行结果证明行为|
|风险意识|高风险部分需要更严格的审查|
|反馈迭代|尽早发现问题，避免错误持续扩大|

## 5. 对应 Skills 的 SOP
| 阶段 | 使用 Skill | 目的 |
| ---- | ---------- | ---- |
| 需求澄清 | `grill-with-docs` | 暴露遗漏和歧义 |
| 形成规格 | `to-spec` | 产出明确的实现与验收依据 |
| 拆分任务 | `to-tickets` | 将大功能拆成可验证的小任务 |
| 实施 | `implement` | 按规格执行开发 |
| 遇到 Bug | `diagnosing-bugs` | 复现、定位、修复、回归 |
| 完成验收 | `code-review` + 测试 | 检查代码质量和规格符合性 |

### 最终 SOP

1

需求澄清 → 变更分析

Grill → Spec → 阅读代码、确认边界与方案

2

分阶段实现

Tickets（需要时）→ Implement → 测试反馈

3

验收与交付

功能测试 → 回归测试 → Diff / 风险审查 → 交付

一句话：你负责判断正确的问题、关键方案和交付标准；AI 负责提高实现效率，而测试与反馈负责证明结果。
