结合您提供的《小飞Agent PO 需求拆解说明》文档，以及企业级数据产品的普遍设计原则，不让LLM直接生成SQL，是基于**业务准确性、数据安全、系统稳定性、可审计性**等多方面权衡后的必然选择。这实际上是当前业界“Text2SQL”方案向“Text2IR2SQL”（自然语言转中间表示再转SQL）演进的核心原因。

具体来说，原因可以归结为以下五个核心维度：

### 1. 杜绝“幻觉”，保障业务数据的绝对准确性
*   **防指标重复计算（Fan-out）**：文档中特别强调了 `Grain Analyzer` 和扇出风险。如果让LLM直接写SQL，它很容易忽略表与表之间的 `1:N` 或 `N:N` 关系，直接写个简单的 `JOIN`，这会导致指标严重膨胀（比如订单金额被翻倍）。通过 `Query IR` 和确定性编译器，系统可以强制将 `1:N` 关系转换为 `EXISTS` 或预聚合 CTE，从底层物理逻辑上杜绝数据失真。
*   **防字段与表名臆造**：LLM不可避免地会“幻觉”出不存在的表名或字段名。文档中明确规定 LLM 只输出“结构化语义槽”，不输出表名和字段名。通过图谱和元数据校验，能确保每一个字段都在已发布的资产范围内。

### 2. 守住数据安全与权限管控的底线
*   **防恶意SQL与注入攻击**：如果让LLM生成SQL，它有可能被提示词注入攻击，生成 `DELETE`、`DROP` 甚至 `UPDATE` 等破坏性语句。而确定性编译器只会生成只读的、参数化的模板SQL。
*   **权限校验的可行性**：文档中提出“Query IR 与 Candidate SQL 可以包含未授权资源”，这意味着在生成SQL阶段，系统其实并不知道用户有没有权限。只有到了 `SQL Guard` 阶段，通过 AST 解析出实际的表（actualTables），才能去校验用户的问数资源权限。如果由LLM直接生成SQL，权限拦截、授权引导（Authorization Required）以及 `RequestID` 的全链路审计将变得极其难以实现。

### 3. 满足复杂业务逻辑与性能的“确定性”要求
*   **严格遵循已发布的语义约束**：文档规定“多Join只能来自已发布的语义关系映射”、“不得按字段同名或LLM猜测Join”。LLM很难精准遵守这些极其严格的企业级业务规则。而 `Join Planner` 基于图谱和算法（最小连通图）来规划，能够精准控制 Join 的数量（默认最多5条）并处理路径歧义。
*   **防止生成“自由且低效”的复杂SQL**：LLM喜欢写嵌套子查询、多重 CTE。文档明确“P0允许DIRECTJOIN、PRE_AGGREGATE受控CTE、SEMIJOIN_EXISTS与已发布DISTINCT_BRIDGE策略；不支持任意自由复杂SQL”。确定性编译器生成的SQL是受控的，性能更可预测，避免拖垮底层数据库。

### 4. 满足企业级审计与可复现的合规要求
*   文档在“6.1 request_id全链路规则”中要求：每次请求都要记录 `图谱版本`、`JoinGraph`、`IR`、`Candidate SQL摘要` 等。如果SQL是由LLM生成的黑盒产物，一旦出错，很难定位是语义理解错了、模型幻觉了，还是图谱配置有问题。而采用 `Query IR -> Candidate SQL` 的确定性链路，每一步都可以被精准审计、还原和复现。

### 5. 降低数据库方言与工程维护成本
*   不同数据库（MySQL、PostgreSQL、Hive等）的SQL方言差异巨大。让LLM适配所有方言成本极高且不可控。而将语义理解（LLM擅长）与SQL编译（确定性代码擅长）解耦后，未来若增加新的数据源，只需扩充底层的编译器模板，无需重新训练或调整大模型。

**总结：**
在“小飞Agent”的设计中，LLM被精准地限制在了它最擅长的领域——**自然语言理解与意图提取**（生成 Query IR）。而将 **SQL生成、Join规划、权限校验、执行管控** 交给了确定性的工程系统。这是当前企业级数据智能体最成熟、最安全的技术架构。
