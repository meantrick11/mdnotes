## 开发规范


### 1. 代码管理规范

#### 1.1 分支定义

DEV -> 用于开发者调试使用环境
SIT -> 功能验收测试环境，用于测试环境下的软件测试使用
UAT-> 用户验收测试环境
PRD -> 生产环境

#### 1.2 针对不同环境的不同分支

1. master分支

主分支，用于部署到正式环境(PRD),一般由release|hotfix分支合并而来，**任何情况都不能直接在master分支上修改代码**

2. release分支

release为预上线分支，用于部署到预线上环境(UAT),始终与master分支一致，一般由develop/hotfix分支合并，**不建议直接在release分支上直接修改代码**。如果release分支测试出问题，需要回归验证develop分支产看是否存在词问题。

3. hotfix分支

紧急修复分支，命名为hotfix-分支开头，当线上出现紧急问题需要马上修复时，**需要基于release&develop分支，一旦修复上线，便将其删除**

4. develop分支

develop为测试分支，用于部署到测试SIT,始终保持最新完成以及bug修复后的代码，根据大小程度确定是由feature分支合并还是直接在上面开发。**一定是满足测试的代码才能往上合并或提交**


5. feature分支

feature为需求开发分支，命名规则为feature-开头，也是本地管理分支，一旦该需求上线，便可以将其删除。**合并到develop分支之后，测试->release分支->master分支上线PRD环境之后**


#### 开发场景


**对任何未测试完毕的分支操作都要注意**

1. 新需求：优先从develop创建feature分支，如果未测试完毕的develop，那么就基于master分支创建

feature-develop-realse-(hotfix)-master

2. 普通迭代：如果一个订单管理的迭代需求<1h,直接在develop开发，如果>1h，则需要创建feature分支

3. 修复测试环境bug（develop环境）
如果develop出现bug <2h,直接修复，>2h，创建feature并重复需求分支过程

4. 修改预上线环境bug(UAT环境)

在release上出现bug，先排查develop分支，然后按照3进行bug修复，如果不是，则可能是环境问题

5. 修改正式环境bug（PRD）

在master测试出现问题，首先向下回归release分支和develop分支，走3/4策略

如果有正在测试的环境，那么考虑创建hotfix分支进行bug修复，修复后同步master\release\develop分支

6. 并行提测

部署可供测试人员的测试的分支

#### commit日志规范

commit -m "fix/feat/test/style/docs/refactor:+scope"


- fix：修复 xxx Bug
- feat：新增 xxx 功能
- test：调试 xxx 功能
- style：变更 xxx 代码格式或注释
- docs：变更 xxx 文档
- refactor：重构 xxx 功能或方法


scope 表示 影响范围，可分为：模块、类库、方法等。 subject 表示 简短描述，最好不要超过 60 个字，如果 有相关 Bug id，建议在描述中加上。


**重点就是1.溯源修复2.确定代码拉取分支3.不确定的操作问一下老师傅**

## 5. 设计思想

### 5.1 基于接口而非实现编程，基于抽象而非实现
核心：
接口是一组协议、约定，只说明“做什么”，不说明“怎么做”。
上游依赖接口，而不是具体实现。实现变化时，上游代码尽量不变。

文中例子：
最初是 AliyunImageStore：

java
uploadToAliyun()
downloadFromAliyun()
generateAccessToken()
方法名暴露了阿里云细节。后来要换私有云，发现：

方法名要改；

access token 流程私有云不需要；

所有调用处都要改。

重构后：

java
public interface ImageStore {
    String upload(Image image, String bucketName);
    Image download(String url);
}
AliyunImageStore 和 PrivateImageStore 都实现 ImageStore。
调用方只依赖 ImageStore，不关心阿里云还是私有云。

落地到当前项目：
不要写：

java
if ("mysql".equals(type)) { ... }
else if ("oracle".equals(type)) { ... }
而应抽象：

java
interface DatabaseMetadataExtractor {
    List<DbTableMetaData> extract(Connection con);
}
MySQL、Oracle、PostgreSQL 各自实现。新增数据库时，主流程不动。

注意：
不是每个类都要定义接口。
如果只有一种实现，未来也不会替换，就直接用实现类。
越不稳定、越可能替换、越多实现的地方，越需要接口。


### 5.2 多用组合少用继承


核心：
继承是强依赖，父类改动会影响所有子类。继承层次深、关系复杂时，可读性和可维护性都会变差。

文中例子：
鸟类设计：

大部分鸟会飞，但鸵鸟不会飞；

如果还考虑“会不会叫”“会不会下蛋”，继承类会爆炸：
AbstractFlyableTweetableBird、AbstractUnFlyableTweetableBird……

重构思路：

java
interface Flyable { void fly(); }
interface Tweetable { void tweet(); }
interface EggLayable { void layEgg(); }

class Ostrich implements Tweetable, EggLayable {
    private TweetAbility tweetAbility = new TweetAbility();
    private EggLayAbility eggLayAbility = new EggLayAbility();

    public void tweet() { tweetAbility.tweet(); }
    public void layEgg() { eggLayAbility.layEgg(); }
}
用接口 + 组合 + 委托替代复杂继承。

判断标准：

继承结构稳定、层次浅、不复杂：可以用继承。

系统不稳定、继承层次深、关系复杂：优先组合。

只是为了复用代码，但业务上没有 is-a 关系，不要硬抽父类。

文中例子：
Crawler 和 PageAnalyzer 都用到 URL 拼接，但没有继承关系。
应写成：

java
class Crawler {
    private Url url;
}
而不是硬抽一个 UrlParent。

落地到当前项目：
不同数据库的“连接、取表、取字段、写配置”能力，可以用组合拼装，而不是搞一个巨大的 AbstractDbSource 继承体系。

### 5.3 解耦：封装、抽象、模块化、中间件


**基于接口概念进行编程、多实现解耦、解耦之后使用组合**

**接口而非实现、组合而非继承、解耦而非融合**

### 5.4 其他原则

单一职责原则
依赖注入
迪米特法则：不该有直接依赖关系的类之间，不要有依赖；有依赖时，尽量只依赖必要接口。
