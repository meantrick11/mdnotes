# 业务理解、业务抽象与标准工作流 SOP


**什么角色，在什么场景或条件下，想要完成什么事情/达成什么目标/价值**

**围绕哪些对象，按照什么流程和规则完成目标，过程中有哪些状态变化&异常情况**

**现有系统是如何做的？期望变成什么样？两者有什么差异，会影响哪些现有能力？**

## 一、核心思想

无论是**理解已有项目、开发全新业务，还是修改已有需求**，核心都是：

**业务理解 → 业务抽象 → 技术设计/映射 → 实现与验证**

- **业务理解**：明确业务为什么存在、谁在使用、如何运作。
- **业务抽象**：从具体场景中提炼业务对象、关系、行为、状态和规则。
- **技术设计/映射**：明确由哪些模块、接口、服务、数据表及技术组件承担这些职责。
- **实现与验证**：通过代码和测试，确认系统满足业务目标。

不要从记忆类、方法、接口入手，而应该先理解它们服务于什么业务，以及为什么这样设计。

---

## 二、业务理解的七个核心问题

| 维度                | 核心问题          | 示例：文件上传         |
| ----------------- | ------------- | --------------- |
| 1. 角色（Who）        | 谁参与？谁发起？      | 普通用户、管理员        |
| 2. 场景（When/Where） | 什么情况下发生？      | 用户需要上传业务附件      |
| 3. 目标（Why）        | 为什么做？期望什么结果？  | 保存文件，供后续查看、下载   |
| 4. 流程（How）        | 从开始到结束经历哪些步骤？ | 选择文件→校验→上传→保存   |
| 5. 规则（Rules）      | 有什么前提、限制、约束？  | 文件大小、格式、权限、去重规则 |
| 6. 对象（What）       | 涉及哪些业务对象及关系？  | 用户、文件、业务记录、引用关系 |
| 7. 状态与异常          | 状态如何变化？失败怎么办？ | 上传中、成功、失败、重试    |

其中：

- **前五项侧重业务理解**：弄清楚业务需求与实际流程。
- **后两项进一步支持业务抽象**：提炼出可用于系统设计的业务模型。

注意：业务规则贯穿业务理解与建模两个阶段，不应该被忽略。

## 三、从业务理解到业务抽象

业务理解解决的是：**业务具体怎么运作？**

业务抽象解决的是：**业务背后存在哪些稳定的概念、关系与规则？**

### 业务抽象的五个要素

| 要素 | 核心问题 | 文件管理示例 |
|---|---|---|
| 对象 | 业务中有什么？ | 文件、用户、业务记录 |
| 关系 | 对象之间如何关联？ | 一个业务记录关联多个文件 |
| 行为 | 对象可以执行什么操作？ | 上传、下载、删除、关联 |
| 状态 | 对象经历哪些状态变化？ | 待上传→上传中→成功/失败 |
| 规则 | 行为受到什么约束？ | 权限校验、文件去重、删除约束 |

**举例：文件上传**

业务理解：

用户在编辑业务记录时，需要上传附件；系统检查文件是否合法，保存文件并关联业务记录。

进一步抽象：

- 文件内容与文件业务记录可能是两个不同概念。
- 一个文件可能被多个业务记录引用。
- 重复文件可能复用相同的物理存储内容。
- 删除文件引用不一定意味着删除物理文件。

这些都是可能的设计，需要结合实际业务规则判断，而不是直接当成系统事实。

最终再将这些抽象映射为 Service、数据库表、对象存储等技术实现。

## 四、通用标准工作流

### Step 1：业务背景与目标

**任务：理解业务为什么存在。**

分析参与角色、触发场景、业务痛点、目标和成功标准。

**产出：** 业务场景描述与目标说明。

### Step 2：业务流程与规则

**任务：理解业务如何运转。**

分析正常流程、前置条件、分支、业务规则、边界及异常情况。

**产出：** 业务流程图、规则清单。

### Step 3：业务抽象与建模

**任务：将具体业务提炼为结构化模型。**

识别业务对象、对象关系、行为、状态与规则，并明确各项业务职责的边界。

**产出：** 业务对象模型、职责划分。

### Step 4：技术设计或现有实现映射

**任务：建立业务与代码之间的联系。**

分析模块职责、上下游依赖、接口、数据模型、数据库表、存储组件和关键处理逻辑。

- 新业务：设计技术方案，决定如何实现。
- 旧项目：阅读现有实现，还原其技术设计。

**产出：** 技术架构图、核心链路、接口及数据映射。

### Step 5：验证与沉淀

**任务：确认理解或实现是否正确。**

- 新业务：通过测试和验收验证需求。
- 旧项目：通过实际操作、请求、代码与数据验证分析结论。

记录关键设计原因、技术入口、尚未解决的问题。

**产出：** 验证结果、项目认知笔记。

## 五、不同工作场景下的具体应用

整体框架一致，但不同场景的起点和目标不同。

### 场景 A：理解已有项目 / 已有业务

**目标：还原现有业务模型与技术实现，建立系统认知。**

推荐流程：

1. **整体认知**：了解产品定位、主要业务、用户角色、模块及技术架构。
2. **选择业务场景**：优先分析核心业务链路，而不是逐个阅读所有类和接口。
3. **理解业务**：梳理场景、目标、流程、规则、对象与状态。
4. **还原技术实现**：结合实际操作、网络请求、代码及数据库，追踪核心链路。
5. **验证与沉淀**：能够独立讲清楚该业务如何实现、为什么这样设计。

**例：理解 file 模块**

不要一开始就阅读全部 Controller、Service、Mapper。

先选择「文件上传」场景：

- 用户为什么上传？
- 上传涉及哪些对象和业务规则？
- 为什么上传前调用 `checkExists`？
- 文件内容保存在哪里？文件记录保存在哪里？
- 前端、接口、Service、数据库和 MinIO 如何协作？

最终形成一份业务链路与代码索引，而不是类和方法的记忆清单。

### 场景 B：开发全新业务

**目标：从业务需求出发，建立合理的业务模型并实现功能。**

推荐流程：

1. **需求澄清**：明确角色、场景、目标和验收标准。
2. **业务流程设计**：明确正常流程、规则、边界及异常。
3. **业务抽象**：识别对象、关系、行为、状态和职责。
4. **技术方案设计**：确定模块、接口、数据模型、存储方式及其他技术组件。
5. **编码、测试与交付**：实现功能，验证业务规则与目标。

**例：从零开发文件管理功能**

先明确需要上传、下载、查询、删除哪些能力，再分析文件模型、去重和权限等规则，最后设计接口、数据库及对象存储方案。

不要一开始就决定需要几个 Controller、Service 或数据库表。

### 场景 C：修改已有需求 / 新增功能

**目标：理解变化，找到最合适的修改位置并控制影响范围。**

推荐流程：

1. **明确新需求**：分析目标、规则和验收标准。
2. **理解现状（As-Is）**：梳理当前业务流程及实现。
3. **明确目标（To-Be）**：描述变更后的业务行为。
4. **差异与影响分析**：识别改变的对象、规则、流程、接口及数据结构。
5. **方案设计与修改**：尽可能复用已有能力，明确修改范围。
6. **测试与回归**：验证新需求，同时确保原有功能不受影响。

**例：将手动输入 Schema 改为选择路径**

- 现状：用户手动输入 Schema。
- 目标：用户通过选择路径指定 Schema。
- 差异：输入方式、数据来源、校验规则可能发生变化。
- 技术分析：是否需要新增查询接口？后端字段是否变化？现有校验能否复用？
- 验证：新功能正确，原有相关流程正常。

这里最重要的方法是：

**As-Is（现状）→ To-Be（目标）→ Gap（差异）→ Impact（影响）→ Implementation（实现）**

## 六、最终工作原则

1. **以业务场景或需求为分析单位**，不要盲目遍历整个代码模块。
2. **先理解业务，再分析技术**，避免只知道代码如何执行，却不知道为什么这样设计。
3. **区分业务模型和技术模型**，业务对象不一定与 Entity、DTO、数据库表一一对应。
4. **关注业务规则和设计原因**，它们比具体类名、方法名更值得长期记忆。
5. **使用实际系统验证理解**，文档描述、自己的推断和真实代码实现可能存在差异。
6. **按复杂度控制分析深度**，小需求一张表即可，复杂业务再绘制流程图、模型图和技术链路。
7. **沉淀可复用的认知，而不是记忆代码**，重点保留业务模型、核心流程、关键设计决策和代码定位入口。

**最终能力目标：**

能够面对一项业务或需求，独立完成：

**理解业务 → 提炼模型 → 明确职责 → 定位或设计技术实现 → 验证结果。**

这套能力与具体编程语言、框架和公司项目无关，是从初级开发逐渐成长为能够独立负责业务模块的工程师所需要的基础能力。
