# 产品开发流程（依据 GitLab Handbook 原文）

来源：[GitLab Handbook — Product Development Flow](https://handbook.gitlab.com/handbook/product-development/how-we-work/product-development-flow/)；查阅日期：2026-10-25。以下按原文章节顺序整理，保留 GitLab 的角色、状态、标签、产出与活动，不加入其他团队的流程要求。原文所用的“必须”与“建议”在下文分别保留。GitLab Handbook 内容采用 [CC BY-SA 4.0](https://handbook.gitlab.com/handbook/about/handbook-usage/) 许可；本文是中文整理版本，同样以 CC BY-SA 4.0 共享。原文如有更新，以原网页为准。

## 1. 概述与理念

GitLab 的产品开发流程用于让跨职能团队以可重复的方式把想法转化为客户价值。功能开发通常经过各阶段并达成相应产出；其他具体做法属于最佳实践和建议。部分改进可以按产品经理与设计、工程团队的共同判断缩短阶段。开源社区的贡献也可能在流程中的任意位置进入。

这些阶段并非线性瀑布流程：可以重叠、并行，且不规定每阶段的固定时长。把握充分时，可缩短或跳过不会增加信心的阶段。例如，工程团队可以在验证期间同步进行技术评审；已确认的问题和解法明确的缺陷可以直接进入构建轨。

## 2. 工作流总览与统一记录

工作项主要经历：`Validation backlog` → `Problem validation` →（需要设计时）`Ready for design` → `Design` → `Solution validation` → `Planning breakdown` → `Ready for development` → `In dev` → `In review` → `Verification` → `Complete`。`Refinement`、`Blocked`、`Awaiting security release` 等状态按对应情形使用；适当时可以跳过状态。

**Issue 描述必须始终作为单一事实来源（SSOT）。** 每个阶段的直接责任人（DRI）负责维护准确性，其他参与者发现不一致或遗漏也应更新，避免必须通读全部评论才能了解现状。

GitLab 已从 `workflow::*` 范围标签迁移到 Issue 状态。原文的状态对应关系如下：

| 旧工作流标签 | 当前状态 |
| --- | --- |
| `workflow::validation backlog` | `Validation backlog` |
| `workflow::problem validation` | `Problem validation` |
| `workflow::ready for design` | `Ready for design` |
| `workflow::design` | `Design` |
| `workflow::solution validation` | `Solution validation` |
| `workflow::planning breakdown` | `Planning breakdown` |
| `workflow::scheduling` | 已移除 |

## 3. 验证轨（Validation track）

客户问题尚不清楚时，产品经理（PM）与用户体验团队（UX）在进入构建轨前共同验证新机会。验证轨独立于持续推进的构建轨；GitLab 希望验证工作至少提前两个月，为构建轨准备已充分验证的机会。缺陷、已充分理解的迭代改进、轻微设计修正和技术债可能无需验证周期。验证深度取决于对问题及方案已有的理解。

**何时进行：** 对问题是否足够重要，或方案是否易懂、易用尚无充分信心时。

**参与者：** 产品经理、产品设计师、UX 研究员、产品设计经理、工程经理。

**目标与总体产出：** 理解用户问题；确定业务目标及成功指标；提出假设并开展研究、实验或用户测试；定义 MVC（Minimum Viable Change）与后续迭代；用定性和定量分析降低价值、可用性、可行性及商业可行性风险。最终应有信心认为方案会积极影响一个或多个产品 KPI；如无对应 KPI，应明确例外理由。对 MVC 或成功标准仍无信心时，继续验证。

### 3.1 Validation backlog：验证待办池

**状态：** `Validation backlog`。产品经理维护并排序团队的 Issue 和 Epic 待办，使机会与产品方向及策略一致；待办也是利益相关方了解下一步工作的主要来源。

| 产出 | 原文列举的活动 |
| --- | --- |
| Issue 和 Epic 保持最新，作为产品变更的事实来源 | 根据反馈来源创建 Issue；新功能可考虑问题验证模板；将讨论、外部信息和相关链接更新到描述中；维护元数据并回应利益相关方。 |
| 待办按优先级排序 | 定期检查看板排序和里程碑；与产品方向、成熟度对齐；可考虑 RICE 及跨职能优先级讨论。 |

### 3.2 Problem validation：问题验证

**状态：** `Problem validation`。从已验证的问题开始。已被记录且充分理解的问题，可以把现有客户反馈、研究、数据与访谈链接到 Issue 或 Epic 后较快通过；复杂或模糊的问题需要进一步与用户验证。

| 产出 | 原文列举的活动 |
| --- | --- |
| 充分理解问题：谁受影响、何时及为何发生、与业务需求和产品策略如何关联 | 使用问题验证模板创建 Issue；可完成 Opportunity Canvas 并评审；必要时与 UX 研究员开展研究；与用户验证并记录发现。 |
| 更新 Issue/Epic 描述，清楚表达客户问题 | 持续更新理解；可使用 JTBD 记录用户想完成的任务；持续客户访谈；向相关方沟通结果，并确认设计师已理解问题。 |
| 启动 Dogfooding（内部试用） | 在验证阶段记录内部客户反馈，用于当前或后续迭代。 |

### 3.3 Ready for design：待设计

**状态：** `Ready for design`。问题验证完成且需要设计工作的 Issue 进入设计队列。

| 产出 | 原文列举的活动 |
| --- | --- |
| 可供设计的问题陈述 | Issue 包含清晰且已验证的问题；研究发现、用户画像、JTBD 或用户旅程可供查看；业务目标与成功指标明确。 |
| 设计团队知晓工作且有容量 | 与产品设计师沟通背景、研究及预计时间，必要时安排交接或启动讨论。 |
| 已记录技术约束 | 写明已知限制、工程侧可行性意见及 Web、移动端、API 等平台因素。 |

### 3.4 Design：设计

**状态：** `Design`。团队可以先发散不同解法再收敛；若问题验证已经明确指向现有方案的渐进式修改，可以省略这一发散过程。方案需兼顾用户与业务目标、技术可行性及法律合规；DRI 评估原文所指的法律风险清单是否需要处理。

| 产出 | 原文列举的活动 |
| --- | --- |
| 找到并记录拟议方案 | 团队探索多种方法并收敛到少量候选项；可使用用户流程、低保真设计、设计评审、内部访谈等；在 Issue/Epic 描述中链接设计文件与研究结果。 |
| 团队对方案形成共同理解 | 与团队及领导层评审，让参与者提出疑问、顾虑和替代方案。 |
| 对技术可行性有信心 | 尽早与工程团队讨论实施影响；复杂方案可安排技术探索（spike）。 |
| Issue/Epic 描述保持最新 | 更新方案与相关实验定义；适用时继续 Dogfooding。 |

### 3.5 Solution validation：方案验证

**状态：** `Solution validation`。对满足业务需求且技术可行的候选方案，确认其是否满足用户需要和预期。信心可以来自设计阶段，也可通过用户访谈、可用性测试或进一步研究补充。此时还需考虑并记录非功能需求，例如应用限制、数据存储和默认值。

| 产出 | 原文列举的活动 |
| --- | --- |
| 对拟议方案有较高信心，能完成问题陈述中的用户任务 | 收集相关方反馈，并按方案验证方法开展验证。 |
| 方案验证所得被记录且为团队理解 | 记录研究发现；如使用 Opportunity Canvas，则更新之；在 Issue/Epic 描述中写入或链接结果。 |

## 4. 构建轨（Build track）

构建轨负责规划并交付 MVC，也包括缺陷、安全漏洞、体验及性能改进。交付后通过使用与性能数据及客户反馈指导下一次迭代。

**参与者：** 产品经理、产品设计师、开发团队。

**目标与总体产出：** 适当面向部分或全部客户发布；评估用户体验、功能、技术性能和客户影响；收集数据与成功指标比较；持续迭代。目标是交付能改善产品或工程 KPI 的 MVC。若没有达到，应考虑放弃当前方案并重新开始验证。

### 4.1 Plan：计划

| 状态/标签 | 原文用法 |
| --- | --- |
| `Planning breakdown` | DRI 在当月 4 日或之前设置，表示有意将 Issue 排入下个里程碑。 |
| `Ready for development` | Issue 已拆分并确定开发优先级，具有 `type::` 工作类型标签与里程碑。 |
| `Deliverable` | DRI 将 Issue 接纳进当前里程碑时添加。 |

缺陷、技术债等非功能工作可以从计划阶段进入。DRI 标记拟优先处理的 Issue，工程师进一步拆分并赋予工作量权重；团队将功能方案收敛成一个里程碑可交付的 MVC。进入 `Planning breakdown` 不保证下个里程碑一定实施，还需按容量和紧迫性取舍。计划期间应让应用安全工程师了解日程，以便安排动态测试。

| 产出 | 原文列举的活动 |
| --- | --- |
| 范围恰当的 MVC Issue | 拆成单个里程碑可交付项；为推迟工作建后续 Issue；必要时建 Epic、实施 Issue、POC 或工程调查；与贡献者评审范围与迭代计划。 |
| 已确定优先级的里程碑 | DRI 设置 `Ready for development`、`type::` 与里程碑；用 `Deliverable` 表示接纳，并创建计划 Issue。 |
| 明确的计划 | DRI 了解团队容量并进行协调规划。 |
| 实施 Issue 进一步细化（可选） | 团队可将 `Refinement` 作为独立的迭代式细化步骤。 |

### 4.2 Develop & Test：开发与测试

| 状态 | 原文用法 |
| --- | --- |
| `In dev` | 包括文档在内的工作已开始，通常已有相关 MR。 |
| `In review` | 关闭该 Issue 所需的全部 MR 已进入评审。 |
| `Blocked` | 存在技术问题、待产品或设计回答的问题、跨团队依赖等阻塞。 |
| `Verification` | MR 合并后，需要在 Staging 或 Production 验证。 |
| `Awaiting security release` | 安全 Issue 已通过验证，等待下次月度安全发布。 |

DRI 负责里程碑整体优先级；工程团队按工程工作流实施并负责完成定义。工程师按优先级领取或被分配 Issue，更新状态。应用安全工程师在评审阶段帮助验证风险缓解措施。工程师与技术写作者共同编写、评审文档。代码合并后，负责的工程师在 Staging 或 Production 手工验证。工程侧认定超出范围或未完成的工作，回到计划阶段细化和重新排期。

| 产出 | 原文列举的活动 |
| --- | --- |
| 功能已构建 | 检查完成定义；定期向利益相关方提供状态信息，优先异步更新；工程师遵循工程流程。 |
| 功能已测试 | 工程师测试其实现；DRI 在 Issue 指定测试要求并跟进覆盖率；技术写作者审阅文档；应用安全工程师验证风险缓解措施。 |

### 4.3 Launch：上线

**状态：** 原文列出 Issue 为 `Closed`；变更在生产环境可用并完成必要验证后设置 `Complete`。DRI 随后按适用情况协调发布说明和 Dogfooding。

| 产出 | 原文列举的活动 |
| --- | --- |
| GitLab.com 托管客户可以使用功能 | 代码部署到生产环境；如有功能开关则启用。 |
| 自管理客户可以使用功能 | 代码按截止时间纳入下一次计划发布。 |
| 利益相关方知道功能可用 | 完成生产验证后设置 `Complete`；产品经理可通知相关方。 |
| 客户获知重大变更 | 适用时由产品经理编写并合并发布说明条目。 |
| 继续 Dogfooding | 准备好内部使用时进行内部推广。 |
| 实验结果有后续跟踪 | 创建后续 Issue，记录实验结果和下一步。 |

### 4.4 Improve：改进

上线后，DRI 关注产品使用数据和指标采集，并征求客户反馈，直到成功指标达到或超过目标、产品体验达到足够水平。此阶段原文不指定状态或标签。

| 产出 | 原文列举的活动 |
| --- | --- |
| 理解定性反馈 | 可建专门反馈 Issue；继续 Dogfooding；阅读用户反馈；联系客户并进行访谈或可用性调查。 |
| 衡量定量影响 | 更新并查看仪表板与使用指标，观察变更对核心指标的影响。 |
| 对体验建立基准 | 可使用 UX Scorecard 评估可用性并记录改进机会。 |
| 根据学习结果采取行动 | 创建或更新后续迭代 Issue；记录并分享发现；必要时调整市场推广和文档；在实验后续 Issue 中写明结果与下一步。 |

## 5. 发布阶段指南

原文建议：除非有充分理由，功能从一开始就应以普遍可用（GA）方式发布；避免会损害或泄露生产数据、破坏其他功能稳定性，或给高月活区域带来明显摩擦的变更。

### 5.1 实验功能

实验用于验证假设，最常用于问题验证；不是默认的功能范围、成熟度或质量等级。问题已通过其他方式验证时可跳过。实验不用于获取损坏功能的反馈或变相提前发布，也不保证一定进入 GA。原文要求实验有可检验假设、预先定义的成功/失败标准、尽可能短的运行期、结果与下一步记录；理想情况下持续 1–2 个里程碑。参与者应能方便地选择加入，有体现实验状态的文档和 UI 及反馈 Issue；原文规定实验功能不写入发布说明。满足审核标准的实验需启动 PREP 评估并填写就绪模板相应部分。

### 5.2 Beta 功能

Beta 主要用于方案验证：问题已验证、方案有一定把握，但仍需客户进一步验证。Beta 可跳过，不能用来收集损坏功能的反馈或变相提前发布；原则上应有较高概率进入 GA。原文建议在开始前与 UX、工程团队讨论退出标准，考虑招募客户及外部贡献者，并在文档、UI、反馈 Issue 中明确 Beta 状态；发布说明和 UI 推广按需使用。符合审核标准者需按 PREP 流程填写就绪模板至 Beta 部分。

### 5.3 公开可用、GA 与提前访问

公开可用功能需满足原文所指的审核标准、PREP 流程及就绪模板的 GA 部分。GA 功能还须在 GitLab.com、GitLab Self-Managed、GitLab Dedicated 和 GitLab Dedicated for Government 平台可用。原文主张有价值时允许外部用户主动选择体验实验功能，而非长期只在内部测试。

实验、Beta 和有限可用阶段都应设退出标准，尽量缩短 GA 前周期。原文列出的判断维度为：目标时间、足够数量的客户反馈、进入 GA 前必须完成的有限功能、系统性能指标，以及是否达到成功标准。若早期反馈表明另一方向更有价值，可以转向而非强行进入 GA。原网页中部分遥测、UX、工程及公开可用细则仍标为 `TODO`，此处不将这些未完成条目写成已生效要求。
