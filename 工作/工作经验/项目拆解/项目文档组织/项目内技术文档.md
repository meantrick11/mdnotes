# 项目内文档管理笔记
**大部分公司为了项目赶进度，都没有非常细分的文档管理，很容易野蛮长，让新人/用户不知从何看起（不过也是常情）**
## 一、核心一句话

**日常直接在原文档上改，版本完全跟随代码 Tag，靠 Git 追溯；只有对外交付时才存只读快照。不写独立版本号，不搞复杂基线。**

---

## 二、定位与区别

项目内文档和上层管控文档是两套体系，不能混用。

| 维度 | 上层管控文档 | 项目内文档（研发伴随文档） |
|---|---|---|
| 读者 | 业务、产品、高层、跨团队 | 开发、测试、运维（本团队） |
| 内容 | 业务目标、需求基线、架构决策 | 开发指南、API说明、部署手册、Bug记录 |
| 生命周期 | 长期，跨版本复用 | 跟随代码，代码重构文档就废弃 |
| 版本控制 | 独立版本号，存 `releases/` 快照 | 跟随代码 Tag，无独立基线 |
| 变更审批 | 严格 CR（变更申请） | 开发顺手改，Code Review 即可 |

## 三、标准目录架构

一级目录按**文档用途**分，二级目录按**业务模块**分。

```text
project-docs/
├── README.md                     # 项目介绍 + 文档导航
├── 00-overview/                  # 入门与概述
├── 01-architecture/              # 架构与设计
├── 02-api/                       # 接口与集成
├── 03-modules/                   # 模块与业务专题
├── 04-ops/                       # 部署与运维
├── 05-records/                   # 记录、踩坑、Bug、方案
├── 06-releases/                  # 版本发布记录
└── 07-assets/                    # 附件、工具、图片
```

---

## 四、各模块内容说明

### 1. `00-overview/` — 入门与概述
- **给谁看**：新入职开发、交接人员。
- **包含什么**：
  - 项目概述、业务背景
  - 技术栈说明
  - 开发环境搭建
  - 代码规范、分支规范
  - 本地启动步骤

### 2. `01-architecture/` — 架构与设计
- **给谁看**：开发、架构师。
- **包含什么**：
  - 系统架构图、模块划分
  - 核心模块详解
  - 数据库设计、时序图
  - 技术方案（technical_design）

### 3. `02-api/` — 接口与集成
- **给谁看**：前后端联调、外部对接。
- **包含什么**：
  - API 文档（或自动生成的 OpenAPI）
  - Postman 集合、环境变量
  - 第三方系统对接说明

### 4. `03-modules/` — 模块与业务专题
- **给谁看**：各业务模块负责人。
- **包含什么**：
  - 按业务模块划分的子目录，如 `xiaofei-agent/`、`security/`、`job/`。
  - 每个模块内的详细设计、核心逻辑、注意事项。

### 5. `04-ops/` — 部署与运维
- **给谁看**：运维、DevOps、排障人员。
- **包含什么**：
  - 部署指南、环境说明
  - Job 任务调度说明
  - 监控告警、回滚方案

### 6. `05-records/` — 记录、踩坑、Bug、方案
- **给谁看**：全体研发，避免重复踩坑。
- **包含什么**：
  - Bug 记录、修复过程
  - 场景验证记录
  - 性能优化记录
  - 专题攻关记录

### 7. `06-releases/` — 版本发布记录
- **给谁看**：测试、运维、项目经理。
- **包含什么**：
  - 每个版本的发布说明（Release Notes）
  - 版本变更点、修复的 Bug
  - 升级注意事项

### 8. `07-assets/` — 附件、工具、图片
- **给谁看**：文档编写者。
- **包含什么**：
  - 架构图源文件、流程图源文件
  - 图片、PDF、Excel 等附件
  - 数据库脚本、初始化数据

## 五、针对现状的改造示例

以截图中常见的散乱目录为例，建议按以下方式重构：

```text
doc/

├── 00-overview/
│   ├── 01-项目概述.md
│   ├── 03-技术栈.md
│   └── 07-开发指南.md
├── 01-architecture/
│   ├── 02-系统架构.md
│   ├── 04-模块说明.md
│   ├── 05-核心模块详解.md
│   ├── Liquibase数据库....md
│   └── technical_design/              # 原 technical_design 目录
├── 02-api/
│   ├── 08-API文档.md
│   └── postman/                       # 原 postman 目录
├── 03-modules/
│   ├── xiaofei-agent/                 # 原 xiaofei-agent 目录
│   ├── security/
│   │   ├── preauthorize注解....md
│   │   └── security-permissi....md
│   ├── Fongwell-Agent....md
│   └── Fongwell-Java服....md
├── 04-ops/
│   ├── 06-部署指南.md
│   └── 09-Job任务调度....md
├── 05-records/
│   ├── 全链路验证Bug记录.md
│   ├── 智能问数30场景修....md
│   └── 智能问数场景覆盖....md
├── 06-releases/                       # 原 releases 目录
└── 07-assets/                         # 图片、脚本、附件
```

**关键调整**：
1. **根目录只留 `README.md`**：所有散落的 `.md` 全部归入对应文件夹。
2. **`platform/` 拆掉**：里面的内容按类型分到 `00-overview`、`01-architecture`、`02-api`、`04-ops`。
3. **业务专题统一进 `03-modules/`**：比如 `xiaofei-agent`、`security`、`Fongwell` 都按模块建子目录。
4. **记录类统一进 `05-records/`**：Bug、场景验证、优化记录都放这里。
5. **`releases/` 保留**：作为版本发布说明，但不放日常文档。

## 六、版本控制怎么走？

项目内文档**不写独立版本号，不存快照**，完全跟随代码：

1. **直接改原文档**：`git commit -m "docs: 更新API文档，新增智能问数接口"`。
2. **版本跟随代码 Tag**：代码发 `v0.5.0`，整个 `doc/` 就是 `v0.5.0` 的状态。
3. **变更记录靠 Git**：`git log -- doc/02-api/08-API文档.md` 就能看到历史。
4. **发布时写 Release Notes**：在 `06-releases/v0.5.0.md` 里写清楚本次发布了什么、改了什么。
5. **对外交付才存快照**：如果需要给客户交付，把 `doc/` 整体复制一份到 `releases/v0.5.0/`，导出 PDF，作为只读快照。

Git 操作示例：

```bash
# 1. 日常修改文档
git checkout -b feature/update-api-doc
# 修改 doc/02-api/08-API文档.md
git add doc/02-api/08-API文档.md
git commit -m "docs(api): 新增智能问数接口说明"
# 提交 PR，合并到 main

# 2. 发布新版本
git tag -a v0.5.0 -m "发布 v0.5.0：智能问数场景覆盖"
git push origin v0.5.0

# 3. 如果需要归档本次发布的文档快照（可选）
# 在 releases/ 下新建 v0.5.0 文件夹，复制当前 doc 下的关键文档过去
# 提交并合并，作为历史存档
```

## 七、复习速记

- **一套目录**：按用途分一级，按模块分二级。
- **根目录干净**：只留 `README.md` 做导航。
- **不写版本号**：文档头不写 `version: 1.0.0`，跟随代码。
- **直接改原文档**：Git 留历史，不复制文件。
- **版本靠 Tag**：代码发版，文档自动跟随。
- **发布写 Notes**：`06-releases/` 记录每个版本变更。
- **交付存快照**：对外交付才在 `releases/` 复制只读快照。
- **记录归 `05-records/`**：Bug、踩坑、优化统一归档。
