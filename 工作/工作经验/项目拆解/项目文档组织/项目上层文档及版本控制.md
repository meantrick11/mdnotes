# 项目上层文档管理

## 一、核心一句话

**日常只维护一个 `docs/` 当前有效文档库；每个文档独立版本；直接改原文档 + Git 管历史 + 文档内变更记录；只有发布/基线时才在 `releases/` 存只读快照。**

---

## 二、先分清三层版本

| 层次 | 控制对象 | 例子 | 作用 |
|---|---|---|---|
| 文档版本 | 单个文档 | `REQ-001 v1.3.0` | 记录这个文档改了什么 |
| 基线版本 | 一组文档快照 | `需求基线 v1.0` | 表示这套文档被评审冻结过 |
| 发布版本 | 对外交付版本 | `v2.0.0` | 对客户、运维、其他团队说的版本 |

一个发布版本可以包含不同版本的文档：

```text
发布版本 v2.0.0
├── BIZ-001 业务蓝图 v1.2
├── REQ-001 订单创建 v1.3
├── ARC-001 架构总览 v2.1
├── API-ORDER-001 创建订单 v1.4
└── TC-REQ-001-001 测试用例 v1.1
```

## 三、精简原则

1. **一个文档一个稳定 ID，文件名不带版本**
   - 正确：`REQ-001-订单创建.md`
   - 错误：`REQ-001-订单创建-v2.md`

2. **当前只保留一份有效文档**
   - 日常编辑永远在 `docs/`。
   - 旧版本靠 Git 历史找回，不复制文件。

3. **每个文档独立版本**
   - 业务、需求、架构、接口各自递增，不强行统一。

4. **Git 管历史，tag 管里程碑**
   - 普通修订：commit。
   - 重要版本：打 tag。

5. **只有发布/基线/对外交付才存只读快照**
   - 放 `releases/`。
   - 已发布快照只读，不回头改。

6. **变更必须做影响分析**
   - 上游业务、下游架构、模块、接口、数据、测试、追溯矩阵都要检查。

7. **必须维护追溯矩阵**
   - 业务 → 需求 → 架构 → 模块 → 接口 → 测试 → 发布。

8. **状态与版本号有规则**
   - 状态：`draft -> review -> approved -> frozen -> deprecated`
   - 版本：修订 `1.0.0 -> 1.0.1`；兼容增强 `1.0.1 -> 1.1.0`；破坏性变更 `1.1.0 -> 2.0.0`。

## 六、变更怎么做？一个小案例

场景：`REQ-001 订单创建` 从 `v1.2.0` 改成 `v1.2.1`，只是澄清“库存不足”错误码。

1. 提 CR：`CR-2026-002`。
2. 拉分支：`change/REQ-001-inventory-error-code`。
3. 直接改当前文档：`docs/02-requirements/REQ-001-订单创建.md`。
4. 更新文档头：

```yaml
version: 1.2.1
status: review
updated: 2026-10-01
```

5. 变更记录加一行。
6. 影响分析：
   - 接口 `API-ORDER-001` 是否同步错误码？
   - 测试用例 `TC-REQ-001-001` 是否加断言？
   - 追溯矩阵是否更新？
7. 提交 PR，评审通过后合并。
8. 判断是否形成新基线：
   - 未发布：不形成新发布版本。
   - 已发布：进入 `v2.0.1`，发布时在 `releases/v2.0.1/` 存新快照。

Git 操作：

```bash
git checkout -b change/REQ-001-inventory-error-code
# 修改文档
git add docs/02-requirements/REQ-001-订单创建.md
git commit -m "docs(REQ-001): v1.2.1 澄清库存不足错误码"
git tag -a doc-REQ-001-v1.2.1 -m "REQ-001 v1.2.1"
```

## 九、复习速记

- **一个当前库**：`docs/`。
- **一个只读归档**：`releases/`。
- **每个文档独立版本**，文件名不带版本。
- **直接改原文档**，Git 留历史，文档末尾写变更记录。
- **重大变更单独建 CR/ADR**。
- **发布时记录基线**：发布版本对应哪些文档的哪个版本。
- **已发布快照只读**，新变更进新版本。
- **追溯矩阵串起全链路**：业务 → 需求 → 架构 → 模块 → 接口 → 测试 → 发布。
