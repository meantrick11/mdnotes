# 多租户 SaaS

## 基本形态

SaaS（软件即服务）通常由服务提供方部署和持续运营，客户通过网页、App 或 API 使用。多租户表示多个客户组织共用某些运行资源，同时各自拥有独立的业务数据、配置、账号和权限边界。

~~~text
企业 A 用户 ─┐
企业 B 用户 ─┼→ 厂商运营的应用 → 租户识别与权限 → 数据存储
企业 C 用户 ─┘
~~~

“共用”不意味着所有数据存进同一张表。常见隔离方式包括共享数据库并用租户标识区分、同一数据库内分 Schema、每租户独立数据库，甚至重要客户独立部署。选哪一种取决于隔离要求、成本、运维能力和法规约束。

## 谁是租户，谁是用户

租户通常是购买或使用服务的企业；用户是企业内的个人。一次请求至少要确定两个问题：**它属于哪个租户，以及该用户在这个租户内能做什么**。一个人加入多个企业时，同一个登录身份可能拥有多个租户角色，操作前需明确当前租户上下文。

“单租户”也不等于单用户：一家公司独占一套部署，内部仍可能有许多员工、角色和部门。

## 一次请求的边界

以查询客户名单为例：请求经过登录验证；系统确认当前租户；检查该用户的数据范围；查询只属于该租户、且在其权限内的记录；记录必要的审计信息。只在页面上隐藏其他租户数据远远不够，后端查询、缓存、导出、异步任务和日志都需保持隔离。

## 多租户带来的设计问题

- **数据隔离**：主表、关联表、搜索索引、对象存储路径和缓存键如何带上租户边界？
- **配置隔离**：各企业是否能有不同菜单、流程、字段、品牌和集成配置？
- **资源公平**：某个租户的大任务不能占满所有共享资源；可能需要配额或限流。
- **升级节奏**：统一部署便于集中升级，却要兼顾不同租户的配置与旧接口。
- **运营边界**：平台管理员和企业管理员的权限不同；跨租户支持操作需要审计。
- **备份与删除**：能否只恢复或导出单个租户的数据？客户退出时如何处理数据？

## 优势和代价

厂商集中维护，客户通常无需自行安装；统一发布和监控也更容易。但隔离、配置、计费、资源调度、故障影响面都更复杂。某个公共服务故障可能影响多个客户，因此需要明确服务等级和应急处理。

## 何时适合

客户能接受厂商托管、网络可达、需求相对标准化、希望快速开通和持续更新时，多租户 SaaS 通常合适。若客户要求数据和系统必须留在自己的环境，可能转向企业本地部署或混合部署。

## 常见误解

- 多租户不是“有很多用户”，而是**有多个客户组织边界**。
- SaaS 是交付和运营模式，不要求必须是微服务。
- 企业登录后只能看本企业的数据，既是产品需求，也是每条数据路径都要落实的技术约束。
- 统一部署不意味着每个租户的所有配置完全一样。

## 如何拆解 SaaS 需求

除了功能本身，逐项问：租户能否配置？不同租户的数据是否隔离？平台管理员和企业管理员各能做什么？上线是否同时影响所有租户？是否涉及配额、计费、迁移和导出？
