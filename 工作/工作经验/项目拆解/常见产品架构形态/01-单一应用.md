# 单一应用

## 典型样子

一套面向有限用户群的功能，通过一个主要入口访问，由一个后端应用承接大多数业务逻辑。入门项目常见形式是“网页前端 + 后端 API + 一个数据库”；也可以由后端直接渲染页面。

~~~text
用户浏览器 → 网页前端 → 后端应用 → 数据库
~~~

这不严格等同于“单体架构”：前后端即便分开部署，业务后端仍可以是单体；反过来，只有一个前端也可能调用多个服务。

## 谁在用、谁在维护

常见于内部工具、早期产品、小团队管理系统。使用者可能只有一个主要角色，也可能有管理员和普通员工。部署可在本地电脑、企业服务器或云主机上。用户少不等于没有认证：只要存在不同权限或敏感数据，就仍需账号、访问控制和操作记录。

## 一个请求怎样走

以“查看订单”为例：浏览器发送请求；后端核对登录态和权限；读取订单数据；转换为页面需要的结果；前端展示。新增订单还涉及参数校验、写库、错误处理和审计。规模小时，这些能力可以在同一后端应用的不同模块中完成。

## 为什么这种方式有效

- 产品范围较小，调用链短，定位问题相对直接。
- 本地启动、联调、部署和回滚比较简单。
- 模块间调用通常在同一进程内，避免早期引入大量远程调用与部署成本。
- 团队可以先验证业务需求，再决定是否拆分。

“简单”是组织方式上的优势，不代表可以忽略代码边界。即使只有一个后端，也应把认证、业务逻辑、数据访问分清楚，避免所有功能堆进一个控制器。

## 何时开始不够用

当用户角色和工作流明显分化，可能需要另一个入口，例如运营后台；当多个团队高频修改不同业务、部署节奏冲突，可能需要拆分服务；当客户要求在各自环境独立部署，则需要考虑配置、升级和数据隔离。性能问题本身不必然要求微服务，先确认瓶颈在哪里。

## 常见误解

- **“只有一个后端，就不能做大业务”**：业务复杂度与进程数不是一回事。
- **“加了管理员页面，就变成微服务”**：新增页面是入口变化，服务是否拆分是另一项决策。
- **“本地运行就不用登录”**：部署位置与用户权限无关。
- **“一个仓库就等于一个产品”**：仓库和产品不是一对一关系。

## 拆解此类项目时怎么读

先跑通一条用户操作，记录页面、API、业务方法、数据表；再看异常和权限。不要从框架配置开始通读。需求拆解可按“现有流程 → 目标流程 → 页面变化 → 接口和数据变化 → 验收场景”组织。
