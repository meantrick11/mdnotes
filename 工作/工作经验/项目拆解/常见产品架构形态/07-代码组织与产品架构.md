# 代码组织与产品架构

## 五个常被混用的词

| 词 | 回答的问题 | 示例 |
| --- | --- | --- |
| 产品 | 提供给谁，解决什么问题？ | 企业本地数据资产管理产品 |
| 入口／端 | 谁在哪里使用，或系统承担什么职责？ | 用户网页、运营后台、企业侧连接器端 |
| 服务／模块 | 运行时和代码内部怎样分工？ | 认证服务、元数据模块、分类分级模块 |
| 仓库 | 源代码放在哪里？ | 前端仓库、后端仓库、模型服务仓库 |
| 分支 | 某一时间的代码线及版本如何演进？ | 开发、测试、发布、功能分支 |

这些词没有固定的一对一关系。一个产品可有多个入口和仓库；一个仓库可有多个模块，甚至衍生出多个产品方向；一个模块也可能被多个产品复用。

## 三种常见代码组织方式

### 一个仓库承载一个产品

小团队常见。前端、后端可以同仓，也可以分仓。优点是边界清晰；挑战是当共享组件增多时，可能出现重复实现或跨仓版本协调。

### 一个仓库承载多个服务或产品方向

共享代码容易同步修改，也方便统一构建；但仓库名可能沿用历史名称，旧模块和旧文档容易留存。需靠模块清单、构建配置、版本说明和清晰的代码所有权帮助识别当前产品。Git 分支可以承载不同版本，却不宜仅凭分支名推断每个功能是否真的存在。

### 多仓库共同组成一个产品

大型产品常见前端、后端、模型服务、部署配置分别存放。一个需求可能跨几个仓库；每个仓库还可能各有版本和分支。要明确接口契约和发布兼容性，不能只在一个仓库里找完整产品。

## 分支不是文件夹

Git 分支是同一仓库不同时间线上的代码状态。切换分支后看到的模块、配置和文档可能变化；历史提交、合并记录又会保留不同产品方向的痕迹。因此“仓库里搜索到了某个类”不足以证明当前目标版本启用了这个能力。应同时核对**当前分支、构建模块、配置、调用入口和实际部署**。

当前工作区中的飞数相关后端仓库可作为例子：仓库名保留旧体系的名称，能见到飞数、数宝和小飞相关分支；数宝分支内仍有共享模块和历史文档，而前端位于其他仓库。这里描述的是观察到的组织方式，不意味着所有飞数代码都在同一后端仓库。

## 为什么文档会相互矛盾

不同文档可能写于不同产品、版本或部署环境；根 README 可能更新滞后；旧模块删除后，说明文字和注释仍在。解决方法不是选一份“最长的文档”全盘相信，而是给每个结论记录来源和适用范围：**产品、版本、分支、日期、环境**。产品需求说明目标；当前代码和配置说明现状；实际页面与部署验证运行效果。

## 接新需求时的定位步骤

1. 写下产品名、需求版本和目标环境。
2. 确认当前仓库、分支以及是否还有前端或模型服务仓库。
3. 找到用户操作入口和一条可运行的业务流程。
4. 沿页面 → API → 服务 → 数据存储逐段核对。
5. 做“已有／需修改／需新增／待确认”对照表。
6. 标注跨仓库、跨端依赖，再估计工作量和风险。

这样读一个大项目，范围由需求牵引，而不是按目录从头读。

## 常见判断错误

- 看到“Agent”就认为是 AI Agent，忽略它可能只是企业侧连接器的旧称。
- 看到多个前端就认为有多个独立产品。
- 看到微服务就认为每个服务对应一个仓库。
- 看到旧 README 写着某项技术，就认为当前分支仍使用它。
- 看到本地部署就认为没有登录、权限和审计。
- 看到门户中的产品就认为原始数据一定全部上传到门户。

每次遇到这些推断，回到产品、入口、部署、代码四个维度重新核对。
