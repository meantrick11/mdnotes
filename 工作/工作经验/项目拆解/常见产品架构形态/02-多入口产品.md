# 多入口产品

## 为什么会出现多个前端

当同一产品服务不同角色，各角色的任务、权限和使用设备差异很大，一个页面体系往往不合适。于是出现用户 App、用户网页、商家后台、创作者工具、客服后台、运营后台、开放 API 等多个入口。

以短视频产品为**概念示例**：普通用户浏览和发布内容，创作者管理作品，商家经营商品，运营人员处理审核与申诉。这里说明的是典型角色拆分，并非某家公司的真实内部架构图。

~~~text
手机 App ─────┐
用户网页 ─────┤
创作者后台 ───┼→ 网关／API → 账号、内容、审核、交易等业务能力
运营后台 ─────┤
外部系统 API ──┘
~~~

## 多入口与多后端是两回事

多个前端可以共用一个后端，也可以调用多项服务。后端拆成几个服务，取决于业务边界、团队规模、性能和部署要求。不能看到五个网页就推断有五套完整系统。

共同能力可以位于统一身份、权限和业务 API 中，同时对不同角色提供合适的接口。各入口是否共用账号体系要看产品设计；即便共用账号，也不代表共用全部权限。

## 一条流程怎样跨入口

以“商品上架”为例：商家后台提交商品；系统校验和保存；审核人员在运营后台审查；通过后消费者在用户端看到商品。三个入口使用同一业务对象，但各自能做的操作不同。只从消费者页面看需求，会漏掉上架和审核。

短视频内容发布也类似：创作者提交、系统处理、审核、用户浏览、运营处理举报。不同入口对应同一业务生命周期的不同阶段。

## 什么时候适合多入口

- 使用角色的目标和权限显著不同。
- 设备不同：移动端强调随时使用，后台强调批量处理。
- 外部合作方需要程序化调用，因此增加开放 API。
- 运营、审计、客服任务不适合出现在普通用户界面。

不要为了“架构完整”提前拆许多前端。如果只有少量管理功能，同一网页内基于角色显示不同页面可能足够。

## 关键设计问题

1. **身份和权限**：同一人能否兼任多个角色？跨入口切换如何生效？
2. **数据一致性**：商家修改后，用户端多久可见？审核中的内容如何展示？
3. **业务状态**：草稿、待审核、已发布、下架等状态由谁改变？
4. **接口边界**：不同入口直接调用同一 API，还是需要各自的聚合接口？
5. **版本协调**：手机 App 升级慢，后端如何兼容旧版本？
6. **审计和风控**：敏感操作由谁发起、谁审批、怎样追溯？

## 如何阅读多入口项目

选一条完整流程，列出各角色在各入口的动作，再追到后端。不要一次看完所有前端仓库。需求拆解要写清哪些入口要改、哪些角色受影响、状态变化如何反映到其他入口。
