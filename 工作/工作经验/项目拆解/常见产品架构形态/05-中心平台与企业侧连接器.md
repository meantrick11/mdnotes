# 中心平台与企业侧连接器

## 这种形态解决什么问题

多个企业希望参与共同的服务或协作流程，但各自的数据系统、网络和权限掌握在自己手中。一个中心系统负责统一的目录、规则、任务协调或交易流程；企业侧部署连接器，靠近本地数据处理接入和执行。

~~~text
企业 A 数据 ← 企业 A 连接器端 ─┐
                              ├→ 中心平台 → 门户或其他使用入口
企业 B 数据 ← 企业 B 连接器端 ─┘
~~~

这是**概念模型**。箭头表示协作关系，不表示原始数据一定流入中心。每个产品都应另画具体的数据流和信任边界。

## 三类角色怎样分工

**企业侧连接器端**认识本企业的数据源和本地环境，处理接入、采集、授权范围内的任务执行，并与中心交换必要的信息。它不是 LLM Agent；“连接器”强调系统边界与本地执行位置。

**中心平台**可能负责接入方管理、任务协调、统一规则、产品目录或许可管理。它能协调并不意味着拥有所有企业数据，也不应简单叫“监管平台”；只有产品明确承担监管业务时才能这样称呼。

**门户端**如果存在，面向人提供数据产品展示、申请、发布或交易入口。门户可能通过平台服务完成业务流程，不一定直接访问企业连接器。其他企业也不一定能进入某家企业内部系统。

## 从企业加入到一次协作

以一个假设流程说明各边界：企业部署连接器，配置数据源与访问权限；连接器注册到中心；企业在其授权范围内发布某种数据产品的描述信息；使用者从门户查看并提出申请；平台协调审批或任务；企业侧按授权执行；结果按约定方式交付或展示。

这个流程**不代表任何具体产品的事实**。需逐项核实：发布的究竟是元数据、产品描述、接口、数据副本还是计算结果；数据是否出域；审批由谁负责；任务失败如何补偿。

## 这种形态难在哪里

1. **身份与信任**：平台怎样确认请求来自可信连接器？连接器怎样确认平台指令有效？
2. **权限分层**：平台的授权、企业内部权限、数据源原有权限如何同时生效？
3. **网络与断连**：企业可能只允许连接器向外发起连接；断网或中心不可用时哪些业务能继续？
4. **数据边界**：目录、样本、明文数据、计算结果分别是否可离开企业环境？
5. **版本兼容**：中心更新快、企业侧更新慢，协议如何兼容不同连接器版本？
6. **审计**：申请、批准、执行、交付各发生在哪一端，日志怎样串起来？
7. **故障定位**：中心、网络、连接器、数据源任何一环都可能失败。

## 飞数与数宝怎么放进这个模型

飞数原体系可帮助理解“平台端 + 企业侧连接器端 + 门户端”。数宝则从连接器端的代码和业务能力出发，把客户自身数据治理需要的能力本地化，减少对中心平台和门户的依赖。因此，**原连接器和数宝都能部署在企业侧**；主要区别是所服务的产品流程与对外部平台的依赖程度。

以上只是产品关系的高层理解。具体飞数版本支持哪些流通方式、数据怎样传输，仍需根据该版本的需求与架构资料确认。

## 如何阅读这类项目

先确定每个系统的运行位置和负责人，再选一条跨端流程。给每条箭头标注：谁发起、调用什么接口、传输什么、是否含敏感数据、失败后谁重试。若这些问题还没有答案，不能仅凭一张三端示意图写实现方案。
