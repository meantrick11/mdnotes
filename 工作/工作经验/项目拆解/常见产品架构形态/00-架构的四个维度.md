# 架构的四个维度

## 为什么“大项目有很多端”容易看晕

“端”没有单一含义。用户端和运营端按**使用者**区分；平台端和企业侧连接器端按**职责与部署位置**区分；前端和后端按**技术职责**区分。把这些词放在一张图里，却不注明它们回答的问题，就会误以为每个端都必须对应一个仓库、一台服务器或一个独立产品。

建议先画四张小图，而不是一张包含全部技术组件的大图。

## 维度一：产品与业务

先问：这套东西提供什么价值，面向哪些角色？同一家公司可能同时经营平台产品、面向客户的独立产品，以及嵌入其中的 AI 功能。产品名称回答“卖给谁、用来做什么”，不直接回答部署和代码位置。

例如，某产品负责企业自身数据治理，另一产品负责多组织之间的数据产品流通。它们可以复用代码，但业务边界不同。反过来，一个产品也可能使用多个后端仓库。

## 维度二：使用入口

入口是人或其他系统接触产品的方式：手机 App、用户网页、运营后台、开放 API、企业侧客户端等。多个入口常因角色和任务不同而产生，不一定意味着多套独立后端。

~~~text
普通用户网页 ─┐
商家后台 ────┼─→ API 层 → 业务能力 → 数据
运营后台 ────┘
~~~

判断入口时问：谁登录、看什么页面、发起什么操作？同一个角色也可能同时用网页和手机 App。

## 维度三：部署与数据位置

问：软件运行在厂商云上，还是客户自己的服务器上？是否一部分位于客户环境，一部分位于中心？原始数据、索引、元数据和计算结果分别放在哪里？

“本地部署”不等于“单机程序”，也不等于“无需登录”；“平台统一管理”不等于“平台持有所有原始数据”。应分别记录**运行位置、访问路径、数据驻留位置、运维责任**，四者不总相同。

## 维度四：技术与代码组织

问：后端是一个进程还是多个服务？前端和后端在一个仓库还是多个仓库？同一仓库如何按模块和分支组织？这些选择服务于产品，但不能直接当作产品定义。

- **单体／微服务**：运行时服务如何拆分。
- **单仓库／多仓库**：源代码如何存放。
- **主干／版本分支／功能分支**：代码如何演进。
- **单租户／多租户**：客户之间的数据和配置如何隔离。
- **本地／云端／混合**：运行位置和运维方式。

一个多入口产品仍可用单体后端；一个企业本地产品也可采用微服务；同一仓库中的不同分支也可能服务于不同产品方向。

## 阅读任意项目的最小顺序

1. 一句话定位：用户是谁，核心问题是什么？
2. 入口：用户在哪个页面或客户端完成关键任务？
3. 一条业务流程：从操作到结果，经过哪些系统边界？
4. 部署和数据：服务在哪里运行，原始数据与结果在哪里？
5. 代码坐标：当前产品、版本、仓库、分支、模块分别是什么？

完成前四步，再深入技术架构图。遇到陌生名词，先判断它属于哪个维度。

## 一个容易混淆的例子

“企业侧连接器端”和“AI Agent”都可能在旧资料中叫 Agent，但前者是部署在企业侧的系统角色，后者是使用模型完成任务的能力。先问它在图中承担什么职责，不要仅凭名称判定相同。

## 画图时的核对表

入门架构图只需标出角色、入口、系统边界、主要请求方向、数据驻留位置。实线箭头表示已确认的调用或数据流；猜测和待确认事项写在图旁。缓存、消息队列和注册中心等细节可放进第二张图。
