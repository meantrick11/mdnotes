# 项目链路拆解：从页面和接口清单走向业务闭环

拆解一个项目时，我会以**业务对象的流转**为主线。数据转换是其中的重要部分，但只看“输入变成什么输出”还不够：同一份数据可能已保存、正在处理、处理成功，却尚未被确认或发布。完整的链路还要看触发方式、状态变化和下游如何使用结果。

## 一、先确定起点和终点

先用一句话定义范围：**谁从哪里开始操作，最终要得到什么结果？**

例如“用户提交申请”不是终点；“申请完成审核，并能在结果页查询”才是可验证的终点。起终点不清楚，拆解时就容易只整理到某个接口返回成功为止。

## 二、找出贯穿链路的业务对象

不要一开始就按页面或服务列接口。先找出链路中不断被创建、加工和引用的对象，例如文件、订单、任务、执行记录、审核结果。

对每个对象问：

- 它从哪里产生？输入是用户填写、文件上传，还是上游系统返回？
- 它有哪些关键 ID？下游拿哪个 ID 查询或关联？
- 它经过了哪些转换？原始数据、中间结果、最终结果分别是什么？
- 它何时才算完成？保存成功、处理成功、人工确认是否是不同状态？

这样画出的链路通常比接口调用顺序更接近真实业务。

## 三、逐段核对五个连接点

对链路中的每一步，我固定记录：

| 要核对的点 | 关键问题 |
| --- | --- |
| 触发 | 谁在什么条件下发起？是用户点击、定时任务，还是上游事件？ |
| 输入 | 请求带了什么数据和 ID？这些值从哪一步来？ |
| 处理 | 前端调用哪个 API？后端哪个模块真正执行？ |
| 输出 | 返回或写入了什么？状态如何变化？ |
| 消费 | 下一步凭什么找到并使用这个结果？ |

如果“输出”与下一步的“输入”接不上，这里就是需要重点调查的断点。

## 四、把数据流和状态流放在一起看

接口返回成功，不一定代表业务完成。尤其在上传、异步任务、审批和人工确认场景中，要把状态拆开：

> 请求已受理 → 数据已保存 → 任务已触发 → 任务执行成功 → 结果已确认 → 结果可查询

每个状态都应有对应的记录或查询方式。还要看失败后前面的数据是否保留、能否重试，以及页面向用户展示的是哪一个状态。

## 五、最后再整理接口与需求

先弄清业务对象和状态，再按业务动作整理接口，而不是按 Controller 名称罗列。接口表至少写清**前端路径、调用方式与关键参数、后端入口、业务场景**。同时区分页面直接调用、服务内部调用，以及“代码里有接口但当前页面并未使用”。

拆解完成后，把发现转成可验收的问题：能否从起点走到终点？每一步能否用 ID 回溯？失败能否定位？最终结果在哪里查看？尚未实际验证的环节，明确标注为待验证，而不写成“已跑通”。

**我会用一句话检查自己的拆解是否完整：能否拿着上一步产生的数据和 ID，解释下一步为何能够发生，并一直解释到最终结果可见。**
