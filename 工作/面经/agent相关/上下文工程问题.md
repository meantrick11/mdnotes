# 面试官询问上下文管理相关的问题

## 考察本质/意识

1. 上下文窗口属于有限资源
2. 任务成功率：当前任务/长任务/后续任务
3. 压缩时的信息分级意识
4. 可恢复性
5. 工程落地：怎么出发、怎么存储、怎么评估、怎么减少幻觉和污染
6. 权衡意识


## 完整框架

### 1. 压缩前-预防增长

**重点是在上下文窗口增长阶段就不要有减少可能超上下文窗口的意识**

- 工具最大输出预防：如果工具返回的内容太大，那么需要考虑简短保留，只保留关键部分，比如20000token的内容，需要考虑**外部存储结果**，如果真的需要才加载到上下文窗口当中
- sub-agent：通过sub-agent的方式减少主agent的窗口增长，主agent窗口只保留关键信息/结论
- RAG：记忆太多/文档性输入需要按需检索，而不是全量文档塞入
- 记忆分层：当前的会话的短期记忆、长期记忆、外部记忆等等分层
- 任务状态外置：比如TODO、计划、实体表、约束表结构化保存（**同时还可以保留随时可调取，而不迷失**）

### 2. 压缩时-分级+压缩手段

#### 压缩分级

**最重要的就是保留什么信息，什么信息重要，有助于当前+以后的推理/任务完成**

P0(不能删): 系统提示词/安全/工具提示词，当前用户目标、约束、验收标准，当前任务状态，当前轮工具调用结果

p1（可摘要）： 最近对话、相关RAG片段、工具调用元数据，**可建立索引/重新调用工具获取的信息**等等

p2(可外置/丢弃)：历史工具输出、十分久远的对话、寒暄等几乎无作用的内容


#### 压缩手段

**确定上面的信息分级之后,需要确定如何压缩**

保留上述必要的信息之后，可以尝试对其他非必要(对当前/后续任务帮助不大的内容进行压缩)

滚动摘要：旧对话压成“目标、约束、决策、待办、未解决问题”。

结构化摘要：不是自由文本，而是 JSON/表格，保留实体、字段、关系。

工具结果处理：小结果保留，大结果外置，只留 tool_call_id、参数、摘要、存储 URI、时间戳、版本。

动态 token 预算：系统/当前任务固定预算，历史弹性，超限触发压缩。

按需恢复：需要时再检索原文或重新调用工具。

**注意:大多数压缩最好是可溯源压缩，也就是agent能够快速通过建立的索引获取到对应的信息，比如调用什么工具/什么参数可以快速获取最新电影的信息，但是不必保留所有的电影信息.为了更快速、能溯源、可恢复**



## 总结

**核心在于：任务成功率为导向，在有限的上下文窗口中通过减少窗口消耗（关键信息返回:sub-agent/工具结果）+信息内容分级（p0-p2）+执行压缩(比如按照压缩token保留还是messages保留等等策略)**


预防增长 + 分级保留 + 可回溯压缩 + 按需恢复 + 任务成功率评估。

**在有限的上下文窗口中通过预防增长+分级保留+可回溯压缩/按需恢复等等方式来增大任务的整体成功率**
