# 应用进程与生命周期

应用部署成功至少需要一个可管理的运行进程；“命令执行了”不代表服务健康。生命周期是 **启动 → 就绪 → 服务请求 → 停止或失败 → 恢复**。每一阶段都有不同的可观察信号。

| 阶段 | 应用责任 | 运行平台责任 |
| --- | --- | --- |
| 启动 | 校验配置、初始化依赖、绑定明确端口 | 注入配置并启动进程 |
| 就绪 | 只有能处理请求时才报告就绪 | 就绪后才接入流量 |
| 运行 | 处理请求、输出结构化日志与必要指标 | 监测退出、资源和端口 |
| 停止 | 拒绝新请求、完成或中断进行中工作、释放资源 | 发送停止信号并等待，超时再强制结束 |
| 失败 | 返回非零退出状态，保留错误上下文 | 按策略重启并告警，避免无限快速重启掩盖故障 |

**存活检查**回答进程是否还应被重启；**就绪检查**回答能否接新流量。一个进程存在但数据库不可达，可能存活却不就绪；检查策略要避免把短暂下游故障放大为重启风暴。

FastAPI 在 Linux 上可由 ASGI 服务器运行，并交给 systemd 管理。systemd 负责启动、重启与日志接入；Nginx 负责对外入口；应用自己负责正确处理信号和请求。容器环境中由容器运行时或编排器承担进程管理职责，避免重复叠加进程守护层。

排查次序：查看退出状态和日志 → 检查配置与工作目录 → 检查端口监听 → 从主机本地探测服务 → 再检查代理与外部网络。不要仅凭外部 502 就认定应用代码错误。
