# 应用部署与交付的本质

**部署**是把指定版本的应用放进目标环境并使它按预期运行；**交付**还包含可验证、可追踪、可更新、可恢复的能力。把代码复制到服务器只是其中一个动作。

## 从源码到服务

```text
源码 + 依赖声明 + 构建规则 → 测试 → 版本化制品
版本化制品 + 环境配置 + 运行资源 → 进程或容器
进程或容器 + 网络入口 + 依赖服务 → 对外服务
对外服务 + 健康检查 + 日志/指标 → 可持续运行
```

以 FastAPI 为例：开发者本地写接口并提交 Git；流水线安装受控依赖、运行测试，生成包或镜像；测试环境部署同一制品并验证数据库连接、接口和权限；生产环境用受控配置启动服务，经反向代理接入流量；发布后观察错误率和延迟。下一版复用这条链路，失败则按既定版本回退。

## 六个必须明确的对象

| 对象 | 需要回答的问题 |
| --- | --- |
| 版本 | 当前运行的代码对应哪个提交和制品？ |
| 环境 | Python、系统库、CPU 架构和外部依赖是否满足要求？ |
| 配置 | 域名、数据库地址、密钥由谁提供，如何分环境管理？ |
| 运行 | 谁启动、监控、重启进程，退出时如何处理？ |
| 入口 | 请求如何经过 DNS、TLS、代理到达应用？ |
| 恢复 | 健康检查失败时如何止损，数据变更能否回退？ |

“可回滚”不等于只切换旧镜像：数据库迁移、消息格式和外部副作用也可能使旧版无法运行。发布前应先检查兼容性，保留可恢复的制品和配置。

## 验收

另一位工程师拿到版本号、部署说明和必要授权后，能在目标环境重现运行、执行冒烟验证并定位日志；下一次更新可沿相同流程完成，失败时能识别原因和恢复路径。
