对，你说的是核心，但前面还要加上**明确场景和版本边界**，后面要加上**回归验证和停止条件**。否则容易一直调指标，却不知道什么时候算做好。

完整流程是：

**明确场景 → 定义验收标准 → 建立评测集 → 跑当前基线 → 定位失败 → 提出改进假设 → 对照实验 → 回归验收 → 交付并收集反馈。**

每一步回答一个具体问题：

| 步骤 | 要回答的问题 | 在 NoteAgent 中的例子 |
|---|---|---|
| 1. 明确场景 | 用户究竟要完成什么？本版支持到哪里？ | 技术文章整理成笔记，保存后能在新会话中查找 |
| 2. 定义验收 | 怎样算可用？哪些错误绝不能发生？ | 未审批不能写入；关键内容不遗漏；检索能找到对应段落 |
| 3. 建立评测集 | 用哪些任务代表真实使用？ | 长文、代码、含糊提问、无答案问题、修改和删除后的查询 |
| 4. 跑当前基线 | 现有系统到底做到什么程度？ | 固定代码、Prompt、模型和数据，记录结果、耗时与成本 |
| 5. 定位失败 | 错误最早发生在哪一层？ | 信息生成时就丢了，还是切块后没召回，还是回答误用证据 |
| 6. 提出假设 | 为什么这个改动可能有效？ | “定义与示例被切开，导致查询只召回定义” |
| 7. 对照实验 | 改动是否真的改善目标问题？ | 只调整切块策略，与旧策略对比 |
| 8. 回归验收 | 修好这一类，有没有破坏其他能力？ | 长文检索改善，但短笔记、删除同步和引用仍正常 |
| 9. 交付反馈 | 达标了吗？真实使用出现了哪些新问题？ | 达标则结束本轮；新失败经过核实后加入后续评测 |

**这里有四个关键区别。**

**第一，验收标准要分层。**  
正确性底线用测试证明，例如审批、文件写入、删除、索引同步；生成和检索质量用评测衡量；完整业务链路用端到端场景验证。不能把这些混成一个“综合分”，让高检索分掩盖错写文件的问题。

**第二，实验集与最终验收集最好区分。**  
日常用开发集分析失败、调整方案；保留一部分样例做阶段验收，避免只对反复看过的题有效。早期样本少可以先从小集开始，但结论只能覆盖这些场景，不能宣称普遍有效。

**第三，先定位，再调技术。**  
例如用户问一个问题，系统没答对，应依次检查：

> 来源有没有这条信息？→ 笔记有没有保留？→ 索引里有没有？→ 检索有没有召回？→ 模型有没有正确使用？

在哪一步首次出错，就优先处理哪一步。只有证据指向当前技术的能力限制时，才考虑更换技术选型。

**第四，迭代要有停止条件。**  
目标应是本版必需场景达到预先确定的门槛，且成本、延迟和维护复杂度可接受。一次实验没有显著收益，就不必保留额外复杂度；达标之后交付，不必无限追求更高分。
