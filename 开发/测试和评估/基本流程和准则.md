# 评估迭代方法论

## 一、整体方法论：建立评估闭环（Eval-Driven Development）

不管优化哪个模块，都遵循同一个循环：

```
定义指标 → 构建测试集 → 跑baseline → 做error analysis → 定位问题 → 针对性优化 → 回归测试 → 上线
```

关键原则：**没有测试集，就不要动手优化**。因为 Agent 系统里各模块互相耦合，改了 prompt 可能让工具调用变差，改了检索策略可能让最终回答变啰嗦。没有量化基线，你无法判断改动是变好还是变坏，只能靠"感觉"，这在生产环境里非常危险。

## 二、数据集怎么构建

### 1. 数据来源（按优先级）
- **真实生产日志**：最有价值。把线上跑过的 trace（用户输入、中间步骤、工具调用、最终输出）全部记录下来，这是最真实的分布。
- **人工构造的 case**：针对你能想到的边界情况、高频场景、历史 bug 手写测试样本。
- **对抗性/极端 case**：模糊指令、多轮打断、工具报错、检索无结果等异常路径，专门测试鲁棒性。
- **合成数据**：用 LLM 根据你的业务场景批量生成变体问题（比如同一个意图换10种问法），扩充覆盖面，但要人工抽检质量。

### 2. 数据集分层管理
- **Golden Set（黄金集）**：50~200条精挑细选、人工标注过"正确答案"或"验收标准"的case，长期稳定，每次改动都跑一遍，作为回归测试的"防线"。
- **Regression Set（回归集）**：历史上出过问题的case集合，专门防止"修好一个坏一个"。
- **Exploration Set（探索集）**：持续从生产日志里滚动采样的新case，用来发现你还没意识到的问题。

### 3. 标注方式
- 小规模（几十到几百条）：人工标注期望输出/评分标准，质量最高。
- 大规模：用 **LLM-as-Judge**（用更强的模型或精心设计的评分 prompt 打分），但一定要先用一批人工标注去校准这个 judge 的可靠性（人机一致率最好 >85%）。

## 三、按模块拆解评估指标

### 系统提示词（System Prompt）优化
- **任务成功率**：是否达成用户意图（可用 LLM-as-Judge 或规则判断）。
- **指令遵循度**：格式是否正确、语气是否符合要求、是否遵守了约束条件（比如"不要用markdown"）。
- **对比实验**：A/B 跑不同版本的 prompt，在同一测试集上打分对比，避免只改一处却没对照。
- 常见做法：把 prompt 拆成可复用的"模块"（角色设定、工具使用规则、输出格式），单独做消融实验（ablation），看哪一段真正起作用。

### 工具（Tool）优化
- **工具选择准确率**：该调用A工具时是否真的调用了A（而不是瞎猜或漏调）。
- **参数正确率**：传给工具的参数是否符合工具schema、语义是否正确。
- **工具调用效率**：完成任务所需的调用次数、是否有冗余/重复调用。
- **失败恢复能力**：工具报错后 Agent 能否合理重试或降级,而不是卡死或胡编结果。
- 建议单独维护一个"工具调用"测试集，输入是用户query，标注是"应该调用的工具+参数"，这样可以脱离最终文本生成单独评估这一层。

### RAG 优化
这是最需要分层评估的模块，因为它有两个独立环节：

**检索环节：**
- Recall@K / Precision@K：召回的文档里有没有包含标准答案所需的信息。
- MRR / NDCG：相关文档排序是否靠前。

**生成环节（拿到检索结果后）：**
- **Faithfulness（忠实度）**：回答是否完全基于检索到的内容，有没有幻觉。
- **Answer Relevancy**：回答是否切题。
- **Context Precision/Recall**：检索出来的内容有多少是真正被用上的、有用信息有没有遗漏。

这套指标业界已经有现成框架，比如 **Ragas**、**TruLens**、**DeepEval** 都可以直接拿来用，不用自己从零造轮子。

### Agent 整体端到端
- **任务完成率**（Task Success Rate）：最终目标是否达成，这是北极星指标。
- **效率指标**：完成任务的步数、token消耗、延迟、成本。
- **多轮鲁棒性**：中途改需求、打断、纠错时 Agent 能否正确适应。
- **安全/合规性**：有没有输出不该输出的内容。

## 四、具体执行流程建议

1. **先把"任务成功"的定义写清楚**，最好写成可判断的 checklist 或 rubric，而不是模糊的"回答得好"。
2. **建60~100条覆盖主要场景的 Golden Set**，先跑一遍当前系统，得到 baseline 分数。
3. **做 Error Analysis**：把失败case一条条看，人工分类失败原因(比如"检索没召回相关文档" vs "召回了但没用上" vs "工具参数错了" vs "prompt理解偏了")。这一步最容易被跳过，但恰恰是最重要的——很多人直接开始"调prompt"，结果发现问题根本出在检索层。
4. **针对最高频的失败模式做一次改动**，一次只改一个变量（比如只改 chunk 大小,或只改 prompt 的一段),重新跑测试集对比分数。
5. **改动上线前必须跑 Regression Set**，确保没有"按下葫芦浮起瓢"。
6. **建立持续采样机制**：定期从生产日志抽样，补充进探索集，因为用户的真实使用方式会不断超出你最初的想象。

## 五、可以直接用的工具链

- **评估框架**：Ragas（RAG专用）、DeepEval、Promptfoo（prompt对比测试很方便）、TruLens
- **Trace/Observability**：LangSmith、Langfuse、Braintrust —— 这些能自动记录 Agent 的完整执行轨迹，方便做 error analysis 和维护测试集
- **LLM-as-Judge**：直接用 Claude/GPT 写评分 prompt，配合少量人工校准

---

一句话总结：**先定义"什么叫好"，再拆分到每个模块单独可测，再靠 error analysis 找到真正的瓶颈在哪一层，而不是凭直觉到处调**。这套流程一旦建立起来，后面无论是加新工具、换模型、还是调 RAG 策略，都能快速验证效果，不会做"盲人摸象"式的优化。
