# 分布式 ID 方案笔记：普通自增、雪花 ID 及其他常见方式

> 核心结论：**普通自增适合单库单表、低并发、强连续场景；雪花 ID 适合分布式、高并发、分库分表场景。** 两者最本质的区别是：普通自增是**中心化发号**，雪花 ID 是**本地生成、去中心化**。

---

## 一、普通自增 ID 是什么？

普通自增通常指：

- 数据库自增主键：`AUTO_INCREMENT`
- 数据库序列：`SEQUENCE`
- 单表维护一个自增字段

特点：

```text
1, 2, 3, 4, 5, ...
```

优点很直接：

| 优点 | 说明 |
|---|---|
| 实现简单 | 数据库原生支持，几乎零开发成本 |
| 严格递增 | ID 连续、有序，可读性强 |
| 长度小 | 通常用 `BIGINT`，存储和索引友好 |
| 索引性能好 | 递增写入 B+ 树，页分裂少 |
| 便于排查 | 按 ID 大小能大致判断先后顺序 |

缺点也很明显：

| 缺点 | 说明 |
|---|---|
| 中心化瓶颈 | 所有 ID 都依赖同一个数据库生成 |
| 单点风险 | 数据库故障会影响 ID 生成 |
| 分库分表失效 | 多库各自自增会产生重复 ID |
| 扩容合并困难 | 多表合并、数据迁移时 ID 容易冲突 |
| 暴露业务量 | 外部可通过 ID 推测订单量、用户量 |
| 性能有限 | 高并发下数据库自增会成为写入瓶颈 |

**一句话：普通自增简单可靠，但扩展性差，不适合大规模分布式系统。**

---

## 二、雪花 ID 和普通自增的核心区别

雪花 ID 典型结构：

```text
1 位符号位 + 41 位时间戳 + 10 位机器 ID + 12 位序列号
```

| 对比项 | 普通自增 | 雪花 ID |
|---|---|---|
| 生成位置 | 数据库中心生成 | 各节点本地生成 |
| 是否依赖中心 | 强依赖数据库 | 基本无中心依赖 |
| 唯一性范围 | 单库单表唯一 | 多节点全局唯一 |
| 有序性 | 严格递增 | 趋势递增，非严格递增 |
| 性能 | 较低，受数据库限制 | 很高，本地生成无网络 IO |
| 分库分表 | 不友好，容易冲突 | 友好，适合分布式 |
| 长度 | 较短 | 64 位整数，也较短 |
| 运维复杂度 | 低 | 中，需要处理时钟和机器 ID |
| 主要风险 | 单点、瓶颈、扩展难 | 时钟回拨、workerId 冲突 |
| 适用场景 | 单库单表、中小系统 | 高并发、多节点、分库分表 |

### 关键区别 1：中心化 vs 去中心化

普通自增：

```text
服务 A ─┐
服务 B ─┼──> 数据库自增序列
服务 C ─┘
```

所有请求都打到数据库，数据库是**中心节点**，也是瓶颈和单点。

雪花 ID：

```text
服务 A ──> 本地生成 ID
服务 B ──> 本地生成 ID
服务 C ──> 本地生成 ID
```

每个节点本地生成，不需要网络调用，扩展能力强。

### 关键区别 2：严格递增 vs 趋势递增

普通自增是**严格递增**：

```text
1001, 1002, 1003, 1004
```

雪花 ID 是**趋势递增**：

```text
同一毫秒内可能乱序，但整体随时间增长
```

雪花 ID 不保证连续，也不保证全局严格递增，但整体趋势向上，对数据库索引仍然友好。

### 关键区别 3：单库唯一 vs 全局唯一

普通自增在单库单表下没问题，但一旦分库分表：

```text
库 A：1, 2, 3 ...
库 B：1, 2, 3 ...
```

就会产生重复 ID。

雪花 ID 通过“时间戳 + 机器 ID + 序列号”保证多节点下全局唯一。

---

## 三、雪花 ID 的优缺点

### 优点

1. **全局唯一**：多节点、多机房并发生成也不容易重复。
2. **高性能**：本地生成，无网络 IO，单机吞吐高。
3. **趋势递增**：比 UUID 更适合做数据库主键。
4. **去中心化**：不依赖数据库或 Redis 发号。
5. **64 位整数**：存储小，索引效率高。
6. **可嵌入信息**：机器位可划分机房、业务、分片。

### 缺点

1. **时钟回拨风险**：机器时间回拨可能导致 ID 重复或服务异常。
2. **workerId 分配问题**：容器化、弹性扩缩容下机器 ID 容易冲突。
3. **非严格递增**：不能依赖 ID 连续或严格排序。
4. **单毫秒上限**：单节点单毫秒最多 4096 个 ID。
5. **信息泄露**：可能暴露生成时间和机器规模。

**一句话：雪花 ID 用“时钟和节点管理成本”换来了“高性能、全局唯一、去中心化”。**

## 四、其他常见方式简要比一比

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **普通自增** | 简单、严格递增、短小、索引友好 | 中心化、单点、分库分表失效 | 单库单表、中小系统 |
| **雪花 ID** | 高性能、全局唯一、趋势递增、去中心化 | 时钟回拨、workerId 管理 | 分布式、高并发、分库分表 |
| **UUID** | 本地生成、无依赖、绝对唯一 | 无序、存储大、索引性能差 | 非主键标识、临时 ID |
| **Redis 自增** | 比数据库性能好、严格递增 | 依赖 Redis、网络开销、持久化风险 | 中小规模分布式发号 |
| **号段模式** | 批量取号，降低数据库压力 | ID 不连续、取号瞬间抖动 | 高并发但可接受非连续 |
| **Leaf / UidGenerator** | 工业级、解决 workerId 和时钟问题 | 组件依赖多、复杂度高 | 大型生产系统 |

### 1. 对比 UUID

UUID 最大优势是**完全本地生成、无依赖**，但作为数据库主键时**完全无序**，会导致 B+ 树频繁页分裂，存储空间也更大。

雪花 ID 比 UUID 更适合做数据库主键，因为它是**趋势递增的 64 位整数**。

### 2. 对比 Redis 自增

Redis 自增性能比数据库好，但仍然是**中心化发号**，有网络开销，且强依赖 Redis 可用性。持久化配置不当时，宕机还可能造成 ID 回退或重复。

雪花 ID 不依赖中心存储，延迟和吞吐更稳定。

### 3. 对比号段模式

号段模式从数据库批量取一段 ID 缓存在内存中发放，比如一次取 `1~1000`。它大幅降低了数据库压力，但：

- ID 不连续；
- 号段切换时可能有取号抖动；
- 服务重启可能浪费未用完号段。

雪花 ID 没有号段耗尽问题，但需要处理时钟和机器 ID。

### 4. 对比 Leaf / UidGenerator

美团 Leaf、百度 UidGenerator 是雪花思想的**生产级增强版**：

- Leaf 支持号段模式和雪花模式，可用 ZooKeeper 协调 workerId；
- UidGenerator 使用 RingBuffer 预生成，性能很强。

它们解决了原生雪花的部分痛点，但引入了额外组件和运维复杂度。

## 五、选型建议

### 选普通自增，如果：

- 单库单表；
- 并发量不高；
- 需要严格递增、连续 ID；
- 系统简单，不想引入额外组件；
- ID 主要用于内部标识，不暴露给外部。

### 选雪花 ID，如果：

- 分库分表；
- 多节点、多服务实例；
- 高并发写入；
- 希望 ID 本地生成、无中心依赖；
- 能接受趋势递增而非严格递增；
- 有能力处理时钟同步和 workerId 分配。

### 选其他方案，如果：

- **UUID**：只做请求 ID、临时标识，不作为数据库主键；
- **Redis 自增**：中小规模，能接受 Redis 依赖；
- **号段模式**：高并发但可接受 ID 不连续；
- **Leaf / UidGenerator**：不想自己处理时钟和 workerId，愿意接受更高系统复杂度。

---

## 六、最终记忆版

```text
普通自增：简单、严格递增、单库好用；但中心化、有瓶颈、分库分表会冲突。

雪花 ID：本地生成、高性能、全局唯一、趋势递增；但要防时钟回拨、管好 workerId。

UUID：无依赖但无序，做主键伤索引。

Redis 自增：比数据库快，但仍依赖中心。

号段模式：批量取号降压力，但 ID 不连续。

Leaf / UidGenerator：工业级雪花，稳定但更复杂。
```

**选型口诀：**

> 单库低并发用自增，分布式高并发用雪花；  
> 主键优先趋势递增，临时标识可用 UUID；  
> 不想管时钟和机器 ID，就上 Leaf 这类工业方案。
