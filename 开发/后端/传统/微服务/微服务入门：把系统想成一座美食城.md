# 微服务入门：把系统想成一座美食城

刚接触微服务时，你可能会同时遇到 Spring Boot、Nacos、Gateway、Feign 等名字。先别急着记配置。想象你要经营一座美食城：有面馆、甜品店、收银台和商场导览牌。把一次点餐走完，这些技术各自负责什么就清楚了。

> 本文用 Spring 生态举例，但“按业务拆分、独立运行、通过网络协作”才是微服务的核心；Nacos、Gateway、Feign 是实现这些事情的可选工具，并不是微服务的定义。

## 一、先看全景：从一家大饭店到一座美食城

**单体应用**像一家大饭店：点餐、做面、做甜品和结账的业务代码放在同一个应用中，通常一起构建、一起部署。它可以有清晰的内部模块，也能部署多个实例；“单体”并不意味着代码一定混乱，或每次修改都要停机。

**微服务架构**像一座美食城：面馆、甜品店、订单店分别经营自己的业务。它们是独立运行的应用，可以分别开发和部署，通过网络请求协作。甜品店更新菜单时，通常不必重新部署面馆。但如果面馆必须等甜品店确认库存才能出餐，甜品店故障仍可能影响面馆。这也是微服务需要处理的问题。

| 技术概念 | 美食城类比 | 实际职责 |
| :--- | :--- | :--- |
| 一个业务服务 | 一家店 | 负责一块明确的业务，独立运行和部署 |
| Spring Boot | 开店用的一套设备和流程 | 帮助构建、启动 Java 应用；一个 Spring Boot 应用不一定就是微服务 |
| Nacos 服务注册与发现 | 商场导览牌 | 记录“哪家店现在在哪里”，让调用方按服务名找到可用实例 |
| Gateway | 面向顾客的入口和引导台 | 接收外部请求，按规则转发，也可统一处理鉴权、限流等事项 |
| Feign | 店与店之间按约定填写的点餐单 | 用 Java 接口描述并发起 HTTP 调用 |
| API 契约模块（常叫 `*-api`） | 公布的菜单格式 | 放跨服务调用需要共同遵守的接口或数据结构；是否单独建模块由项目决定 |
| Common 模块（常叫 `*-common`） | 共用工具 | 放通用代码；也不是微服务必备组件 |

注意区分：**服务是运行中的应用；API/Common 通常只是被应用引用的代码模块**。一个 `xxx-api.jar` 不会因为名字里有 `api` 就自动成为一家“店”。

## 二、一笔订单是怎么走完的？

假设顾客在手机上点了一碗面，并加一份甜品。系统有 `order-service`（订单服务）和 `dessert-service`（甜品服务）。

```text
顾客（浏览器或 App）
        │  POST /orders
        ▼
Gateway（入口：匹配路径、转发请求）
        │
        ▼
order-service（创建订单）
        ├──① 按 dessert-service 这个名字查询──→ Nacos
        │                                   └──返回可用实例地址
        │
        └──② Feign：向选中的实例发 HTTP 请求──→ dessert-service
                                             └──返回甜品信息

order-service 根据返回结果完成订单，再通过 Gateway 回复顾客
```

这张图有一个容易混淆的地方：**Nacos 不负责转送每一次甜品查询的业务数据**。甜品服务启动时向 Nacos 注册自己的服务名和地址；调用方通过服务发现取得可用地址后，业务请求发往甜品服务。实际调用中还会有负载均衡组件负责从多个实例中选一个。

例如甜品服务同时开了两家分店：

```text
dessert-service → 10.0.0.11:8080
dessert-service → 10.0.0.12:8080
```

订单服务只需知道服务名 `dessert-service`，不用把其中某个地址写死。扩容、缩容或实例地址变化时，服务发现才能发挥价值。Nacos 还可以承担配置管理工作；本文的“导览牌”只解释它的服务注册与发现能力。

## 三、用一点代码对上这些概念

下面是**展示调用关系的简化片段**，不是可直接复制运行的完整工程。真正运行还需要匹配的 Spring Boot / Spring Cloud / Spring Cloud Alibaba 版本及相应依赖。

### 1. 甜品店：提供 HTTP 接口

```java
// 运行在 dessert-service 中
@RestController
@RequestMapping("/desserts")
class DessertController {

    @GetMapping("/{id}")
    DessertDto getDessert(@PathVariable Long id) {
        // 示例：实际项目中通常从数据库或业务服务中查询
        return new DessertDto(id, "芒果布丁", true);
    }
}

record DessertDto(Long id, String name, boolean available) {}
```

`GET /desserts/42` 就是甜品店对外公布的一项“菜单”。请求路径、参数和返回数据共同构成调用约定。示例中的 `record` 需要支持它的 Java 版本；若使用较早版本，可以换成普通 Java 类。

### 2. 导览牌：用服务名登记地址

在使用 Spring Cloud Alibaba Nacos Discovery 时，甜品服务可以配置服务名和 Nacos 地址：

```yaml
spring:
  application:
    name: dessert-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
```

`spring.application.name` 可以作为默认注册服务名；`server-addr` 指向 Nacos 服务端。服务启动并成功注册后，其他服务才能通过 `dessert-service` 发现它。这里的 `127.0.0.1` 只适合 Nacos 与应用在同一台机器上运行的本地示例；分机器或容器部署时，要填应用能够访问的地址。

### 3. 店间点餐单：用 Feign 调用

订单服务可以声明一个客户端接口：

```java
// 运行在 order-service 中；需要启用并扫描 Feign 客户端
@FeignClient(name = "dessert-service")
interface DessertClient {

    @GetMapping("/desserts/{id}")
    DessertDto getDessert(@PathVariable("id") Long id);
}
```

业务代码调用 `dessertClient.getDessert(42L)`，看起来像调用本地方法，背后却是一次**跨进程的 HTTP 请求**。`@FeignClient` 中的服务名用于查找目标服务；路径、参数和返回类型必须与甜品服务公布的接口约定一致。如果双方在不同代码库，团队可以通过 API 契约模块或接口文档维护这份约定，但不必为了“用微服务”而强行创建共享模块。

Gateway 做的是另一件事：把顾客的 `/orders` 请求引到 `order-service`。它处理的是外部进入系统的流量；Feign 展示的是订单服务向甜品服务发起的内部调用。两者可以同时存在，但不是所有请求都必须经过 Gateway，也不是服务间调用都必须使用 Feign。

## 四、为什么不把所有店都拆出来？

拆店之后，独立发布和按需扩容更方便；代价是原本在一个进程内完成的调用变成了网络调用。网络会超时，服务会暂时不可用，多个服务的数据也不再天然处于同一个数据库事务中。还需要日志、监控和请求追踪，才能查清“这笔订单卡在哪家店”。

因此，划分服务时首先看**业务边界**，例如订单、商品、支付各自负责什么，而不是按 Controller、Service、DAO 技术层各拆一家店。新项目或业务规模较小时，结构清楚的单体应用往往更容易开发和维护。等到团队、业务或部署需求确实要求独立演进，再拆分也来得及。

## 五、最后记住这五句话

1. **微服务**：围绕业务能力划分、独立运行并通过网络协作的服务。
2. **Nacos**：服务登记地址、按名称查找服务；还可以管理配置。
3. **Gateway**：按路由规则接收并转发外部请求。
4. **Feign**：用 Java 接口发起服务间 HTTP 调用，调用仍可能超时或失败。
5. **API/Common 模块**：可选的代码组织方式，不是运行中的微服务。

把它们连起来看：**顾客从入口下单，订单店通过导览牌找到甜品店，再按双方约定的菜单发起请求。**这就是理解一条典型微服务调用链的起点。
