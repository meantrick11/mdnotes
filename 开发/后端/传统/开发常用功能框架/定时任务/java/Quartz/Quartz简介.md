## Quartz 框架笔记

### 一、定位：它是什么，不是什么

Quartz 是一个**开源的任务调度库**，完全由 Java 编写，以 `.jar` 文件的形式分发，可以嵌入几乎任何 Java 应用——从最小的独立程序到大型电商系统。它的核心职责只有一件事：当预定的时间到达时，执行（或通知）其他软件组件。

理解 Quartz 时，有几个“不是什么”值得先明确，这有助于划定它的能力边界：

- **它不是作业队列**：虽然小规模下可以勉强当作队列使用，但它不提供队列语义（如消息确认、死信处理）。
- **它不是网格计算引擎**，也不是给业务人员使用的“作业执行服务”——它是给开发者用的代码库，嵌入到应用中为应用自身调度任务。
- **它与 `java.util.Timer` 的根本区别在于**：`Timer` 没有持久化机制，调度规则僵硬（只能设起始时间和重复间隔），不利用线程池，也没有任何任务管理能力。Quartz 恰恰在这些维度上提供了系统性支持。

因此，Quartz 适合的场景是：**应用内部需要在未来某个时间点或按周期执行的、需要持久化和可管理性的调度任务**，例如定时报表、订单超时取消、会员权益到期处理、周期性数据同步等。


### 二、基础用途

Quartz 的典型使用方式，是围绕“定义一个任务”和“规定它何时运行”这两个维度展开，再交给调度器去管理执行。具体而言：

**驱动业务流程**。Quartz 不止能运行系统级的定时进程，也可以驱动应用的业务逻辑。例如，订单创建后触发一个延迟检查，若未支付则在指定时间后自动取消。

**支持复杂的调度规则**。调度可以简单到“每 40 秒运行一次”，也可以复杂到“每月第二个周一”或“每年三月的最后一个工作日”——后一种模式超出了标准 Cron 表达式的表达能力，需要通过 Quartz 的 `RecurrenceTrigger`（RFC 5545 RRULE）来实现。

**动态管理**。一旦任务注册到调度器中，就可以在运行时进行暂停、恢复、删除、修改触发时间等操作，而不需要重启应用。这对于需要运维介入或根据外部条件调整调度策略的系统尤为重要。


### 三、核心组件及其作用

Quartz 的 API 围绕几个职责分明的接口构建。理解它们之间的分工，是理解 Quartz 的关键。

#### 1. Scheduler：调度器

`Scheduler` 是 Qua​​rtz 的**运行时容器和操作入口**。它由 `SchedulerFactory` 创建，生命周期从创建开始，到调用 `shutdown()` 结束。

它的核心作用不是“执行任务”，而是**管理任务与触发器的注册关系，并控制调度器的运行状态**。你可以通过它添加、删除、列出 Job 和 Trigger，也可以暂停某个触发器。一个关键但容易被忽略的细节是：**创建后的 Scheduler 在没有调用 `start()` 之前，不会对任何 Trigger 采取行动**，即使 Trigger 的时间已经到了。

Scheduler 内部依赖线程池来实际执行 Job。默认线程池的并发上限是 10，意味着同一时刻最多有 10 个 Job 在运行。这个数字需要根据任务的性质（CPU 密集型还是 I/O 密集型）来调整，因为阻塞型的 Job 会占用线程池名额，导致其他任务无法及时执行。

#### 2. Job 与 JobDetail：任务的定义与实例

**Job** 是你要执行的内容本身。它是一个接口，只有一个方法：`execute(JobExecutionContext context)`。你的业务逻辑就写在这个方法里。

**JobDetail** 则是 Job 的**定义/实例描述**。它把“用哪个 Job 类”和“这个 Job 实例叫什么名字、属于哪个组”绑定在一起。一个 Job 类可以被多个 JobDetail 引用，每个 JobDetail 拥有独立的身份和生命周期。

两者的关系可以这样理解：Job 是“代码”，JobDetail 是“一条具名的任务记录”。Scheduler 存储和管理的是 JobDetail，而不是裸的 Job 类。`execute` 方法接收的 `JobExecutionContext` 提供了运行时环境信息——包括执行它的 Scheduler 句柄、触发它的 Trigger、对应的 JobDetail 等，让 Job 代码能够在执行时获取上下文。

#### 3. Trigger：时间规则

`Trigger` 定义**一个 Job 在什么时间、按什么规则执行**。Quartz 的灵活性很大程度上来自 Trigger 与 Job 的分离：Job 只关心“做什么”，Trigger 只关心“什么时候做”。

主要类型包括：

- **SimpleTrigger**：适用于单次执行或以固定间隔重复执行的场景。
- **CronTrigger**：通过 Cron 表达式定义复杂的日历式规则，是实际项目中最常用的类型。
- **CalendarIntervalTrigger / DailyTimeIntervalTrigger**：基于日历间隔或每日时间窗口的调度。
- **RecurrenceTrigger**（较新特性）：支持 RFC 5545 RRULE，覆盖 Cron 无法表达的复杂模式，如“每月第二个周一”。

Trigger 与 Job 的关系是**多对一**：一个 Job 可以绑定多个 Trigger（例如同一任务既有日常调度又有月末补跑），但一个 Trigger 只服务一个 Job。


### 四、运行时机制：JobStore、集群与 Misfire

组件定义了“是什么”，运行时机制则决定了“在真实环境中如何可靠地运行”。

#### JobStore：状态存放的位置

JobStore 决定了 Job 和 Trigger 的状态保存在哪里，这是 Quartz 在生产环境中行为差异最大的一个配置项。

**RAMJobStore** 把状态放在 JVM 内存中。性能最高，配置最简单，但应用停止时所有调度状态丢失，且无法用于集群。

**JDBCJobStore** 通过 JDBC 将状态持久化到数据库。应用重启后调度信息不会丢失，并且是集群模式的必要条件。代价是配置更复杂，每次读写的性能取决于数据库。

选择哪个 JobStore，本质上是在“性能与简单性”和“持久性与集群能力”之间做取舍。单机、可丢失的调度用 RAM 即可；生产环境、需要重启恢复或集群部署，则必须用 JDBC。

#### 集群：通过数据库行锁实现“恰好一次”触发

Quartz 的集群不是靠节点之间的网络通信协调的，而是**所有节点指向同一个数据库和同一组 `QRTZ_` 表**。当某个 Trigger 到期时，多个节点竞争同一行记录的行锁，**抢到锁的节点执行该次触发**，从而保证每个预定时刻只有一次实际触发。

这带来了两个重要特性：**负载均衡**（触发分散到不同节点）和**故障转移**（但故障转移是选择性加入的——只有 JobDetail 显式标记了 `requestRecovery` 的 Job，才会在节点死亡后被其他节点重新执行）。

集群部署有两个硬性约束值得记住：第一，必须使用持久化的 JDBC JobStore，RAMJobStore 无法集群；第二，**各节点的时钟必须通过 NTP 等机制保持在一秒以内同步**，否则锁机制会产生漏触发或重复触发。


#### Misfire：错过触发时怎么办

当调度器因为线程池耗尽、应用暂停或节点故障等原因，没有在预定时刻触发某个 Trigger，就发生了 Misfire。Quartz 不会静默丢弃这种情况，而是根据 Trigger 类型和配置的策略来决定行为。

默认策略是 `SmartPolicy`：对于 SimpleTrigger，解析为“立即触发一次”；对于 CronTrigger，解析为“立即触发一次，然后按原计划继续”。其他策略包括“忽略所有错过的触发，只从下一个正常周期继续”等。Misfire 策略的选择直接影响系统的补偿行为，在设计对时间敏感的任务（如财务对账、定时通知）时需要显式考虑。


### 五、小结

Quartz 的设计可以用一句话概括：**把“做什么”（Job）和“什么时候做”（Trigger）分开，交给一个可持久化、可集群的 Scheduler 去协调**。它的核心价值不在于“能跑定时任务”——`Timer` 也能——而在于持久化、动态管理、复杂调度规则和集群容错这些生产级能力。

在实际使用时，组件选择的关键决策点集中在两处：**JobStore 选 RAM 还是 JDBC**（决定了持久性和集群能力），以及 **Trigger 类型与 Misfire 策略**（决定了调度的精确性和异常补偿行为）。把这两处想清楚，Quartz 的使用就不会出现方向性的偏差。


> **补充说明**：Quartz 存在 Java 版和 .NET 版（Quartz.NET）。两者共享同一套核心设计理念和组件模型，但 API 命名和部分特性（如 Quartz.NET 4.x 的 DI 集成、HTTP API、OpenTelemetry 支持）存在差异。上述笔记以 Java 版的核心概念为主线，组件层面的理解对两个版本是共通的。
