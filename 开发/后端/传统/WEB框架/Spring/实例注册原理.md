# 笔记：一次接口请求背后的 Spring 全链路

> 案例：`GET /upload/checkExists`（文件秒传检查）—— 从代码定义到运行机制

---

## 一、静态结构：代码在哪，谁干什么

### 1.1 五层调用链

```
前端: GET /prod-api/file/upload/checkExists?guid={文件MD5}&scope=0
  │  nginx(/prod-api 前缀) → 网关 8080 → 路由 → fongwell-file:9300
  ▼
① HTTP入口层   SysFileController#checkExists
  │             位置: fongwell-file/controller/SysFileController.java L146-156
  │             职责: 接参、鉴权(@PreAuthorize)、包 R<T> 返回；不写业务逻辑
  ▼ 调用 iSysFileService.checkExists(guid, scope)
② 契约层       ISysFileService（接口，12 个方法只有声明，无方法体）
  │             位置: fongwell-file/service/ISysFileService.java
  │             职责: 定义"存储层必须提供的能力"清单，不执行任何代码
  ▼ implements（编译器强制全部实现）
③ 实现层       MinioSysFileServiceImpl#checkExists
  │             位置: fongwell-file/service/impl/ L239-243
  │             职责: 真正干活——拼 key、调工具类
  ▼
④ 工具层       MinioUtils.checkFileExist / getFileStat
  │             职责: 封装 MinIO SDK 调用
  ▼ statObject（HTTP HeadObject 请求）
⑤ 外部服务     MinIO 对象存储（bucket: fsp-agent-dev）
```

### 1.2 配套要素（数据类 + 配置）

| 要素 | 位置 | 说明 |
|---|---|---|
| `R<T>` | fongwell-common-core | 统一响应包装：`code/msg/data`，只在 Controller/Feign 边界用 |
| `FileInfoVO` | fongwell-api-system | 跨模块共享 VO：fileId、filePath、fileName、size、uploadedChunks |
| `FileUploadScope` | fongwell-common-core | scope 枚举：COMMON(0) → 目录 `common/`；CUSTOM(4) → `custom/` |
| `SysFile` | fongwell-file/domain | 实体，对应 `sys_file` 表 |
| `file.storage.type: minio` | fongwell-file/bootstrap.yml | **决定 5 个存储实现里谁生效** |
| minio 连接配置 | bootstrap.yml / Nacos | url、accessKey、bucketName |

### 1.3 业务逻辑（checkExists 到底做了什么）

```
checkExists(guid, scope):
  ① getUploadScope(scope)  Integer→枚举；null/非法值 → 兜底 COMMON
  ② fileKey = saveDir + guid    例: "common/{md5}"
  ③ MinioUtils.checkFileExist → client.statObject()
       MinIO 返回成功 → true
       抛 "Object does not exist" → false
                                        （"检查"由 MinIO 服务端裁定，
                                          Java 侧只拼 key + 解析响应）

命中后补信息 getFileInfoByGuid:
  statObject 拿 size（存储侧元数据）
+ sys_file 表按 hash=guid 查 fileId/name（数据库侧）
= FileInfoVO 返回
```

> 关键认知：**guid 就是文件内容的 MD5**（前端预先计算）。hash 相同 → key 相同 → 命中 → 秒传。

## 二、Spring 三大机制（"这一切怎么跑起来的"）

### 机制 1：组件扫描 —— "要实例化什么类"在哪定义？

**答案：没有集中清单。注解就是清单，分散在各文件。**

| 说明层次 | 写在哪里 | 具体内容 |
|---|---|---|
| ① 扫描范围 | 启动类 `FongwellFileApplication` L22 | `@SpringBootApplication` + `@ComponentScan(basePackages={"com.fongwell"})` |
| ② 我是组件 | 每个类头 | `@RestController`（Controller）、`@Service`（服务）、`@Configuration`（配置）——本质都是 `@Component` 的派生 |
| ③ 激活条件 | 类头 + yml | `@ConditionalOnProperty(havingValue="minio")` + `file.storage.type: minio` |
| ④ 依赖什么 | 构造器签名 | `@RequiredArgsConstructor` + `final` 字段 |

对照记忆——老式 Spring 是集中清单：

```xml
<!-- XML 时代：所有 bean 集中声明 -->
<bean id="minioService" class="...MinioSysFileServiceImpl"/>
<bean id="controller" class="...SysFileController">
    <constructor-arg ref="minioService"/>
</bean>
```

Spring Boot 改成"谁上岗谁自己带证件"（约定优于配置）。

### 机制 2：条件装配 —— 5 个实现类怎么变成 5 选 1

```
5 个实现类，各有条件注解：
  MinioSysFileServiceImpl     @ConditionalOnProperty(type=minio)      ✔ 生效
  RustFSSysFileServiceImpl    @ConditionalOnProperty(type=rustfs)     ✘ 丢弃
  LocalSysFileServiceImpl     @ConditionalOnProperty(type=local)      ✘ 丢弃
  FastDfsSysFileServiceImpl   @ConditionalOnProperty(type=fastdfs)    ✘ 丢弃
  SeaweedFsSysFileServiceImpl @ConditionalOnProperty(type=seaweedfs)  ✘ 丢弃

配置来源（bootstrap.yml L43）:
  file:
    storage:
      type: minio     ← 改这个值即可切换存储，业务代码零改动
```

### 机制 3：构造器注入 + 动态绑定 —— "指向"与"只传参就能干活"

**（a）"指向" = 一条赋值语句，自动完成：**

```
源码只写：                @RequiredArgsConstructor + private final ISysFileService iSysFileService;

编译期 Lombok 生成：      public SysFileController(ISysFileService iSysFileService, ...) {
                              this.iSysFileService = iSysFileService;   ← "指向"就是这行赋值
                          }

启动期 Spring 执行：      按类型(byType)在容器找 ISysFileService → 唯一命中 Minio 实例
                          → 反射调构造器，把实例传入 → 赋值执行 → 指向完成

运行时调用：              iSysFileService.checkExists(...)
                          → JVM invokeinterface：看引用实际指向的对象
                          → 执行 MinioSysFileServiceImpl.checkExists 方法体（多态/动态绑定）
```

**（b）候选唯一性规则：**
- 只有一个候选 → 按类型自动注入（本项目 5 选 1 后恰好唯一）
- 多个候选 → 需 `@Qualifier("bean名字")` 指名（项目里 RustFS 旁路注入即如此）

**（c）接口不能被 new，但接口引用可以指向实现对象：**

```java
ISysFileService x = new MinioSysFileServiceImpl();   // 合法！向上转型
x.checkExists("abc", 0);                             // 执行的是实现类方法体
// Spring 做的与上面等价，只是把 new 挪到了启动阶段（反射）
```

## 三、时间线全景（三阶段）

### 阶段 1：编译期

```
① javac 检查：MinioSysFileServiceImpl implements ISysFileService
   → 12 个方法必须全部实现，缺一个编译报错（"声明必有实现"的保证来源）
② Lombok 生成构造器：把 final 字段变成构造器参数 + this.x = x 赋值
```

### 阶段 2：启动期（Spring 流水线）

```
SpringApplication.run(FongwellFileApplication.class) 触发
│
▼ ① 扫描注册
   按 @ComponentScan("com.fongwell") 扫包，识别身份注解
   → 每个组件生成 BeanDefinition 登记卡（类名/构造器/依赖/条件）→ 登记表
▼ ② 条件过滤
   读配置 file.storage.type=minio → 只有 Minio 的登记卡保留
▼ ③ 实例化 + 注入（依赖递归）
   遍历登记卡逐个反射 newInstance：
   ├─ new MinioSysFileServiceImpl()（无参）→ 入单例池
   ├─ 建 SysFileServiceImpl：构造器要 ISysFileService → 已存在 → 传入
   ├─ 建 SysFileController：要 6 个依赖 → 逐一解决 → 构造器调用 → 字段赋值
   └─ 先建被依赖者、后建依赖者（递归解析）
▼ ④ 单例池就绪，等待请求（之后所有请求复用同一批对象）
```

### 阶段 3：运行期（一次请求的完整旅程）

```
前端 GET /prod-api/file/upload/checkExists?guid=ab12&scope=0
  ▼ nginx → 网关 → fongwell-file
① DispatcherServlet 映射到 SysFileController.checkExists
② @PreAuthorize("isInternal() or isLogin()") 鉴权（失败 403）
③ iSysFileService.checkExists("ab12", 0)
     → 动态绑定 → Minio 实现方法体
     → 拼 key "common/ab12" → statObject → true/false
④ Controller 分支：
     true  → getFileInfoByGuid（存储元数据 + sys_file 表）→ R.ok(FileInfoVO)
     false → R.ok(null)
⑤ JSON 响应前端：
     有数据 → 秒传（直接用 fileId）
     null   → 分片上传：chunkUpload(逐片) → chunkMerge(合并)
```

## 四、QA 速记卡（复习自测）

| 问题 | 答案要点 |
|---|---|
| 接口没方法体为什么能工作？ | 方法体在 impl/ 实现类；接口只是契约；`Ctrl+Alt+B` 可跳转验证 |
| 没写 new，对象哪来的？ | Spring 启动期反射 new 的，业务代码里省略了 |
| "指向"怎么实现？自动吗？ | 自动。Lombok 生成 `this.x = 参数`；Spring 按类型找实例后反射调用构造器传入 |
| 要实例化哪些类，在哪说明？ | 无集中清单；= 启动类扫描范围 + 类头注解 + 条件注解 + 配置文件 |
| 为什么精确找到 Minio 实现？ | `@ConditionalOnProperty` 保证 5 个实现只创建 1 个，按类型查找无歧义 |
| 换存储要改什么？ | 只改 `file.storage.type` 配置；Controller/Service 零改动（面向接口编程的价值） |
| "检查"逻辑在哪实现？ | Java 侧只拼 key 发请求；是否存在的判断权在 MinIO（statObject 响应） |

## 五、排查速查表 + 读码三步法

### 排查表

| 现象 | 检查点 |
|---|---|
| 403 | @PreAuthorize 表达式、登录态、网关白名单 |
| checkExists 恒 false | bucket 名、scope 与上传时是否一致（目录前缀不同会查不到） |
| 启动报 NoUniqueBeanDefinitionException | 是否有多个实现条件同时满足（应只保留一个） |
| 换存储不生效 | 配置项 + 新实现类 @ConditionalOnProperty 的 havingValue |

### 读码三步法（本项目通用）

```
1. 找入口    → Controller 的 URL 注解方法，看鉴权/日志注解
2. 看契约与实现 → Service 接口 → Ctrl+Alt+B 跳实现类看真正逻辑
3. 追边界    → 实现里调的 Utils/Feign/SDK 即系统边界；数据类跟 import 找模块归属
```

## 核心一句话

**注解声明"我是谁"，扫描生成"登记卡"，条件决定"谁上岗"，反射完成"new 与注入"，多态负责"运行时找对人干活"。** 接口是标签，标签背后那个 Spring 提前实例化的对象才是真正干活的。
