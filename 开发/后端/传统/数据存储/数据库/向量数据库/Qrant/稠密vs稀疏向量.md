# 核心一句话
**稠密向量：每个维度都有浮点数，信息均匀铺开；稀疏向量：绝大多数维度是0，只有少量位置有有效值。**
二者本质是两种不同的信息编码方式，不是检索算法的区别，只是向量本身的数据形态，底层适合的索引、存储、硬件、场景完全不一样。

> 先对齐：
> - 稠密向量（Dense）：`[0.12, 0.44, -0.21, 0.77, ...]`，全部维度都有值，常见768/1024/1536维（BGE、Embedding、LLM出来的）
> - 稀疏向量（Sparse）：`[(12, 0.87), (45, 0.31), (99, 0.52)]`，只存非0维度id+权重，其余全部视为0；典型：BM25、SPLADE、SparseEmbed

## 一、底层差异（直接影响你选 Qdrant / pgvector）
|维度|稠密向量|稀疏向量|
|---|---|---|
|数据形态|固定维度，全部位置存浮点数|极高维度（几万~百万维），仅少量非零|
|存储开销|维度固定，开销稳定；768维 fp32 单条 ~3KB|看非零元数量，维度再大也只存少量坐标|
|索引结构|HNSW、IVF，**靠距离度量（余弦/L2）**|倒排索引（和ES一样），**靠分数累加**|
|计算特点|向量点积是全局运算，吃内存、适合NVMe|只对命中的term做计算，随机访问少，CPU轻|
|Qdrant/pgvector支持|原生完美支持|Qdrant原生sparse vector；pgvector不原生稀疏，要自己用数组/JSON模拟，性能差|

> 重点误区：稀疏 ≠ 低维。SPLADE 经常是 30522 维（BERT词表大小），维度远大于稠密向量，但每条向量只有几十到几百个非零值。

## 二、信息表达逻辑差别
- **稠密向量：语义抽象**
  模型把“含义”压缩进连续浮点数空间。
  同义词、近义词、写法不一样但意思接近，向量距离就近。
  > `苹果手机` 和 `iPhone`，稠密向量很接近。
  缺点：丢失精确词信号；容易出现语义漂移、幻觉相关的召回偏差，无法强制“必须包含某个关键词”。

- **稀疏向量：词级信号 + 弱语义**
  每个维度**对应一个词/子词**，权重代表这个词在文本里的重要程度。
  天然继承关键词匹配能力，同时模型给权重，比纯BM25更懂语义。
  > `苹果手机` 会在“苹果”“手机”两个维度有高分；`iPhone` 在“iphone”维度高分。
  优点：可控、可解释；你能看到是哪些词贡献分数；缺点：泛化弱一点，同义词如果分词不一样就匹配不上。

BM25 其实就是**传统稀疏表征**；SPLADE 是**神经网络稀疏向量**（现在RAG主流稀疏方案）。

## 三、场景怎么选
### ✅ 稠密向量优先场景
1. **跨表述语义检索**：用户口语提问、自然语言，措辞和文档差别很大。
   > 用户问：有没有轻量化向量库，文档标题是轻量 embedding database
2. **多模态检索**：图片、音频、视频embedding，不存在“词”的概念，只能稠密
3. **长文本整体语义匹配、摘要检索、推荐系统**
4. **需要模糊语义匹配，不关心精确关键词**

短板：关键词硬约束很难做；比如你要求召回结果**必须包含“NVMe”**，稠密向量很难保证。

### ✅ 稀疏向量优先场景
1. **关键词强相关检索、企业知识库、文档有专有名词/代码/型号/编号**
   > 技术文档：Qdrant、pgvector、PCIe、NVMe、报错栈、函数名、订单号
   这类专有名词，稠密embedding很容易混；稀疏能牢牢抓住这个词信号。
2. **需要可解释召回**：要告诉用户“这篇文档命中是因为匹配了xxx关键词”
3. **短query、关键词查询为主（类似搜索引擎）**
4. **冷文本、专业术语、低频词**：稠密模型对低频专有词容易编码崩坏

短板：纯稀疏泛化差；用户换个说法、同义改写，召回直接没了。

## 四、工业界标准做法：混合检索（Hybrid Search）
现在成熟RAG几乎都是：**稠密 + 稀疏两路召回，再做RRF/分数融合**
- 稠密：抓语义，解决同义改写、自然问句
- 稀疏：抓精确词、专有名词、标识符，兜底防止关键信息漏召回
- Qdrant 原生支持同时存稠密+稀疏向量，一次查询两路召回融合，这也是它对比pgvector在RAG里一个很大的加分项

举个你熟悉的例子：
> Query：Qdrant mmap 配置在NVMe上怎么调
> - 稀疏：命中 `qdrant`、`mmap`、`nvme` 这些词，保证相关文档不漏
> - 稠密：理解整句话语义，召回讲“磁盘索引、内存映射调优”的文档，而不是只包含这几个词但无关的垃圾文档
