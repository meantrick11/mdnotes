# Runtime / State / 业务变换规则 概念笔记
> 用途：区分通用执行抽象，适配编程语言、容器、Agent框架等场景，便于阅读源码、架构文档、论文。

## 核心概念定义
### State（状态）
仅代表**被处理、被流转、被修改的数据集合**。
- 特性：被动实体，自身不包含执行逻辑；在整个执行生命周期中不断被读取、更新、快照保存。
- 本质：执行过程的“输入‑中间‑输出”全部数据载体。

### 业务变换规则（工件 Artifact）
由使用者定义的一份静态描述，规定**数据应当如何变换、分支走向、调用哪些能力**。
- 特性：只是一份描述/图纸，本身没有执行能力，需要外部引擎加载才可以运行。
- 在不同载体下的形态：源码、字节码、容器镜像、Agent工作流图、节点与边定义。

### Runtime（运行时）
底层执行引擎/整套执行设施。负责加载业务工件，驱动工件执行，读写与维护State完整生命周期。
- 核心职责：调度执行流程、状态读写、异常捕获、重试、快照/恢复、资源与生命周期管理。
- 重要边界：Runtime**不定义业务要做什么变换**，只负责把用户写好的业务规则真正跑起来。
- 区分：写在业务内部的重试、异常捕获属于业务规则；框架底层统一提供的重试、异常处理才属于Runtime。

## 通用概念对照表
|概念|本质|核心特点|
|---|---|---|
|State|被操作的数据载体|被动，只存数据，不会自己执行；可快照、可恢复|
|业务变换规则（工件）|用户定义的静态执行方案|描述“要做什么”；静态图纸，自身无法运行|
|Runtime（运行时）|底层执行设施/引擎|负责“怎么跑起来”；加载工件，调度执行，处理故障与生命周期|

## 以 Python 程序举例对照
1. **State**：变量、对象、栈帧、异常实例等内存数据。
2. **业务变换规则（工件）**：Python源码 / 编译后的字节码。描述业务计算逻辑。
3. **Runtime（CPython运行时）**：字节码解释器主循环、GC、引用计数、异常栈机制、线程管理、内置运行时库。负责执行字节码，管理对象生命周期，抛出并回溯异常。

## LangGraph Agent场景实例对照
1. **State**
Agent会话字典：消息列表、工具返回结果、中间变量、循环标记。全程被节点读取、追加、修改。纯数据，无执行逻辑。

2. **业务变换规则（工件）**
用户编写的Graph定义：各个业务Node、节点之间的边、条件分支逻辑。
> 例如：调用LLM节点、调用工具节点；条件判断：工具结果为空走重查询分支，结果有效直接结束。
> Graph只是静态图定义，不具备自动执行能力。

3. **Agent Runtime（LangGraph内置执行引擎）**
框架内部的执行设施，不随业务改动，负责：
- 加载Graph工件，按图规则调度各个Node依次执行
- 将Node返回结果合并更新回State
- Checkpoint状态快照、会话恢复
- 框架层面配置化重试、超时处理、异常捕获
- 子Agent生命周期管理：派生、等待子任务返回结果、合并子任务State

> 边界示例：
> - 在Graph配置设置`retry=3`：重试逻辑属于Runtime。
> - 在Node函数内部手写`try‑except`与循环重试：属于业务变换规则，不属于Runtime。

## 关键易错总结
1. Runtime不是编程语言专属概念，是通用抽象：WASM Runtime、Container Runtime、Agent Runtime 都遵循这套模型，只是处理的工件类型不一样。
2. 行业文档经常将【业务工件 + Runtime】混在一起统称为XX‑Runtime，阅读时需要在头脑中将二者拆分。
3. State永远是数据；业务规则规定变换内容；Runtime负责驱动整个变换流程落地执行。
