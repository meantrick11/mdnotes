
# Haystack：如何选择 Document Store（文档存储）

> 官方文档：https://docs.haystack.deepset.ai/docs/choosing-a-document-store
>
> 文档版本：Haystack 3.3
>
> 类型：官方文档主要内容中文翻译与整理（非逐字全文翻译）

## 1. 概述

无论开发的是聊天机器人、RAG 系统，还是图像描述生成应用，AI 应用通常都需要将用户输入与已有的知识进行比较，从而找到相关信息。

Document Store（文档存储）是 Haystack 中负责保存文档，并为检索组件提供数据访问能力的重要基础设施。

Haystack 当前支持七大类 Document Store：

1. **向量数据库（Vector Databases）**
   - 专门用于 Embedding 检索和语义搜索。

2. **搜索引擎（Search Engines）**
   - 基于全文搜索构建，并逐渐扩展了向量检索（kNN）能力。

3. **关系型数据库（Relational Databases）**
   - 通过插件或扩展，为传统 SQL 数据库增加向量检索能力。

4. **文档型 / NoSQL 数据库（Document / NoSQL Databases）**
   - 在通用文档数据库基础上增加向量检索功能。

5. **内存键值数据库（In-memory Key-Value Stores）**
   - 提供极低延迟的数据访问，同时支持 HNSW 向量检索。

6. **向量索引库（Vector Index Libraries）**
   - 轻量级、进程内运行的向量相似度搜索工具，无需部署独立服务。

7. **多模型数据库（Multi-model Databases）**
   - 使用同一个数据库引擎支持图、文档、键值和向量等多种数据模型。

## 2. Haystack 的 Document Store 集成

Haystack 的集成分为两个层级。

### 2.1 核心集成（Core Integrations）

由 Haystack 团队开发和维护。

特点：

- 随每个 Haystack 版本进行测试。
- 遵循统一的 API 约定。
- 提供完整的文档和支持。
- 与 Haystack 的发布周期保持一致。

### 2.2 外部集成（External Integrations）

由社区贡献和维护。

特点：

- 扩展 Haystack 对第三方技术的支持。
- 不完全受 Haystack 核心版本发布周期约束。
- 维护质量、更新节奏取决于社区及对应项目。

### 2.3 主要集成产品一览

| 类别 | 核心集成 | 外部集成 |
|---|---|---|
| 向量数据库 | Chroma、Pinecone、Qdrant、Weaviate | LanceDB、Milvus |
| 搜索引擎 | Azure AI Search、Elasticsearch、OpenSearch、Solr、Vespa | Needle |
| 关系型数据库 | AlloyDB、Oracle、PGVector、Supabase | SingleStore |
| 文档型 / NoSQL | Astra、Azure DocumentDB、MongoDB Atlas | Couchbase |
| 内存键值数据库 | Valkey | — |
| 向量索引库 | FAISS | — |
| 多模型数据库 | ArcadeDB、ArangoDB、FalkorDB | Neo4j |

说明：

- 上表依据官方页面的集成分类整理。
- OpenSearch、Qdrant、Weaviate 等支持混合检索。
- PGVector 基于 PostgreSQL 的 pgvector 扩展。
- Neo4j 虽然主要定位为图数据库，但可结合向量索引使用。

## 3. 向量数据库（Vector Databases）

### 3.1 核心特点

- 专门为向量检索和 Embedding 搜索设计。
- 采用高级索引技术，提高相似度检索效率。
- 面向大规模、高维向量数据设计，注重可扩展性与可用性。
- 大多数支持将元数据过滤与向量检索结合使用。
- 越来越多的产品开始支持混合检索（向量检索 + 关键词检索）。
- 多数提供开源版本，也广泛提供托管云服务。

### 3.2 适用场景

适合对大规模文档集合进行语义搜索。

典型案例：

企业知识库检索。

用户输入一个问题，系统并不单纯依赖关键词匹配，而是通过语义相似度查找相关文档。

### 3.3 代表产品

| 产品 | 简要说明 |
|---|---|
| Chroma | 专门用于向量存储和检索 |
| Pinecone | 云托管向量数据库 |
| Qdrant | 支持稠密向量、稀疏向量及混合检索 |
| Weaviate | 支持向量检索及混合检索 |
| LanceDB | 基于 Lance 列式格式的嵌入式向量数据库 |
| Milvus | 面向可扩展相似度检索的开源向量数据库 |

官方链接：

- [Chroma](https://docs.haystack.deepset.ai/docs/chromadocumentstore)
- [Pinecone](https://docs.haystack.deepset.ai/docs/pineconedocumentstore)
- [Qdrant](https://docs.haystack.deepset.ai/docs/qdrantdocumentstore)
- [Weaviate](https://docs.haystack.deepset.ai/docs/weaviatedocumentstore)

## 4. 搜索引擎（Search Engines）

### 4.1 核心特点

- 最初主要为全文检索（例如 BM25）设计。
- 后续增加向量检索（kNN）功能。
- 对文本数据、分词和语言相关查询具有良好支持。
- 在生产环境中支持水平扩展和垂直扩展。
- 非常适合同时结合关键词检索和语义检索。
- 已经在大量企业环境中得到应用，具有成熟的工具链和可观测能力。

### 4.2 适用场景

适合同时需要全文搜索和向量检索的企业级应用。

典型案例：

电商商品搜索系统。

用户可以：

- 使用关键词搜索商品。
- 通过语义查找相似商品。
- 根据价格、品牌等属性进行过滤。

此外，也适用于日志分析与企业搜索系统。

### 4.3 代表产品

| 产品 | 简要说明 |
|---|---|
| Elasticsearch | 分布式搜索与分析引擎，支持 BM25 和向量检索 |
| OpenSearch | 开源分布式搜索引擎，支持 BM25、kNN 和混合检索 |
| Azure AI Search | Azure 托管搜索服务 |
| Solr | 基于 Apache Lucene 的分布式搜索服务 |
| Vespa | 分布式搜索与在线数据服务引擎 |
| Needle | 托管式 RAG 服务，集成文档存储和检索 |

## 5. 关系型数据库（Relational Databases）

### 5.1 核心特点

- 在标准 SQL 数据库的基础上，通过扩展或插件增加向量检索能力。
- 向量数据和关系型数据可以保存在同一个数据库中。
- 支持结合 SQL 查询与向量检索。
- 如果技术栈已经使用 PostgreSQL，可以减少额外的运维负担。
- 向量检索性能通常不如专门设计的向量数据库，但对于很多应用已经足够。
- 保留关系型数据库成熟的事务、数据完整性和管理工具。

### 5.2 适用场景

适合文档数据与结构化关系数据紧密关联的业务。

典型案例：

商品目录系统。

系统同时需要：

- 保存商品的结构化属性。
- 使用 SQL JOIN 查询商品相关关系。
- 使用 Embedding 进行商品语义搜索。

这些能力可以在同一个数据库中实现。

### 5.3 代表产品

| 产品 | 简要说明 |
|---|---|
| PGVector | PostgreSQL + pgvector 扩展 |
| Supabase | 基于 PostgreSQL 的云数据库平台 |
| AlloyDB | Google Cloud 托管的 PostgreSQL 兼容数据库 |
| Oracle | 支持原生 AI Vector Search |
| SingleStore | 支持向量检索和全文检索的分布式 SQL 数据库 |

### 5.4 选型价值

如果现有项目已经采用 PostgreSQL，并且向量检索需求不是特别复杂，那么可以优先考虑 pgvector。

这样能够避免单独引入一套向量数据库基础设施。

但需要结合实际数据规模、索引类型和查询负载进行性能评估。

## 6. 文档型 / NoSQL 数据库（Document / NoSQL Databases）

### 6.1 核心特点

- 在通用文档数据库基础上增加向量检索能力。
- 数据模型灵活，不强制要求固定 Schema。
- 适合存储结构差异较大的文档集合。
- 继承底层 NoSQL 系统的水平扩展和高可用能力。
- 如果项目已经使用某种 NoSQL 数据库，可以减少引入新数据库的成本。
- 向量检索性能可能不如专用向量数据库。

### 6.2 适用场景

适合已经使用 NoSQL 数据库，希望直接增加 RAG 能力的应用。

例如：

某业务系统已经将大量业务文档存放在 MongoDB 中。

如果数据库已经支持向量索引，那么可以在原有系统中加入向量检索，而不必立即部署独立的向量数据库。

### 6.3 代表产品

| 产品 | 简要说明 |
|---|---|
| MongoDB Atlas | 支持向量搜索和全文搜索的云文档数据库 |
| Astra | 基于 Apache Cassandra 的托管 NoSQL 服务 |
| Azure DocumentDB | 兼容 MongoDB、支持多种向量索引 |
| Couchbase | 支持文档管理及向量搜索的分布式 NoSQL 数据库 |

---

## 7. 内存键值数据库（In-memory Key-Value Stores）

### 7.1 核心特点

- 基于内存的数据架构具有极低的读写延迟。
- 在缓存基础设施之上提供 HNSW 向量搜索。
- 适合已经使用 Valkey 作为缓存或会话存储的项目。
- 数据默认具有易失性，持久化需要进行专门配置。
- 当文档集合规模较大时，内存成本可能成为问题。

### 7.2 适用场景

适合低延迟、实时检索系统。

典型案例：

需要极低响应时间的聊天机器人。

### 7.3 代表产品

- Valkey

Valkey 是内存键值数据库，并通过相关搜索能力支持向量检索。

---

## 8. 向量索引库（Vector Index Libraries）

### 8.1 核心特点

- 提供底层、进程内的向量相似度搜索能力。
- 本身不是完整的数据库系统。
- 不需要通过网络访问外部数据库服务。
- 能够有效利用 CPU 或 GPU 资源。
- 主要负责向量索引和相似度计算。
- 元数据通常需要额外存储与管理。
- 不直接提供完整数据库级别的持久化、复制或多客户端访问能力。

### 8.2 适用场景

适合：

- 本地原型开发。
- 算法研究。
- 小规模应用。
- 不希望部署独立数据库服务器的场景。

### 8.3 代表产品

- FAISS

FAISS 是一个专门用于高效向量相似度搜索的库。

需要注意：

**向量索引库与向量数据库并不等价。**

向量数据库通常还包含数据管理、服务化访问、持久化和集群管理等能力。

而 FAISS 更偏向底层的相似度搜索组件。

---

## 9. 多模型数据库（Multi-model Databases）

### 9.1 核心特点

- 一个数据库引擎可以支持多种数据模型。
- 包括图、文档、键值和向量等。
- 减少为不同数据模型分别维护数据库的需求。
- 适合知识图谱以及复杂实体关系场景。
- 可以将图关系遍历与向量搜索相结合。
- 相较于一些传统数据库类别，生态和社区规模可能较小。

### 9.2 适用场景

适合需要在单一数据库中管理多种数据模型的应用。

典型案例：

知识图谱系统。

系统不仅需要：

- 保存实体和实体之间的关系。
- 根据实体关系进行图遍历。
- 通过向量相似度搜索查找相关实体。

还希望将这些能力结合在一个数据库引擎中。

### 9.3 代表产品

| 产品 | 简要说明 |
|---|---|
| ArangoDB | 支持图、文档、键值及向量检索 |
| ArcadeDB | 支持多种数据模型及 HNSW 向量检索 |
| FalkorDB | 基于 OpenCypher 的图数据库，支持向量检索 |
| Neo4j | 图数据库，支持图遍历与向量相似度搜索 |

## 10. Haystack 内置的 InMemoryDocumentStore

除上述七大类别之外，Haystack 还提供了特殊的内存文档存储：

`InMemoryDocumentStore`

### 10.1 主要特点

- 基于 Python 内存数据结构。
- 不需要额外部署数据库服务。
- 无需安装额外的数据库依赖。
- 数据保存在当前程序的内存中。
- 适合少量数据和快速原型开发。

### 10.2 适用场景

适合：

- 学习 Haystack。
- 快速验证 RAG 流程。
- 小数据集实验。
- 开发初期的功能测试。

它不属于上述任何一种专门的向量数据库类别。

## 11. 最终选型建议（Final Considerations）

官方强调：

**不能仅仅根据基准测试中的性能排名选择 Document Store。**

原因包括：

1. 不同基准测试可能使用完全不同的运行环境。
2. 有些测试针对云服务，有些使用固定的本地测试机器。
3. 是否包含元数据过滤等能力，会影响测试结果。
4. 微小的测试条件差异也可能导致性能排名变化。

因此，单纯比较吞吐量和延迟，并不足以决定哪种存储方案最好。

### 11.1 Haystack 的额外开销

Haystack 的 Document Store 接口本身不会增加太多额外成本。

不同向量数据库在独立运行时的相对性能表现，在接入 Haystack Pipeline 后通常仍会保持相近的相对关系。

### 11.2 选型结论

应结合实际业务需求进行选择，包括：

- 当前技术栈。
- 数据结构。
- 检索方式。
- 数据规模。
- 部署与运维成本。
- 性能需求。
- 是否需要混合检索。
- 是否需要复杂关系查询。

## 12. 七大类型对比速查

> 本节为辅助理解而整理的归纳表，并非官方原文表格。

| 类别 | 核心优势 | 主要限制 | 代表产品 |
|---|---|---|---|
| 向量数据库 | 专业语义检索、向量索引能力 | 可能增加基础设施成本 | Qdrant、Milvus、Chroma |
| 搜索引擎 | 全文检索、混合检索成熟 | 部署和配置可能较复杂 | ES、OpenSearch |
| 关系型数据库 | SQL 与向量数据统一管理 | 大规模专用向量检索未必最优 | PostgreSQL + pgvector |
| 文档型数据库 | 灵活 Schema、兼容已有 NoSQL 业务 | 向量能力依赖具体产品 | MongoDB Atlas |
| 内存键值数据库 | 极低访问延迟 | 内存成本、持久化配置 | Valkey |
| 向量索引库 | 轻量、高效、易于嵌入 | 缺少完整数据库服务能力 | FAISS |
| 多模型数据库 | 图、文档、向量统一管理 | 技术生态及复杂度存在差异 | ArangoDB、Neo4j |

## 13. 如何根据需求选择？

> 以下为工程实践补充，不属于官方原文。

| 业务场景 | 可以优先评估 |
|---|---|
| RAG 入门与小规模实验 | InMemoryDocumentStore、Chroma |
| 已经采用 PostgreSQL | PGVector |
| 专业语义检索服务 | Qdrant、Milvus、Weaviate |
| 关键词 + 语义混合检索 | Elasticsearch、OpenSearch、Qdrant |
| 已有 MongoDB 业务系统 | MongoDB Atlas |
| 极低延迟检索 | Valkey |
| 本地向量检索实验 | FAISS |
| 知识图谱 + 向量检索 | Neo4j、ArangoDB |

**核心原则：先明确业务需要怎样检索，再决定使用哪类存储，而不是先选择数据库。**

## 14. 相关概念

- **Document Store**：文档存储的抽象接口或具体实现。
- **Embedding**：将文本等数据映射为向量表示。
- **Vector Search**：根据向量相似度查找相关数据。
- **BM25**：基于词项匹配和统计信息的文本相关性排序算法。
- **kNN**：寻找与查询向量距离最近的 k 个向量。
- **ANN**：近似最近邻搜索，通过一定程度的近似换取检索效率。
- **HNSW**：一种常见的基于分层图结构的近似最近邻索引算法。
- **Hybrid Search**：结合多种检索策略，常见形式为关键词检索与向量检索相结合。
- **Metadata Filtering**：在检索时根据文档属性进行条件过滤。
- **Retriever**：Haystack 中负责从 Document Store 检索相关文档的组件。
