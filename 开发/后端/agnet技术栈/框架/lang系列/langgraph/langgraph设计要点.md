# LangGraph 基础介绍：从设计理念到底层运行机制

## 一、为什么需要 LangGraph

LangChain 最初的设计哲学是基于有向无环图的"链式调用"：输入 → 提示词模板 → 模型 → 输出解析器。这种线性的流处理非常适合简单的问答或 RAG 应用，但随着应用向"智能体"进化，线性的链式结构变得捉襟见肘——智能体需要循环（不断调用工具直到任务完成）、需要根据结果回退、需要复杂的条件分支。

LangGraph 正是为解决这些问题而生。它不是对 LangChain 的简单修补，而是一次重新设计。LangChain 团队在设计 LangGraph 时确立了核心原则：**不预设 AI 的未来形态，做尽可能少的假设，专注于控制（Control）和持久性（Durability）** 。他们从实际生产经验中提炼出智能体的三大特征：延迟高、重试代价大、非确定性需要检查点和审批机制，这些特征直接决定了 LangGraph 的底层设计。

在此基础上，LangGraph 的设计遵循两个关键原则：**可控性优先**——开发者精确定义每一条执行路径，而非完全依赖 LLM 自主决策；**状态显式化**——所有中间状态可检查、可持久化、可回滚。

理解了"为什么要造这个工具"，接下来就可以进入它的核心——状态。


## 二、状态：LangGraph 的核心设计

### 2.1 状态的本质与设计初衷

状态是 LangGraph 最核心的概念。它代表应用当前快照的共享数据结构，由图的 Schema 以及指定如何将更新应用到状态的 reducer 函数组成。

设计状态的初衷源于一个根本问题：**在多步骤的智能体工作流中，数据需要在不同节点之间共享和流转，而每个节点都会对数据产生修改。如果没有一个统一的状态载体，节点之间的协作将变得极其混乱。** 因此，LangGraph 将状态设计为贯穿整张图的共享数据结构，所有节点都接收状态作为输入，并返回对状态的更新。在 LangGraph 中，状态对象充当运行期间的短期记忆。

### 2.2 状态的多种定义方式

LangGraph 对状态的 Schema 定义提供了灵活的选项，开发者可以根据需求选择不同的方式：

**TypedDict** 是最常用的方式，轻量、性能最优。它本质是一个类型化的字典，节点通过键名访问状态字段。适合大多数场景，尤其是内部状态管理。

**Pydantic 模型** 提供运行时验证和类型强制转换，适合需要严格数据校验或复杂嵌套结构的场景。它的代价是额外的验证开销，因此通常建议在图的边界（如用户输入/输出）使用 Pydantic，而内部节点间流转使用 TypedDict。

**dataclass** 也受支持，适合偏好标准库风格的开发者。

无论选择哪种方式，State 的 Schema 都会作为图中所有节点和边的输入 Schema，这意味着一套类型定义贯穿全图，保证了数据流转的一致性。

### 2.3 Reducer：状态更新的核心机制

状态设计中最精妙的部分是 **Reducer**。当多个节点向同一个状态键写入数据时，如何合并这些更新？Reducer 正是回答这个问题的函数。

每个状态键都可以拥有自己独立的 reducer 函数，控制节点更新如何应用到状态上。**如果未显式指定 reducer，默认行为是覆盖**——即新值直接替换旧值。

LangGraph 提供了几种常用的 reducer 模式：

- **默认覆盖**：适合存储单一权威值的字段，如意图、状态标记等。例如一个 `intent` 字段，每次更新都应该直接替换旧值。
- **`add_messages`** ：专为消息型工作流设计，将新消息追加到列表中，同时支持根据消息 ID 更新已有消息和删除消息。
- **`operator.add`** ：用于累加型字段，如总计数、日志等。
- **自定义 reducer**：开发者可以定义任意合并逻辑。例如一个列表合并函数，去除重复项同时保持顺序。

Reducer 的设计使状态管理既灵活又可控。例如，对话历史需要累积（使用 `add_messages`），而当前步骤的意图判断只需保留最新值（使用默认覆盖），这两者在同一个状态 Schema 中可以共存。

### 2.4 输入/输出 Schema 分离

LangGraph 还支持为图定义独立的输入 Schema 和输出 Schema，使外部 API 更加清晰。内部状态可以包含节点间流转所需的全部字段，而输入和输出只暴露必要的字段。这种设计模式使得图的内部实现细节可以被封装，对外呈现简洁的接口。

### 2.5 状态在运行时的真实形态：Channel

理解 Reducer 之后，还需要回答一个更底层的问题：**状态在运行时究竟以什么形态存在？多个节点同时写入时，如何保证不出乱子？**

答案是：你定义的 State Schema 在编译时，**每一个键都会被编译成一个独立的 Channel（通道）** 。这是 LangGraph 最底层的设计之一，也是理解其运行时的关键。

可以把 Channel 想象成状态中每个键的"专属邮箱"。State 不是一块统一的白板，而是一组独立邮箱的集合。一个节点返回 `{"value": 6}`，Pregel 引擎就像邮差一样，把 6 精准投递到名为 `value` 的邮箱里；另一个节点读取状态时，引擎从对应的邮箱取出当前内容。

每个 Channel 都有自己的**类型**，决定了更新的行为规则。LangGraph 内置了几种核心 Channel 类型：

- **LastValue（默认）** ：只保留最后一次写入的值。对应默认的"覆盖"更新行为。
- **Topic（发布/订阅）** ：可以累积多个值，支持去重。`add_messages` 本质上就是 Topic 通道的一种特化实现。
- **BinaryOperatorAggregate**：通过二元运算符（如 `operator.add`）将新值聚合到当前值上，适合累加型字段。
- **Context**：管理外部资源的生命周期，如数据库连接。

**为什么这个设计重要？** 因为它从根本上解释了并行安全的问题。当同一个超级步内两个节点并行执行并分别向 `value` 和 `messages` 写入时，它们**操作的是完全不同的 Channel**，互不干扰。这正是 LangGraph 能在超级步中安全并行执行多个节点的底层保障。之前提到的"Reducer"概念，在运行时层面其实就是"Channel 的更新函数"。

理解了状态及其运行时形态，接下来看状态如何被节点和边组织成一张图。


## 三、节点与边：图的构建单元

### 3.1 节点：执行逻辑的载体

节点是 LangGraph 的最小执行单元，本质是接收当前状态作为输入、执行计算或副作用、返回更新后状态的函数。节点可以封装大模型推理、工具调用、结果审核、数据解析等各类业务逻辑。

关键的设计决策是：**节点和边本质上不过是函数，它们可以包含 LLM，也可以只是普通的代码**。这种"无抽象"的设计意味着开发者不会被框架的约定所束缚，可以用最自然的方式编写业务逻辑。

### 3.2 边：控制流转的规则

边决定了节点之间的执行顺序，分为两种类型：

**固定边**是最简单的形式，表示从一个节点到另一个节点的固定转换，类似于流程图中的箭头。

**条件边**则是 LangGraph 超越传统编排工具的关键特性。它是一个读取当前状态、返回目标节点标识的函数。条件边可以根据状态中的任意字段进行路由判断，例如根据风险评分路由到不同的处理分支。条件边的设计使得图能够表达复杂的业务逻辑分支，而不需要将判断逻辑硬编码到节点内部。

### 3.3 编译：从定义到可执行

在定义完状态、节点和边之后，需要调用 `.compile()` 方法将图编译为可执行对象。编译过程会进行基本的结构检查，如确保没有孤立节点等，同时也可以在此阶段指定运行时参数，如检查点保存器和断点。编译也是 State Schema 被转换为 Channel 的时刻。

### 3.4 超越普通边：Send 与 Command

在真实的多智能体、Map-Reduce 场景中，**边的数量和目标在编译时可能是未知的**。LangGraph 为此提供了两个超越普通边的控制流原语。

**Send：动态生成并行分支**

典型场景是 Map-Reduce：一个节点生成了一个列表（比如 10 个待处理的子任务），你需要对这 10 个对象分别执行同一个下游节点。问题在于——**编译图的时候，你不知道会有几个对象，所以无法预先定义固定数量的边。**

`Send` 解决这个问题。你可以在条件边中返回一组 `Send` 对象，每个 `Send` 携带目标节点名称和要传递的状态。运行时引擎收到这些 `Send` 后，会**动态地为每一个生成一个独立的下游执行实例**，它们属于同一个超级步，并行执行。

**Command：同时完成状态更新和路由跳转**

普通节点只能返回状态更新，条件边只能负责路由判断，两者是分离的。但有些场景下，**一个节点既需要更新状态，又需要决定下一步跳转到哪个节点**——最典型的就是多智能体系统中的"交接"（Handoff）：Agent A 完成任务后，需要把结果写入状态，同时把控制权移交给 Agent B。

`Command` 对象可以同时携带 `update`（状态更新）和 `goto`（目标节点），从节点函数中直接返回。它本质上把"状态更新"和"控制流转"两个动作合并到了一个原语里。

**它们的共同意义是什么？** 它们让 LangGraph 的图从"静态拓扑"变成了"运行时动态展开的拓扑"。编译时的图定义了**可能**的路径，而 Send 和 Command 让运行时可以**创造**路径。

图定义好了，那么它在运行时究竟是如何被驱动的？


## 四、运行时机制：Pregel 与超级步

### 4.1 Pregel 计算模型

LangGraph 的底层运行时基于自研的 Pregel 引擎，其核心思想借鉴了 Google 的 Pregel 大规模图计算系统。Pregel 将执行者（actors，即节点）和通道组合成一个应用程序：执行者从通道读取数据并向通道写入数据，通道则用于在节点之间进行通信。

这个架构的核心组件包括：**Pregel** 作为高层编排器，负责驱动整体迭代执行；**_loop** 管理超级步的迭代流程；**_algo** 在每个超级步内应用状态更新并确定下一批要执行的任务；**_runner** 负责具体节点的执行调度。这种清晰的分层设计确保了运行时的高效和可扩展。

### 4.2 超级步：同步并行的执行单元

超级步是 LangGraph 执行模型中最具特色的概念。程序的运行分为离散的"超级步"，每个超级步可以被视为对图节点的一次迭代。

超级步的执行逻辑如下：

1. **激活判断**：图开始执行时，所有节点处于非活动状态。当节点在任何入边上收到新消息时，它变为活动状态。
2. **并行执行**：在同一个超级步内，所有活动节点并行执行各自的函数。**并行运行的节点属于同一个超级步，而串行运行的节点属于不同的超级步**。
3. **状态更新**：活动节点运行函数后返回更新，这些更新通过 reducer 函数合并到全局状态中。
4. **终止判断**：在每个超级步结束时，没有收到新消息的节点将自己标记为非活动状态。当所有节点都处于非活动状态且没有传输中的消息时，图执行终止。

**超级步的划分完全自动化，由图的拓扑结构决定，不可手动配置**。这意味着开发者只需定义节点和边的连接关系，并行执行由运行时自动优化。如果希望最大化并行度，只需从同一个父节点连接多个独立的子节点，它们会自动在同一个超级步中并行执行。

这种批量同步并行模型的价值在于：它在保证状态一致性的前提下实现了最大程度的并行化。每个超级步开始时，所有节点看到的是同一份状态快照；每个超级步结束时，所有更新被统一合并。这消除了数据竞争的风险，同时充分利用了并行计算的性能优势。

### 4.3 Pregel 引擎的三阶段执行模型

超级步的概念描述了"节拍"，而每个节拍内部到底发生了什么，由 Pregel 引擎的三个严格阶段来定义：

**第一阶段：计划（Plan）** 。引擎检查所有 Channel 的版本变化，确定哪些节点订阅了发生变化了的 Channel，将这些节点标记为"本轮要执行"。

**第二阶段：执行（Execute）** 。所有被选中的节点并行执行。关键约束是：**在此阶段，任何节点对 Channel 的写入对其他节点都不可见**。节点只能读取超级步开始时的那份状态快照。这消除了数据竞争。

**第三阶段：更新（Update）** 。所有节点执行完毕后，引擎收集它们写入 Channel 的值，按照每个 Channel 定义的更新规则（即 Reducer）统一应用。更新完成后，Channel 的版本号递增，触发下一轮"计划"阶段的判断。

这个"计划 → 执行 → 更新"的三段式循环，正是**批量同步并行（Bulk Synchronous Parallel）** 模型的具体实现。它也是 LangGraph 实现容错的基础：如果在"执行"阶段某个节点失败了，该超级步中已经成功完成的其他节点的写入会被保存为"挂起写入"（Pending Writes），从该超级步恢复时无需重新运行已成功的节点。

运行机制保证了图能正确执行，但要让它在生产环境中真正可靠，还需要持久化。


## 五、持久化与检查点：让"有状态"真正落地

Checkpointer 在每个超级步边界保存一个完整的图状态快照，以 `thread_id` 为标识组织。它的作用远不止"保存进度"：

- **人机协作（Human-in-the-Loop）** ：`interrupt()` 函数可以在节点执行过程中暂停图，将当前状态持久化，并等待外部输入。恢复时通过 `Command(resume=...)` 将人工输入注入回 `interrupt()` 调用点，继续执行。没有 Checkpointer，中断就无法工作，因为暂停后状态会丢失。

- **时间旅行（Time Travel）** ：由于每个超级步都有完整快照，你可以通过 `get_state_history()` 浏览整个执行历史，从任意检查点恢复，甚至**分叉**出一条新的执行轨迹——就像 Git 的 branch 一样。

- **容错执行**：结合前面提到的"挂起写入"，Checkpointer 让长时运行的任务在失败后可以从最近的成功超级步恢复，而不是从头重来。

**理解要点**：Checkpointer 不是可选的"附加功能"，它是 LangGraph 许多核心能力的**前置条件**。中断、时间旅行、跨会话记忆，都建立在检查点机制之上。

至此，单张图的完整生命周期已经清晰。但 LangGraph 的能力不止于单张图——它支持图与图的嵌套组合。


## 六、子图：图的可组合性

LangGraph 的图可以嵌套。一个编译好的图可以**直接作为另一个图的节点**使用。这为构建多智能体系统提供了结构化的方式：每个智能体可以是一个独立的子图，拥有自己的状态 Schema 和内部逻辑；父图负责协调多个子图之间的通信和流转。

子图与父图通信有两种模式：**共享状态键**时，编译好的子图可以直接 `add_node` 作为节点，读写父图相同的 Channel；**状态 Schema 不同**时，用一个包装函数在调用子图前转换状态，返回后再转换回来。

这种设计让 LangGraph 具备了**分形架构**的能力：大系统由小系统组成，每个小系统又是完整的图。这也是 LangGraph 构建多智能体 Supervisor 模式的基础。


## 七、整体设计理念的回顾

回顾 LangGraph 的完整设计，可以提炼出几条贯穿始终的理念：

**低抽象、高控制**。LangGraph 刻意不提供过多的高级抽象，而是让开发者通过状态、节点、边这三个基本元素精确控制每一步的执行逻辑。这与那些试图"猜测"开发者意图的框架形成了鲜明对比。

**状态为中心**。状态不是附属品，而是整个系统的核心。图的拓扑结构、节点的输入输出、超级步的同步机制，都围绕状态展开。更准确地说，状态在编译后被拆解为 Channel，由 Pregel 引擎在超级步的节拍下驱动，通过 Reducer 安全地合并更新，通过 Checkpointer 获得持久性，通过 Send/Command 获得动态性，通过子图获得可组合性。

**生产级可靠性**。从 Pregel 引擎的超级步机制到检查点持久化，LangGraph 的每一项设计都考虑了生产环境的需求：延迟管理、故障恢复、人机协作审批。

**循环与条件分支的原生支持**。与仅支持 DAG 的框架不同，LangGraph 原生支持循环，这对于 LLM 工具调用循环（模型反复调用工具直到决定停止）至关重要。

LangGraph 用一张图、一个状态、一套超级步机制，构建了一个既能表达复杂智能体逻辑、又能保证生产级可靠性的运行时框架。它的设计哲学可以概括为一句话：给开发者足够的控制力，让框架做最少但最正确的事。


## 八、建议的学习路径

如果你要系统性地理解 LangGraph 的架构和运行机制，建议按这个顺序推进：

**第一步：建立心智模型**。理解 State / Node / Edge 三要素，理解"节点干活、边指路"的基本隐喻，跑通一个最简单的线性图。

**第二步：理解状态的运行时形态**。重点理解 Channel 的概念——状态键在编译后变成 Channel，Reducer 是 Channel 的更新函数。这是理解并行安全和 Reducer 设计的分水岭。

**第三步：理解执行模型**。掌握超级步、Pregel 三阶段循环、批量同步并行。理解"为什么并行节点属于同一个超级步"以及"节点如何被激活和终止"。

**第四步：掌握控制流原语**。在条件边的基础上，学习 Send（动态并行）和 Command（状态更新 + 路由跳转），理解它们解决的是"编译时未知拓扑"的问题。

**第五步：引入持久化**。理解 Checkpointer 的工作方式，以及它如何解锁中断、时间旅行和容错。

**第六步：向上组合**。学习子图、多智能体模式，以及流式输出如何贯穿整个执行过程。

这六个步骤对应着同一个问题的不同侧面：**LangGraph 的"状态中心"设计到底意味着什么？** 把这六个层面串联起来，LangGraph 的架构才算真正完整。
