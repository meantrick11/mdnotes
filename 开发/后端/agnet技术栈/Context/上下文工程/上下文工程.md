# Context Engineering

## 什么是上下文工程？

**上下文是提供给LLM的用于完成下一步推理或生成任务的全部信息的集合**,其中包括：

- Instructions/Systemo Prompt
- User Prompt
- State/Current chat history
- Long-term Memory/Short-term Memory
- Retrieved Information/RAG
- Available Tools(Tools' output)

以下给出具体分类：
1. **指导性上下文**：这类上下文的核心功能是**知道模型该做什么以及如何做？**，主要为模型行为设定框架和规则，**Prompt Engineering一般旨在优化指导性上下文**它包括:Sytem Prompt,user Prompt(Task Description\Examples\output schema)
2. **信息性上下文**：这类上下文的核心功能是告诉模型需要知道什么信息，为推理所具备的事实，数据&知识，包括RAG,Memory(shot/long-term memory),State等
3. **行动性上下文**，这类上下文核心告诉模型能做什么以及做了之后的结果，为模型提供外部为世界交互的能力，比如Tool Definition,Tool Calls &Results/Tool traces

以下给出Context Engineering的定义：**Context Engineering 是一门系统性学科，专注于设计、构建并维护一个动态系统，该系统负责在 Agent 执行任务的每一步，为其智能地组装出最优的上下文组合，以确保任务能够被可靠、高效地完成。**

## 为什么需要上下文工程？

1. **模型能力的局限**：基座模型自身的能力不足，需要对模型本身优化，(Context Window，长输入导致transformer注意力稀疏等问题)
2. **上下文缺失**：模型没有生成高质量回复所需要的上下文，比如缺乏工具的参数定义，结果输出规范等等

如果无上下文工程，那么针对LLM窗口有限，却不断向对话中添加新的历史记录，那么会导致
1. **性能下降**：早期无关紧要的信息会稀释当前核心信息的注意力，造成**上下文扰动**
2. **成本和延迟激增**：随着上下文的线性增长，每次API调用的Token数量急剧膨胀，造成成本失控和更高的延迟
3. **最终崩溃**：最终系统撞上模型限制--**上下文溢出**，导致API调用失败、任务中断，输出质量大大降低等情况

## 什么是上下文退化？

除了上下文暴增带来的成本和协同压力外，更暴露出了四类上下文失效：
- **上下文污染**：主要是幻觉进入Context导致异常结果
- **上下文扰动**：当Context接近溢出时，模型训练中获得的知识会被"覆盖"，导致模型降智
- **上下文混淆**：冗余不相关的Context让输出结果偏离期望
- **上下文冲突**：当上下文中信息相互矛盾时，比如上下文存在过去错误的答案

## 上下文工程的最佳实践

业界已经有了一套系统性的应对框架，将上下文工程分为四个部分：写入、选取、压缩和隔离，每一个部分都有很多细节可以深挖，这里只简略概述
写入（Write）

1. **写入**主要是将 上下文持续久化，超越上下文窗口的限制，在未来按需取用。通常情况下分为：

会话内写入 (Session-level Write): Agent 将中间思考、计划或临时数据写入一个会话内的草稿纸 (Scratchpads)。这是一种轻量级的、非持久化的写入，用于管理当前任务的复杂性。
持久化写入 (Persistent Write): 系统将具有长期价值的信息（如用户偏好总结、关键事实）写入外部的记忆 (Memory) 系统，如向量数据库或知识图谱。这实现了跨会话的知识积累。例如，ChatGPT 和 Cursor 等应用通过这种方式，让 Agent 在与用户的持续交互中“学习”和“成长”，用户在解决某些问题时无需手动引入上下文。
Anthropic 也曾在博客中建议，Subagent output to a filesystem to minimize the ‘game of telephone.’ 通过把 subagent 的输出写到文件以避免无意义的上下文传递，上下文窗口占用等。

2. **选取（Select）**
选取的目的，是在每次 LLM 调用前，从所有可用的信息源中，动态地拉取与当前子任务最相关的信息。这是保证上下文信噪比的关键。

上下文工程的中的选取包括三类：

- 确定性选取 (Deterministic Select): 指根据预设规则加载上下文。例如，编码 Agent （Claude Code）在启动时，固定加载 项目根目录下的 CLAUDE.md 文件，这是一种简单高效的先验知识注入。
- 模型驱动选取 (Model-driven Select): 当可用信息源过多时（如海量工具或文档），可以利用模型自身的能力进行筛选。
- 检索式选取 (Retrieval-based Select): 这是最主流的方式，其核心范式是通过相似度检索，从记忆、草稿纸或外部知识库中选取信息。因此，选取操作的成败，在很大程度上依赖于底层检索系统的质量。

3. **压缩（Compress）**

压缩的目的，是在信息进入上下文窗口之前，对其进行有损或无损的压缩，用更少的 Token 承载最核心的信号。 这是在上下文窗口容量有限的情况下，容纳更多有效信息的直接手段。
- 比如让agent自动执行"auto-compact"在上下文快要溢出的时候让它自动总结Context保留"它一位最重要的部分",
- 另有修剪策略：如硬截断超限历史，代价是失去部分语境。

4. **隔离（Isolate）**

相较于前三个在“信息流”内部进行优化的原则，隔离是一种在系统架构层面进行的、更根本的上下文管理策略。隔离的目的，在多信息流之间设置边界，由子流程先行消化，仅上交要点。可视为跨流层面的‘压缩’。

在多智能体系统中，子智能体扮演了“智能过滤器”的角色。它们在各自的领域内隔离且并行工作，消化大量原始信息，然后将最关键的“压缩后”的洞见（the most important tokens）提交给主智能体。这种方式也减少了主智能体的上下文窗口消耗，是另一种良好的实践。

>压缩 vs 隔离 的思考
>- 压缩作用于单一信息流的内容，旨在提升其内在的信息密度。
>- 隔离则作用在多条信息流上，旨在管理系统的复杂性，同时也能起到广义的压缩作用。
>它们的目的，在我看来殊途同归，最终都是为了提升 Context 中的信息密度。一个成熟的系统，往往会同时运用这两种策略。
