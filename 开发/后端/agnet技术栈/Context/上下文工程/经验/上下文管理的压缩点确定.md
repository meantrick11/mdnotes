# 上下文管理

## 为什么需要上下文管理

### 模型架构问题
**模型的transformer决定了必须要在有限的窗口中放入适合推理的有效信息：**
1. **自注意力机制决定了队头队尾效应**（中间注意力稀释）
2. 自注意力机制的计算时间复杂度为O(n^2),太长则会**计算时间暴涨**
3. 由于上述缺点，位置编码也不可能无限增长，所以**位置编码也有限制**
### 工程与经济问题
1. **KV Cache的显存墙（GPU VRAM限制）**：实际部署中，显存占用比计算时间更早成为瓶颈。推理时，模型需要为所有历史token缓存Key-Value矩阵（KV Cache）。这个缓存大小是 O(n × 层数 × 隐藏维度) 的，且随batch size倍增。——当上下文达到100万token时，单次推理的KV Cache可能占用几十GB显存。如果不压缩，即使计算时间能忍，GPU直接Out of Memory（OOM），推理服务根本跑不起来。
2. 如果执行长任务始终不压缩，则**token数会暴增，经济成本暴涨**，且由于信息噪音等原因，模型表现力还可能下降
3. **首字延迟（TTFT）过长**：O(n²)复杂度意味着Prompt越长，模型生成第一个字的等待时间越长（Pre-fill阶段耗时）。用户无法忍受Agent思考10分钟才吐出第一个字，压缩是为了保住用户体验的基本底线。

### 语义/注意力稀释问题

1. 从语义层面看，长上下文中往往充斥着大量的工具返回结果（如爬取的网页源码、几十行日志、冗长的API响应）。这些内容**噪声远大于信号**。
2. **“规划能力”随上下文膨胀而退化**，当上下文塞满细枝末节的对话历史和工具结果时，模型会陷入“只见树木，不见森林”的困境，它的推理链（CoT）会变得混乱，频繁做出短视的错误工具调用。
3. 跨段落的“长程依赖”推理失败
位置编码虽然有限制（你提到的第3点），但即使模型支持1M上下文（如Gemini），实测发现在中间位置（~50%-70%）的事实召回准确率会从90%骤降到不足40%（即“迷失在中间”现象）。压缩通过摘要将分散在100页中的证据融合成3句话，反而能帮助模型跨段落地建立起逻辑关联。

### Agent 特有的状态管理难题
1. **工具调用结果的结构化污染**
Agent的上下文包含大量结构化数据（如JSON Schema、代码块、坐标点）。这类数据对压缩算法（如简单的字符串截断）极其不友好——截断一个JSON的大括号或数组，会导致模型解析失败。因此压缩点必须避开这些“结构性高密度”区域，这远比单纯压对话复杂。
2. **“压缩时机”与“工具执行状态”的耦合**
当Agent处于多工具并行调用或连环依赖调用（Tool A的输出是Tool B的输入）的中间状态时，绝对不能压缩！如果强行压缩，会打断中间变量的暂存。这就是为什么实际工程中必须配合“工具结果暂存区”（如单独的记忆池）来协调，压缩只动历史对话，不动当前活跃的工具上下文。

整体来讲，由于底层的transformer架构，模型不能无限制的增长窗口，加上其他种种因素。所以需要进行上下文管理，在有限的上下文窗口中尽可能放入适合完成任务（长任务/当前任务）的信息(有可能需要保存高密度的对话历史/工具调用结果等等，如何做取舍)，使得Agent能更好的完成用户的请求/任务。

## 当前的问题的确定

当前问题是当前的token数量超过某一个阈值(上下文窗口的80%？)，如何正确的压缩?对于基础的sys\tool_difine+tool_result必须字段必须保留，然后对分割点（硬性的token确定分割点？还是动态的任务确定，比如当前任务/用户请求开始，很久之前的其他任务自然要压缩？交割LLM进行自我判断？）


**如何保证在合理压缩的情况下能够最大程度地不影响后续/长任务/当前任务的连贯性？**

## 压缩点的确定

#### 单阈值点压缩

80%是一个经验性的行业共识，并非模型厂商的硬性规定，而是长期实践沉淀下来的最佳平衡点。

太早(50%)->频繁压缩，每次都会丢失信息，模型反复丢失上下文信息，影响任务连贯性

太晚(95%)->压缩本省要求LLM进行做摘要，摘要请求本身也要求消耗token，如果剩余空间不够发摘要请求，发生死锁

80% -> 留出20%的余量给压缩操作本身(压缩提示词)+下一轮对话的空间，较为合理

#### 双阈值点压缩


// 典型的双阈值配置
tokenThreshold: 0.8,    // 80%时触发常规压缩
hardCapThreshold: 0.95, // 95%时强制压缩（安全兜底）

有的甚至设计了三级压缩策略：70%时仅记录日志监控，80%时触发压缩，95%时强制安全兜底。也有框架采用更激进的50%阈值，或更保守的85%，具体取决于你的任务对信息密度的敏感度。

**这个n%需要根据模型的能力，Agent的具体应用场景进行测试，最终确定符合特定任务场景的n%，比如代码agent可能在70%就要压缩了，防止下次加载进来大量代码，聊天可能85%等等**

#### 当前剩余预算 or 剩余显存动态决定压缩

剩余预算就是之前的token剩余预算，而剩余显存则是根据cache等的具体物理瓶颈进行动态决定是否压缩

### 压缩策略

既然找到何时决定压缩，那么怎么进行压缩？是对固定的message，比如前10条之前的历史直接压缩还是让LLM自己决定压缩动态message之前的？硬性截断n token之前的？

1. 硬性保留：
    - 保留头部(sys-prompt+tool_define+固定的其他内容)
    - 保留尾部(最近的n(3-10)条/轮消息，确保当前任务/短期记忆的连贯性，不完全割裂当前任务+本轮工具调用的输出等等，必要内容)
2. 中间部分
除了头部必要内容+尾部内容以外的历史消息(user+assistant+tool(如果assistant中已经有了，则无需))交给LLM生成摘要来替代原始内容

3. 前置优化：
在调用LLM做摘要之前，可以先做一轮不走LLM的字符串截断——比如工具调用返回的write_file内容体量很大但后续几乎没人再看，直接截断可以省掉一次昂贵的摘要调用。

4.  高阶方案：让Agent自主决策
LangChain的Deep Agents等最新框架已经支持让Agent自己决定何时压缩。Agent通过manage_context工具主动触发压缩，将原始内容保存到外部存储，后续需要时再通过query_memory回查。这种方式比固定阈值更智能，能避免在"复杂重构中途"等糟糕时机压缩。

### 对任务的影响

无论怎么做压缩，多多少少都会丢失一些信息，所以尽可能减少影响任务/后续可能会用到的信息的缺失。以下一些可用缓解措施：

|措施	|说明|
|---|---|
|保留最近N轮原文|	确保模型"还记得刚才在做什么"|
|头部保护|	系统指令和初始任务目标永不压缩|
|分层摘要（Tiered Summary）|	多级摘要层叠，避免单次摘要过于粗糙|
|外部存储 + 按需回查|	压缩后的原始内容存入外部存储，需要时可查询恢复|
|避免过于频繁压缩|	频繁压缩会频繁破坏缓存、增加成本|
|压缩后验证|	压缩后询问Agent关键事实，验证是否正确保留|


## 小总结
压缩点：80%是行业默认值，留20%给压缩操作本身；实际工程常用"80%触发 + 95%强制"双阈值。

压缩策略：不是简单的"LLM判断 vs 硬截断"二选一，而是头部+尾部硬性保留，中间部分由LLM摘要，并可前置轻量截断优化。

任务连贯性：压缩确实会影响连贯性，但通过保留最近对话、保护系统指令、分层摘要、外部存储回查等机制，可以将影响控制在可接受范围。


## 上下文分类
