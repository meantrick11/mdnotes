# Agent Skills 技能输出质量评估笔记
来源：https://agentskills.io/skill‑creation/evaluating‑skills

目标：开展结构化评测，验证技能在多样提示、边界场景下稳定输出；建立反馈循环，对比有无技能的基线差异，系统性迭代优化技能。

## 设计测试用例
测试用例由三部分构成：真实用户提示、成功的预期输出描述、可选输入文件。配置文件存放在技能目录 `evals/evals.json`。
编写要点：
1. 前期仅准备2‑3条用例，后续再扩充；
2. 提示的句式、详细程度、正式风格多样化；
3. 必须覆盖边界、异常输入场景；
4. 使用真实业务上下文，带上文件路径、字段名，避免笼统模糊提问；
5. 断言不需要一开始就写，跑完第一轮看到实际输出后再补充。

## 执行评测
核心：每个用例跑两组对比，一组**启用技能**，一组**基线（不启用技能，也可拿旧版本技能做基线）**。
1. **工作目录**：独立workspace文件夹，每轮迭代建立`iteration‑N`目录；每个测试用例分`with_skill`、`without_skill`子目录，存放输出产物、性能数据、打分结果。
2. **环境隔离**：每轮评测会话必须干净，清除历史上下文残留，保证行为只受技能文件控制。
3. **采集性能数据**：记录token消耗量、执行耗时，输出`timing.json`，用来权衡输出质量与资源开销。

## 编写断言
断言是对输出的客观可核验判定条件，第一轮运行结束后再编写。
- 合格断言：可脚本校验、可观测、可计数；
- 不合格断言：主观模糊描述、严格匹配固定文字（语义正确但措辞变化就误判失败）。

> 写作风格、主观观感不适合做断言，交给人工评审。断言添加到evals.json对应测试用例中。

## 输出打分
针对每条断言标记 PASS / FAIL，必须附带输出证据。
- 文件、格式、数量等机械校验优先使用脚本，可靠性高于大模型；
- 其余交由大模型评判，输出`grading.json`记录每条断言结果。

打分原则：
1. 通过必须要有确凿证据，不主观放水；
2. 同时检查断言本身，删掉过简单、过难、无法核验的断言；
3. 盲测对比：隐藏版本信息交由模型评审，用来评估整体体验，弥补断言的不足。

## 聚合统计结果
汇总评测数据，计算通过率、耗时、token消耗，算出启用与不启用技能之间的差值`delta`，保存至`benchmark.json`。
`delta`用来权衡收益与代价：看技能提升多少通过率，同时带来多少时间、token开销。早期用例数量少，标准差参考意义低，测试规模扩大后统计指标才具备价值。

## 结果模式分析
聚合数据会掩盖细节，需要进一步分析：
1. 无论是否启用技能全部都能通过的断言：没有价值，直接删除；
2. 全部用例均失败的断言：修改断言或者调整测试用例；
3. **仅开启技能才可以通过**：代表技能真正发挥价值；
4. 结果波动大：说明技能指令存在歧义，补充示例减少随机性；
5. 个别用例耗时异常：读取完整执行日志定位瓶颈。

## 人工复核
断言只能覆盖预先设想的条件，人工审查可以发现意料之外的问题。输出具体可落地的反馈`feedback.json`，避免“效果不好”这类笼统评价。

## 技能迭代循环
迭代参考三类信号：失败的断言、人工反馈、完整执行日志。
把全部信号连同`SKILL.md`交给大模型生成修改方案，遵循原则：
1. 修复底层共性问题，不要针对单条测试用例打补丁；
2. 保持技能精简，移除无效指令；
3. 指令尽量说明背后原因，比强硬禁令更容易被模型遵守；
4. 反复出现的重复逻辑，封装进`scripts`脚本。

迭代流程：
1. 根据评测信号生成技能修改；
2. 人工审核变更；
3. 新建迭代目录，完整重跑全部用例；
4. 聚合统计打分；
5. 人工复核结果。

循环迭代，直到几乎没有负面反馈、质量不再明显提升。

> 工具提示：`skill‑creator`技能可以自动化整套评测工作流。
