# 阶段一 索引阶段

RAG最重要的第一步，面对可能上万份的数据，最开始就应该做好数据处理工作，否则就算成功入库，也会因为原始数据的质量内容差，以及权限不分明等等原因导致后期检索的内容质量差、不符合等原因，导致原始输入是错误的，LLM再强也无能为力了。

对于大量的文档/数据需要入库，需要做到以下几点：

## 一、文档加载

## 二、数据清洗

### 1. 盘点

对于不同来源的文档，需要对齐具体的颗粒度，比如文档来源，所属部门，版本划分、负责人、所属权限、有效性等等，进行盘点分类。

### 2. 分级

对于不同等级的文档进行多级分类，以更好得区分文档得重要性，方便后续检索权重比对：

#### 按照重要程度分级(重要->不重要)：

1. 一级：核心制度文档/合同模板、计划文档等等重要资产
2. 二级：产品守则，接口文档等
3. 培训资料、会议纪要等
4. 草稿、废弃、重复文件等
#### 按照时间分级(新->旧)：

时间越靠近，则文档的权重越高，真实效力越高，比如新文档的有效期>>过期文档

### 3. 特殊文件处理

对于不同的文件使用不同的处理方式：
1. PDF -> 提取文本内容，比如PyMuPDF\pdfplumber\unstructured工具，扫描PDF得走OCR
2. word -> 标题列表、批注，使用python-docx足够
3. excel -> 工作表、上下表合并等策略，使用python的pandas
4. 图片 -> 提取图片文字、特征、OCR等技术实现，PaddelOCR\EasyOCR\百度OCR API等
5. 语音 -> 文字,使用Whisper/阿里云ASR等

### 4. 数据清洗等

将文档中的杂质内容进行处理
**清洗内容**：
- 去除页眉、页脚、水印、页码串
- 去除乱码、特殊符号串
- 去除多余空格、换行
- 去除重复段落（simhash 去重）
- 剔除无效短文本（<20 字）
- 内容缺失 >50% → 直接丢弃
- 矛盾内容标记、校对
- 内容填充等

可能需要使用正则匹配、simhash文本去重、长度过滤、噪音规则过滤等

## 三、文档分块

### 1. 分块

完成上述步骤后，可以进行分块了，通过不同的分块模型实现对文档的分块，这里分块需要适宜：

**分块太大**：
1. 语义稀释，一个大块包含很多无关主题，检索召回大量无关内容
2. 上下文窗口给浪费，塞给LLM的内容太多，很容易让上下文窗口爆满
3. 无法精确定位原文
4. 更新颗粒度粗，资源浪费
**分块太小**：
1. 语义碎片化，语义不完整、检索精度暴跌
2. 召回片段多，冗余上下文拉低LLM效果
3. 检索性能变差，分块太小、chunk数量成倍上涨，条数变多，建索引、检索耗时过多
4. 丢失完整逻辑，跨块丢失原本语境信息

总体来说，块大小在300-500tokens为合理，重叠率在10%-20%为合理
使用langchain的RecursiveCharacterTextSplitter、LLamaIndex的SemanticSplitter等分块工具

### 2. 分块校验

对于模型分块后的内容进行人工审查，检查分块是否跨语义边界，重叠率是否达标(10-20%)，减少后续返工。

## 四、向量化


### 1. 向量化(embedding)

分块完成之后就是就是对于不同的分块进行向量化，可以使用huggingface上的开源模型，比如bge-base系列或者调用api，比如OpenAI的text-embedding-ada-002，或者国内大厂的embedding API

向量维度最好选在768/1024维度最好，可以通过Python的HuggingFaceTransformersEmbeddings或者sentence-transformers模块实现。

### 2. 标注元数据

元数据 = 描述切片/文档的附加属性，不是正文文本，给数据打标签

对于不同的文档甚至分块，需要清楚的标注元数据信息，大型的项目需要原文本与向量库存储隔离，这里元素据可以起到：
1. **检索过滤**
对于大量的检索内容，通过元数据对比，避免无关内容，比如你搜索请假流程，库内所有的请假流程(财务、技术、人事等内容)全部返回，如果有元数据category="人事制度",那么只召回人事部门的请假流程就可以了
2. 文档溯源
对于召回的内容有溯源性，后续llm输出答案时，可以标注对应的溯源元数据，防止LLM瞎编，用户能直接参考对应原文
3. 排序加权
对于普通检索召回只通过相似度一维打分，元数据可以调整二次召回顺序，避免仅仅通过语义召回的局限性
4. 元数据和业务数据隔离
通过元数据索引，而不是直接存文本甚至图片数据到向量数据库中，通过元数据将目标image_url链接到业务数据库中的具体的文本/图片内容，再结合发给llm，提供了更多的上下文、减少了向量数据库中的存储内容。
5. 权限隔离
向量数据库中存储的大量内容，如何保证研发部门不能直接检索财务部门的数据呢？在向量数据库中的对应数据中存储权限元数据，标注不同的分级/部门等权限隔离

## 五、入库存储

**绝对不要将大量文本、图片等内容直接存储到向量数据库中**，因为向量数据库的核心是向量检索，高位浮点向量索引极快，但是如果数据过大，直接存储原始文本，内存的向量存储量就大大减少，且挤占索引内存，检索命中率下降。推荐模式是：
向量数据库存储embeddings+元素据+chunk_id，使用Mulvus/Qdrant/PGVector等向量数据库
业务数据库存储chunk_id+原始内容（文本/图片等），使用PostgreSQL/MySQL/MongoDB等数据库
