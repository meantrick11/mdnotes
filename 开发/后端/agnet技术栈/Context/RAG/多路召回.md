# 多路召回
# 多路召回的本质

"多路"这个词容易被望文生义地理解成"语义 + 关键字"两路，但工业界的本意其实更广：**从不同的信号源/表示空间/检索算法分别产出候选集，再做融合(fusion)和精排(rerank)**。因为任何单一检索方式对"相关性"都有系统性偏差，多路的价值在于用互补性弥补召回的盲区，最后靠rerank收敛精度。

## 广义上"多路"包含哪些维度

**1. 检索算法维度**
- 稀疏检索：BM25/TF-IDF（倒排索引，精确词匹配强）
- 稠密检索：向量语义相似度（embedding，语义泛化强）
- 可学习稀疏：SPLADE、uniCOIL 等（兼具关键词可解释性和语义能力）

**2. 表示空间/模型维度**
- 不同embedding模型并行召回（通用模型 + 领域微调模型）
- 多粒度切分（句子级、段落级、整篇文档级各建一路索引）

**3. 结构化 vs 非结构化**
- 向量/全文检索非结构化内容
- SQL/元数据过滤精确字段（时间、类别、权限等）
- 知识图谱/实体关系检索（GraphRAG一类，基于图遍历找关联节点）

**4. 查询侧扩展**
- Query改写、多query生成、HyDE（生成假设答案再用它去检索）——每个变体各自召回一路，再合并

**5. 多模态**
- 文本向量 + 图片向量 + 表格/代码专用检索器

**6. 业务信号召回**（类似推荐系统的多路召回思路）
- 热度、新鲜度、用户历史交互/点击反馈等

**融合方式**：工业界最常用 **RRF (Reciprocal Rank Fusion)**，不需要分数归一化、鲁棒性好；也有用LTR模型学习融合权重的。最后几乎都会接一层 **cross-encoder rerank**（如BGE-reranker、Cohere rerank）来做最终排序，因为多路召回解决的是"全不全"，rerank解决的是"准不准"。

## PostgreSQL + pgvector 能满足吗？

**可以满足中小规模场景**，而且是个挺优雅的方案：
- pgvector：HNSW/IVFFlat 索引做稠密向量检索
- PostgreSQL 自带全文检索（tsvector/tsquery + GIN索引），如果想要更标准的BM25打分，可以加 **ParadeDB (pg_search)** 插件
- 结构化过滤直接用SQL WHERE，甚至RRF融合都能写成一条SQL（对两路结果排名做加权）

单实例PG确实可以实现"语义+关键字+结构化过滤"三路合一，中小数据量（千万级以内）延迟和精度都不错，架构还简单，少一个中间件。

**但大规模工业场景会遇到瓶颈：**
- 向量数据到十亿级时，单机HNSW的内存/构建时间/查询延迟会成为问题，专用向量库（Milvus、Qdrant、Vespa）做分片、量化压缩、GPU加速更成熟
- 全文检索方面，Elasticsearch/OpenSearch的分词、同义词、多字段boost、聚合分析能力比PG原生全文检索强很多
- 高并发写入+近实时索引更新，专用系统的运维工具链更完善
- 图检索通常还是需要独立的图数据库（Neo4j等）

## 工业界典型架构

```
Query
  ├─→ 稠密向量检索 (Milvus/Qdrant/Vespa 或云向量库)
  ├─→ 稀疏/关键字检索 (Elasticsearch/OpenSearch, BM25)
  ├─→ 结构化过滤 (PostgreSQL/MySQL 元数据前置/后置filter)
  └─→ (可选) 图检索 (Neo4j / 内存图)
        ↓
   融合层 (应用层做RRF或加权融合)
        ↓
   Rerank (cross-encoder, GPU服务)
        ↓
      Top-K 结果
```

值得一提的是，**Elasticsearch 8.x、OpenSearch、Vespa、Weaviate** 这些系统现在都原生支持"混合检索"（同时算BM25分数和向量分数并内置融合），所以有些团队会用一个系统就搞定两路，省掉自己写融合逻辑的麻烦——这也是为什么很多新项目直接选Elasticsearch/Vespa做主检索引擎，而不是PG。

**一句话总结**：PG+pgvector在数据量不大、架构想从简的场景下完全够用，是很好的起步方案；但当数据规模、QPS、多模态/图检索需求上来后，工业界通常会拆分成"向量库+搜索引擎+关系库"的组合架构，在应用层做异步并行召回和融合。
