# 有效工具的构建

Agent和单纯的LLM的主要区别就是Agent能够在输入之后，经过LLM进行"思考"，然后对工具进行匹配，匹配之后执行对应的工具，工具具体执行之后，似乎Agent就能够帮你做一些事情了。

## 一、什么是工具？
在计算领域，确定性系统在输入相同时每次都会产生相同的输出，而非确定性系统（例如智能体）即便初始条件相同，也可能生成不同的响应。

所以，**Agent的工具的构建至关重要，工具需要什么参数？模型如何确定选取什么工具？工具怎么定义？怎么描述才能更好地进行匹配？**

在传统的软件开发中，我们是在确定性系统之间建立一种约定。例如，像getWeather(“NYC”)这样的函数调用，每次被调用时，都会以完全相同的方式获取纽约的天气数据。

**工具是一种新型软件，它体现了确定性系统与非确定性智能体之间的契约关系。**当用户询问“我今天应该带伞吗？”时，智能体可能会调用天气工具、依据常识给出回答，甚至先提出一个关于地点的澄清问题。偶尔，智能体也可能出现幻觉，甚至无法掌握工具的使用方法。

这就意味着，我们应该重新思考如何为智能体构建适用的工具？而不是像传统开发一样写函数以及API接口。

## 二、如何编写工具？

### 工具开发完整设计流程：原型 → 评测 → Agent协同迭代（循环迭代）

这是一套**评测驱动开发**的工作流，不是写完代码就结束，而是拿Agent真实调用轨迹反推工具缺陷，并且让Agent本身参与优化工具代码与描述。

### 1）Building a prototype｜快速搭建原型
> 不要一开始追求完美，先跑通最小可用版本。
1. 快速实现工具原型；如果用Claude Code生成工具，把SDK、API文档（llms.txt）喂给模型。
2. 把工具封装成本地MCP Server / DXT桌面扩展，接入Claude Desktop / Claude Code做本地测试；也可以直接调用Anthropic API做程序调用测试。
3. 人工测试，收集用户真实场景，感知哪些工具对Agent“好用”，哪些反直觉。

> 关键点：人很难凭空预判Agent会怎么用工具，**必须实际跑一遍才知道坑在哪里**。

### 2）Running an evaluation｜运行完备评测（整个流程最重要环节）
评测的目的：量化工具好不好用，定位为什么不好用，而不是只看是否能跑通代码。
1. **生成高质量评测任务集**
    - ✅好任务：贴近真实业务，多步骤、多工具调用；例如：约会议、处理客户扣款异常，需要多轮工具调用。
    - ❌坏任务：单步简单指令，像直接写SQL语句，没有模拟真实用户自然语言提问。
    - 每条任务配套可验证结果；验证器可以是字符串比对，也可以让Claude当裁判；**不要因为格式、标点的差异误判正确结果**。可以记录预期工具调用，但不要强制固定调用路径，解决同一个任务可以有多条路径。
2. **程序化执行评测**：写简单Agent循环，输入任务+工具，跑完整调用链路；开启`interleaved thinking`（交错思考），拿到模型思维链CoT，看到Agent为什么选/不选某个工具。
3. **采集多维指标**：不只是准确率；还要采集任务耗时、工具调用次数、Token消耗、工具报错。
4. **分析结果**：阅读完整调用日志 transcript，看Agent卡壳、参数传错、重复调用的地方。
    > 注意：LLM反馈里**没说出来的问题往往比说出来的更重要**，不能只看模型输出的反馈，要看原始调用记录。

### 3）Collaborating with agents｜与Agent协作优化，循环迭代
把评测完整调用日志 transcript丢给Claude Code，让Agent分析问题、重构工具代码、修正工具Schema、改写工具描述。
- 用**留出测试集held‑out test set**，防止工具、描述过度拟合评测集。
- 循环：原型→评测→Agent优化→再评测，直到真实任务表现达标。
- 文章给出实验数据：Slack、Asana的MCP服务，Claude优化后，测试集准确率显著高于人类专家手写版本。

> 核心思想：**用Agent去优化给Agent用的工具**，这是本篇标题的含义。

**其实，上面这套方法适用于任何构建，比如提示词，RAG，tool，mcp等等，任何构建都是先建立原型+不断测试评估，迭代改进**

## 三、四大核心设计原则
### 原则1：Choosing the right tools｜选对要实现的工具（宁缺毋滥，拒绝无脑封装API）
> 误区：把后端所有API全部封装成MCP工具，工具越多Agent越强。**事实恰恰相反**。
1. LLM有有限上下文窗口，计算机内存无限。底层API返回海量原始数据，会大量消耗Token，把处理负担压给大模型。
    - ❌坏例子：通讯录工具`list_contacts`返回全部联系人，让Agent自己暴力筛选。
    - ✅好例子：直接做`search_contacts`，工具内部完成过滤，只返回匹配结果。
2. 优先面向**业务目标**封装工具，而不是暴露底层原子接口。把多步API编排放到工具代码内部，不要让LLM做编排。
    - ❌：`list_users`、`list_events`、`create_event`三个独立工具。
    - ✅：`schedule_event`，工具内部查可用性、创建会议，一次调用完成。
3. 工具要有清晰独立职责；工具重叠、数量泛滥，会干扰Agent做选择。**少而精，聚焦高价值工作流**。

### 原则2：Namespacing tools｜工具命名空间，做好命名隔离
Agent可能同时接入几十上百个来自不同MCP服务的工具，名字模糊会造成选错工具、传错参数。
1. 增加服务/资源前缀做命名区分：如`asana_projects_search`、`jira_search`。
2. 前缀/后缀命名效果会随模型变化，需要通过评测来验证哪个命名方式更适合你的模型。
3. 好名字可以减少Agent思考负担，降低错误调用概率。

### 原则3：Returning meaningful context + Optimizing token efficiency（合并理解：工具返回结果设计，兼顾信息质量与Token开销）
> 这是两个原文小节，逻辑高度关联，可以合并理解，对应你理解的“第四个”。
1. **返回高信号内容，减少无意义底层ID**
    - 尽量返回可读业务名称，而不是晦涩UUID；UUID可以保留在`detailed`模式下，供后续工具调用使用。
    - 提供`response_format`枚举：`concise`简洁模式（省token） / `detailed`详细模式（带ID用于后续调用）。
2. **控制Token消耗**：大结果集必须做分页、过滤、截断；Claude Code默认限制工具返回25000token。
3. **截断提示与友好错误信息**
    - 截断返回时，告诉Agent如何做进一步筛选、翻页；引导Agent做多次小范围精准查询，而不是一次拉取全部数据。
    - 错误返回不要返回原始堆栈、晦涩错误码；要给出易懂总结、合法参数示例、告诉Agent下一步该调用哪个工具修复。
4. 返回格式（JSON/Markdown/XML）没有万能最优解，以评测结果为准。

### 原则4：Prompt‑engineering tool descriptions｜对工具描述与Schema做提示工程
工具描述、参数Schema会直接加载进Agent上下文，深刻影响Agent调用行为。
1. 写工具描述，想象你在给新入职同事讲解工具；把所有隐式知识显式写出来。
2. 参数命名无歧义：不要参数叫`user`，要叫`user_id`；严格定义输入输出Schema。
3. **工具描述微小改动，就可以带来巨大性能提升**。文中举例SWE‑bench Verified，就是微调工具描述大幅降低错误率。
4. MCP工具可以使用`tool annotations`注解，标记工具是否会修改数据、访问外部网络，提升安全性。

## 四、整体底层世界观（读懂文章的关键）
1. 传统开发：写函数、API，面向程序员；Agent工具开发，**面向大模型的认知弱点去设计**。
2. 不要靠人主观评审判断工具好坏；一切以**评测集+真实调用轨迹**为准。
3. 可以让Agent参与工具开发全流程：写原型、分析报错日志、重构代码、改写描述，但是**必须使用隔离测试集，防止过拟合**。
4. MCP只是传输协议，MCP本身不会让工具变好用；协议只是管道，真正决定Agent能力上限的是工具本身的设计。

## 六、展望

要为智能体构建高效的工具，我们需要将软件开发实践从可预测的确定性模式转向非确定性模式。

通过我们在本文中描述的迭代式、以评估为导向的流程，我们发现了工具成功的一致规律：有效的工具具备明确且刻意的定义，能审慎地利用智能体上下文，可在多样的工作流中相互组合，还能让智能体直观地解决现实世界的任务。

未来，我们预计智能体与世界交互的具体机制会不断演进——从 MCP 协议的更新到底层大语言模型（LLMs）本身的升级。通过采用系统化、以评估为导向的方法来改进智能体工具，我们可以确保随着智能体能力的不断提升，其使用的工具也能同步演进。
