首先应该明确：训练 Loss、验证 Loss、业务评估指标是三个不同层面的东西。

比如，一个客服模型的验证 Loss 下降了 20%，但这并不能保证它在退款流程、投诉处理或者转人工等具体场景上的表现更好。

## 8.1 建立多层评估体系

建议至少分为四层：

|层次|评估什么|方法|
|---|---|---|
|训练层|是否学到了训练目标|Training/Validation Loss|
|能力层|问答、分类、指令遵循等|标准数据集、自动评分|
|业务层|是否正确完成业务任务|业务测试集、人工标注|
|系统层|能否在生产中稳定运行|延迟、吞吐、资源、稳定性测试|

客服任务可以进一步定义几个具体指标：

业务流程准确率

\[ \text{Accuracy}=\frac{\text{流程处理正确的案例数}}{\text{全部评估案例数}} \]

转人工召回率

\[ \text{Recall}=\frac{\text{正确识别需要转人工的案例数}}{\text{实际需要转人工的案例数}} \]

此外还可以考察回复格式合规率、错误承诺率、引用知识正确率、工具调用成功率等。

需要提前固定评分标准。比如什么叫“流程正确”，能不能包含部分正确，无法确定的结果由谁复核。

## 8.2 评估时应该比较哪些模型？

至少三种：

1. 原始基座模型。
    
2. 微调后的模型。
    
3. 原始模型配合经过优化的 Prompt（必要时加 RAG）。
    

例如，假设某次实验得到：

|指标|基座模型|Prompt 优化|LoRA 微调|
|---|---|---|---|
|回复格式合规率|65%|86%|95%|
|流程准确率|72%|80%|87%|
|转人工召回率|60%|75%|90%|
|通用问答准确率|88%|88%|83%|

以上均为虚构实验数据，仅用于说明模型选择时的权衡。

你会发现一个问题：

微调模型在业务指标上变好了，但通用问答能力有所下降。

那它到底是成功还是失败？

取决于最初制定的验收标准。例如，如果客服模型只负责特定业务，业务表现可能比通用问答更重要；但如果它还承担通用助手任务，就需要进一步调查能力退化。

因此，模型评估不应该只有一个总分。

## 8.3 建立错误样本库

除了统计通过率，还应该保存失败案例。

假设某条评估记录是：

```
{
  "case_id": "refund_0182",
  "category": "refund",
  "input": "退款失败两次后还能继续申请吗？",
  "expected": "先查询退款状态；符合规则时进入人工核实流程",
  "actual": "您可以直接重新发起退款申请",
  "error_type": "business_rule_violation",
  "model_version": "customer-lora-v1"
}
```

这样才能回答：

- 错误集中在哪些业务类别？
    
- 是不是所有长对话都容易失败？
    
- 是否只在某种输出格式下失败？
    
- 某种问题在训练数据中是否严重不足？
    
- 模型是否记住了过时业务规则？
    
- 错误能否通过 Prompt 或 RAG 修复？
    

这里建议把评估数据分成一个长期固定的回归测试集，以及不断补充的新问题集。

固定集用于比较各个版本，新问题集用于覆盖新的业务失败模式。新增样本可以进入训练集，但应避免让最终测试集直接参与训练和调参。
