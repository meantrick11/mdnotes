真正标准化的做法不是“感觉哪里不好就改哪里”，而是：

失败归因 → 实验假设 → 受控修改 → 重新训练或推理测试 → 对比评估 → 接受或回滚。

我们用一个完整案例来走一遍。

## 10.1 第一轮：模型发生问题

假设模型 v1 完成了训练，结果是：

- 整体流程准确率 87%。
    
- 转人工召回率 90%。
    
- 复杂退款流程准确率只有 58%。
    

经过错误样本分析，发现很多失败出现在“退款已经失败两次”的多条件场景中。

我们先不修改学习率。

而是对失败样本进行分类和数据调查，发现：

- 复杂退款样本占训练集的比例很低。
    
- 现有样本大多只包含单一条件。
    
- 部分旧客服答案不符合现行规则。
    
- 模型在存在多个判断条件时容易遗漏一个条件。
    

现在可以形成具体假设。

## 10.2 第二轮：提出实验假设

假设 H1：

> 复杂退款流程准确率较低，主要是因为训练集中多条件判断样本不足且部分标签过时。如果补充经过审核的多条件场景数据，模型的该项准确率应得到提升。

这是一个可验证的假设。

对应实验设计：

|项目|v1|v2|
|---|---|---|
|基座模型|相同|相同|
|LoRA 配置|相同|相同|
|Learning Rate|相同|相同|
|Epoch|相同|相同|
|训练数据|原始清洗集|修正旧标签、补充复杂场景|
|验证标准|固定|固定|

只有数据发生变化，才能相对清楚地判断数据改进是否产生效果。

实际实验还要注意数据量增加会改变每轮训练的更新步数。如果希望严格比较数据质量的影响，可以控制总训练 Token、更新步数等训练预算。

现在你可以说：

在这次实验的固定评估集上，补充复杂场景数据后，复杂退款准确率由 58% 提升至 79%。

但还不能立即认定新模型应该上线。

还要检查样本数量、置信区间或重复实验结果、新旧模型在其他业务上的退化程度，以及实际收益是否满足发布门槛。

## 10.4 第四轮：接纳还是回滚？

一种简单的发布判断：

```
新模型业务主指标是否达到预期？
    │
    ├─ 否 → 保留实验记录，重新分析
    │
    └─ 是
         ↓
是否出现不可接受的能力退化？
    │
    ├─ 是 → 不发布，继续修正
    │
    └─ 否
         ↓
候选模型通过回归和系统测试？
    │
    ├─ 否 → 定位问题
    │
    └─ 是 → 允许进入灰度部署
```

这里最重要的工程原则是：每次实验都应该可以追溯到一个明确的假设，并且能够与基线比较。
