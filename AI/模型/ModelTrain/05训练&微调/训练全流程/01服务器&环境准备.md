

# 环境准备：确保训练可运行且可复现

假设我们拿到一台 GPU 服务器。

这里涉及三类环境。

|环境层次|需要解决的问题|工具|
|---|---|---|
|硬件与操作系统|GPU 是否存在、驱动是否正常、磁盘是否足够|Linux、nvidia-smi|
|计算运行时|CUDA 是否兼容、PyTorch 能否访问 GPU|CUDA、PyTorch|
|项目依赖|Python 包版本、代码环境一致性|uv、pip、Docker|

## 3.1 检查 GPU

```
nvidia-smi
```

检查 GPU 型号、显存、驱动版本、当前显存占用和其他 GPU 进程。

再验证 PyTorch：

```
import torchprint(torch.__version__)print(torch.cuda.is_available())if torch.cuda.is_available():    print(torch.cuda.get_device_name(0))
```

要注意，NVIDIA 驱动、系统 CUDA Toolkit、PyTorch 自带或依赖的 CUDA Runtime 是相关但不同的组件。不是安装的 CUDA 版本越新越好，关键是兼容性。

## 3.2 环境管理

个人实验可以从 Python 虚拟环境开始，企业团队通常会进一步使用 Docker 镜像。

比如一个训练镜像可以固定：

```
Python 版本
PyTorch 版本
Transformers 版本
PEFT / TRL 版本
CUDA 运行时依赖
项目代码版本
```

不要一开始就假设需要 Kubernetes。单机训练用 SSH、Docker、进程管理和持久化存储就可以完成很多工作。

## 3.3 估算资源

7B 模型如果采用 BF16，单单模型权重就约为 14 GB（按十进制 GB 粗略计算）。

但训练显存不只包含模型参数，还包括：

\[ M_{\text{total}} \approx M_{\text{weights}}+M_{\text{gradients}}+M_{\text{optimizer}}+M_{\text{activations}}+M_{\text{other}} \]

因此模型能加载，不意味着它能训练。

LoRA 可以减少可训练参数、梯度及优化器状态的开销，但基础模型权重、激活、临时计算缓冲区等仍占用显存。

Hugging Face

如果显存不足，常见调整顺序是：先减少每卡 Batch Size、缩短序列长度、启用梯度检查点，再考虑 QLoRA、CPU Offload、多 GPU 或更小模型。


### 小经验

GB10的GPU&CPU的内存共存，GPU模型训练会大量吃掉内存，可能会导致反复的Swap换页，从而导致内存中其他的进程反复换出换入，其他进程也无法正常运行，比如ssh连接不上等等内容
