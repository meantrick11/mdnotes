这个阶段需要满足模型的数据准备，包括：
1. 原始数据清理
2. 数据标注
3. 数据划分
-  **训练集（Train set）**：训练模型、学规律，占比 70%～80%
- **验证集（Validation set / Dev set）**：调超参、选模型、监控过拟合，占比 10%～15%
- **测试集（Test set）**：**只用最后一次**，评估模型真实泛化能力，占比 10%～15%
4.版本管理  

## 2.1 明确原始数据是什么

我们的客服数据可能来自：

|数据来源|原始形式|可能的问题|
|---|---|---|
|客服聊天记录|JSON、数据库|有无效对话、个人信息、错误回答|
|企业 FAQ|Excel、CSV|问答过时、表述不统一|
|产品手册|PDF、Markdown|不适合直接作为问答监督样本|
|人工标注数据|JSONL|标注标准不一致|
|历史工单|数据库|同一问题的处理方式互相矛盾|

原始数据通常不能直接送入 SFT。

例如，一段原始客服记录：

```
客户：我退款怎么还没到？
客服：稍等。
客户：已经三天了。
客服：那你再等等吧。
```

这是真实数据，但不代表这是我们希望模型学习的行为。

如果直接训练，模型可能学会敷衍客户。

## 2.2 数据清洗与标注

这个阶段通常包括：

1. 清洗：删除乱码、无效记录、系统噪声、敏感信息。
    
2. 去重：消除重复或高度相似样本，检查训练集与测试集之间的数据泄漏。
    
3. 质量筛选：剔除错误答案、过时信息、低质量对话。
    
4. 标注或重写：将原始记录转换成符合目标行为的标准答案。
    
5. 数据统计：检查数据量、类别分布、文本长度和长尾问题。
    

例如把刚才的对话转换成：

```
{
  "messages": [
    {
      "role": "user",
      "content": "退款已经三天还没到账怎么办？"
    },
    {
      "role": "assistant",
      "content": "您可以先查看退款状态。不同支付方式的到账时间可能不同。如果超过预计时间，请提供订单编号，由客服进一步核实。"
    }
  ]
}
```

真正有价值的并不是把数据变成 JSON，而是确保这个答案符合业务规定。

对于复杂业务，还需要审核模型是否应当提供某个回答、是否必须调用外部工具，以及什么情况下应该转人工。

## 2.3 划分数据集

假设经过清洗后，剩余 40,000 条样本，可以从以下比例开始：

训练集 80%

32,000 条

验证集 10%

4,000 条

测试集 10%

4,000 条

比例不是强制规范，应该根据样本规模和业务分布调整。

- 训练集：用于更新模型参数。
    
- 验证集：用于选择超参数、监控过拟合和选择 Checkpoint。
    
- 测试集：用于最终独立评估，不应该反复根据测试集结果调整模型。
    

更重要的是划分方式。对于客服数据，应该考虑按客户、工单或时间划分，避免同一个问题及其近似答案出现在多个集合中。

## 2.4 Tokenization

随后需要将数据转换为模型能够处理的 Token。

大致过程：

```
对话消息
   ↓
Chat Template
   ↓
Tokenizer
   ↓
input_ids / attention_mask
   ↓
构造 labels 与 loss mask
   ↓
Batch
   ↓
模型训练
```

这里有一个非常容易踩坑的点：训练时到底让模型预测哪些 Token？

对于指令微调，通常希望模型学习 assistant 的回答，而不是把 user 的提问也作为同等的预测目标。是否只计算 assistant 部分的 Loss，取决于数据格式和训练配置。

另外必须检查：

- Chat Template 是否与基座模型匹配。
    
- EOS、PAD 等特殊 Token 是否正确。
    
- 长文本有没有被截断。
    
- 答案是否在截断过程中被丢失。
    
- 实际参与 Loss 计算的 Token 是否正确。
    

TRL 的 SFTTrainer 支持对话数据、assistant-only loss、序列打包等功能，但需要满足其对应的数据格式和模板要求。

Hugging Face

这个阶段的交付物应该包括：清洗后的数据集、数据版本、统计报告、预处理脚本以及数据质量检查结果。
