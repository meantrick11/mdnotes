# 评审稿章节蓝图

本蓝图以 skill 内置的 V1.10 非结构化语义分类分级评审稿为主要目标样本。它说明各章要回答的问题，而不是固定页数或固定业务标题。具体标题要写当前需求的对象和决策。

| 章节 | 必须回答 | 优先呈现 |
|---|---|---|
| 封面与阅读路径 | 文档评审什么、依据哪个代码/SPEC 版本、希望评审决定什么 | 版本信息、三至五行阅读路径 |
| 1 产品场景 | 谁遇到什么问题；现状与目标差异；边界与成功标准 | 现状/目标对照表、端到端业务图 |
| 2 关键决策 | 复用哪些实际模块；为何改造或新建；方案代价 | 模块复用矩阵、取舍表；每项写推荐与理由 |
| 3 系统设计 | 现有服务组织与目标组织如何变化；数据归属如何变化 | 同尺度架构图、现状/目标数据关系图、表变化矩阵 |
| 4 核心业务流程 | 各阶段如何触发、校验、调用、落库和反馈；失败如何处理 | 阶段流程/时序/状态图及少量解释 |
| 5 页面与接口地图 | 每个页面、弹窗、Tab 调哪些现有/改造/新增接口 | 按页面小节的接口表；接口作用与变更点 |
| 6 非功能与实施验收 | 权限、并发、一致性、兼容、性能、发布和回退如何受控 | 风险控制表、实施顺序、验收门禁 |
| 附录 | 结论从哪里来；有哪些待确认差异 | SPEC 章节、代码文件/版本、争议清单 |

## 每一节的写法

1. 首句给出该节的判断或设计意图。
2. 用图说明结构或顺序，用表说明比较与映射。
3. 补一段解释“为何这样设计”和“评审需要决定什么”。
4. 对事实、目标和未确认事项使用不同措辞。目标不能写成现状，推断不能写成代码事实。

## 页面接口小节模板

### 页面名称：包含的 Tab 或弹窗

一句话说明页面目标、结构化/非结构化共存方式和数据来源。

| 方法与路径 | 状态 | 复用/改造/新增范围 | 页面作用 | 依据 |
|---|---|---|---|---|
| GET /example/list | 现有·改造 | 增加类型隔离，旧调用默认旧类型 | 两个 Tab 的列表 | 代码 + SPEC |

内部服务接口可附在同一小节末尾，标明“谁调用谁”；若跨多个页面复用，首次详细说明，后续引用该接口及前一小节，避免重复长文。

## 与 Technical SPEC 的边界

上级 `02TechnicalDesign` 目录中的 `08TechnicalDesign(Template).md` 是实施设计主模板，覆盖字段、业务逻辑、异常、配置等。评审稿提炼其上层决策和跨模块关系，必要时给出接口清单，但不复写每个 DTO 字段、SQL、错误码和方法步骤。评审结论与设计基线在评审完成后回填，不能由生成工具预设为通过。
