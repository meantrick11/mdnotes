# 技术设计评审文档

产出让评审人能判断“为什么做、现状是什么、目标怎样落地、复用和改造哪里、风险与待决策是什么”的材料。它是 Technical SPEC 的评审视图：保留决策、关系和边界；字段级请求响应、SQL 与逐函数实现留在 SPEC。

本 skill 内置 [`assets/reference-review-v1.10.docx`](assets/reference-review-v1.10.docx)，即“非结构化数据语义分类分级设计说明书-评审版-V1.10”。开始写作前先读[参考稿解剖](references/reference-analysis.md)，需要核对版式、表格或图文比例时再打开 DOCX。参考稿是**组织与表达目标**，其中的分类分级事实、接口及数量不能迁移到其他需求。

## 输入与证据

先收集需求原文、阶段 SPEC、目标仓库与版本、输出格式及评审受众。用户提供新参考稿时以新参考稿为准；否则使用内置 V1.10。缺少某项时继续处理已知资料，并把影响结论的缺口列为待确认。参考稿控制阅读组织与视觉密度，不自动成为本需求的事实来源。

按以下规则核对：

| 内容             | 首要依据          | 文中写法                 |
| -------------- | ------------- | -------------------- |
| 系统现状、已有接口、表与模块 | 指定代码版本及配置     | “当前代码存在”；附代码定位       |
| 目标行为、目标接口与新表   | 已确认需求和最新 SPEC | “目标设计/拟新增”；附 SPEC 章节 |
| 页面场景与业务目标      | 需求文档          | 写清用户、触发、结果与验收        |
| 格式与阅读顺序        | 用户指定的参考评审稿    | 提炼结构和呈现方式，不复制业务内容    |
|                |               |                      |

代码与 SPEC 不一致时建立差异表，写出现状方法/路径、目标约定和评审需定项。不要将目标能力画成已上线现状，也不要用旧接口名称猜测其语义。

## 生成流程

1. **形成证据台账。** 列需求目标、现状模块和入口、现有表/接口、SPEC 阶段、页面、目标变更及证据位置。确认“复用”“改造”“新增”“保持”“不采用”的判断。
2. **确定评审问题与目录。** 参照 V1.10 的“使用场景 → 决策 → 系统设计 → 核心流程 → 页面接口 → 实施验收”阅读顺序，但按本需求的评审问题增减小节。每节标题点明对象和判断；需求小则缩减章节，不为了凑模板堆内容。
3. **先做图表骨架。** 准备现状/目标架构对照、全业务流程、阶段时序或状态图、现状/目标数据关系、模块复用矩阵和页面接口地图；每张图只服务一个明确判断。参照内置图源的组织方式，替换全部业务节点、关系和术语。
4. **撰写正文。** 每节按“现状 → 目标 → 处理方式/理由 → 预期效果或风险”展开。短段落解释因果，表格承载可比较项，图承载关系与顺序。
5. **按页面核对接口。** 对每个页面、弹窗或 Tab 逐一列出读、写、下载、导入、内部调用。把结构化/非结构化两个 Tab 的相关接口放在同一页面小节。逐条核对 HTTP 方法、路径、当前代码状态、改造点和页面作用；内部服务契约标明调用方。
6. **检查兼容与实施边界。** 说明旧功能如何保持、数据如何隔离、状态/权限/异常/回退与验收门禁。未决定事项单列，不写成已批准结论。
7. **生成与校验交付物。** 保存可编辑图源和渲染图，嵌入 DOCX 或用户指定格式；按 [质量检查表](references/quality-gates.md)核对文字、结构、图、接口与版面。DOCX 需逐页渲染检查，发现裁切或表格断裂后修正并重渲染。无法渲染时如实报告限制，不能声称完成逐页检查。

## 推荐目录

从[评审稿章节蓝图](references/outline.md)选取与需求有关的章节。默认顺序为：产品场景与现状目标、关键决策、系统与数据设计、核心业务流程、按页面组织的接口、非功能及实施验收、证据附录。不要把“技术评审结果”和“设计基线确认”预填为通过；它们在评审后形成。

## 图表与接口呈现

- **架构图**：现状和目标保持同一范围与粒度，覆盖入口、业务模块、基础模块、外部系统和数据归属；标注复用、改造、新增以及调用方向。
- **流程与时序图**：一张总业务流程图串起端到端闭环；各阶段展开门禁、分支、异步、失败和回写，不只画线性主路径。
- **数据图**：展示现有表、改造表、新表及一对多/逻辑关联；旁边用表说明现状字段/目标变更/承担职责。逻辑关联不冒充物理外键。
- **图源**：Mermaid `.mmd` 与渲染的 SVG/PNG 同步保存；Word 中嵌入已渲染图。`assets/diagram-sources/` 保留 V1.10 的图源实例，只学习信息组织与复杂度，不复制业务节点。可调用 `review-sequence-diagram` 与 `review-mermaid-relations` 细化图稿；没有这些 skill 时仍按本规则完成。
- **接口表**：每行至少包含“HTTP 方法与路径｜代码现状/目标性质｜复用或改造点｜页面作用”。同一页面内列出结构化与非结构化入口；现有接口的“保持”也要写明。字段契约通过 SPEC 引用，不在评审稿复述大段 JSON。

## 完成标准

评审人仅看正文、图表和接口地图，就能回答：当前链路在哪里、目标链路怎样闭合、哪些模块与表直接复用、哪些接口改造或新增、现有功能是否受影响、失败时会怎样、仍需评审决定什么。每个关键事实都能追到需求、SPEC 或代码；每张图已实际渲染，最终文档已检查正常阅读尺寸的可读性。
