# 02. Technical Design 基础认知

## 2.1 什么是 Technical Design？为什么需要技术设计？

在完成需求分析与拆解之后，我们已经明确了：

- 本次需求为什么要做？
- 需要解决什么问题？
- 系统需要提供哪些功能？
- 有哪些业务规则和约束？
- 正常流程、异常流程分别是什么？
- 如何判断最终实现正确？

但这些信息还不足以直接进入编码阶段。

因为需求分析解决的是业务层面的问题，而开发人员还需要进一步明确系统应该如何实现这些需求。

例如，产品经理提出：

> 用户可以上传 PDF、Word 文件，系统自动解析文件内容，并通过 AI 生成笔记，支持用户查看和编辑。

经过需求拆解，我们已经明确了文件类型限制、上传要求、解析行为、笔记生成规则、异常处理和验收标准。

但对于开发人员而言，仍然存在很多技术问题：

- 当前项目使用什么技术栈和架构？
- 应该在哪些现有模块中实现这些功能？
- 是否已经存在文件上传、文件解析或 AI 调用能力？
- 是否需要新增模块或修改现有模块？
- 文件上传和解析应该如何协作？
- 是否需要引入异步任务？
- 是否需要新增或修改数据库表？
- API、数据结构和状态应该如何设计？
- 如何保证新功能不会破坏现有功能？

这些问题都属于 Technical Design 需要解决的范畴。

**Technical Design 的核心目的：将已经明确的业务需求转化为与现有项目相适配、可以指导后续编码的技术实现方案。**

它是需求分析与实际代码实现之间的桥梁。

---

## 2.2 Technical Design 与 Requirement Analysis 的区别

这两个阶段容易混淆，但它们解决的是不同层面的问题。

| 维度 | Requirement Analysis | Technical Design |
|---|---|---|
| 核心问题 | What & Why | How |
| 关注视角 | 业务需求 | 系统实现 |
| 分析对象 | PRD、原型、业务规则 | 需求文档、现有代码库、技术资料 |
| 核心工作 | 需求理解、功能拆解、场景分析 | 代码库探索、影响分析、方案设计 |
| 关注内容 | 系统应该表现成什么样 | 系统应该如何实现 |
| 最终产出 | Requirement Specification | Technical Specification |

例如：

需求分析阶段：

- 支持 PDF 和 DOCX 上传。
- 文件上传成功后能够进行解析。
- 解析完成后能够生成笔记。
- 用户能够查看和编辑笔记。

技术设计阶段：

- 复用现有文件上传模块。
- 设计文件解析模块的职责。
- 确定解析任务的执行方式。
- 设计笔记生成的数据流。
- 明确接口、数据模型、状态管理和异常处理。

需要注意：

需求分析不负责决定使用什么技术库、如何设计数据库；技术设计也不应该擅自改变产品的业务规则。

如果在技术设计过程中发现需求存在歧义或无法合理实现的情况，应当返回需求澄清阶段，而不是自行做业务决策。

## 2.3 Technical Design 的核心认知：基于项目现状进行技术设计

这是技术设计阶段最重要的认知之一。

**技术设计不是脱离现有项目，从零开始设计一个理想系统，而是在理解现有项目的基础上，结合本次需求寻找合理的实现方案。**

在真实开发中，大多数需求都是对已有系统进行修改和扩展，而不是从零开始建设。

因此，在开始技术设计之前，必须先理解项目本身。

例如，面对文件解析需求，不能直接开始研究有哪些 PDF 解析库，而应该先了解：

- 项目当前的技术栈是什么？
- 是否已经存在文件上传模块？
- 是否已经有文件解析能力？
- 现有文件处理流程是什么？
- AI 模型调用是否已经统一封装？
- 当前是否有异步任务机制？
- 相关模块之间如何协作？

只有理解现有项目，才能判断哪些能力可以复用，哪些地方需要修改，哪些能力需要新增。

技术设计应该优先考虑：

1. 复用现有能力，避免重复建设。
2. 遵循现有项目合理的架构规范和代码设计。
3. 尽可能减少不必要的改动范围。
4. 保持模块职责清晰，避免产生不合理的耦合。
5. 当现有架构无法满足需求时，允许进行合理的架构调整。

但需要注意：

**基于现有项目设计，不代表盲目沿用现有实现。**

如果现有设计存在明显缺陷，或者已经无法满足新需求，就应该分析是否需要优化、重构或引入新的技术方案。

既不能为了复用而复用，也不能为了追求技术先进而随意引入新技术。

## 2.4 技术探索应该如何开展？

技术探索并不只有一种形式。

根据是否依赖现有项目，可以分成两个方向。

### 1. 项目内技术探索（Project-oriented Exploration）

以当前项目为基础，理解已有实现和技术约束。

主要关注：

- 当前项目使用什么技术栈？
- 整体架构和模块如何组织？
- 相关功能目前如何实现？
- 是否存在可复用的组件或能力？
- 现有模块之间如何调用？
- 当前实现有哪些限制和潜在问题？

例如，新增文件解析能力时，首先需要理解项目已有的文件处理机制，而不是直接重新设计一套文件管理系统。

这部分工作通常包括 Repository Exploration 和 Impact Analysis。

### 2. 项目外技术调研（Independent Technical Research）

当现有项目能力无法满足需求，或者存在明显的技术选型问题时，需要进行独立的技术调研。

主要关注：

- 是否存在更合适的技术方案？
- 有哪些可选框架、库或服务？
- 不同方案的优缺点是什么？
- 性能、成本、部署和维护难度如何？
- 是否与当前技术栈兼容？
- 是否值得引入新的技术依赖？

例如，当前项目不支持扫描版 PDF 的识别，就需要调研不同 OCR 方案，再判断如何集成到现有系统。

两者之间的关系是：

先理解现有项目，明确实际技术问题；再针对需要解决的问题开展技术调研；最后结合项目约束确定最终实现方案。

**不是先脱离项目寻找最先进的技术，再强行将它集成进项目。**

## 2.5 技术设计的核心工作内容

技术设计不是简单地写一份技术文档，而是需要完成一系列技术分析与决策。

主要包括：

### 1. Repository Exploration（代码库探索）

理解现有项目：

- 技术栈。
- 系统架构。
- 代码组织。
- 模块职责。
- 核心调用链。
- 已有业务能力。
- 相关技术规范。

目的：建立对现有项目的基本认知。

### 2. Impact Analysis（影响分析）

分析本次需求会影响哪些现有系统：

- 哪些模块需要修改？
- 哪些模块可以复用？
- 是否需要新增模块？
- 是否涉及多个微服务？
- 是否需要修改现有接口？
- 是否影响数据库或数据结构？
- 是否影响现有业务流程？
- 是否存在兼容性风险？

目的：明确本次开发的技术影响范围。

### 3. Technical Exploration（技术探索）

针对具体技术问题进行方案研究：

- 是否需要引入新技术？
- 是否存在多种实现方案？
- 不同方案的优缺点是什么？
- 哪种方案更适合当前项目？
- 技术成本和维护成本如何？

目的：找到合理的技术解决方案。

### 4. Solution & Architecture Design（方案与架构设计）

明确系统整体如何协作：

- 模块职责。
- 系统边界。
- 模块之间的交互。
- 核心数据流。
- 关键处理流程。
- 依赖关系。

目的：确定整体实现思路。

### 5. Detailed Design（详细设计）

明确后续编码所需要遵循的具体设计：

- API 接口。
- 请求和响应结构。
- 数据模型。
- 核心业务处理逻辑。
- 状态管理。
- 异常处理。
- 权限控制。
- 必要的事务与并发约束。

目的：让后续编码有明确的实现依据。

### 6. Technical Review（技术评审）

检查最终设计是否合理：

- 是否覆盖所有功能需求？
- 是否符合现有项目架构？
- 是否存在重复建设？
- 是否存在不合理的模块耦合？
- 是否考虑异常和边界情况？
- 是否存在安全、性能和兼容性风险？
- 是否存在过度设计？

目的：在编码之前尽可能发现设计问题。

## 2.6 Technical Design 与 Implementation Planning 的区别

技术设计和任务规划也容易混淆。

它们虽然都涉及如何实现，但关注点不同。

**Technical Design：确定系统应该如何实现。**

例如：

- 新增文件解析能力。
- 复用现有文件存储模块。
- 通过异步任务执行耗时解析。
- 解析完成后调用笔记生成模块。
- 新增必要的任务状态管理。

**Implementation Planning：确定具体应该如何完成这些开发工作。**

例如：

1. 修改文件上传接口。
2. 新增文件解析服务。
3. 实现解析任务处理逻辑。
4. 增加任务状态查询接口。
5. 实现笔记生成调用。
6. 编写单元测试和集成测试。

两者的区别：

| 维度 | Technical Design | Implementation Planning |
|---|---|---|
| 核心问题 | 系统如何设计？ | 开发工作如何执行？ |
| 关注对象 | 系统、模块、接口、数据 | 任务、依赖、执行顺序 |
| 主要产出 | 技术设计文档 | 实施任务清单 |
| 主要使用者 | 开发人员、技术负责人 | 开发人员、Coding Agent |

简单来说：

**SPEC 定义技术方案，Implementation Plan 将技术方案转化为可执行的开发任务。**

## 2.7 AI 时代，开发人员在技术设计阶段应该承担什么角色？

AI 能够快速阅读代码、分析调用关系、搜索技术方案、生成架构图和技术文档。

但这不代表开发人员可以把技术设计完全交给 AI。

开发人员需要从单纯的代码编写者，逐渐转变为技术方案的分析者、决策者和审核者。

AI 可以承担：

- 阅读代码库，提取项目架构。
- 分析相关模块和代码调用链。
- 识别需求影响范围。
- 搜索候选技术方案。
- 对比不同实现方式。
- 生成架构图、数据流图。
- 生成 API、数据模型和详细设计初稿。
- 检查设计遗漏和潜在风险。

开发人员需要负责：

- 判断 AI 对现有项目的理解是否正确。
- 判断技术方案是否满足需求。
- 判断是否需要复用、扩展或重构现有模块。
- 对关键技术选型和架构决策负责。
- 审核系统交互、数据模型和异常处理。
- 判断设计是否过度复杂。
- 最终确认 Technical SPEC。

尤其需要注意：

AI 很容易在不了解现有项目的情况下生成一套看起来合理的全新架构，也可能误判已有模块的职责和实现能力。

因此，不能只因为 AI 生成的设计文档完整、架构图漂亮，就认为技术方案正确。

**AI 负责加速信息获取、分析和方案生成；开发人员负责理解上下文、做出技术决策，并对最终设计质量负责。**

## 2.8 Technical Design 的最终目标

技术设计阶段最终应该形成一份 Technical Specification（技术设计说明书）。

这份文档至少需要让开发人员明确：

1. 本次需求需要修改哪些现有模块？
2. 哪些能力可以复用，哪些需要新增或调整？
3. 整体技术方案是什么？
4. 各模块分别承担什么职责？
5. 模块之间如何交互？
6. 数据如何流转和存储？
7. 关键接口和数据结构如何定义？
8. 关键异常和边界如何处理？
9. 有哪些技术风险和待确认事项？
10. 如何验证设计和实现的正确性？

当这些问题已经得到足够明确的回答，技术方案经过必要评审，就可以进入下一阶段 Implementation Planning。

需要注意，技术设计的深度应当与需求复杂度相匹配。

简单功能不需要设计完整的系统架构；复杂的跨模块需求则需要充分分析模块交互、状态流转、数据一致性和异常恢复。

**技术设计不是为了生成一份尽可能详细的文档，而是为了在开始编码之前，让开发人员和 AI Agent 对实现方案形成一致、明确且可执行的理解。**
