# 06. 技术评审（Technical Review）

> 本阶段定位：对已经完成的 Technical SPEC 进行系统性审查，从需求覆盖、影响范围、技术方案、架构合理性、详细设计和工程质量等维度，检查设计是否存在遗漏、矛盾、不合理或不可实现的问题，确保最终设计能够指导后续开发。
>
> 核心问题：这份技术设计是否正确、完整、合理、可实现？是否存在尚未发现的问题？

## 1. 为什么需要技术评审？

在完成前面的阶段之后，我们已经形成了：

- Requirement Specification：明确需要实现什么。
- Repository Exploration：理解当前项目。
- Impact Analysis：明确需求影响范围。
- Solution Exploration：确定技术实现方案。
- Architecture Design：明确整体系统架构。
- Detailed Design：明确具体实现规范。

但文档完成不代表设计一定正确。

在设计过程中，可能出现：

1. **需求遗漏**：部分功能需求或异常场景没有被覆盖。
2. **影响分析不完整**：遗漏了某些共享模块、接口调用方或数据依赖。
3. **方案选择不合理**：引入了不必要的技术，或者忽略了更简单的实现方式。
4. **架构设计不合理**：模块职责不清晰、依赖关系混乱、系统耦合过高。
5. **详细设计存在问题**：接口不一致、数据结构缺失、状态流转不合理。
6. **前后设计矛盾**：架构设计与详细设计不一致，或者与需求存在冲突。
7. **工程质量考虑不足**：忽略安全、性能、兼容性和数据一致性。

如果这些问题直到编码甚至测试阶段才被发现，就可能导致大量返工。

因此，技术评审的核心目的有三个：

- **发现设计问题**：尽可能在编码之前发现设计中的遗漏、矛盾和风险。
- **验证设计质量**：确认设计能够满足需求，并符合项目实际情况。
- **形成设计基线**：经过评审和修改后，确认一份可以作为后续开发依据的技术设计。

核心原则：

**技术评审不是为了证明设计没有问题，而是主动寻找设计中可能存在的问题，并在进入编码之前解决关键问题。**

## 2. 技术评审应该审查什么？

技术评审的对象是完整的 Technical SPEC，而不是只看架构图或详细设计。

建议重点关注以下六个方面。

### 2.1 需求覆盖检查（Requirement Coverage）

首先确认技术设计是否完整覆盖了需求。

重点关注：

- 每项功能需求是否都有对应的设计？
- 主要业务流程是否完整？
- 正常流程是否得到覆盖？
- 关键异常和边界场景是否考虑？
- 业务规则是否得到正确落实？
- 验收标准是否能够通过设计实现？
- 是否存在未经确认的业务规则或自行假设？

例如：

需求明确要求：

- 支持 PDF 上传。
- 自动解析文件。
- AI 生成笔记。
- 用户能够查看和编辑笔记。

那么需要检查：

| 需求 | 是否有对应设计 | 检查内容 |
|---|---|---|
| PDF 上传 | 是 | 文件类型和上传限制 |
| PDF 解析 | 是 | 解析流程及失败处理 |
| AI 笔记生成 | 是 | 模型调用及结果处理 |
| 查看笔记 | 是 | 查询接口和数据关联 |
| 编辑笔记 | 否 | 是否遗漏编辑功能设计 |

这里可以利用需求 ID 建立追踪关系，确保每个功能需求都有对应的技术设计。

**核心目标：确保技术设计没有遗漏需求，也没有擅自改变产品定义的行为。**

### 2.2 影响范围完整性检查（Impact Coverage）

检查前期的影响分析是否充分，以及最终设计是否覆盖了所有必要的改动范围。

重点关注：

- 是否遗漏相关功能模块？
- 是否遗漏公共组件的其他调用方？
- 是否检查了上下游依赖？
- 是否考虑接口兼容性？
- 是否考虑历史数据兼容？
- 是否遗漏配置、部署和第三方依赖变化？
- 是否识别需要回归测试的已有功能？

例如：

本次扩展了公共文件解析模块，那么不仅需要检查 PDF 解析，还需要确认：

- 原有 DOCX 解析是否受到影响？
- 其他调用方是否依赖原有解析结果？
- 是否存在其他异步任务使用该模块？
- 是否需要修改公共接口？

**核心目标：避免只考虑本次新增功能，而忽略对现有系统的连带影响。**

### 2.3 技术方案合理性检查（Solution Validation）

检查最终选择的技术方案是否合理。

重点关注：

- 是否优先复用了现有项目能力？
- 是否引入了不必要的技术依赖？
- 候选方案比较是否充分？
- 是否符合当前技术栈和项目约束？
- 是否存在更简单的实现方式？
- 关键技术假设是否经过必要验证？
- 开发成本和维护成本是否合理？
- 是否存在明显的技术风险？

例如：

如果现有解析库已经能够满足 PDF 解析需求，就需要重新审视是否真的有必要引入一个新的解析服务。

**核心目标：确保技术方案能够满足需求，同时避免不必要的复杂度和技术风险。**

### 2.4 架构设计合理性检查（Architecture Review）

检查整体架构是否合理。

重点关注：

- 模块职责是否清晰？
- 模块边界是否合理？
- 是否存在职责重复？
- 是否存在不必要的模块拆分？
- 模块依赖是否合理？
- 是否存在循环依赖？
- 模块之间的交互方式是否合适？
- 核心业务流程是否完整？
- 数据流和状态归属是否明确？
- 是否存在明显的单点故障？

例如：

如果 Parser Module 直接负责笔记保存、用户权限校验和 AI 模型调用，就需要考虑是否出现了职责混乱。

**核心目标：确保整体系统结构清晰，模块之间能够按照合理的方式协作。**

### 2.5 详细设计完整性检查（Detailed Design Review）

检查详细设计是否足够明确，能够指导后续编码。

重点关注：

- 接口定义是否完整？
- 请求和响应结构是否一致？
- 数据模型和字段约束是否明确？
- 核心业务逻辑是否完整？
- 状态定义和流转是否合法？
- 异常处理是否充分？
- 是否考虑幂等、并发和重试？
- 是否考虑数据一致性？
- 权限校验是否明确？
- 是否遵循现有项目开发规范？

例如：

如果设计中定义了异步解析任务，但没有明确任务状态、失败处理和重试规则，就需要进一步完善。

**核心目标：确保详细设计没有关键歧义，Agent 不需要自行猜测核心业务规则和技术约定。**

### 2.6 工程质量检查（Quality Attributes Review）

最后，从整体工程质量角度检查设计。

| 维度 | 检查内容 |
|---|---|
| Performance | 是否存在明显性能问题？ |
| Security | 是否存在权限、数据泄露或安全风险？ |
| Reliability | 是否考虑失败恢复和异常处理？ |
| Consistency | 是否存在数据不一致风险？ |
| Compatibility | 是否影响旧接口和历史数据？ |
| Maintainability | 是否增加不必要的复杂度？ |
| Scalability | 是否存在明显的扩展瓶颈？ |
| Observability | 是否具备必要的日志和问题追踪能力？ |
| Testability | 是否能够有效测试和验证？ |

不需要每个需求都深入审查所有维度，应根据本次需求的实际风险决定审查深度。

**核心目标：确保技术设计不仅能够实现功能，而且符合项目必要的工程质量要求。**

## 3. 如何进行技术评审？

建议采用以下四个步骤。

### Step 1：准备评审材料

整理本次需求的完整设计资料：

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。
- Solution Exploration。
- Architecture Design。
- Detailed Design。

确保评审人员或 AI 能够理解需求背景、项目现状和最终设计。

尤其需要注意：

不能只把 Architecture Design 和 Detailed Design 给 AI，而不提供原始需求。

否则 AI 很难判断设计是否真正覆盖了需求。

### Step 2：进行独立设计审查

让 AI Agent 以独立技术评审者的角度审查整份 Technical SPEC。

不要只是让它总结文档或检查格式，而是要求它主动寻找：

- 遗漏的需求。
- 不合理的设计。
- 前后矛盾的内容。
- 未明确的业务规则。
- 不合理的模块依赖。
- 不完整的异常处理。
- 潜在的兼容性问题。
- 未经验证的技术假设。

最好让 Agent 不直接沿用原设计者的判断，而是独立验证关键结论。

### Step 3：分析评审问题并进行修改

AI 发现问题后，不应该全部无条件接受。

需要对每项问题进行判断：

- 是否确实存在？
- 是否有真实依据？
- 是否影响最终实现？
- 是否需要修改设计？
- 是否属于产品规则，需要重新确认？
- 是否只是优化建议，而非必须修改的问题？

建议将评审问题分类：

| 严重程度 | 定义 | 处理方式 |
|---|---|---|
| Critical | 设计存在重大错误，无法满足需求或存在严重风险 | 必须解决 |
| High | 重要功能遗漏、架构缺陷或关键设计问题 | 原则上必须解决 |
| Medium | 局部设计不完整或存在一定风险 | 评估后处理 |
| Low | 优化建议、文档表达或非关键改进 | 按需处理 |

修改完成后，可以针对存在问题的部分再次评审。

不需要每次都从头审查全部内容，但涉及接口、数据模型或架构调整时，需要检查相关章节的一致性。

### Step 4：确认最终评审结果

最终需要明确：

- 评审是否通过？
- 是否还有未解决的关键问题？
- 是否存在已经接受的遗留风险？
- 是否需要产品经理进一步确认？
- 是否已经具备进入编码阶段的条件？

当关键问题已经解决，剩余问题不影响当前开发范围，并且设计已经得到开发人员确认，就可以进入下一阶段。

## 4. AI 时代如何进行技术评审？

这是一个非常适合利用 AI 提效的环节。

甚至可以让 Agent 充当独立的技术评审者，对自己生成的设计进行反向审查。

但需要注意：

**不要只让同一个 Agent 生成设计，然后简单地问它设计有没有问题。**

因为它可能沿用之前的假设，难以发现自身设计中的盲区。

### 4.1 推荐的 AI 评审方式

建议采用两轮审查。

**第一轮：完整性审查（Completeness Review）**

重点检查：

- 是否覆盖全部需求？
- 是否遗漏功能和异常场景？
- 是否遗漏影响模块？
- 接口、数据和状态设计是否完整？
- 是否存在前后设计矛盾？

这一轮重点是找遗漏。

**第二轮：合理性审查（Correctness & Quality Review）**

重点检查：

- 技术方案是否合理？
- 架构是否存在过度设计？
- 模块职责是否清晰？
- 是否存在更简单的实现？
- 是否存在数据一致性或兼容性问题？
- 是否存在安全和性能风险？

这一轮重点是找设计缺陷。

简单需求可以合并为一轮，复杂需求则可以分开执行。

### 4.2 AI 可以承担什么？

| 工作内容 | AI 的作用 |
|---|---|
| 需求追踪 | 检查需求与技术设计的覆盖关系 |
| 设计审查 | 检查架构和详细设计 |
| 一致性检查 | 发现不同章节之间的矛盾 |
| 风险分析 | 识别潜在技术风险 |
| 反向质疑 | 从独立评审角度挑战现有方案 |
| 问题分类 | 根据严重程度整理评审问题 |
| 文档修订 | 根据确认的问题辅助修改设计 |
| 复审 | 检查修改是否解决了原有问题 |

### 4.3 开发人员需要负责什么？

- 提供完整且准确的评审输入。
- 判断 AI 发现的问题是否真实。
- 对关键业务规则进行确认。
- 审核技术方案是否合理。
- 决定哪些问题必须修改。
- 确认遗留风险是否可接受。
- 最终决定是否通过评审。

需要特别注意：

AI 评审不能替代真实代码验证。

例如，AI 认为某个公共接口没有影响其他调用方，但实际项目可能存在动态调用、消息订阅或运行时注册机制。

因此，对于重要结论，仍然需要结合真实代码、测试和项目约束进行验证。

### 4.4 AI 技术评审提示词

```text
# Role

你是一名独立的软件架构评审专家。

你的任务不是帮助设计者证明当前方案合理，
而是以审慎、客观和批判性的角度审查整份 Technical SPEC，
主动发现遗漏、矛盾、不合理设计和潜在风险。

# Context

当前已经完成：
1. Requirement Specification
2. Repository Exploration
3. Impact Analysis
4. Solution Exploration
5. Architecture Design
6. Detailed Design

请基于完整需求文档、项目代码信息和技术设计开展评审。

# Review Scope

1. Requirement Coverage
   - 是否覆盖所有功能需求？
   - 是否遗漏重要场景和业务规则？

2. Impact Coverage
   - 是否遗漏受影响模块？
   - 是否考虑上下游依赖及兼容性？

3. Solution Validation
   - 技术方案是否合理？
   - 是否存在不必要的技术引入？
   - 关键假设是否得到验证？

4. Architecture Review
   - 模块职责是否清晰？
   - 依赖关系是否合理？
   - 交互和数据流是否完整？
   - 是否存在过度设计？

5. Detailed Design Review
   - 接口定义是否完整？
   - 数据模型是否合理？
   - 核心逻辑是否明确？
   - 状态和异常处理是否充分？

6. Quality Attributes
   - 是否存在性能、安全、可靠性、
     数据一致性和兼容性风险？

7. Cross-document Consistency
   - 不同设计章节之间是否存在矛盾？
   - 需求、架构、接口和数据定义是否一致？

# Constraints

- 必须以原始需求和项目实际情况作为评审依据。
- 不要默认当前设计一定正确。
- 不要为了提出问题而刻意挑刺。
- 每个问题必须说明具体依据。
- 尽可能指出对应的需求 ID、模块、文件或设计章节。
- 区分确定问题、潜在风险和优化建议。
- 不得编造项目事实或技术问题。
- 无法确认的内容标记为待验证。
- 不要直接修改项目代码。

# Severity

Critical：重大错误，阻止进入开发。
High：重要设计缺陷，原则上需要解决。
Medium：一般设计问题，需要评估处理。
Low：优化建议或非关键问题。

# Output

1. Overall Review Conclusion
2. Requirement Coverage Issues
3. Impact Analysis Issues
4. Solution & Architecture Issues
5. Detailed Design Issues
6. Cross-document Consistency Issues
7. Quality & Security Risks
8. Review Findings

对于每个问题，请提供：
- Issue ID
- Severity
- 问题描述
- 具体依据
- 潜在影响
- 修改建议

最后给出：
- 必须修改的问题
- 建议修改的问题
- 可以接受的遗留风险
- 是否具备进入开发阶段的条件

注意：只有经过证据支持的评审问题才能作为正式 Findings。
```

## 6. 如何判断技术评审已经完成？

建议使用以下检查清单：

- 已经使用原始需求检查技术设计的完整性。
- 已经检查需求与设计之间的追踪关系。
- 已经检查主要影响范围和上下游依赖。
- 已经评估技术方案的合理性。
- 已经检查模块职责和架构关系。
- 已经检查接口、数据模型和核心业务逻辑。
- 已经检查异常处理和状态流转。
- 已经检查关键工程质量要求。
- 所有 Critical 和 High 问题已经解决。
- 剩余风险和待处理事项已经明确。
- 开发人员已经确认最终评审结论。

**判断标准：技术设计已经经过系统性检查，关键问题得到解决，并且能够作为后续开发的可靠依据。**

## 7. 本阶段核心认知总结

1. **技术评审的对象是完整 Technical SPEC，而不是单独的架构图。**

2. **技术评审的核心是主动寻找问题。** 不要只是让 AI 总结设计或证明方案合理。

3. **需求覆盖检查非常重要。** 必须回到原始需求，确认所有功能和关键场景都有对应设计。

4. **需要检查不同设计章节之间的一致性。** 架构、接口、数据和业务逻辑不能各自成立但组合后互相矛盾。

5. **AI 适合承担大量设计审查工作。** 但评审结论必须有实际依据，不能把 AI 的推测直接视为事实。

6. **问题需要分级处理。** 重大设计缺陷必须解决，一般优化建议可以根据成本和收益决定。

7. **评审不是一次性动作。** 如果评审后修改了重要设计，需要针对修改内容进行复审。

8. **技术评审不是追求零风险。** 而是在充分理解风险的前提下，确认当前设计是否值得进入开发。

## 8. 在整个研发流程中的位置

Technical Review 是 Technical Design 的第六个环节。

**Input：**

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。
- Solution Exploration。
- Architecture Design。
- Detailed Design。

**Process：**

- 需求覆盖检查。
- 影响范围检查。
- 技术方案审查。
- 架构合理性审查。
- 详细设计审查。
- 工程质量检查。
- 问题修复与复审。

**Output：**

- Technical Review Record。
- Review Findings。
- 问题修改记录。
- 遗留风险清单。
- 最终评审结论。

后续流程：

```text

       |
       v

       |
       v

       |
       v

       |
       v
04 架构设计
       |
       v
05 详细设计
       |
       v
06 技术评审
       |
       v

```

**最终目标：通过 AI 辅助审查和开发人员最终确认，尽可能在编码之前发现技术设计中的问题，确保后续 AI Agent 能够基于一份经过验证的 Technical SPEC 开展开发。**
