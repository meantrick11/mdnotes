# 03. 方案探索（Solution Exploration）

> 本阶段定位：在完成项目代码库探索和影响分析之后，针对本次需求涉及的技术问题，研究可行的实现方式，评估现有技术能力与候选方案，必要时开展技术验证，最终确定合理的技术方案，为后续架构设计和详细设计提供依据。

## 1. 为什么需要方案探索？

在完成前两个阶段之后，我们已经明确了：

- 本次需求需要实现什么？
- 当前项目使用什么技术栈和架构？
- 本次需求会影响哪些模块？
- 哪些现有能力可以复用？
- 哪些地方需要扩展、修改或新增？
- 当前项目有哪些技术约束？

但这些信息还不足以直接确定最终的实现方案。

因为面对同一个技术问题，往往存在多种实现方式。

例如：

> 现有系统需要增加 PDF 文件解析能力。

经过前面的分析，我们发现：

- 当前项目已经有文件上传能力。
- 已经存在统一的文件解析模块。
- 当前解析模块仅支持 DOCX。
- PDF 文件需要提取文本内容。
- 解析结果需要交给后续 AI 笔记生成流程。

接下来就需要考虑：

- 是否可以直接扩展现有解析库？
- 是否需要引入新的 PDF 解析库？
- 是否需要引入第三方文档解析服务？
- 是否需要 OCR 能力？
- 是否需要调整现有解析模块的实现方式？

这些问题都需要进一步研究和判断。

如果没有经过方案探索，直接进入架构设计，很容易出现：

1. **技术选型随意**：根据个人熟悉程度直接选择技术，没有考虑其他可行方案。
2. **重复建设**：没有充分利用项目现有能力，引入不必要的技术依赖。
3. **过度设计**：简单需求引入复杂架构，增加系统维护成本。
4. **技术风险滞后**：关键技术问题没有提前验证，直到正式开发才发现无法满足需求。
5. **缺少决策依据**：无法解释为什么选择当前方案，以及其他方案为什么不适合。

因此，方案探索的核心目的有三个：

- **寻找可行方案**：针对当前需求中的技术问题，找到合理的实现路径。
- **评估方案优劣**：比较不同方案的适用性、成本、复杂度和风险。
- **形成技术决策**：确定最终采用什么方案，以及为什么采用它。

核心原则：

**方案探索不是为了寻找最先进的技术，而是为了找到满足需求、适合当前项目、复杂度合理且长期可维护的技术方案。**

## 2. 方案探索需要关注什么？

方案探索不意味着每次都要进行完整的技术调研。

应该根据前面的影响分析结果，识别真正需要研究和决策的技术问题。

主要关注以下四个方面。

### 2.1 现有技术能力评估

首先判断当前项目已有的技术能力是否能够满足需求。

重点关注：

- 现有模块是否已经具备相关能力？
- 是否可以直接复用现有实现？
- 是否只需要扩展现有能力？
- 当前技术库是否支持新的业务场景？
- 是否需要调整现有实现？

建议优先考虑：

1. 直接复用现有能力。
2. 在现有能力上进行扩展。
3. 优化或调整现有实现。
4. 引入新的技术、组件或服务。

例如：

当前项目已经存在文件解析模块，只是尚未支持 PDF。

首先应该确认现有解析库是否已经支持 PDF，而不是直接寻找新的 PDF 解析技术。

需要注意：

这不是绝对的优先级。如果现有实现存在明显缺陷，或者无法满足未来业务要求，也可以考虑替换。

**核心目标：尽可能利用现有项目能力，避免重复建设和不必要的技术引入。**

### 2.2 技术实现方案探索

当现有能力无法直接满足需求，或者存在多种实现路径时，需要进一步探索候选方案。

重点关注：

- 同一个技术问题是否存在多种实现方式？
- 不同方式的核心区别是什么？
- 哪种方式更适合当前项目？
- 是否需要引入新的组件或服务？
- 是否会改变现有模块之间的协作方式？

例如：

PDF 文件解析可能有以下方案：

| 方案 | 实现方式 | 特点 |
|---|---|---|
| A | 扩展现有解析库 | 改造范围较小 |
| B | 引入独立 PDF 解析库 | 技术选择更加灵活 |
| C | 使用第三方解析服务 | 减少自行维护解析能力的成本 |
| D | 自建统一文档解析服务 | 便于统一管理多种解析能力，但建设成本较高 |

需要注意：

候选方案不需要越多越好，保留真正可行且有比较价值的方案即可。

也不是所有需求都需要多个候选方案。如果现有项目已经有成熟且合理的实现方式，直接沿用即可。

**核心目标：针对真正需要解决的技术问题，找到合理的实现路径。**

### 2.3 技术选型与可行性验证

如果候选方案涉及新的框架、技术库、第三方服务或基础设施，就需要进一步研究其适用性。

重点关注：

| 评估维度 | 关注内容 |
|---|---|
| 功能能力 | 是否满足当前需求？ |
| 项目兼容性 | 是否兼容当前技术栈和运行环境？ |
| 性能 | 处理速度、资源占用是否合理？ |
| 稳定性 | 技术是否成熟，是否存在明显缺陷？ |
| 开发成本 | 集成和改造是否复杂？ |
| 维护成本 | 后续升级和维护是否方便？ |
| 扩展能力 | 是否能够满足未来可能的扩展？ |
| 安全性 | 是否存在安全隐患？ |
| 运行成本 | 是否需要额外资源或服务费用？ |

对于存在不确定性的关键技术问题，需要进一步验证。

常见验证方式：

- **官方文档研究**：确认功能、API、版本和兼容性。
- **源码研究**：理解现有实现或第三方技术的底层机制。
- **技术实验**：通过最小代码验证某项能力是否可用。
- **PoC**：针对复杂技术路径构建小型验证原型。
- **Benchmark**：对性能、资源占用等进行实际测试。

例如：

如果需要支持扫描版 PDF，就不能仅仅确认某个解析库支持 PDF，还需要验证它是否具备 OCR 能力，或者是否需要额外集成 OCR 技术。

注意：

不是每个技术选型都需要 PoC。只有当关键技术存在不确定性，且错误选择的代价较高时，才值得进行专门验证。

**核心目标：确认候选技术不仅理论上可行，而且能够满足当前项目的实际要求。**

### 2.4 技术成本与风险评估

最终选择技术方案时，不能只考虑功能能否实现，还需要考虑长期成本。

重点关注：

- 是否增加新的技术依赖？
- 是否需要调整现有架构？
- 是否增加系统复杂度？
- 是否增加运行资源和服务费用？
- 是否增加后续维护成本？
- 是否存在第三方服务依赖？
- 是否存在兼容性和迁移风险？
- 是否会影响现有功能？

例如：

| 方案 | 开发成本 | 运行成本 | 维护成本 | 主要风险 |
|---|---|---|---|---|
| 扩展现有解析库 | 低 | 低 | 低 | 现有能力存在限制 |
| 引入新解析库 | 中 | 低 | 中 | 新依赖维护 |
| 第三方解析服务 | 低 | 中/高 | 低/中 | 外部服务依赖 |
| 自建解析服务 | 高 | 中/高 | 高 | 建设和运维复杂度 |

具体评价应当有实际依据。

无法确定的成本和风险应该标记为待验证，而不是为了填满表格而编造数据。

**核心目标：选择不仅能够实现需求，而且长期成本和风险可接受的方案。**

## 3. 如何进行方案探索？

实际执行时，不需要机械地完成所有技术调研，而是按照以下四个步骤开展。

### Step 1：识别需要解决的技术问题

回到前两个阶段的产出：

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。

整理本次需求中真正需要进行技术决策的问题。

例如：

| ID | 技术问题 | 产生原因 |
|---|---|---|
| TP-001 | PDF 使用什么方式解析？ | 当前只支持 DOCX |
| TP-002 | 是否需要 OCR？ | 可能需要支持扫描版 PDF |
| TP-003 | 是否需要调整任务处理方式？ | 文件解析可能耗时较长 |

这里需要区分：

- 已经有成熟实现，可以直接复用的问题。
- 存在多种技术路径，需要比较的问题。
- 存在技术不确定性，需要验证的问题。
- 业务规则不明确，需要返回需求阶段确认的问题。

不是所有问题都需要技术调研。

例如，是否支持某种特殊文件类型，如果这属于产品规则，就应该由产品经理确认，而不是由开发人员自行决定。

### Step 2：研究候选方案

针对需要解决的技术问题，寻找可行的实现方式。

例如：

TP-001：PDF 如何解析？

- 方案 A：扩展现有解析库。
- 方案 B：引入新的 PDF 解析库。
- 方案 C：使用第三方解析服务。

研究时优先参考：

- 当前项目已有实现。
- 官方技术文档。
- 技术库的官方说明和源码。
- 可靠的技术案例。
- 实际项目集成经验。

对于新的技术依赖，需要关注其版本、兼容性、维护情况和集成成本。

### Step 3：比较方案并进行必要验证

将候选方案放在统一的标准下进行比较。

例如：

| 评估维度 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|
| 功能满足程度 | 高 | 高 | 高 |
| 项目兼容性 | 高 | 中 | 中 |
| 开发成本 | 低 | 中 | 低 |
| 维护成本 | 低 | 中 | 低/中 |
| 外部依赖 | 无新增 | 无新增 | 依赖第三方 |
| 扩展能力 | 中 | 高 | 高 |

如果某个关键指标无法通过文档确认，就需要通过实验或 PoC 验证。

例如：

- 不同解析库对中文 PDF 的支持情况。
- 扫描版 PDF 的 OCR 准确率。
- 大文件解析时的内存占用。
- 新技术与当前框架的兼容性。

对于简单需求，直接比较即可；对于复杂需求，才需要深入研究和验证。**（如果方案不是那么成熟，那么可能需要理论方案可行性排除-poc验证方案（如果是模型可能还涉及数据集搭建、微调方案、gpu约束等等内容的设计）-具体实验-记录实验必要参数和结果-后续内容。）**

### Step 4：确定推荐方案并记录决策

最终需要明确：

- 采用什么方案？
- 为什么选择它？
- 相比其他方案有什么优势？
- 为什么不采用其他候选方案？
- 是否存在尚未解决的风险？
- 是否还有需要进一步确认的问题？

例如：

**推荐方案：**

扩展现有文件解析模块，增加 PDF 解析能力，继续复用现有文件存储和任务处理机制。

**选择原因：**

1. 最大程度复用现有系统能力。
2. 不需要重新建设独立解析服务。
3. 对现有架构的改动范围较小。
4. 后续可以根据实际需求扩展 OCR 能力。

**遗留问题：**

扫描版 PDF 是否需要支持 OCR，需要结合产品需求进一步确认。

注意：以上仅为示例，真实决策需要以实际代码和技术验证结果为依据。

## 4. AI 时代如何进行方案探索？

方案探索是 AI 非常适合发挥作用的环节。

AI 可以帮助开发人员快速搜索技术资料、阅读官方文档、研究源码、比较候选方案，甚至编写 PoC。

但不能让 Agent 直接根据需求生成一个它认为最好的技术方案。

更合理的方式是：

**先让 AI 理解问题，再让 AI 研究方案，最后由开发人员审核并确定技术决策。**

### 4.1 AI 可以承担的工作

| 工作内容 | AI 的作用 |
|---|---|
| 技术问题识别 | 根据需求和影响分析提取技术问题 |
| 候选方案研究 | 搜索不同的技术实现路径 |
| 技术选型 | 比较框架、库和第三方服务 |
| 文档研究 | 阅读官方文档和技术资料 |
| 源码分析 | 研究技术库的实现和能力限制 |
| 可行性验证 | 辅助编写实验代码和 PoC |
| 方案对比 | 整理不同方案的优缺点和风险 |
| 决策文档 | 生成技术方案和决策记录 |

### 4.2 开发人员需要负责什么？

- 判断技术问题是否真实存在。
- 确认候选方案是否适合当前项目。
- 核实 AI 提供的技术资料和结论。
- 判断是否有必要引入新的技术依赖。
- 审核 PoC 的验证结果。
- 确认成本和风险是否可以接受。
- 最终确定推荐方案。

尤其需要注意：

AI 可能推荐一个技术上很先进、但对于当前项目而言完全没有必要的方案。

因此，不能只看技术能力，还需要考虑现有项目的实际情况。

### 4.3 AI 方案探索提示词

```text
# Role
你是一名资深技术架构师，负责协助开发人员进行技术方案探索。

# Context
当前已经完成：
1. Requirement Analysis
2. Repository Exploration
3. Impact Analysis

请基于当前需求和项目实际情况，开展技术方案探索。

# Tasks

1. 识别本次需求中真正需要进行技术决策的问题。

2. 优先分析项目现有能力：
   - 是否可以直接复用？
   - 是否可以扩展？
   - 是否需要调整现有实现？

3. 对确实需要研究的问题，提出合理的候选方案。

4. 对比不同方案：
   - 功能满足程度
   - 项目兼容性
   - 开发成本
   - 运行成本
   - 维护成本
   - 扩展能力
   - 技术风险

5. 对存在关键不确定性的技术问题，
   提出必要的实验或 PoC 验证建议。

6. 给出推荐方案，并说明：
   - 为什么选择它？
   - 其他方案为什么不适合？
   - 是否存在遗留风险？
   - 哪些问题仍需确认？

# Constraints

- 优先考虑复用现有项目能力。
- 不要为了技术先进而引入不必要的依赖。
- 技术结论必须有可靠依据。
- 不允许编造性能、成本和兼容性数据。
- 区分已验证事实、推测和待验证事项。
- 不要提前进行详细架构设计。
- 当前阶段只进行技术研究和方案决策，不修改正式业务代码。

# Output

1. Technical Problems
2. Existing Capability Assessment
3. Candidate Solutions
4. Solution Comparison
5. Recommended Solution
6. Technical Risks & Open Questions
```

## 5. 方案探索的最终产出

本阶段不需要生成一份非常庞大的技术调研报告。

建议最终只沉淀一份简洁的方案决策记录。

### Technical Solution

**1. 技术问题**

本次需求有哪些需要解决的技术问题？

**2. 现有能力评估**

当前项目是否已经存在可以复用的技术能力？

**3. 候选方案**

有哪些可行的实现方式？

**4. 方案对比**

不同方案在功能、兼容性、开发成本、维护成本和风险方面有什么区别？

**5. 推荐方案**

最终决定采用什么方案？为什么？

**6. 技术验证**

是否进行了文档研究、实验或 PoC？结果是什么？

**7. 遗留问题**

还有哪些问题需要在后续架构设计或需求澄清中进一步确认？

对于简单需求，上述内容可以合并成几段文字；对于复杂需求，再详细记录技术选型和验证结果。

## 6. 如何判断方案探索已经完成？

不需要研究所有技术，也不需要穷举所有可能性。

满足以下条件，就可以进入架构设计：

- 已明确本次需求真正需要解决的技术问题。
- 已评估现有项目能力是否可以复用。
- 需要选型的技术已经有合理的推荐方案。
- 关键技术不确定性已经得到必要验证。
- 已经明确推荐方案及选择原因。
- 主要技术风险和待确认事项已经记录。

**判断标准不是调研了多少技术，而是是否已经具备足够的信息，可以开始设计系统如何组织和协作。**

## 7. 本阶段核心认知总结

1. **方案探索是为了解决技术选择问题，而不是直接设计系统架构。**

2. **优先复用现有技术能力。** 不要为了技术先进而重复建设或引入不必要的依赖。

3. **不是每个需求都需要完整的技术调研。** 简单需求沿用成熟方案，复杂需求再深入研究。

4. **技术选型需要考虑项目适配性。** 不仅要关注功能，还要考虑兼容性、开发成本、维护成本和长期风险。

5. **关键技术假设需要验证。** 对于不确定且影响较大的问题，通过实验或 PoC 降低风险。

6. **AI 负责加速研究，开发人员负责技术决策。** 最终方案必须经过开发人员理解和确认。

7. **方案探索的最终目的是形成明确的技术决策。** 不要让技术调研无限延伸，影响后续设计和开发。

## 8. 在整个研发流程中的位置

**Input：**

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。
- 当前项目技术约束。

**Process：**

- 识别技术问题。
- 评估现有技术能力。
- 研究候选实现方案。
- 必要时开展技术验证。
