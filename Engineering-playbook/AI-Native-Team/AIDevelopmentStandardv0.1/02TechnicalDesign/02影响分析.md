# 02. 影响分析（Impact Analysis）

> 本阶段定位：在理解现有项目的基础上，结合本次需求，识别需求可能涉及的系统模块、代码、接口、数据及上下游依赖，明确需要修改、复用、新增或关注的范围，为后续技术方案探索与设计提供依据。
>
> 核心问题：本次需求会影响什么？为什么会影响？影响范围有多大？有哪些潜在风险？

---

## 1. 为什么需要影响分析？

在完成 Requirement Analysis 和 Repository Exploration 之后，我们已经具备了两个重要信息：

**Requirement Analysis：**

明确本次需求需要解决什么问题、系统需要提供哪些功能，以及对应的业务规则和验收标准。

**Repository Exploration：**

理解当前项目的技术栈、系统架构、模块职责、核心业务调用链、数据模型和开发规范。

但是，这些信息还不足以直接确定本次需求的实际开发范围。

因为一个需求可能涉及多个功能域，也可能横跨多个微服务、代码模块和数据模型。

例如：

> 用户上传 PDF 文件后，系统自动解析文件内容，并通过 AI 生成笔记，最后允许用户查看和编辑。

从需求层面看，涉及：

- 文件上传。
- 文件解析。
- AI 笔记生成。
- 笔记查看。
- 笔记编辑。

但结合现有项目，可能发现：

- 文件上传能力已经存在，可以直接复用。
- 文件解析模块只支持 DOCX，需要扩展 PDF。
- AI 调用已经封装，但没有笔记生成的业务能力。
- 笔记模块已经存在，需要增加新的数据关联。
- 任务模块需要支持新的异步处理流程。
- 前端需要增加文件处理状态展示。

如果没有进行影响分析，开发人员很容易：

1. 不知道本次需求实际需要修改哪些模块。
2. 重复开发已有能力。
3. 只关注直接涉及的功能，忽略间接影响。
4. 忽略接口、数据模型和上下游依赖。
5. 低估改动范围和技术风险。
6. 在编码过程中不断发现新的修改点，导致开发计划反复调整。

因此，影响分析的核心目的有四个：

1. **明确影响范围**：识别本次需求涉及哪些现有模块、代码和系统能力。
2. **识别复用与改造机会**：明确哪些能力可以直接复用、哪些需要扩展、哪些需要新增。
3. **发现间接影响**：识别由于模块依赖、数据变化和接口变化而受到影响的其他功能。
4. **识别技术风险**：提前发现兼容性、数据一致性、功能回归和系统耦合等问题。

核心原则：

**影响分析不是简单地找出需要修改的文件，而是分析本次需求的变化会传播到现有系统的哪些部分，以及这些变化可能带来什么影响。**

---

## 2. 影响分析应该分析什么？

影响分析不是只关注需求直接涉及的业务模块，而是需要从系统的多个维度进行分析。

我建议主要关注以下八个维度。

### 2.1 功能模块影响（Functional Impact）

首先明确本次需求会影响哪些已有功能，以及是否需要新增系统能力。

重点关注：

- 哪些现有功能需要修改？
- 哪些现有功能可以直接复用？
- 是否需要新增功能？
- 是否会改变已有功能的行为？
- 是否影响其他功能的正常使用？
- 是否存在多个功能共享同一能力的情况？

例如：

本次需要支持 PDF 文件解析。

| 功能 | 当前情况 | 影响类型 | 说明 |
|---|---|---|---|
| 文件上传 | 已支持 | 复用 | 沿用现有上传能力 |
| 文件解析 | 仅支持 DOCX | 修改 / 扩展 | 增加 PDF 解析能力 |
| AI 笔记生成 | 已存在 AI 调用能力 | 复用 / 扩展 | 增加笔记生成业务逻辑 |
| 笔记管理 | 已存在 | 修改 | 可能需要关联源文件 |
| 任务管理 | 已存在 | 修改 | 增加新的任务处理类型 |

这里需要区分几种不同的影响类型：

| 类型 | 含义 |
|---|---|
| Reuse | 直接复用现有能力，无需修改 |
| Extend | 在现有能力上增加新的支持 |
| Modify | 修改现有实现或行为 |
| New | 新增能力或模块 |
| Remove | 删除不再需要的能力 |
| Unchanged | 已确认不受本次需求影响 |

注意：

不要因为某个功能域与本次需求有关，就认为它一定需要修改。需要结合实际代码确认。

**探索目标：明确本次需求涉及哪些功能，以及每项功能需要进行什么类型的变化。**

### 2.2 代码模块与文件影响（Code Impact）

明确本次需求可能涉及哪些实际代码位置。

重点关注：

- 哪些 Controller / Router 需要修改？
- 哪些 Service 需要修改或新增？
- 哪些 Repository / DAO 需要调整？
- 是否需要新增公共组件或工具类？
- 是否需要修改前端页面和组件？
- 是否涉及公共基础模块？
- 是否存在多个模块引用同一代码的情况？

例如：

| 代码位置 | 当前职责 | 影响类型 | 影响说明 |
|---|---|---|---|
| file/controller | 文件接口入口 | Reuse | 沿用现有上传入口 |
| file/service | 文件业务处理 | Extend | 支持新的文件类型 |
| parser/service | 文件解析 | Modify | 增加 PDF 解析逻辑 |
| note/service | 笔记业务 | Extend | 增加文件解析结果关联 |
| task/service | 任务管理 | Modify | 扩展任务处理流程 |

这里需要注意：

影响分析阶段可以定位到具体目录、类和函数，但不要求立即确定每一处代码应该如何修改。

具体的修改方案留到后续技术设计阶段。

**探索目标：从功能影响进一步定位到实际代码实现，明确潜在的改动位置。**

### 2.3 接口影响（API & Integration Impact）

分析本次需求是否会影响系统内部或外部的接口契约。

重点关注：

- 是否需要新增 API？
- 是否需要修改已有 API？
- 请求参数是否发生变化？
- 响应结构是否发生变化？
- 是否需要修改内部服务之间的调用接口？
- 是否影响第三方服务接口？
- 是否影响其他系统对当前接口的调用？
- 是否存在接口兼容性问题？

例如：

| 接口 | 当前情况 | 影响类型 | 影响说明 |
|---|---|---|---|
| 文件上传 API | 已存在 | Extend | 可能需要扩展文件类型支持 |
| 文件解析 API | 已存在 | Modify | 增加 PDF 解析支持 |
| 笔记生成 API | 不存在 | New | 新增生成笔记的接口 |
| 任务查询 API | 已存在 | Unchanged / Extend | 视状态展示要求判断 |

需要特别注意：

接口不仅包括前端调用的 HTTP API，还包括：

- 内部 RPC 接口。
- 消息队列消息结构。
- 事件订阅与发布契约。
- 第三方 API。
- 共享 SDK 或公共接口。

如果修改了某个公共接口，需要进一步了解有哪些调用方可能受到影响。

**探索目标：明确本次需求对系统通信契约的影响，以及可能受到影响的调用方。**

### 2.4 数据影响（Data Impact）

分析本次需求是否会影响已有数据结构和数据处理方式。

重点关注：

- 是否需要新增数据表？
- 是否需要修改现有字段？
- 是否需要增加关联关系？
- 是否需要修改数据类型？
- 是否影响数据查询逻辑？
- 是否影响数据写入和更新逻辑？
- 是否涉及历史数据兼容？
- 是否涉及数据迁移？
- 是否影响数据生命周期？

例如：

本次需求需要将生成的笔记与源文件关联。

可能涉及：

| 数据对象 | 当前情况 | 影响类型 | 影响说明 |
|---|---|---|---|
| File | 已存在 | Unchanged | 继续使用现有文件数据 |
| Note | 已存在 | Extend | 可能需要增加源文件关联 |
| Task | 已存在 | Extend | 可能需要记录处理任务类型 |
| File-Note Relation | 不存在 | New | 根据数据模型决定是否新增关联 |

需要特别关注：

**数据结构的变化往往不只影响当前功能，还可能影响历史数据、其他查询逻辑和下游业务。**

例如：

新增一个数据库字段，看起来只是简单修改，但还需要考虑：

- 原有记录是否有该字段？
- 历史数据如何处理？
- 该字段是否允许为空？
- 是否需要建立索引？
- 是否影响已有查询？
- 是否需要数据库迁移？
- 是否影响其他服务的数据消费？

具体的数据结构和迁移方案留到后续详细设计阶段确定。

**探索目标：识别本次需求对数据结构、数据流转及历史数据的潜在影响。**

### 2.5 上下游依赖影响（Dependency Impact）

这是影响分析中非常重要的一部分。

因为一个模块的变化可能会通过依赖关系影响其他模块。

重点关注：

- 当前模块依赖哪些其他模块？
- 是否有其他模块依赖当前模块？
- 修改公共能力会影响哪些调用方？
- 是否影响上游数据提供方？
- 是否影响下游数据消费者？
- 是否存在跨服务调用？
- 是否存在消息事件或异步任务依赖？

例如：

当前项目存在以下调用关系：

```text
File Service
     |
     v
Parser Service
     |
     v
AI Service
     |
     v
Note Service
```

如果修改 Parser Service 的返回数据结构，就需要进一步确认：

- AI Service 是否依赖原有解析结果？
- 其他文件处理功能是否也调用 Parser Service？
- 是否有异步任务依赖原有结果格式？
- 是否有其他服务直接消费解析结果？

这说明：

**影响范围不能只看本次需求直接修改的模块，还需要沿着依赖关系检查可能受到影响的其他模块。**

尤其需要关注：

1. 公共组件。
2. 被多个模块调用的 Service。
3. 共享数据模型。
4. 公共接口。
5. 消息事件。
6. 跨服务依赖。

**探索目标：识别直接改动之外，可能受到连带影响的系统部分。**

### 2.6 配置与基础设施影响（Infrastructure Impact）

分析本次需求是否需要调整项目运行环境或基础设施。

重点关注：

- 是否需要新增环境变量？
- 是否需要调整配置文件？
- 是否需要新增第三方依赖？
- 是否需要增加新的基础设施服务？
- 是否需要调整 Docker 或部署配置？
- 是否需要新增消息队列、存储或缓存能力？
- 是否需要调整权限、网络或资源配置？
- 是否涉及 CI/CD 流程变化？

例如：

引入新的 OCR 能力，可能需要：

- 增加 OCR SDK。
- 配置第三方 API Key。
- 增加相关环境变量。
- 调整网络访问权限。
- 增加服务调用监控。

这些变化可能不涉及主要业务代码，但依然属于本次需求的技术影响范围。

**探索目标：识别业务代码之外的配置、依赖和运行环境变化。**

### 2.7 测试与质量影响（Testing Impact）

分析本次需求需要验证哪些已有功能和系统行为。

重点关注：

- 是否需要新增单元测试？
- 是否需要修改现有测试？
- 是否需要新增集成测试？
- 是否影响已有 E2E 测试？
- 是否需要覆盖新的异常场景？
- 是否需要回归测试其他功能？
- 是否影响性能或安全测试？

例如：

增加 PDF 解析能力后，至少需要考虑：

| 测试范围 | 关注内容 |
|---|---|
| 文件上传测试 | PDF 是否能够正常上传 |
| 解析单元测试 | PDF 内容能否正确提取 |
| 异常测试 | 损坏文件如何处理 |
| 集成测试 | 上传到解析的完整流程 |
| 笔记生成测试 | 解析结果能否正确进入 AI 生成流程 |
| 回归测试 | 原有 DOCX 解析是否正常 |

需要注意：

影响分析阶段主要识别测试范围和受影响的测试对象，具体测试用例和测试策略可以在后续设计阶段进一步明确。

**探索目标：明确本次需求需要验证哪些新能力，以及哪些原有功能需要回归验证。**

### 2.8 非功能与运行影响（Non-functional Impact）

除了功能本身，还需要关注本次需求可能对系统整体运行产生的影响。

重点关注：

| 维度 | 需要分析的问题 |
|---|---|
| Performance | 是否增加响应时间、CPU、内存或数据库压力？ |
| Scalability | 并发量增加后是否存在扩展问题？ |
| Security | 是否引入新的权限、数据泄露或攻击面？ |
| Reliability | 是否影响系统稳定性和故障恢复？ |
| Compatibility | 是否影响旧版本客户端或已有调用方？ |
| Maintainability | 是否增加系统复杂度和维护成本？ |
| Observability | 是否需要新增日志、指标和链路追踪？ |

例如：

新增大文件解析功能，可能带来：

- 单次任务占用大量内存。
- 长时间占用 Worker。
- 并发任务导致资源竞争。
- 文件解析失败后需要重试。
- 用户等待时间增加。

这些问题需要提前识别，避免只关注功能能够实现，而忽略系统运行质量。

**探索目标：识别本次需求对系统性能、安全、可靠性和长期维护的潜在影响。**

---

## 3. 如何进行影响分析？

前面八个维度是分析范围，但不能简单地逐项填写表格。

真正有效的影响分析，需要从需求出发，结合代码库逐步追踪。

我建议采用以下六个步骤。

### Step 1：明确本次需求涉及的功能

首先回到 Requirement Specification。

提取本次需求涉及的：

- 功能需求（FR）。
- 业务规则（BR）。
- 业务场景（SC）。
- 主要业务流程。
- 异常与边界场景。
- 验收标准（AC）。

将本次需求拆解成可以独立分析的功能点。

例如：

| 需求 ID | 功能描述 |
|---|---|
| FR-001 | 支持上传 PDF 文件 |
| FR-002 | 支持解析 PDF 内容 |
| FR-003 | 支持通过 AI 生成笔记 |
| FR-004 | 支持查看生成的笔记 |
| FR-005 | 支持编辑笔记 |

目的：明确本次需求具体涉及哪些系统行为，避免遗漏分析对象。

### Step 2：定位相关代码与现有实现

基于上一阶段的 Repository Exploration，定位每项功能在当前项目中的实现位置。

重点查找：

- 相关模块。
- 入口 Controller / Router。
- 核心 Service。
- 数据访问层。
- 相关 Entity / Model。
- API 接口。
- 公共组件。
- 相关测试。

例如：

| 需求 ID | 相关模块 | 相关代码位置 | 当前实现 |
|---|---|---|---|
| FR-001 | File | file/service | 已支持文件上传 |
| FR-002 | Parser | parser/service | 目前仅支持 DOCX |
| FR-003 | AI / Note | ai/service、note/service | 已有模型调用能力 |
| FR-004 | Note | note/controller | 已支持笔记查询 |
| FR-005 | Note | note/service | 已支持笔记编辑 |

这里需要强调：

不要只通过搜索关键词找到一个文件，就认为已经理解相关实现。

需要结合调用关系、实际逻辑和数据流，确认当前功能是如何工作的。

目的：建立需求功能与现有代码实现之间的对应关系。

### Step 3：识别影响类型

针对每个相关模块、代码和数据对象，判断本次需求究竟需要进行什么变化。

统一使用以下分类：

| 影响类型 | 含义 | 判断标准 |
|---|---|---|
| Reuse | 直接复用 | 现有能力已经满足需求 |
| Extend | 扩展能力 | 在现有能力上增加支持 |
| Modify | 修改实现 | 现有逻辑或行为需要调整 |
| New | 新增能力 | 当前不存在，需要新建 |
| Remove | 移除能力 | 本次需求要求废弃相关能力 |
| Unchanged | 不受影响 | 已确认不需要调整 |

例如：

PDF 解析需求：

- 文件上传：Reuse。
- 文件解析：Extend。
- AI 笔记生成：New / Extend，取决于现有实现。
- 笔记查询：Reuse。
- 笔记关联源文件：Extend。

需要注意：

这些分类是为了描述变化性质，并不意味着某种类型一定需要修改代码。

例如 Reuse 表示直接复用现有能力，而不是再实现一遍。

目的：明确每个相关部分需要发生什么变化。

### Step 4：沿依赖关系分析间接影响

这是影响分析中最容易遗漏的步骤。

当我们找到需要修改的模块后，还需要分析它的上下游依赖。

例如：

```text
Frontend
   |
   v
File Controller
   |
   v
File Service
   |
   v
Parser Service
   |
   v
AI Service
   |
   v
Note Service
   |
   v
Database
```

假设本次需要修改 Parser Service。

那么就不能只关注 Parser Service 自身，还需要确认：

- 哪些模块调用了它？
- 哪些功能依赖它的输出？
- 返回数据结构变化会影响谁？
- 是否存在异步任务依赖？
- 是否有其他文件类型共用这套解析逻辑？

这里需要区分：

**直接影响：** 本次需求明确需要修改或使用的模块。

**间接影响：** 由于直接影响引起的，可能需要调整或验证的其他模块。

并不是所有上下游模块都需要修改，但都应该判断是否存在影响。

目的：尽可能发现需求变化可能传播到的范围。

### Step 5：识别技术风险和验证范围

在明确影响范围后，需要进一步判断可能出现的问题。

重点考虑：

- 是否存在接口兼容性问题？
- 是否会影响历史数据？
- 是否会改变已有功能行为？
- 是否存在模块之间的循环依赖？
- 是否引入新的第三方依赖？
- 是否增加性能或资源压力？
- 是否需要调整部署配置？
- 哪些已有功能需要回归测试？

例如：

如果扩展了公共文件解析模块，那么除了验证 PDF 解析是否正确，还需要验证原有 DOCX 解析是否受到影响。

将这些问题记录下来，作为后续技术设计和评审的输入。

目的：提前发现潜在风险，明确后续需要重点验证的范围。

### Step 6：整理影响分析结果

最后，将前面的分析汇总为结构化的影响范围清单。

至少需要明确：

1. 本次涉及哪些模块？
2. 哪些能力可以复用？
3. 哪些模块需要修改或扩展？
4. 是否需要新增能力？
5. 哪些接口和数据可能受到影响？
6. 哪些上下游模块需要关注？
7. 有哪些潜在风险？
8. 哪些内容仍然需要进一步确认？

完成后，进入下一阶段 Technical Exploration。

## 4. AI 时代如何进行影响分析？

影响分析非常适合使用 AI Agent，因为它涉及大量代码检索、依赖关系分析、调用链追踪和信息整理工作。

但需要注意：

**不能让 Agent 仅根据需求文档直接判断代码影响范围，而应该让它基于真实代码进行分析。**

推荐的工作方式：

### 4.1 AI 的主要工作

| 分析环节 | AI 可以承担的工作 |
|---|---|
| 需求提取 | 提取 FR、BR、SC、AC |
| 代码定位 | 搜索相关 Controller、Service、Repository |
| 调用链分析 | 追踪函数调用和模块依赖 |
| 现有能力分析 | 识别可复用、需要扩展的实现 |
| 接口分析 | 搜索相关 API、消息和调用方 |
| 数据分析 | 识别相关 Entity、Schema、数据库操作 |
| 间接影响分析 | 根据依赖关系识别潜在受影响模块 |
| 风险识别 | 发现兼容性、数据一致性和回归风险 |
| 文档生成 | 汇总影响范围和分析依据 |

### 4.2 开发人员的主要职责

AI 负责分析，但开发人员仍然需要判断：

- AI 是否正确理解了需求？
- 是否找到了真正的代码入口？
- 是否完整追踪了调用链？
- 是否遗漏了隐式依赖？
- 判断的影响范围是否合理？
- 是否把可能影响误判为确定影响？
- 风险是否真实存在？
- 是否存在更简单的复用方式？

特别是对于复杂项目，代码依赖关系可能并不完全体现在函数调用上。

例如：

- 通过消息队列进行异步通信。
- 通过事件订阅实现模块协作。
- 通过数据库共享数据。
- 通过配置决定不同模块行为。
- 通过反射或动态注册实现调用。

这些都可能造成 AI 单纯通过静态代码搜索无法发现完整影响范围。

因此，重要影响结论需要结合实际实现验证。

### 4.3 AI 影响分析的核心约束

建议始终要求 Agent 遵守以下原则：

1. 以真实代码为依据，不允许只根据需求推测修改范围。
2. 重要结论提供文件路径、类名、函数名。
3. 明确区分直接影响和间接影响。
4. 明确区分已确认影响和潜在影响。
5. 不能确定的内容标记为待验证。
6. 不要把所有相关模块都判定为需要修改。
7. 关注公共能力及其其他调用方。
8. 只进行分析，不提前修改代码。
9. 不要在本阶段擅自决定完整技术方案。

## 6. 如何判断影响分析已经完成？

影响分析并不要求提前找到所有可能受影响的代码，而是要达到足以支撑后续技术方案探索的程度。

建议使用以下检查清单：

| 检查项 | 完成标准 |
|---|---|
| 需求映射 | 本次需求功能点均有对应的项目实现分析 |
| 模块识别 | 已识别直接涉及的主要模块 |
| 影响类型 | 已区分复用、扩展、修改、新增等类型 |
| 代码定位 | 重要影响位置能够追溯到实际代码 |
| 接口影响 | 已检查相关接口和调用方 |
| 数据影响 | 已检查相关数据模型及数据流转 |
| 依赖分析 | 已识别主要上下游及共享能力 |
| 基础设施 | 已检查相关配置和运行环境 |
| 测试范围 | 已识别新功能及回归验证范围 |
| 风险识别 | 主要风险和待确认事项已经记录 |

当以上内容已经足以明确本次需求的技术影响范围，就可以进入下一阶段。

## 7. 本阶段核心认知总结

1. **影响分析不是简单地搜索需要修改的文件，而是分析需求变化对现有系统产生的影响。**

2. **影响分析必须基于真实项目实现。** 不能仅根据 PRD 或功能模块名称推测代码修改范围。

3. **不能只看直接影响，还要分析间接影响。** 特别是公共模块、共享数据、接口调用方和异步依赖。

4. **需要区分复用、扩展、修改和新增。** 不是每个相关模块都需要重新开发。

5. **影响分析不等于技术方案设计。** 本阶段确定影响范围和潜在问题，不提前决定具体如何实现。

6. **AI 可以加速代码定位、依赖追踪和风险识别，但最终影响范围需要开发人员验证。**

7. **分析深度应当与需求复杂度相匹配。** 简单需求不需要机械地展开所有影响维度，复杂的跨模块需求则需要更加充分的分析。

## 8. 在整个研发流程中的位置

Impact Analysis 是 Technical Design 的第二个环节。

**Input：**

- Requirement Specification。
- Repository Exploration 产出的项目认知。
- 当前项目真实代码。

**Process：**

- 需求功能映射。
- 相关代码定位。
- 功能模块影响分析。
- 接口与数据影响分析。
- 上下游依赖追踪。
- 技术风险及测试范围识别。

**Output：**

- Impact Analysis。
- 模块影响清单。
- 代码、接口及数据影响清单。
- 上下游依赖关系。
- 风险与待确认事项。

后续流程：

```text
00 SPEC 认知篇
       |
       v
01 项目代码库探索
       |
       v
02 影响分析
       |
       v
03 方案探索
       |
       v
04 架构设计
       |
       v
05 详细设计
       |
       v
06 技术评审
       |
       v
07 设计基线
```

**最终目标：在开始技术方案设计之前，明确本次需求会触及现有系统的哪些部分，哪些能力可以复用，哪些地方需要调整，以及这些变化可能带来的风险，从而让后续技术设计建立在准确的影响范围之上。**
