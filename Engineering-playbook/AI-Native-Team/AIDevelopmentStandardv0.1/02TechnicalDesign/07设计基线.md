# 07. 设计基线（Design Baseline）

> 本阶段定位：在技术设计通过评审之后，将最终确认的 Technical SPEC 正式确认为本次需求的技术设计基线，明确最终设计版本、设计范围、技术决策、遗留问题及后续变更规则，为后续 Implementation Planning、AI Coding 和质量验收提供统一、可靠的技术依据。
>
> 核心问题：最终以哪一份设计作为开发依据？后续开发应该遵循什么？如果设计发生变化，应该如何管理？

## 1. 为什么需要设计基线？

在完成前面的阶段之后，我们已经形成了完整的 Technical SPEC，并且通过了技术评审。

但这里还存在一个问题：

**经过评审的设计，如何正式成为后续开发的依据？**

例如：

一个需求经过多轮设计和评审，可能产生了多个版本：

- V1：最初的技术设计。
- V2：根据 AI 评审意见修改后的设计。
- V3：根据开发人员进一步确认后的最终设计。

那么后续 Agent 开始编码时，究竟应该使用哪个版本？

如果没有明确的设计基线，很容易出现：

1. **版本混乱**：开发人员和 Agent 使用了不同版本的设计文档。
2. **设计偏离**：编码过程中 Agent 根据自己的理解修改原有设计。
3. **决策丢失**：之前确认的技术方案和设计约束没有得到保留。
4. **变更失控**：开发过程中发现新问题，直接修改设计，却没有同步其他相关内容。
5. **缺少追溯依据**：无法判断最终代码是否符合已经确认的技术设计。

因此，设计基线的核心目的有三个：

- **明确最终版本**：确认通过评审的 Technical SPEC 是后续开发的正式依据。
- **固定关键决策**：保留已经确认的技术方案、架构和实现约束。
- **管理后续变更**：确保开发过程中发生的设计调整能够被记录、评估和同步。

核心原则：

**设计基线不是将设计永久冻结，而是将当前已经确认的设计作为开发起点，后续发生变化时通过明确的变更流程进行更新。**

---

## 2. 设计基线需要明确什么？

设计基线不需要重新编写一份完整的技术设计文档，而是对已经评审通过的设计进行确认和管理。

主要关注以下四个方面。

### 2.1 最终设计版本（Baseline Version）

首先明确本次需求最终采用哪一份 Technical SPEC。

需要确认：

- 最终设计文档在哪里？
- 当前设计版本是什么？
- 是否已经通过技术评审？
- 评审遗留问题是否已经处理？
- 是否存在尚未解决但可以接受的风险？
- 后续开发应该以哪个版本为准？

例如：

| 项目 | 内容 |
|---|---|
| Requirement | PDF 解析与 AI 笔记生成 |
| Technical SPEC | technical-spec.md |
| Version | V1.0 |
| Review Status | Pass |
| Baseline Status | Approved |
| Baseline Date | 2026-11-04 |

需要注意：

如果技术评审尚未通过，或者仍然存在阻塞开发的关键问题，就不应该直接确立正式设计基线。

### 2.2 最终技术决策（Technical Decisions）

明确本次需求已经确认的关键技术决策。

例如：

| ID | 决策事项 | 最终方案 | 状态 |
|---|---|---|---|
| TD-001 | PDF 解析方式 | 扩展现有解析模块 | Confirmed |
| TD-002 | OCR 能力 | 本次暂不引入 | Confirmed |
| TD-003 | 异步处理方式 | 复用现有任务机制 | Confirmed |

这些决策是后续开发必须遵循的技术依据。

如果 Agent 在编码过程中发现当前决策存在问题，可以提出修改建议，但不能直接将原有设计替换成自己的方案。

### 2.3 设计约束与遗留问题（Constraints & Open Questions）

除了明确已经确定的内容，还需要保留当前设计中尚未解决的问题和必须遵守的约束。

例如：

**设计约束：**

- 优先复用现有文件解析模块。
- 不新增独立解析微服务。
- 沿用现有任务管理机制。
- 不改变已有文件上传接口的兼容性。

**遗留问题：**

- 扫描版 PDF 的 OCR 能力暂不纳入本次开发。
- 后续是否支持更多文件类型，需要根据产品需求确定。

需要区分：

- 已经确认的设计约束。
- 已经接受的遗留风险。
- 尚未解决但不影响当前开发的问题。
- 仍然阻塞开发的问题。

不能把尚未解决的关键问题简单记录为 Open，然后直接进入编码。

### 2.4 后续设计变更管理（Design Change Management）

设计基线确立之后，并不意味着后续不能修改。

在实际编码过程中，可能发现：

- 原有项目实现与前期理解不一致。
- 某个技术方案存在未发现的限制。
- 接口设计无法满足实际调用要求。
- 数据模型存在遗漏。
- 出现了新的业务规则。
- 实际实现成本明显高于预期。

这些情况都可能要求修改原有设计。

但需要注意：

**当实际实现需要偏离已经确认的设计时，应该先明确变更原因、影响范围和修改方案，再更新设计基线，而不是让 Agent 自行改变设计。**

建议采用以下变更流程：

```text
开发过程中发现设计问题
          |
          v
     记录变更原因
          |
          v
     分析影响范围
          |
          v
     评估变更方案
          |
          v
     确认是否需要修改
          |
          v
     更新 Technical SPEC
          |
          v
     必要时重新技术评审
          |
          v
     发布新的设计基线
          |
          v
     Agent 基于新基线继续开发
```

不是每个实现细节调整都需要重新走完整评审。

例如：

- 普通内部函数命名调整：通常不需要修改设计基线。
- 不影响外部契约的内部代码重构：通常不需要重新评审。
- API 请求响应结构变化：需要更新详细设计。
- 数据模型和状态流转变化：需要更新相关设计。
- 模块职责或整体架构变化：通常需要重新评审相关架构设计。

**核心目标：保证实际代码始终有明确的设计依据，重要设计变化能够被追踪和管理。**

## 3. 如何建立设计基线？

实际执行时，可以按照以下三个步骤进行。

### Step 1：确认技术评审结果

首先检查 06 Technical Review 的最终结果。

确认：

- 技术评审是否通过？
- Critical 和 High 问题是否已经解决？
- 是否还存在影响开发的待确认事项？
- 遗留风险是否已经明确并被接受？
- 相关设计修改是否已经同步完成？

如果评审不通过，返回对应阶段修改设计。

### Step 2：整理并确认最终 Technical SPEC

将最终确认的设计内容统一整理。

包括：

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。
- Solution Exploration。
- Architecture Design。
- Detailed Design。
- Technical Review Record。

这里不意味着每个阶段都必须有一份独立文件。

可以将它们组织成一份完整的 Technical SPEC，也可以根据项目复杂度拆分为多个文档。

关键是确保：

1. 所有文档版本一致。
2. 设计内容不存在明显矛盾。
3. 关键技术决策已经确认。
4. 遗留问题已经记录。
5. 后续开发能够明确找到唯一有效的设计版本。

### Step 3：正式确立设计基线

最终记录：

- Technical SPEC 的版本。
- 技术评审结果。
- 最终技术决策。
- 已确认的设计约束。
- 遗留风险和待处理事项。
- 后续变更管理规则。

完成之后，就可以将这份 Technical SPEC 作为后续开发的正式输入。

## 4. AI 时代如何管理设计基线？

AI Agent 在后续编码过程中，可能会持续阅读设计文档、修改代码，甚至提出新的技术实现方式。

因此，必须明确 Agent 与设计基线之间的关系。

**Agent 是设计的执行者和建议者，不是未经授权的设计决策者。**

### 4.1 AI 可以承担什么？

| 工作内容 | AI 的作用 |
|---|---|
| 文档整理 | 整理最终 Technical SPEC |
| 版本检查 | 检查不同设计文档之间的版本一致性 |
| 决策提取 | 提取已经确认的技术决策 |
| 约束整理 | 整理编码过程中必须遵循的设计约束 |
| 变更识别 | 识别实际实现与设计之间的偏差 |
| 影响分析 | 分析设计变更涉及的模块和接口 |
| 文档更新 | 根据确认的变更同步修改设计文档 |
| 一致性检查 | 检查更新后的设计是否存在矛盾 |

### 4.2 开发人员需要负责什么？

- 确认最终设计版本。
- 确认关键技术决策。
- 确认设计约束和遗留风险。
- 判断开发过程中发现的问题是否需要修改设计。
- 审核 Agent 提出的变更建议。
- 决定是否重新进行技术评审。
- 确认新的设计基线。

### 4.3 给 AI Agent 的设计基线约束

建议在后续 AI Coding 的任务描述中加入：

```text
# Design Baseline Constraints

当前需求已经完成 Technical Design，
并确立了正式设计基线。

你必须遵循当前 Technical SPEC 中已经确认的设计。

具体要求：

1. 编码前先阅读并理解完整 Technical SPEC。

2. 严格遵循已经确认的：
   - Architecture Design
   - Module Responsibility
   - API & Interface Definition
   - Data Model
   - Business Logic
   - State & Flow
   - Exception Handling

3. 不得擅自修改已经确认的接口契约、
   数据模型、业务规则和架构设计。

4. 如果发现设计存在问题：
   - 暂停相关实现；
   - 说明具体问题；
   - 分析影响范围；
   - 提出可行的修改建议；
   - 等待开发人员确认。

5. 如果实际项目代码与设计不一致，
   必须指出差异，不得自行假设设计或代码哪一方正确。

6. 如果存在设计中没有定义的实现细节，
   优先遵循当前项目已有规范；
   如果涉及关键业务规则或架构决策，
   必须先提出问题。

7. 不要为了完成编码而自行扩大需求范围。

最终目标：
确保实际实现与已确认的 Technical SPEC 保持一致。
```

## 6. 如何判断设计基线已经完成？

满足以下条件即可：

- 已经通过技术评审。
- 已经明确最终 Technical SPEC 版本。
- 已经确认关键技术决策。
- 已经记录设计约束。
- 已经记录可接受的遗留风险。
- 已经解决影响开发的关键问题。
- 已经明确后续设计变更规则。
- 开发人员已经确认可以进入实施阶段。

**判断标准：所有参与开发的人员和 Agent，都能够明确知道当前应该遵循哪一份技术设计，以及发生设计变化时应该如何处理。**

## 7. 本阶段核心认知总结

1. **设计基线是经过评审和确认的最终技术设计。** 它不是新的设计阶段，而是对已有设计的正式确认。

2. **设计基线不是永久冻结。** 开发过程中可以根据实际情况调整，但重要变化需要经过明确的评估和确认。

3. **Agent 不应该擅自修改已确认的设计。** 发现问题时应该提出差异和建议，由开发人员确认。

4. **保持设计与代码的一致性非常重要。** 设计发生变化时，需要同步更新相关文档，避免设计和实现逐渐脱节。

5. **不需要为每个微小改动重新进行完整评审。** 根据变更影响范围决定是否需要重新评审。

6. **设计基线是后续 AI Coding 的重要输入。** 它为 Implementation Planning、Task Breakdown 和 Agent 执行提供统一依据。

## 8. 在整个研发流程中的位置

Design Baseline 是 Technical Design 的最后一个环节。

**Input：**

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。
- Solution Exploration。
- Architecture Design。
- Detailed Design。
- Technical Review Record。

**Process：**

- 确认评审结果。
- 整理最终设计文档。
- 确认技术决策和约束。
- 记录遗留问题和风险。
- 确立设计版本。
- 明确后续变更规则。

**Output：**

- Approved Technical SPEC。
- Design Baseline Record。
- Confirmed Technical Decisions。
- Design Constraints。
- Open Questions & Accepted Risks。

后续流程：

```text
00 SPEC 认知篇
       |
       v
01 项目代码库探索
       |
       v
02 影响分析
       |
       v
03 方案探索
       |
       v
04 架构设计
       |
       v
05 详细设计
       |
       v
06 技术评审
       |
       v
07 设计基线
       |
       v
08 Implementation Planning
       |
       v
09 AI Coding
```

**最终目标：将经过评审的 Technical SPEC 正式确认为后续开发的统一技术依据，确保 AI Agent 在执行编码任务时有明确的设计约束，并且在实际实现发生变化时，能够及时更新设计、保持设计与代码的一致性。**
