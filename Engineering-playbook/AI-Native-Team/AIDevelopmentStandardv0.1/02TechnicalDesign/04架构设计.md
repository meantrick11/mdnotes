# 04. 架构设计（Architecture Design）

> 本阶段定位：基于需求分析、项目代码库探索、影响分析和技术方案探索的结果，确定本次需求在现有系统中的整体组织方式，明确模块职责、系统边界、模块之间的交互关系、核心业务流程和数据流，为后续详细设计提供整体架构依据。
>
> 核心问题：本次需求最终应该由哪些模块实现？各模块分别负责什么？它们如何协作？整体系统如何运行？

## 1. 为什么需要架构设计？

在完成前面的阶段之后，我们已经明确：

- 本次需求需要实现什么？
- 当前项目是什么架构？
- 本次需求会影响哪些模块？
- 哪些能力可以复用、扩展或新增？
- 采用什么技术方案？
- 关键技术问题是否已经得到验证？

但这些信息还不足以直接指导具体编码。

因为技术方案解决的是采用什么技术、通过什么方式实现，而架构设计需要进一步明确这些技术和能力在当前系统中应该如何组织。

例如：

> 用户上传 PDF 文件后，系统自动解析文件内容，并通过 AI 生成笔记，最后允许用户查看和编辑。

经过前面的分析，我们已经确定：

- 复用现有文件上传能力。
- 扩展现有文件解析模块。
- 沿用现有 AI 调用能力。
- 复用已有笔记管理模块。
- 使用现有异步任务机制处理耗时操作。

但仍然需要明确：

- 文件上传、文件解析、AI 生成和笔记管理分别由谁负责？
- 文件解析模块和 AI 模块之间如何协作？
- 是否需要新增独立的任务处理模块？
- 整个处理流程如何流转？
- 任务状态由哪个模块维护？
- 解析失败和 AI 生成失败如何传递？
- 最终结果如何关联到源文件？

这些问题都属于架构设计需要解决的内容。

如果没有明确整体架构，就直接进入详细设计和编码，很容易出现：

1. **模块职责不清晰**：多个模块重复承担相同职责，或者某些职责没有明确归属。
2. **模块耦合过高**：模块之间直接依赖过多，后续修改困难。
3. **交互关系混乱**：不知道应该由哪个模块调用哪个模块。
4. **业务流程不完整**：只设计了局部功能，没有考虑完整执行过程。
5. **数据流转不清晰**：不同模块之间传递什么数据、如何关联没有明确。
6. **局部设计合理但整体不合理**：单个模块看起来没有问题，但组合起来存在架构缺陷。

因此，架构设计的核心目的有三个：

- **明确系统组织方式**：确定本次需求涉及哪些模块，以及各模块的职责和边界。
- **明确模块协作关系**：确定模块之间如何交互，以及核心业务流程如何运行。
- **保证整体设计合理**：让技术方案能够融入现有项目，同时满足需求和长期维护要求。

核心原则：

**架构设计不是重新设计整个系统，而是在理解现有架构的基础上，明确本次需求应该如何融入和扩展现有系统。**

## 2. 架构设计需要关注什么？

架构设计不需要每次都重新绘制完整的系统架构图，而是围绕本次需求，明确必要的系统组织和协作关系。

主要关注以下五个方面。

### 2.1 系统边界与模块划分（System Boundary & Module Structure）

首先明确本次需求涉及哪些模块，以及是否需要新增或调整模块。

重点关注：

- 哪些现有模块需要参与本次需求？
- 哪些模块可以直接复用？
- 是否需要新增模块？
- 是否需要调整现有模块的职责？
- 模块之间的边界是否清晰？
- 是否存在职责重复或不合理的耦合？

例如：

| 模块 | 类型 | 架构职责 |
|---|---|---|
| File | 现有模块 | 文件上传、存储和管理 |
| Parser | 现有模块扩展 | 负责不同文件类型的内容解析 |
| AI | 现有模块复用 | 提供模型调用能力 |
| Note | 现有模块扩展 | 笔记生成、查询和编辑 |
| Task | 现有模块复用 | 管理异步任务执行 |

需要注意：

模块划分不等于代码目录划分，也不等于微服务拆分。

一个业务模块可能由多个代码模块共同实现，也可能分布在多个微服务中。

不要为了本次需求就随意增加微服务或创建新的抽象层。

**核心目标：明确本次需求由哪些模块承担，以及各模块的职责边界。**

### 2.2 模块职责与依赖关系（Module Responsibility & Dependency）

确定模块之后，需要进一步明确每个模块负责什么，以及模块之间如何依赖。

重点关注：

- 每个模块的核心职责是什么？
- 哪些功能属于当前模块？
- 哪些能力应该交给其他模块？
- 模块之间如何调用？
- 是否存在不合理的循环依赖？
- 是否存在多个模块重复实现同一能力？
- 是否需要通过接口或事件进行解耦？

例如：

| 模块 | 主要职责 | 依赖模块 |
|---|---|---|
| File | 文件上传和存储 | Storage |
| Parser | 文件内容解析 | File |
| AI | 模型调用 | External LLM |
| Note | 笔记管理和生成结果保存 | AI、Database |
| Task | 异步任务调度和状态管理 | Parser、Note |

这里需要注意：

架构设计不只是列出模块名称，还需要明确模块之间的依赖关系及其合理性。

例如，Parser 不应该直接承担笔记管理职责，Note 也不应该重复实现文件解析能力。

**核心目标：明确模块各自负责什么，以及它们之间应该如何依赖。**

### 2.3 模块交互与核心业务流程（Interaction & Business Flow）

这是架构设计最重要的部分之一。

模块划分只是明确了系统由什么组成，还需要明确它们如何协作完成业务。

重点关注：

- 哪个模块作为业务入口？
- 哪个模块负责协调业务流程？
- 模块之间采用同步调用还是异步通信？
- 请求和结果如何传递？
- 异步任务如何触发和执行？
- 任务完成后如何通知或更新状态？
- 异常如何在模块之间传递？

例如：

```text
用户上传 PDF
      |
      v
File Module
      |
      v
创建解析任务
      |
      v
Task Module
      |
      v
Parser Module
      |
      v
AI Module
      |
      v
Note Module
      |
      v
保存生成结果
      |
      v
更新任务状态
      |
      v
用户查看笔记
```

实际项目可能存在不同的交互方式，例如：

- 同步函数调用。
- HTTP / RPC 调用。
- 消息队列。
- 事件驱动。
- 异步任务调度。

具体采用什么方式，需要结合前面的技术方案和现有项目架构确定。

这里还需要考虑正常流程之外的关键分支：

- 文件解析失败。
- AI 调用失败。
- 任务超时。
- 重复提交。
- 任务重试。
- 用户取消任务。

不需要在架构阶段定义每个异常的具体代码处理方式，但需要确保整体流程能够合理处理这些情况。

**核心目标：明确模块之间如何协作，以及完整业务如何从入口执行到最终结果。**

### 2.4 数据流与状态管理（Data Flow & State Management）

系统架构不仅需要明确模块之间如何调用，还需要明确数据如何流转。

重点关注：

- 各模块分别产生什么数据？
- 数据由哪个模块负责维护？
- 数据如何传递给下游模块？
- 是否存在共享数据？
- 不同业务对象之间如何关联？
- 是否存在跨模块的数据一致性问题？
- 关键业务状态由谁维护？

例如：

```text
File
 |
 | file_id
 v
Parser
 |
 | parsed_content
 v
AI
 |
 | generated_note
 v
Note
 |
 | note_id
 v
Task
```

这里的具体数据字段和结构可以在详细设计阶段定义，架构阶段重点明确数据流向和归属关系。

尤其需要注意状态管理：

例如，文件解析和 AI 笔记生成可能属于一个完整的异步任务。

需要明确：

- Task 模块是否负责整个任务的状态？
- Parser 是否只负责解析结果？
- Note 是否负责笔记自身的业务状态？
- 各模块如何将处理结果反馈给任务管理模块？

不要让多个模块无明确约定地共同维护同一个业务状态。

**核心目标：明确数据如何流转、由谁负责，以及关键状态如何在系统中管理。**

### 2.5 架构约束与关键质量属性（Architecture Constraints & Quality Attributes）

最后，需要从整体角度检查架构设计是否满足项目的技术约束和质量要求。

重点关注：

| 维度 | 需要考虑的问题 |
|---|---|
| Performance | 是否存在明显的性能瓶颈？ |
| Scalability | 是否支持未来业务增长？ |
| Reliability | 单个模块失败是否会影响整个流程？ |
| Security | 模块之间的数据访问是否安全？ |
| Consistency | 跨模块数据是否能够保持一致？ |
| Maintainability | 模块职责是否清晰，是否容易维护？ |
| Extensibility | 后续增加新功能是否方便？ |
| Observability | 是否能够追踪完整业务执行过程？ |

例如：

文件解析属于耗时操作，如果采用同步请求，可能导致接口长时间阻塞。

因此需要考虑现有异步任务机制是否更适合当前场景。

又例如，如果文件解析和 AI 生成由不同服务执行，就需要考虑任务状态、执行失败和结果一致性。

注意：

不需要每个需求都展开所有质量属性，只需要关注本次需求真正涉及的约束。

**核心目标：确保整体架构不仅能实现功能，而且在性能、稳定性、安全性和可维护性方面满足实际要求。**

## 3. 如何进行架构设计？

实际执行时，我建议按照以下四个步骤进行。

### Step 1：确定整体模块结构

基于前面的影响分析和技术方案，整理本次需求涉及的模块。

明确：

- 哪些模块直接复用？
- 哪些模块需要扩展？
- 是否需要新增模块？
- 哪些模块需要调整职责？
- 模块之间的边界是什么？

输出一份简洁的模块职责清单。

### Step 2：明确模块之间的协作关系

进一步确定模块如何协作。

明确：

- 谁是业务入口？
- 谁负责协调整个流程？
- 哪些模块需要互相调用？
- 使用什么通信方式？
- 同步和异步流程分别是什么？
- 关键异常如何传递？

必要时绘制模块依赖图或时序图。

### Step 3：梳理核心业务流程与数据流

从用户操作出发，梳理完整的业务执行过程。

明确：

- 业务从哪里开始？
- 每个模块依次执行什么？
- 模块之间传递什么数据？
- 数据最终保存在哪里？
- 关键状态由谁维护？
- 异常情况下流程如何变化？

必要时绘制流程图、时序图和数据流图。

### Step 4：检查整体架构合理性

最后从整体角度检查：

- 是否覆盖所有需求？
- 是否充分利用现有项目能力？
- 模块职责是否清晰？
- 是否存在不必要的模块和依赖？
- 模块之间的交互是否合理？
- 数据和状态归属是否明确？
- 是否满足关键性能、安全和可靠性要求？
- 是否能够进入下一阶段详细设计？

完成以上工作后，就可以进入 Detailed Design。

## 4. AI 时代如何进行架构设计？

架构设计非常适合使用 AI Agent 辅助完成。

因为 Agent 已经通过前面的阶段理解了项目结构、影响范围和技术方案，可以进一步帮助我们整理模块职责、生成架构图、分析依赖关系和梳理业务流程。

但需要注意：

**不要让 AI 在不了解项目和技术决策的情况下，直接从需求文档生成一套全新的系统架构。**

### 4.1 AI 可以承担什么？

| 工作内容 | AI 的作用 |
|---|---|
| 模块划分 | 根据需求和现有项目识别相关模块 |
| 职责分析 | 整理各模块应该承担的职责 |
| 依赖分析 | 分析模块之间的调用和依赖关系 |
| 架构图生成 | 生成模块关系图、系统架构图 |
| 流程梳理 | 生成业务流程图和时序图 |
| 数据流分析 | 整理数据流转和状态变化 |
| 风险检查 | 识别潜在耦合、单点故障和一致性问题 |
| 设计文档 | 整理 Architecture Design 初稿 |

### 4.2 开发人员需要负责什么？

- 判断模块划分是否符合项目实际情况。
- 确认各模块职责是否合理。
- 判断模块之间的依赖是否必要。
- 确认业务流程是否完整。
- 审核同步、异步交互方式。
- 确认数据和状态的归属。
- 判断架构是否过度设计。
- 最终确认整体架构。

特别需要注意：

AI 很容易为了追求所谓的高内聚、低耦合，引入过多抽象层、独立模块和微服务。

架构设计不是越复杂越好。

**优先在现有合理架构中完成需求，只有确实存在问题时才进行必要调整。**


## 5. 架构设计的最终产出

本阶段建议形成一份 Architecture Design，作为 Technical SPEC 的核心章节。

不需要每个需求都生成完整的架构报告，根据复杂度选择必要内容。

建议结构：

### 5.1 架构概览（Architecture Overview）

简要说明：

- 本次需求的整体实现思路。
- 如何融入现有系统。
- 主要涉及哪些模块。
- 是否存在架构调整。

### 5.2 模块职责（Module Responsibility）

| 模块 | 类型 | 职责 | 变化说明 |
|---|---|---|---|
| File | Existing | 文件管理 | Reuse |
| Parser | Existing | 文件解析 | Extend |
| AI | Existing | 模型调用 | Reuse |
| Note | Existing | 笔记管理 | Extend |
| Task | Existing | 异步任务 | Reuse |

### 5.3 模块依赖与交互（Module Interaction）

说明模块之间的调用关系、通信方式和协作边界。

必要时附模块依赖图或时序图。

### 5.4 核心业务流程（Core Business Flow）

通过流程图或文字描述，明确正常流程及关键异常分支。

### 5.5 数据流与状态管理（Data Flow & State）

明确核心数据如何流转、关键状态由哪个模块维护。

### 5.6 架构约束与风险（Constraints & Risks）

记录需要重点关注的性能、安全、可靠性、兼容性和一致性问题。

## 6. 如何判断架构设计已经完成？

满足以下条件，就可以进入详细设计：

- 已明确本次需求涉及的主要模块。
- 已明确各模块的职责和边界。
- 已明确模块之间的依赖关系。
- 已明确主要交互方式。
- 已经梳理完整核心业务流程。
- 已明确核心数据流和状态归属。
- 已识别关键架构约束和风险。
- 整体架构能够覆盖需求，并符合现有项目的技术约束。

不要求每个需求都绘制完整的架构图。

简单需求可以用模块职责表和文字说明完成；跨模块、跨服务的复杂需求则应该使用架构图、时序图和流程图辅助表达。

**判断标准：开发人员能够根据架构设计理解系统整体如何组织，以及各模块如何协作完成需求。**

## 7. 本阶段核心认知总结

1. **架构设计不是重新设计整个系统，而是明确本次需求如何融入现有系统。**

2. **架构设计关注整体组织，而不是具体代码实现。** 重点是模块职责、系统边界、依赖关系和交互方式。

3. **模块划分不等于微服务拆分。** 不要为了一个新需求就随意增加独立服务。

4. **模块交互和数据流是架构设计的重点。** 仅仅列出模块名称和职责是不够的。

5. **优先沿用现有合理架构。** 只有现有设计无法满足需求时，才考虑必要的架构调整。

6. **架构设计应当与需求复杂度匹配。** 简单需求不需要过度设计，复杂需求则需要充分明确模块协作和系统边界。

7. **AI 负责辅助分析和生成设计，开发人员负责判断架构合理性。** 最终架构必须由开发人员理解和确认。

## 8. 在整个研发流程中的位置

Architecture Design 是 Technical Design 的第四个环节。

**Input：**

- Requirement Specification。
