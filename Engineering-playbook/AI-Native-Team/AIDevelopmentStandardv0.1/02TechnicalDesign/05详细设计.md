# 05. 详细设计（Detailed Design）

> 本阶段定位：基于需求分析、影响分析、技术方案和架构设计的结果，将整体架构进一步细化为明确的技术实现规范，确定接口定义、数据结构、核心业务逻辑、状态流转、异常处理及关键实现约束，为后续 Implementation Planning 和 AI Coding 提供直接依据。
>
> 核心问题：具体需要修改什么？每个模块应该如何实现？接口和数据如何定义？各种场景应该如何处理？

## 1. 为什么需要详细设计？

在完成架构设计之后，我们已经明确：

- 本次需求涉及哪些模块？
- 每个模块分别负责什么？
- 模块之间如何协作？
- 整体业务流程如何执行？
- 数据如何在模块之间流转？

但这些内容仍然偏向整体设计，无法完全指导具体编码。

例如：

> 用户上传 PDF 后，系统自动解析文件内容，并通过 AI 生成笔记。

架构设计可能已经明确：

```text
File Module
    |
    v
Task Module
    |
    v
Parser Module
    |
    v
AI Module
    |
    v
Note Module
```

但真正开始编码时，还存在很多问题：

- 需要新增哪些 API？
- API 的请求参数和响应结构是什么？
- 文件记录需要增加哪些字段？
- 任务有哪些状态？
- 不同模块之间传递什么数据？
- 解析失败应该如何处理？
- AI 调用超时是否需要重试？
- 重复提交是否会创建多个任务？
- 笔记生成成功后如何与源文件关联？

这些都需要通过详细设计进一步明确。

如果缺少详细设计，直接让 Agent 开始编码，很容易出现：

1. **实现方式不一致**：Agent 根据自己的理解补充实现细节。
2. **接口定义不统一**：不同模块对请求、响应和数据结构产生不同理解。
3. **业务规则遗漏**：正常流程能够运行，但异常和边界场景处理不完整。
4. **数据设计不合理**：字段、关联关系和状态定义不符合业务要求。
5. **模块协作出现偏差**：各个模块单独实现没有问题，但组合后无法正常工作。
6. **代码审核困难**：没有明确的设计依据，难以判断 Agent 的实现是否正确。

因此，详细设计的核心目的有三个：

- **明确实现规范**：将架构设计转化为具体的接口、数据和逻辑定义。
- **减少实现歧义**：让开发人员和 Agent 对具体实现形成一致理解。
- **建立验证依据**：明确哪些行为必须实现，以及如何验证实现正确。

核心原则：

**详细设计不是提前把代码写出来，而是把代码应该遵循的技术约定和实现规则明确下来。**

## 2. 详细设计需要关注什么？

详细设计主要关注六个方面。

### 2.1 接口设计（API & Interface Design）

明确系统内部和外部模块之间如何进行通信。

重点关注：

- 是否需要新增或修改 API？
- 请求参数是什么？
- 响应结构是什么？
- 参数是否必填？
- 参数有哪些限制？
- 返回哪些错误码？
- 是否涉及内部 RPC 接口？
- 是否需要调整消息队列或事件结构？

例如：

新增一个 PDF 解析任务创建接口。

| 项目 | 定义 |
|---|---|
| Method | POST |
| Path | /api/files/{fileId}/parse |
| 功能 | 创建文件解析任务 |
| Path Parameter | fileId |
| Response | taskId、status |
| 认证 | 沿用现有认证机制 |

请求示例：

```json
{
  "fileId": "file_001"
}
```

响应示例：

```json
{
  "taskId": "task_001",
  "status": "PENDING"
}
```

具体接口设计需要进一步明确：

- `fileId` 是否必须属于当前用户？
- 文件是否已经完成上传？
- 是否支持重复创建解析任务？
- 创建成功后返回什么状态？
- 文件不存在时返回什么错误？
- 文件类型不支持时如何响应？

需要注意：

并不是每次需求都需要新增 API。如果能够复用现有接口，就应该优先沿用。

接口设计也不局限于 HTTP API，还包括模块间的函数接口、RPC、消息队列消息结构和事件定义。

**核心目标：明确模块之间通信所遵循的接口契约，避免调用方和被调用方产生理解偏差。**

### 2.2 数据模型设计（Data Model Design）

明确本次需求涉及的数据结构，以及数据之间的关系。

重点关注：

- 是否需要新增数据表？
- 是否需要修改已有数据表？
- 是否需要增加字段？
- 字段类型和约束是什么？
- 数据之间如何关联？
- 是否需要增加索引？
- 是否需要考虑历史数据兼容？
- 数据由哪个模块负责维护？

例如：

本次需求需要将生成的笔记与源文件关联。

可能涉及：

**File**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | 文件 ID |
| user_id | String | 所属用户 |
| file_name | String | 文件名称 |
| file_type | String | 文件类型 |

**Note**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String | 笔记 ID |
| user_id | String | 所属用户 |
| source_file_id | String | 来源文件 ID |
| content | Text | 笔记内容 |
| created_at | DateTime | 创建时间 |

这里还需要考虑：

- `source_file_id` 是否允许为空？
- 一个文件是否可以生成多篇笔记？
- 是否需要建立外键或索引？
- 文件删除后，笔记如何处理？
- 历史笔记数据如何兼容？

具体字段应以现有项目的数据规范和实际业务关系为准。

**核心目标：明确数据结构、字段约束、关联关系及数据维护规则。**

### 2.3 核心业务逻辑设计（Business Logic Design）

明确每个模块内部具体需要执行哪些业务处理。

重点关注：

- 业务入口在哪里？
- 处理步骤是什么？
- 各步骤的执行条件是什么？
- 输入和输出分别是什么？
- 是否存在多个处理分支？
- 是否需要进行权限和数据校验？
- 是否需要保证幂等性？
- 是否涉及事务？

例如：

PDF 解析任务的核心逻辑：

```text
1. 接收解析请求
       |
2. 校验用户和文件权限
       |
3. 检查文件类型及状态
       |
4. 创建解析任务
       |
5. 提交异步处理
       |
6. 执行文件解析
       |
7. 保存解析结果
       |
8. 更新任务状态
```

这里需要进一步明确：

- 文件是否已经上传完成？
- 同一个文件是否允许重复解析？
- 解析任务是否需要关联用户？
- 解析结果保存失败怎么办？
- 任务执行过程中再次提交如何处理？

注意：

详细设计需要明确关键业务规则和执行约束，但不一定要细化到每一个函数内部的代码实现。

**核心目标：让 Agent 理解每个模块内部应该执行什么逻辑，以及必须遵守哪些规则。**

### 2.4 状态与流程设计（State & Flow Design）

对于涉及异步任务、订单、审批、支付等具有生命周期的业务，需要明确状态及其流转规则。

重点关注：

- 有哪些业务状态？
- 每种状态代表什么？
- 什么条件下允许状态转换？
- 哪些状态可以重试？
- 哪些状态属于终态？
- 是否允许重复执行？
- 是否需要处理并发状态更新？

例如：

PDF 解析任务可能定义以下状态：

| 状态 | 含义 |
|---|---|
| PENDING | 等待执行 |
| PROCESSING | 正在处理 |
| SUCCESS | 处理成功 |
| FAILED | 处理失败 |
| CANCELLED | 已取消 |

状态流转：

```text
PENDING
   |
   v
PROCESSING
   |
   +------> SUCCESS
   |
   +------> FAILED
   |
   +------> CANCELLED
```

还需要明确：

- FAILED 是否允许重新执行？
- PROCESSING 超时后如何恢复？
- SUCCESS 是否允许再次处理？
- 任务取消后是否能够继续执行？
- 是否需要记录失败原因？

不是所有业务都需要复杂的状态机。

简单 CRUD 功能可能根本不需要独立设计状态流转。

**核心目标：明确具有生命周期的业务对象，其状态定义和合法流转规则。**

### 2.5 异常与边界处理（Exception & Edge Case Handling）

正常流程只是业务的一部分，还需要明确关键异常和边界情况。

重点关注：

- 参数缺失或格式错误。
- 用户无权访问资源。
- 数据不存在。
- 重复提交。
- 第三方服务异常。
- 网络超时。
- 数据库操作失败。
- 并发冲突。
- 异步任务失败。
- 部分操作成功、部分操作失败。

例如：

| 异常场景 | 预期处理 |
|---|---|
| 文件不存在 | 返回对应错误 |
| 文件类型不支持 | 拒绝创建任务 |
| 文件解析失败 | 标记任务 FAILED |
| AI 调用超时 | 按既定重试策略处理 |
| 笔记保存失败 | 记录失败并保证任务状态一致 |
| 重复提交 | 根据幂等规则返回已有任务或创建新任务 |

这里尤其需要关注：

**异常处理不能只定义如何返回错误，还需要考虑系统数据和业务状态是否保持一致。**

例如：

AI 已经生成笔记，但保存数据库失败，不能简单地将整个流程当成成功。

具体的事务、重试和补偿机制需要结合实际架构设计。

**核心目标：明确系统在非正常情况下应该如何响应，避免出现数据不一致和状态异常。**

### 2.6 权限、配置与实现约束（Security & Implementation Constraints）

最后，明确实现过程中必须遵循的技术约束。

重点关注：

- 用户权限如何校验？
- 是否存在数据隔离要求？
- 敏感数据如何处理？
- 是否需要新增配置？
- 是否存在环境变量？
- 是否需要新增第三方依赖？
- 是否需要遵循项目现有编码规范？
- 是否需要增加日志、监控和链路追踪？
- 是否需要兼容已有客户端或历史数据？

例如：

文件解析功能需要明确：

- 用户只能访问自己有权限的文件。
- 不允许直接信任客户端提供的文件路径。
- 第三方 AI 服务的密钥只能从服务端配置读取。
- 不在日志中输出敏感文件内容。
- 解析任务需要能够通过任务 ID 进行追踪。

**核心目标：明确实现过程中不可违反的安全要求、配置要求和工程约束。**

## 3. 如何进行详细设计？

建议按照以下四个步骤执行。

### Step 1：根据架构确定详细设计范围

回到 Architecture Design，明确需要进一步细化的模块。

例如：

| 模块 | 是否需要详细设计 | 设计内容 |
|---|---|---|
| File | 是 | 上传接口、文件校验 |
| Parser | 是 | PDF 解析逻辑、结果格式 |
| AI | 视情况 | 笔记生成接口及调用约束 |
| Note | 是 | 笔记保存、源文件关联 |
| Task | 是 | 任务状态及执行规则 |

不是每个模块都需要重新设计。

如果某个模块完全复用现有能力，只需要说明沿用现有实现即可。

### Step 2：细化接口和数据结构

针对需要修改或新增的模块，明确：

- API 定义。
- 请求和响应结构。
- 内部接口。
- 消息结构。
- 数据库字段。
- 数据关联关系。
- 必要的索引和约束。

确保模块之间的数据契约一致。

### Step 3：细化业务逻辑和异常处理

根据架构中的核心业务流程，进一步明确：

- 每个模块的执行逻辑。
- 关键校验条件。
- 状态流转。
- 异常分支。
- 幂等和并发要求。
- 重试及补偿规则。

确保正常流程和关键异常场景都具有明确的预期行为。

### Step 4：检查设计完整性

最后检查：

- 是否覆盖所有功能需求？
- 接口定义是否完整？
- 数据结构是否合理？
- 模块之间的契约是否一致？
- 业务逻辑是否存在遗漏？
- 状态流转是否合法？
- 异常处理是否充分？
- 是否遵循现有项目规范？
- 是否足以指导后续编码？

完成后，进入 Technical Review。

## 4. AI 时代如何进行详细设计？

这一阶段是 AI Coding 之前非常重要的准备环节。

AI Agent 可以帮助开发人员快速阅读现有代码、生成接口定义、梳理数据模型、补充异常场景和整理详细设计文档。

但需要注意：

**不能让 Agent 只根据架构图直接生成详细设计，而应该要求它结合真实项目代码和现有开发规范完成设计。**

### 4.1 AI 可以承担什么？

| 工作内容 | AI 的作用 |
|---|---|
| 接口设计 | 参考现有 API 规范，生成接口定义 |
| 数据设计 | 分析 Entity、Schema 和数据库结构 |
| 业务逻辑 | 将业务流程细化为具体处理步骤 |
| 状态设计 | 整理状态枚举及合法流转 |
| 异常分析 | 补充异常场景和边界条件 |
| 权限分析 | 检查权限校验和数据隔离 |
| 设计一致性 | 检查模块之间的接口和数据契约 |
| 文档生成 | 形成 Detailed Design 初稿 |

### 4.2 开发人员需要负责什么？

- 判断详细设计是否符合需求。
- 确认接口定义是否合理。
- 确认数据模型是否符合现有项目规范。
- 审核业务逻辑和关键规则。
- 确认异常处理是否充分。
- 判断设计是否存在过度复杂的问题。
- 确认设计是否可以直接指导编码。

特别需要注意：

Agent 可能会根据常见开发模式自行补充一些看似合理的规则。

例如：

- 自动增加重试次数。
- 自动设置任务超时时间。
- 自动增加数据库字段。
- 自动定义新的状态。
- 自动改变接口返回结构。

这些内容不能因为 Agent 认为合理就直接接受。

涉及业务行为的内容，需要有需求依据；涉及技术实现的内容，需要有项目依据或经过开发人员确认。

### 4.3 AI 详细设计提示词

```text
# Role
你是一名资深软件工程师，负责根据需求、现有项目和架构设计，
协助完成本次需求的 Detailed Design。

# Context

当前已经完成：
1. Requirement Analysis
2. Repository Exploration
3. Impact Analysis
4. Solution Exploration
5. Architecture Design

# Tasks

基于以上资料，结合当前项目真实代码，完成详细设计。

重点包括：

1. 接口设计
   - 新增或修改哪些接口
   - 请求与响应结构
   - 参数约束和错误处理

2. 数据模型设计
   - 新增或修改哪些数据结构
   - 字段类型、约束及关联关系
   - 数据迁移和兼容性要求

3. 核心业务逻辑
   - 各模块具体处理步骤
   - 输入、处理、输出
   - 关键校验和业务规则

4. 状态与流程
   - 状态定义
   - 合法状态流转
   - 幂等、重试和并发要求

5. 异常处理
   - 主要异常场景
   - 预期处理方式
   - 数据一致性要求

6. 安全与工程约束
   - 权限校验
   - 数据隔离
   - 配置及依赖
   - 日志和监控要求

# Constraints

- 必须结合当前项目真实代码和开发规范。
- 优先复用已有接口、组件和数据模型。
- 不得自行改变已经确认的业务规则。
- 不得凭空增加未经确认的业务行为。
- 区分现有实现、新增设计和待确认事项。
- 保证不同模块之间的接口和数据契约一致。
- 不要直接修改业务代码。
- 不需要提前生成完整代码实现。

# Output

1. Design Scope
2. API & Interface Design
3. Data Model Design
4. Business Logic Design
5. State & Flow Design
6. Exception & Edge Case Handling
7. Security & Implementation Constraints
8. Open Questions

最终目标：
形成一份能够指导开发人员和 AI Agent 进行编码的详细技术设计。
```

## 5. 详细设计的最终产出

本阶段建议形成一份 Detailed Design，作为 Technical SPEC 的具体实现章节。

建议结构：

### 5.1 设计范围

明确本次需要新增、修改和复用的模块。

### 5.2 接口设计

| 接口 | Method | 请求参数 | 响应 | 说明 |
|---|---|---|---|---|
| | | | | |

### 5.3 数据模型设计

| 数据对象 | 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|---|
| | | | | |

### 5.4 核心业务逻辑

说明各模块的具体处理步骤、关键规则和输入输出。

### 5.5 状态与流程设计

说明必要的状态定义、状态流转及转换条件。

### 5.6 异常处理

| 异常场景 | 处理方式 | 预期结果 |
|---|---|---|
| | | |

### 5.7 安全与实现约束

说明权限、数据隔离、配置、日志、兼容性及项目规范。

### 5.8 待确认事项

记录尚未明确、需要进一步确认的问题。

注意：

以上是参考结构，不是每次必须完整填写的固定表格。

简单需求可以只包含接口和业务逻辑；涉及数据库变更时再补充数据设计；存在异步任务时再补充状态流转和异常处理。

## 6. 如何判断详细设计已经完成？

建议检查以下内容：

- 已明确本次需要新增、修改和复用的实现范围。
- 新增或修改的接口有明确的定义。
- 涉及的数据结构和关联关系已经明确。
- 核心业务逻辑和处理规则已经明确。
- 关键状态及其流转规则已经明确。
- 主要异常和边界场景已经考虑。
- 权限和安全约束已经明确。
- 模块之间的接口和数据契约一致。
- 所有关键待确认事项已经解决，或明确标记了处理方式。

最终判断标准：

**开发人员或 Agent 能够依据这份设计开展编码，而不需要自行猜测关键业务规则、接口约定和模块协作方式。**

---

## 7. 本阶段核心认知总结

1. **详细设计是将架构设计转化为具体实现规范。** 它关注接口、数据、业务逻辑和异常处理。

2. **详细设计不是提前编写代码。** 重点是明确实现规则，而不是把每个函数都写成伪代码。

3. **接口和数据契约非常重要。** 不同模块之间必须对输入、输出和数据结构形成一致理解。

4. **正常流程和异常流程都需要考虑。** 尤其是异步任务、重试、幂等和数据一致性。

5. **优先沿用现有项目规范。** 不要为了一个需求随意改变现有接口、数据结构和开发模式。

6. **设计深度需要匹配需求复杂度。** 简单需求不需要完整的详细设计，复杂需求才需要深入定义各项技术细节。

7. **详细设计是 AI Coding 的重要输入。** 设计越明确，Agent 自行猜测的空间就越小，最终实现越容易控制。

## 8. 在整个研发流程中的位置

Detailed Design 是 Technical Design 的第五个环节。

**Input：**

- Requirement Specification。
- Repository Exploration。
- Impact Analysis。
- Solution Exploration。
- Architecture Design。

**Process：**

- 明确详细设计范围。
- 细化接口和数据结构。
- 明确核心业务逻辑。
- 定义状态和流程。
- 设计异常处理。
- 检查实现约束和设计一致性。

**Output：**

- Detailed Design。
- API & Interface Definition。
- Data Model Definition。
- Business Logic Specification。
- State & Flow Definition。
- Exception Handling Rules。
- Security & Implementation Constraints。
