# 01. 项目代码库探索（Repository Exploration）

> 本阶段定位：在进行技术设计之前，**先理解现有项目，建立对项目架构、技术栈、模块职责、核心业务调用链及开发规范的基本认知，为后续影响分析、技术方案设计和 AI Coding 提供可靠的项目上下文**。

## 1. 为什么需要项目代码库探索？

在完成 Requirement Analysis 之后，我们已经明确了本次需求需要解决什么问题、系统需要提供哪些功能，以及对应的业务规则和验收标准。

但这些信息还不足以直接进入编码。

因为真实的软件开发通常不是从零开始编写代码，而是在一个已经存在的项目中进行功能新增、修改、重构或者问题修复。

面对一个真实需求，开发人员首先需要了解当前项目：

- 项目使用什么技术栈和开发框架？
- 整个项目是如何组织的？
- 当前系统采用什么架构？
- 各个模块分别承担什么职责？
- 核心业务是如何从入口执行到最终结果的？
- 数据如何在不同模块之间流转？
- 项目有哪些已有能力可以复用？
- 当前项目有哪些开发规范和技术约束？
- 如何启动项目、运行测试和验证修改？

如果没有对现有项目建立基本认知，就直接开始技术设计或编码，很容易出现：

1. **重复建设**：不知道项目已经存在相关能力，又重新实现一套。
2. **修改位置错误**：不了解模块职责，将新功能放在不合理的位置。
3. **破坏现有逻辑**：不清楚原有调用链和模块依赖，修改后影响其他功能。
4. **设计不一致**：没有遵循项目已有的架构和代码规范，产生不一致的实现。
5. **忽略隐藏依赖**：不了解公共机制、数据关系和上下游调用，导致集成问题。
6. **缺少验证能力**：不知道项目如何运行和测试，无法有效验证修改结果。

因此，代码库探索的核心目的有三个：

- **理解现状**：建立对现有项目架构、技术栈和模块职责的认知。
- **发现已有能力**：找到可以复用、扩展或需要调整的现有实现。
- **建立技术上下文**：为后续技术设计和编码提供可靠依据。

核心原则：

**代码库探索不是要求开发人员阅读整个项目的所有代码，而是建立足以支撑当前需求开发的项目认知。**

## 2. 代码库探索应该探索什么？

代码库探索不是漫无目的地阅读代码，而是围绕项目的实际组成，建立一套结构化的认知。

我建议主要从以下八个维度进行探索。

### 2.1 项目整体结构（Project Structure）

首先了解整个项目是如何组织的。

重点关注：

- 项目主要解决什么问题？
- 使用什么编程语言和技术栈？
- 是单体应用、模块化单体，还是微服务架构？
- 前端、后端、基础设施代码如何组织？
- 各个目录分别承担什么职责？
- 项目的启动入口在哪里？
- 配置文件、环境变量和依赖管理在哪里？
- 是否存在 README、架构文档、开发说明等资料？

例如：

```text
project/
├── frontend/
│   ├── src/
│   ├── components/
│   └── pages/
│
├── backend/
│   ├── api/
│   ├── services/
│   ├── models/
│   └── repositories/
│
├── infrastructure/
├── tests/
├── docs/
├── docker-compose.yml
└── README.md
```

这里不要求立即理解所有目录中的代码，而是先建立项目整体地图。

**探索目标：知道项目由什么组成，以及各部分大致承担什么职责。**

### 2.2 技术栈与开发规范（Tech Stack & Conventions）

了解项目使用了什么技术，以及当前已经形成了哪些开发约定。

重点关注：

| 维度 | 探索内容 |
|---|---|
| Programming Language | 编程语言及版本 |
| Framework | 前后端开发框架 |
| Database | 数据库类型及使用方式 |
| Cache | 是否使用 Redis 等缓存 |
| Message Queue | 是否使用消息队列 |
| ORM | 数据访问工具 |
| API Style | RESTful、GraphQL 或其他 |
| Dependency Management | 依赖管理方式 |
| Code Style | 命名、格式化、Lint 规范 |
| Testing | 测试框架及测试规范 |

常见配置文件：

| 技术栈 | 主要配置文件 |
|---|---|
| Node.js | package.json |
| Python | pyproject.toml、requirements.txt |
| Java | pom.xml、build.gradle |
| Go | go.mod |
| Rust | Cargo.toml |
| Docker | Dockerfile、docker-compose.yml |

特别注意：

不要只依赖 README 中的描述，还需要结合实际配置文件和代码进行验证。

因为项目文档可能已经过时，配置文件和实际代码才是判断当前技术实现的重要依据。

**探索目标：明确项目使用什么技术，以及后续开发必须遵循哪些规范。**

### 2.3 系统架构（System Architecture）

理解项目整体是如何运行的。

重点关注：

- 系统由哪些主要模块或服务构成？
- 各模块分别承担什么职责？
- 模块之间如何通信？
- 请求从哪里进入系统？
- 核心业务如何流转？
- 数据如何在不同模块之间传递？
- 是否存在第三方服务依赖？
- 是否涉及消息队列、异步任务等基础设施？

例如，一个典型的 Web 应用：

```text
             Frontend
                 |
                 v
          API / Gateway
                 |
                 v
       Controller / Router
                 |
          +------+------+
          |             |
          v             v
    Business Layer  Infrastructure
          |             |
          +------+------+
                 |
          +------+------+
          |             |
          v             v
       Database    External Services
```

注意：

这只是通用架构示意，实际项目可能采用完全不同的组织方式。

不要仅凭目录名称就推断系统架构，需要结合启动入口、模块依赖、调用代码和运行配置进行确认。

**探索目标：能够解释系统的整体组成，以及主要模块之间如何协作。**

### 2.4 核心模块与职责（Module Analysis）

理解项目中主要模块的职责和边界。

重点关注：

- 有哪些核心业务模块？
- 每个模块分别负责什么？
- 模块之间有哪些依赖关系？
- 是否存在公共模块或共享能力？
- 哪些能力可以被其他模块复用？
- 是否存在职责混乱或循环依赖？

例如：

| 模块 | 主要职责 | 相关依赖 |
|---|---|---|
| User | 用户信息与账户管理 | Database |
| File | 文件上传与管理 | Storage |
| Parser | 文件内容解析 | File |
| AI | 模型调用与生成 | External LLM |
| Note | 笔记管理 | AI、Database |

这里需要注意几个概念：

- **业务模块**：按照业务领域组织，例如文件管理、用户管理。
- **功能模块**：按照系统功能职责组织，例如文件上传、文件解析。
- **代码模块**：代码层面的组织，例如 services、repositories。
- **微服务**：具有独立运行和部署边界的服务。

它们之间可能存在关联，但不是一一对应的。

不要仅凭一个目录名称，就判断它是独立业务模块或微服务。

**探索目标：知道系统有哪些重要模块，以及每个模块的职责和边界。**

### 2.5 核心业务调用链（Business Flow & Call Chain）

这是代码库探索中非常重要的部分。

仅仅知道项目有哪些模块还不够，还需要知道一个真实业务从入口到最终结果是如何执行的。

例如：

用户点击上传文件后，系统究竟发生了什么？

```text
用户操作
   |
   v
Frontend 页面事件
   |
   v
API Request
   |
   v
Controller / Router
   |
   v
Business Service
   |
   v
File Storage
   |
   v
Database
   |
   v
Response
   |
   v
Frontend 更新状态
```

如果涉及异步处理，还需要继续追踪：

```text
文件上传
   |
   v
创建处理任务
   |
   v
消息队列
   |
   v
Worker 消费任务
   |
   v
文件解析
   |
   v
AI 生成笔记
   |
   v
保存结果
   |
   v
更新任务状态
   |
   v
前端查询结果
```

探索时重点回答：

1. 业务入口在哪里？
2. 请求经过哪些模块？
3. 核心业务逻辑在哪里？
4. 哪些模块被调用？
5. 数据如何传递？
6. 是否存在异步执行？
7. 最终结果在哪里产生？
8. 结果如何返回给用户？

这里需要建立一个重要习惯：

**不要只阅读单个函数，而要沿着一个真实的业务调用链阅读代码。**

因为很多问题并不发生在某个函数内部，而是发生在模块之间的交互过程中。

**探索目标：能够从业务入口追踪到核心处理逻辑和最终结果，理解系统实际如何工作。**

### 2.6 数据模型与接口（Data Model & API）

了解项目的数据组织方式，以及模块之间的通信契约。

**数据模型重点关注：**

- 核心 Entity 有哪些？
- 数据表之间是什么关系？
- 主键、外键如何组织？
- 是否存在状态字段？
- 是否存在软删除、版本控制等机制？
- 数据如何创建、更新和查询？
- 是否存在统一的数据模型或 DTO？

**接口重点关注：**

- API 路由如何组织？
- 请求和响应格式是什么？
- 参数校验在哪里执行？
- 错误码如何定义？
- 身份认证和权限控制如何实现？
- 内部模块之间如何通信？

例如：

```text
POST /api/files
GET  /api/files/{id}
POST /api/files/{id}/parse
GET  /api/tasks/{id}
```

这些只是示例。实际探索时应该找到项目真实存在的接口和数据结构，而不是假定它们已经实现。

**探索目标：理解核心数据如何组织，以及不同模块如何通过接口或其他机制进行交互。**

### 2.7 公共机制与横切关注点（Cross-cutting Concerns）

了解项目中被多个模块共同使用的基础机制。

很多开发人员容易忽略这一部分，但它对后续高质量编码非常重要。

| 领域 | 探索内容 |
|---|---|
| Authentication | 身份认证 |
| Authorization | 权限控制 |
| Logging | 日志规范 |
| Error Handling | 异常处理机制 |
| Configuration | 配置管理 |
| Transaction | 事务处理 |
| Cache | 缓存机制 |
| Async Task | 异步任务机制 |
| Retry | 重试机制 |
| Observability | 监控、Tracing、Metrics |

例如，准备新增一个接口时，如果不了解现有的认证、权限和异常处理机制，很可能写出一个功能可以运行，但不符合项目整体规范的实现。

**探索目标：理解项目中通用的技术机制，避免新代码与现有系统规范脱节。**

### 2.8 测试、构建与运行方式（Testing & Execution）

最后，需要知道项目如何运行，以及如何验证后续修改。

重点关注：

- 本地如何启动项目？
- 项目依赖哪些外部服务？
- 环境变量如何配置？
- 如何运行单元测试？
- 如何运行集成测试？
- 是否有 E2E 测试？
- 如何执行 Lint 和 Type Check？
- 如何构建项目？
- CI/CD 中有哪些质量检查？

例如：

```bash
# 安装依赖
npm install

# 启动项目
npm run dev

# 单元测试
npm run test

# 类型检查
npm run typecheck

# 代码检查
npm run lint

# 构建
npm run build
```

具体命令必须以项目实际配置为准。

**探索目标：知道项目如何启动、测试和构建，为后续开发验证建立基础。**

## 3. 代码库探索的两种层次

这里需要特别区分一个概念：

**项目级探索和需求级探索不是一回事。**

不能认为每次拿到需求，都需要重新完整探索一遍代码库。

建议将代码库探索分为两个层次。

### 3.1 项目级探索（Project-level Exploration）

在首次接触一个项目、建立项目知识库或者项目发生重大架构变化时进行。

主要目标是建立整个项目的基础认知。

探索内容：

- 项目整体结构。
- 技术栈与开发规范。
- 系统架构。
- 核心模块及职责。
- 主要业务调用链。
- 数据模型与 API 规范。
- 公共技术机制。
- 测试与运行方式。

最终形成项目级知识文档，后续持续维护。

### 3.2 需求级探索（Task-level Exploration）

在每次具体需求开发时，围绕本次需求进行定向探索。

主要目标是理解当前需求涉及的现有实现。

探索内容：

- 当前需求涉及哪些模块？
- 相关代码在哪里？
- 现有功能是如何实现的？
- 核心调用链是什么？
- 是否存在可复用的能力？
- 涉及哪些数据模型和接口？
- 相关测试在哪里？
- 当前实现有哪些限制？

例如：

第一次接手一个项目时，先进行一次项目级探索，建立项目地图。

后续产品经理提出「增加文件解析能力」的需求，就不需要重新分析整个项目，而是：

1. 阅读已有项目架构资料。
2. 定位文件管理模块。
3. 追踪文件上传和解析调用链。
4. 查看相关数据模型、接口和测试。
5. 深入理解当前需求涉及的具体实现。

两者关系：

**项目级探索建立长期项目认知，需求级探索围绕具体任务补充必要的代码上下文。**

注意：项目知识文档不是永久正确的。随着代码重构、模块迁移和技术升级，需要持续验证和更新，不能无条件相信历史 AI 生成的总结。

## 4. AI 时代如何进行代码库探索？

传统开发中，开发人员需要自己阅读大量代码，逐渐建立项目认知。

AI 时代可以将大量信息检索、代码阅读、调用链追踪和文档整理工作交给 Agent。

但不应该直接给 Agent 一句：

「帮我分析一下整个项目架构。」

这种指令过于宽泛，很容易得到一份看起来完整、实际上缺少代码依据的架构总结。

更好的方式是让 Agent 分阶段探索。

### 4.1 Agent 分阶段探索

**第一阶段：项目全局扫描**

让 Agent 先回答：

- 项目是什么？
- 使用什么技术栈？
- 整体目录如何组织？
- 有哪些主要模块？
- 项目如何启动和测试？

**第二阶段：架构与模块探索**

进一步分析：

- 系统由哪些主要模块或服务组成？
- 各模块分别承担什么职责？
- 模块之间有哪些依赖？
- 核心基础设施是什么？
- 是否存在外部服务依赖？

**第三阶段：核心业务调用链探索**

选择一个真实业务，让 Agent 追踪：

- 从哪里进入？
- 经过哪些文件？
- 调用了哪些函数？
- 数据如何流转？
- 最终在哪里产生结果？

**第四阶段：项目规范探索**

分析：

- 代码规范。
- 异常处理。
- 日志规范。
- 测试规范。
- API 规范。
- 数据访问规范。

**第五阶段：整理项目知识**

将前面的结果整理成结构化文档，作为后续技术设计的上下文。

### 4.2 AI 探索的核心原则

为了保证 Agent 输出的可信度，需要给它设定明确的约束：

1. **以实际代码为依据**：不能只根据目录名称推断模块职责。
2. **提供代码证据**：重要结论尽可能附带文件路径、类名、函数名。
3. **区分事实和推测**：没有找到实现依据的内容必须标记为未知或待验证。
4. **沿调用链追踪**：不能只分析孤立文件。
5. **避免无目的地阅读**：优先探索核心入口和高价值模块。
6. **保护项目代码**：Repository Exploration 阶段只进行分析，不执行代码修改。
7. **识别文档与实现的差异**：README、架构文档和实际代码不一致时，应明确指出。
8. **避免一次性过度探索**：根据项目规模和当前任务逐步深入，不追求无意义的信息收集。

特别需要注意：

AI 可能根据文件名、目录结构和常见架构模式推断出看似合理的结论，但这些结论不一定符合项目的实际实现。

因此，重要结论必须尽可能能够追溯到真实代码。

**AI 负责加速探索，开发人员负责验证项目认知。**

## 5. 代码库探索的最终产出

代码库探索不应该只是一次性的对话，而应该沉淀为后续可以复用的项目知识。

我建议建立两类产出。

### 5.1 项目级知识文档（Project Knowledge）

首次探索项目后形成，后续持续维护。

建议结构：

```text
project-knowledge/
├── README.md
├── project-overview.md
├── architecture.md
├── module-map.md
├── core-flows.md
├── data-and-api.md
└── development-guide.md
```

各文档职责：

| 文档 | 主要内容 |
|---|---|
| README.md | 项目知识入口及文档索引 |
| project-overview.md | 项目背景、技术栈、整体结构 |
| architecture.md | 系统架构、模块关系 |
| module-map.md | 模块职责、依赖关系 |
| core-flows.md | 核心业务调用链 |
| data-and-api.md | 数据模型、接口规范 |
| development-guide.md | 启动、测试、构建、开发规范 |

不要求一开始全部拆成独立文件。项目规模较小时，可以合并。

### 5.2 需求级探索记录（Task Exploration）

每次具体需求开发时形成，作为后续 Technical SPEC 的输入。

建议结构：

```markdown
# Task Exploration

## 1. Requirement Context
本次需求涉及的业务和系统模块。

## 2. Relevant Modules
相关模块及其职责。

## 3. Existing Implementation
当前相关功能的实现方式。

## 4. Call Chain
核心调用链和数据流。

## 5. Reusable Capabilities
可以复用的现有能力。

## 6. Existing Constraints
当前实现限制和技术约束。

## 7. Related Tests
相关测试及验证方式。

## 8. Unknowns
尚未确认的内容。
```

注意：

这里的探索记录主要用于理解当前实现，不需要提前给出完整的技术改造方案。具体修改范围和影响程度留到下一阶段 Impact Analysis 进一步分析。

---

## 6. 如何判断代码库探索已经完成？

代码库探索不是读完所有代码才算完成，而是需要达到足以支撑后续技术设计的程度。

### 6.1 项目级探索检查

| 检查项 | 完成标准 |
|---|---|
| 项目结构 | 知道主要目录及职责 |
| 技术栈 | 明确核心技术及版本 |
| 系统架构 | 能解释主要模块如何组织 |
| 模块职责 | 知道核心模块分别负责什么 |
| 调用链 | 能追踪主要业务调用链 |
| 数据模型 | 理解核心数据结构 |
| 公共机制 | 知道认证、异常、日志等机制 |
| 开发规范 | 知道如何启动、测试和构建 |
| 代码依据 | 关键结论能够追溯到实际代码 |

### 6.2 需求级探索检查

每次具体需求开发，还需要满足：

- 已经找到本次需求相关的代码入口。
- 已经理解现有相关功能的执行过程。
- 已经识别可以复用的现有能力。
- 已经了解相关数据模型和接口。
- 已经找到相关测试代码。
- 已经记录尚未确认的技术信息。

如果以上内容已经足以支撑下一阶段的影响分析，就不需要继续无目的地深入阅读代码。

---

## 7. 本阶段核心原则总结

1. **代码库探索不是阅读代码，而是建立系统认知。** 需要理解架构、模块、调用链、数据和开发规范。

2. **基于实际代码建立认知。** 不要仅根据目录名称、README 或 AI 的推测判断项目实现。

3. **优先沿业务调用链探索。** 比起孤立地阅读大量文件，理解一个真实功能如何从入口执行到结果更有价值。

4. **区分项目级探索和需求级探索。** 项目级探索建立长期知识，需求级探索解决当前任务，不要每次重复分析整个项目。

5. **AI 负责加速探索，开发人员负责验证认知。** 不要将 AI 的推测直接当成项目事实。

6. **探索深度应当与实际任务相匹配。** 不要求理解整个项目的每一行代码，只需要理解足以支撑当前需求设计的部分。

7. **沉淀项目知识，避免重复探索。** 将高价值的项目认知保存下来，并随着项目演进持续更新。

---

## 8. 在整个研发流程中的位置

Repository Exploration 是 Technical Design 的第一个环节。

它的输入和输出分别是：

**Input：**
- Requirement Specification。
- 当前项目代码库。
- 项目现有文档和技术资料。

**Process：**
- 项目整体扫描。
- 技术栈和架构分析。
- 核心模块分析。
- 业务调用链追踪。
- 数据、接口及公共机制探索。
- 测试与运行方式分析。

**Output：**
- 项目级知识文档（首次探索或重大变化时）。
- 需求级探索记录（每次具体需求时）。
- 已验证的项目认知及待确认事项。

后续流程：

```text
Requirement Analysis
        |
        v
Repository Exploration
        |
        v
Impact Analysis
        |
        v
Solution Exploration
        |
        v
Architecture Design
        |
        v
Detailed Design
        |
        v
Technical Review
        |
        v
Design Baseline
```

**最终目标：在开始技术设计之前，开发人员和 AI Agent 都能够对现有项目建立足够准确的认知，知道当前系统是什么样、已有能力在哪里、相关代码如何运行，从而避免脱离项目实际情况进行技术设计。**
