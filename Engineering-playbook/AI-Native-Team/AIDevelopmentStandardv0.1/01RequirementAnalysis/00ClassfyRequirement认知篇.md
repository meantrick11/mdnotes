
这个阶段是在拿到一个真实的开发需求在后续进行技术SPEC、任务规划（Implementation Plan）、代码实现、代码审查、质量验收的最重要的一步。

## 1.0 需求拆解基础认知

### 1.1 开发人员 vs 产品经理

**需求拆解的目的**：面对的是产品经理已经撰写好的需求文档（PRD），任务不是重新做产品经理拉齐上层业务需求，而是需要转化为清晰、完成可验证、能够进入技术设计阶段的开发需求。

产品经理主要回答：

- 为什么要做？
    
- 给谁使用？
    
- 用户需要什么？
    
- 产品应该表现成什么样？
    

开发人员需要进一步回答：

- 需求具体包含哪些功能？
    
- 每个功能在什么条件下触发？
    
- 输入、处理、输出分别是什么？
    
- 正常流程和异常流程是什么？
    
- 哪些业务规则必须遵守？
    
- 怎么判断最终实现正确？

**AI的作用可以帮助你快速阅读、提取、分析、发现遗漏、整理需求，但是还是需要你对上层业务需要有自己的理解，明白当前当前需求隶属于哪个业务场景（背景），这个业务场景需要做什么？标准的SOP是怎么样的？需要遵循什么样的规则？有什么分支？哪些异常情况需要处理？等等都是需要开发人员明确的，AI只是起到加速的作用**
### 1.2 为什么需要需求拆解？

假设产品经理给你一份 PRD：

> 用户可以上传 PDF、Word 文件，系统自动解析文件内容，并通过 AI 生成笔记，支持用户查看和编辑生成的笔记。

这段话看起来很清楚，但对于开发人员而言，实际上存在大量未明确的信息。**而这些具体的模糊边界，也是需求拆解需要明确的信息**


例如：

|问题|具体疑问|
|---|---|
|文件上传|支持哪些文件类型？最大文件多大？|
|文件校验|如何处理损坏文件？|
|文件存储|上传后存储在哪里？|
|文件解析|使用什么解析方式？解析失败怎么办？|
|AI 生成|生成笔记的内容和格式是什么？|
|任务执行|解析和生成是同步还是异步？|
|状态管理|用户如何知道任务是否完成？|
|编辑功能|编辑后是否覆盖原笔记？|
|异常处理|模型调用失败如何处理？|

这就是为什么不能直接从 PRD 跳到编码。

如果没有经过需求拆解，开发人员很容易：

1. 根据自己的理解补充产品没有定义的行为。
    
2. 忽略异常场景和边界条件。
    
3. 不同模块对同一个业务规则产生不同理解。
    
4. 编码完成后才发现需求遗漏。
    
5. 测试人员不知道应该如何验收。


因此，需求拆解的主要核心目的有三个：
- **完整性**：确保当前需求涉及的功能/场景没有明显的遗漏（因为不可能一下考虑到所有的异常情况，主要流程可能遇到的情况需要尽可能地考虑）
- 明确性：减少模糊描述，**识别需要和产品经理确认的问题**，比如文件上传需要支持哪些文件？以及各自的限制（大小？编码方式？）压缩包是否需要解析等等内容，也就是尽可能地将对应地限制和要求明确，**不能自行决定，应该由产品经理进行判断，因为需要满足上层业务，需求可能只是业务的一个子分支，这些需求要求如果没有写清，那么一定要跟产品经理对齐，不要自行决断，明确开发的同时，也能撇清责任。**
- 可验证性：让每个需求都有对应的实现预期（这个产品经理可能会给UI效果图等等，明确这些预期情况十分重要）和验收依据。

原则：**需求拆解不是把一段文字拆成更多文字，而是把模糊的业务描述转换为明确的系统行为（尽可能明确，如果一旦陷入拆解，可能正式编码就迟迟不会动工了）

### 1.3 需求 vs 业务：理解需求与上层业务的关系

在进行需求拆解时，需要明确一个基本认知：

**需求不是孤立存在的，它始终依附于某个业务目标、业务流程和具体业务场景。**

一个产品通常有自己的核心业务目标，以及围绕目标形成的业务流程。产品经理提出的具体需求，可能是为了完善现有业务流程、解决某个场景下的问题，也可能是引入新的业务能力。

因此，开发人员不能只关注 PRD 中描述的功能，而需要理解当前需求在整个产品业务中的位置，以及它为什么存在。

#### 1.3.1 产品级业务 vs 需求级业务

需要区分两个不同粒度的业务概念：

**1. 产品级业务（Product Business）**

描述整个产品解决什么问题、服务什么业务目标，以及核心业务是如何运转的。

例如，一个企业数据资产管理平台，其核心业务可能包括：

- 数据资产采集
    
- 数据资产识别
    
- 数据分类分级
    
- 分类分级结果审核
    
- 数据资产管理
    
- 数据治理与统计
    

这些业务活动共同构成产品的整体业务链。

**2. 需求级业务（Requirement Business Logic）**

具体需求虽然隶属于产品级业务，但它本身也可能包含相对完整的业务逻辑。

例如，产品经理提出：

> 支持用户上传压缩包，系统自动识别其中的文件，并完成分类分级。

这个需求属于产品整体的「数据分类分级」业务，但它自身也包含：

- 业务目标：减少用户逐个上传文件、手动分类分级的工作量。
    
- 业务场景：用户上传包含多个文件的压缩包，希望系统批量处理。
    
- 业务流程：上传压缩包 → 解压 → 文件识别 → 内容提取 → 分类分级 → 结果展示 → 人工确认。
    
- 业务规则：支持哪些压缩格式、是否支持多层目录、解析失败如何处理、分类结果如何关联原始文件等。
    

可以看到，需求本身也可能是一段完整的业务活动，而不只是一个简单的功能点。

因此，需求拆解时既要理解产品级业务上下文，也要分析当前需求内部的业务逻辑。

#### 1.3.2 需求为什么会产生？

具体需求通常来源于以下几种情况：

1. **新增业务能力**：产品需要支持新的业务活动或业务场景。
    
    - 例如：原本只支持单文件分类分级，现在需要支持压缩包批量处理。
        
2. **现有业务流程增强**：原有业务流程存在能力缺口，需要补充新的能力。
    
    - 例如：原本支持 PDF 文本提取，现在需要支持扫描版 PDF 的 OCR 识别。
        
3. **特殊业务场景处理**：现有流程无法妥善处理某些特殊情况。
    
    - 例如：文件解析失败后，用户需要能够重新发起处理。
        
4. **业务效率与体验优化**：现有业务能够完成，但操作成本较高或用户体验不佳。
    
    - 例如：原本需要用户手动填写分类结果，现在希望系统自动推荐。
        
5. **业务规则或约束调整**：由于业务要求变化，需要调整原有系统行为。
    
    - 例如：调整文件上传限制、分类分级规则或审核流程。
        

因此，并不是所有需求都是原有业务流程的特殊情况。有些需求是在完善已有业务，有些则是在扩展甚至引入新的业务能力。

#### 1.3.3 业务场景、需求与功能之间的关系

需要明确以下三个概念：

- **业务场景（Business Scenario）**：描述用户在什么情况下，为了完成什么业务目标而进行某项活动。
    
- **需求（Requirement）**：描述为了满足业务目标或解决业务问题，系统需要发生什么变化、满足什么要求。
    
- **功能（Feature / System Capability）**：描述系统需要提供哪些具体能力来支撑业务活动、满足需求。
    

例如：

业务目标：帮助企业完成非结构化文件的自动分类分级。

业务场景：用户上传扫描版 PDF，希望系统自动识别文件内容并推荐对应的分类分级结果。

业务问题：当前系统无法提取扫描版 PDF 中的文本内容。

需求：系统需要支持扫描版 PDF 的内容提取。

对应的系统功能可能包括：

- PDF 页面检测
    
- OCR 文本识别
    
- 文本内容提取
    
- 解析结果校验
    
- 解析失败处理
    

这里需要特别注意：

**需求与功能并不是一对一关系，而是可能存在多对多关系。**

- 一个需求可能需要多个功能共同实现。
    
- 一个功能可能同时支撑多个不同需求。
    
- 多个业务场景可能复用同一项系统能力。
    
- 一个需求也可能涉及多个业务模块。
    

例如，文件解析能力既可以支撑扫描版 PDF 识别，也可以支撑文件自动生成笔记、文件内容检索等需求。

因此，不应该将每个需求都理解为一组全新的功能，更不能将需求、功能、业务流程简单地一一对应。

#### 1.3.4 需求拆解时应该如何理解这些关系？

面对一份 PRD，开发人员需要建立以下认知：

1. **先理解上层业务**：当前产品的核心业务是什么？本次需求属于哪个业务领域、哪个业务流程？
    
2. **再理解当前需求**：为什么产生这个需求？它希望解决什么业务问题？是否引入了新的业务场景？
    
3. **分析需求内部的业务逻辑**：涉及哪些用户角色、业务对象、业务活动、流程、规则和状态？
    
4. **再拆解系统功能**：为了支撑上述业务活动，系统需要提供哪些功能？哪些能力已经存在，哪些需要新增或修改？
    
5. **建立需求与功能的关联**：确保每个需求都有对应的实现能力，同时识别可复用的系统功能。
    

最终形成的认知关系可以概括为：

产品业务上下文 → 具体业务场景 → 业务问题与目标 → 需求 → 系统功能 → 技术实现。

需要注意，这是一种便于理解的分析路径，并不是严格的一对一层级结构。实际项目中，需求与业务场景、功能与需求之间都可能存在多对多关系。

**核心原则：需求拆解不能脱离业务，但也不能把需求拆解变成重新进行产品设计。开发人员需要理解需求背后的业务逻辑，明确系统应该如何表现；对于涉及业务目标、业务规则和产品行为的模糊或未决事项，应及时与产品经理确认，而不是自行做业务决策。**
