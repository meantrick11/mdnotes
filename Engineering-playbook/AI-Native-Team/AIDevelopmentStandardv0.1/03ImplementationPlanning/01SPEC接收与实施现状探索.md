# 01 SPEC 接收与实施现状探索

> **所属阶段：** `03ImplementationPlanning`
> 
> **前置阶段：** `02TechnicalDesign`（技术方案设计与评审）
> 
> **后续阶段：** `02基于代码库的开发任务拆解`
> 
> **核心输入：** 已评审 SPEC、技术探索成果、真实代码库、项目工程规范
> 
> **核心产出：** SPEC—Codebase 映射、工程变更清单、实施风险与待确认问题
> 
> **推荐产物：** `IMPLEMENTATION_CONTEXT.md`（可作为实施计划的前置分析或附录）

---

## 一、阶段定位与目标

### 1.1 阶段定位

本阶段是从技术设计转向工程实施的第一步。

经过 `02TechnicalDesign`，已经形成经过评审的技术 SPEC，明确了技术方案、接口设计、数据结构、业务逻辑和相关约束。

但技术设计所描述的目标状态，与代码仓库的当前状态并不完全等价。

即使 SPEC 已通过评审，也需要进一步确定：

- 设计中的能力当前是否已经存在？
    
- 需要修改哪些真实模块及代码？
    
- 哪些能力应该复用，哪些需要扩展或新增？
    
- 是否存在未在 SPEC 中体现的工程依赖？
    
- 代码库当前状态是否仍然符合技术设计时的假设？
    
- 哪些问题会影响后续开发任务拆解？
    

因此，本阶段的核心任务是：

**基于已评审 SPEC，继承技术设计阶段的探索成果，对当前代码库开展定向、增量的实施现状分析，识别真实工程变更，为任务拆解提供可验证的依据。**

### 1.2 本阶段的职责边界

**本阶段需要完成：**

- 接收和理解技术设计成果。
    
- 验证与实施有关的代码现状。
    
- 建立 SPEC 与代码库的映射。
    
- 识别工程变更及实施风险。
    
- 确认能否进入任务拆解。
    

**本阶段不需要完成：**

- 重新开展完整需求分析。
    
- 重新设计已经评审通过的技术方案。
    
- 将所有工程变更拆分成正式 Task。
    
- 为每个 Task 制定详细的文件级执行步骤。
    
- 修改业务代码或开始正式编码。
    

本阶段允许只读分析、搜索和必要的非侵入式验证；需要修改项目状态或运行有副作用的操作时，应另行确认。

## 二、输入与前置条件

### 2.1 必要输入

|输入|内容|用途|
|---|---|---|
|技术 SPEC|已评审的完整技术方案|明确目标状态|
|评审结论|已确认决策、遗留问题、风险|区分确定事项与待处理事项|
|当前代码库|真实项目源码与配置|确认现有实现|
|项目工程规范|AGENTS.md、测试和编码约束等|规范探索行为和实施判断|

### 2.2 推荐复用的技术设计成果

优先复用 `02TechnicalDesign` 中已有的信息：

- 代码库结构和模块职责。
    
- 相关业务调用链。
    
- 变更影响范围。
    
- 技术方案探索结果。
    
- 已有能力及复用建议。
    
- 数据模型与接口设计依据。
    
- POC 验证结果。
    
- 方案评审记录。
    

这些成果并不要求必须作为独立文档存在。

如果相关内容已经完整体现在 SPEC 中，就直接引用 SPEC，不需要重新制造中间文档。

### 2.3 前置检查

开始探索前，应确认：

- SPEC 已有可识别的评审版本。
    
- 当前仓库、分支或提交基线明确。
    
- 能访问相关项目模块及必要依赖。
    
- 已知项目规则和安全限制。
    
- 能识别哪些技术问题已经确认、哪些尚待解决。
    

如果项目没有 `AGENTS.md`，并不意味着必须暂停实施规划。

可以先读取已有 README、构建配置、团队规范和相关代码，建立最小工程约束记录，并将 AGENTS 初始化列入 ProjectLevel 待办。

不得因为缺少 AGENTS 而让 AI 自行编造项目规范。

## 三、标准执行流程

本阶段采用四步工作流：

**01 输入接收与设计基线整理 → 02 定向代码探索 → 03 SPEC—Codebase 映射与工程变更识别 → 04 结果校验与移交。**

### Step 01：输入接收与设计基线整理

**目标：让 AI 理解本次要落地的技术设计，并明确需要验证的工程事实。**

#### 具体操作

**1. 读取设计依据**

包括：

- 已评审 SPEC。
    
- 评审意见及最终决策。
    
- 相关代码探索文档。
    
- 项目现有规范。
    

**2. 提取实施相关设计点**

重点关注：

- 涉及的业务功能。
    
- 接口新增或调整。
    
- 数据库及数据模型变更。
    
- 核心业务逻辑。
    
- 模块间协作与外部依赖。
    
- 异常、并发、权限及兼容性要求。
    
- 测试与非功能性要求。
    

对于设计点，建议分配稳定的引用标识，例如：

`SPEC-API-01`、`SPEC-DATA-02`、`SPEC-LOGIC-03`

如果 SPEC 已经有需求编号或设计项编号，应优先复用，避免建立两套不一致的标识。

**3. 识别需要验证的设计假设**

例如：

- SPEC 假设项目已存在某种任务调度机制。
    
- SPEC 计划复用已有领域服务。
    
- SPEC 假设某个数据模型具有指定字段。
    
- SPEC 假设某个外部接口支持特定调用方式。
    

这些内容需要通过当前代码库、接口契约或其他可信依据确认。

#### 阶段产出

一份用于后续探索的设计点清单，至少包括：

|字段|说明|
|---|---|
|SPEC ID|设计点标识|
|Design Item|目标能力或变更要求|
|Expected Area|预计涉及模块|
|Assumptions|需要确认的设计假设|
|Verification Need|需要探索或验证的内容|

**完成条件：主要实施设计点和待验证假设已识别，可以据此开展定向探索。**

### Step 02：定向代码库探索

**目标：确认各设计点对应的真实代码现状，而不是推测项目的实现方式。**

#### 具体操作

**1. 确认仓库与工程结构**

先读取：

- 项目根目录及模块结构。
    
- 项目规则文件。
    
- 构建和测试配置。
    
- 相关技术栈与依赖。
    
- 当前工作区和版本状态。
    

重点不是全面学习整个项目，而是确认后续探索的可信基础。

**2. 围绕 SPEC 定位代码落点**

优先通过已有探索文档定位，再进行定向搜索。

可按照如下顺序查找：

业务入口 → 核心 Service / Domain → Repository / 数据模型 → 外部依赖 → 测试。

根据实际架构调整，不要求所有项目都采用相同的分层。

**3. 分析现有实现与复用能力**

重点识别：

- 相关功能是否已经存在。
    
- 代码入口和关键调用链。
    
- 数据读写与事务边界。
    
- 可复用的服务、组件和公共工具。
    
- 现有异常处理模式。
    
- 并发与幂等处理。
    
- 现有测试覆盖范围。
    

**4. 检查隐含工程依赖**

例如：

- 调整状态流转可能触发事件通知。
    
- 修改数据库字段可能影响历史数据与迁移。
    
- 新增接口可能需要同步权限、路由和文档。
    
- 修改公共服务可能影响多个调用方。
    
- 修改配置可能涉及不同环境。
    
- 添加异步处理可能引入重试与幂等问题。
    

这些依赖可能没有在 SPEC 中逐项展开，但会直接影响任务拆解。

#### 代码探索的证据要求

对于重要判断，优先记录：

- 仓库及提交基线。
    
- 文件路径。
    
- 关键类型、函数或方法名称。
    
- 相关调用关系。
    
- 必要的测试或配置依据。
    

可以使用 `path/to/file:line` 等便于后续定位的形式；代码发生变化后需重新确认。

要区分以下三类信息：

|类型|含义|处理|
|---|---|---|
|Verified|已通过代码或可信证据确认|可作为任务拆解依据|
|Inferred|根据代码结构推断，但未充分验证|标记假设及验证方式|
|Unknown|暂无足够依据|记录待探索项，不得编造|

#### 阶段产出

- 相关代码位置清单。
    
- 关键调用链及依赖说明。
    
- 可复用能力清单。
    
- 设计假设的验证结果。
    
- 待进一步调查的问题。
    

**完成条件：主要设计点已有可信的代码依据，或已明确尚未解决的不确定项。**

### Step 03：SPEC—Codebase 映射与工程变更识别

**目标：从设计目标和代码现状之间识别实际需要发生的工程变更。**

这是本阶段最核心的工作。

#### 3.1 建立设计与代码映射

建议使用如下结构：

|SPEC ID|设计目标|当前实现|代码依据|实施判断|
|---|---|---|---|---|
|SPEC-01|超时扫描|已有通用任务框架|`jobs/...`|扩展|
|SPEC-02|订单取消|已有状态流转服务|`order/...`|复用/扩展|
|SPEC-03|超时配置|未发现对应配置|配置搜索记录|待确认新增|
|SPEC-04|并发保护|已有条件更新机制|`repository/...`|验证后复用|

以上为示例，实际路径和结论必须由当前代码库支持。

尤其需要注意：

**“未搜索到”不等于“确认不存在”。**

对于尚未发现的能力，需要说明搜索范围、可能遗漏的位置及判断可信度。

#### 3.2 识别工程变更

对每个设计点，分析实际需要：

- `CREATE`：新增能力、模块、接口或数据结构。
    
- `MODIFY`：修改已有逻辑。
    
- `REUSE`：直接复用已有能力。
    
- `REMOVE`：删除不再适用的实现。
    
- `MIGRATE`：执行数据、配置或接口兼容迁移。
    
- `VERIFY`：通过测试或检查确认现有能力满足要求。
    

一个设计点可能涉及多种变更类型。

例如，新增超时取消功能，可能同时需要扩展状态流转逻辑、复用定时任务框架并补充并发验证。

注意：工程变更是后续 Task 拆解的输入，还不是最终 Task。

#### 3.3 确定工程影响范围

对于每个变更，尽可能确定：

- 目标模块。
    
- 相关调用方。
    
- 涉及的数据表或模型。
    
- 接口及外部依赖。
    
- 相关配置。
    
- 测试位置或验证入口。
    
- 潜在兼容性影响。
    

03 阶段重点确认可信的模块级落点，不需要提前穷尽全部文件和方法。

#### 3.4 识别设计与代码之间的冲突

例如：

- SPEC 中的接口字段与当前模型不一致。
    
- SPEC 希望复用的公共能力实际不支持该场景。
    
- 现有调用链与设计时的假设不一致。
    
- 数据库约束不允许设计中的状态变化。
    
- 已有代码使用另一套错误处理或事务机制。
    

对于冲突，需要区分：

**实施细节差异：**

不改变已评审的接口契约、业务规则及关键技术方案，可在后续实施规划中调整。

**实质性设计冲突：**

影响核心业务规则、数据模型、接口契约、安全属性或重要架构决策，需要回到技术设计进行确认。

AI 不得在分析阶段直接修改 SPEC，或者默默选择与评审结论冲突的方案。

#### 阶段产出

工程变更清单，推荐字段：

|字段|说明|
|---|---|
|Change ID|工程变更标识|
|SPEC Reference|来源设计点|
|Change Type|新增、修改、复用、迁移、验证等|
|Code Area|相关模块或代码位置|
|Change Description|需要发生的变化|
|Dependencies|技术及模块依赖|
|Risks|潜在风险|
|Evidence|代码依据|
|Confidence|结论的可信状态|

**完成条件：已识别主要工程变更，并能追溯对应 SPEC 目标及代码依据。**

### Step 04：结果校验与移交

**目标：确认实施现状分析可以可靠地支撑任务拆解。**

建议采取 AI 自检和人工关键项审核相结合的方式。

#### AI 自检

重点检查：

1. SPEC 中的主要设计点是否全部处理。
    
2. 每个设计点是否有代码现状或明确的待验证状态。
    
3. 工程变更是否有可信的代码依据。
    
4. 是否把未经验证的假设写成了确定事实。
    
5. 是否遗漏调用方、事务、配置、迁移或测试影响。
    
6. 是否与评审后的技术方案冲突。
    
7. 是否引入了 SPEC 范围之外的不必要改动。
    
8. 是否存在影响后续任务拆解的阻塞问题。
    

#### 人工审核

开发者重点检查：

- 关键业务逻辑理解是否正确。
    
- 核心代码入口与变更范围是否合理。
    
- 已有能力的复用判断是否正确。
    
- 高风险技术依赖是否被识别。
    
- 设计偏差是否需要重新确认。
    

#### 移交结果

完成后，将分析结果传递至：

`02基于代码库的开发任务拆解`

后续任务拆解应基于工程变更清单，而不是仅重新阅读 SPEC 生成独立的任务列表。

## 四、标准产物设计

### 4.1 推荐文档：IMPLEMENTATION_CONTEXT.md

建议采用一份轻量结构：

```
# Implementation Context

1. 基本信息
   - SPEC 引用与版本
   - 仓库与代码基线
   - 相关工程规范

2. 设计点清单
   - SPEC ID
   - 目标与设计约束
   - 需验证的假设

3. 代码现状
   - 模块和调用链
   - 已有能力
   - 代码依据

4. SPEC—Codebase Mapping
   - 设计目标
   - 代码现状
   - 实施判断
   - 证据状态

5. Engineering Changes
   - 变更标识
   - 变更类型
   - 代码范围
   - 风险与依赖

6. Open Issues
   - 问题
   - 影响程度
   - 后续处理方式

7. Readiness Conclusion
   - 是否可以进入任务拆解
   - 阻塞项与非阻塞项
```

### 4.2 是否必须创建独立文档？

不强制。

推荐策略：

**复杂需求：** 独立维护 `IMPLEMENTATION_CONTEXT.md`，支持复查、追踪和多人协作。

**中小需求：** 可以先作为工作文档，后续将主要结果整合到 `IMPLEMENTATION_PLAN.md`。

**简单变更：** 直接在实施计划的「代码现状与工程变更」章节中记录即可。

无论采用哪种形式，都必须保留重要的代码依据和关键判断。

## 五、AI 辅助执行方式

### 5.1 推荐的 AI 工作方式

建议分为两轮执行。

**第一轮：探索与收集证据**

让 AI 阅读 SPEC、现有探索文档和代码库。

要求其：

- 识别实施设计点。
    
- 验证设计假设。
    
- 定位相关模块。
    
- 分析当前实现。
    
- 明确已知事实与未知项。
    
- 不修改代码。
    

**第二轮：分析与审查**

基于第一轮证据：

- 建立 SPEC—Codebase 映射。
    
- 提出工程变更清单。
    
- 检查影响范围。
    
- 识别设计冲突。
    
- 进行独立质量检查。
    
- 输出移交结论。
    

这样可以减少 AI 一边探索、一边过早形成实施结论的问题。

### 5.2 可直接复用的 Prompt

以下 Prompt 适用于支持仓库读取和代码搜索的 AI 编码工具。

**Prompt A：设计接收与定向代码探索**

```
你现在负责 03ImplementationPlanning 的
「SPEC 接收与实施现状探索」。

输入：
1. 已评审技术 SPEC：[路径]
2. 技术评审结论：[路径]
3. 已有代码探索结果：[路径，可选]
4. 项目工程规范：[路径，可选]
5. 当前项目代码库

目标：
基于 SPEC 和真实代码库，确认设计目标与
现有实现之间的关系，为工程变更分析提供证据。

执行要求：
1. 先阅读 SPEC 与评审结论，提取实施设计点。
2. 优先复用技术设计阶段的代码探索成果。
3. 根据 SPEC 定向探索相关代码，不要无目的扫描仓库。
4. 分析现有模块、调用链、数据模型及可复用能力。
5. 验证影响实施的关键设计假设。
6. 对每项重要发现提供文件路径和代码依据。
7. 区分 Verified / Inferred / Unknown。
8. 不得编造文件、接口、类、方法或项目规范。
9. 发现设计冲突时记录问题，不擅自修改 SPEC。
10. 本轮仅进行只读分析，不修改业务代码。

输出：
- 实施设计点清单
- 相关代码现状与依据
- 设计假设验证结果
- 可能的隐藏依赖
- 待确认问题

本轮不要生成正式开发 Task，也不要开始编码。
```

**Prompt B：工程变更识别与结果审查**

```
请基于已评审 SPEC 和前一轮代码探索结果，
完成 SPEC—Codebase 映射与工程变更分析。

要求：
1. 逐项建立 SPEC 设计点与代码现状的映射。
2. 识别新增、修改、复用、删除、迁移和验证工作。
3. 给每个重要工程变更标记代码依据。
4. 识别调用链、数据库、配置、权限、
   事务、并发和测试方面的潜在影响。
5. 区分已确认事实、合理推断与未知项。
6. 检查是否遗漏 SPEC 内容。
7. 检查是否存在与已评审设计不一致的判断。
8. 不要提前进行 Task 拆解。
9. 对无法确认的信息明确说明限制。

输出：
1. SPEC—Codebase Mapping
2. Engineering Changes
3. Risks and Dependencies
4. Open Issues
5. Readiness Conclusion

Readiness Conclusion 必须明确：
- Ready：可以进入任务拆解
- Conditional：可以继续，但存在需跟踪的问题
- Blocked：存在必须先解决的阻塞问题

请指出结论依据，不能仅输出主观判断。
```

### 5.3 AI Review 的独立性

有条件时，可以由不同的 AI 会话或独立审查代理读取：

- SPEC。
    
- 已完成的 Implementation Context。
    
- 关键代码证据。
    

让其以审查者身份识别遗漏和不可靠判断。

但不同会话并不天然保证独立、准确。所有高风险结论仍应回到真实代码和设计依据验证。

## 六、Skills 使用与沉淀

### 6.1 本阶段的目标能力

|Skill 能力|用途|建议策略|
|---|---|---|
|`codebase-exploration`|定向阅读代码与调用链|优先复用 02 阶段成果|

|`engineering-change-analysis`|识别真实工程变更|候选自建 Skill|
|`implementation-readiness`|结果完整性与就绪审查|可先使用检查清单|

这些名称均为能力标识，不表示已经安装了对应同名 Skill。

### 6.2 建议的 Skill 组织方式

本阶段暂时不必创建四个独立 Skill。

更合理的初始方案是：

**一个核心 Skill：**`**implementation-context-analysis**`

负责：

1. 接收 SPEC 与已有技术探索成果。
    
2. 定向分析代码库。
    
3. 建立设计与代码现状映射。
    
4. 识别工程变更。
    
5. 检查证据完整性。
    
6. 输出标准化 Implementation Context。
    

内部再复用已有的代码探索能力。

当后续实践发现映射分析、工程变更分析经常独立使用时，再考虑拆分。

### 6.3 与 ProjectLevel 的关系

本阶段如果发现稳定的项目级知识，例如：

- 重要模块职责和调用约束。
    
- 标准构建与测试方式。
    
- 数据访问、事务或异常处理规则。
    
- AI 必须遵守的工程限制。
    

应记录为 ProjectLevel 候选更新项。

但不应把一次需求特有的业务逻辑、实施任务或者临时问题全部写入 `AGENTS.md`。

## 七、质量门禁

本阶段的结果至少需要满足以下检查项。

### SPEC 覆盖

- 已提取主要实施设计点。
    
- 每个设计点都有代码映射、实施判断或明确待确认状态。
    
- 已纳入接口、数据、业务逻辑及相关质量要求。
    

### 工程依据

- 关键判断具有真实代码或配置依据。
    
- 重要代码位置可定位。
    
- 已区分 Verified、Inferred、Unknown。
    
- 没有把未搜索到的代码直接认定为不存在。
    

### 变更识别

- 已识别主要新增、修改和复用工作。
    
- 已考虑必要的迁移与兼容性工作。
    
- 已检查关键调用链和模块依赖。
    
- 已识别相关测试及验证入口。
    

### 设计一致性

- 没有未经确认改变已评审设计。
    
- 重大设计冲突已记录。
    
- 阻塞问题有明确处理方式。
    
- 不必要的范围扩张已排除。
    

### 阶段移交

- 工程变更清单可以支撑后续任务拆解。
    
- 重要依赖和风险已记录。
    
- 结果已经完成必要的审核。
    
- 已给出清晰的 Ready、Conditional 或 Blocked 结论。

## 八、常见问题与实践原则

### 8.1 是否需要把所有代码细节都探索清楚？

不需要。

本阶段重点是识别工程变更与真实代码落点。

具体函数如何修改、测试用例如何编写，可以在 04 阶段的 Task Plan 中进一步探索。

但对任务范围和实施依赖有决定性影响的细节，必须在任务拆解之前确认。

### 8.2 如果 SPEC 与代码库不一致怎么办？

先识别差异属于：

- 代码发生变化。
    
- 设计阶段遗漏或假设错误。
    
- 文档描述不准确。
    
- 实施细节可调整。
    
- 关键技术设计需要变更。
    

对于不影响已评审设计的实施细节，可记录建议，进入计划编制。

对于影响接口契约、业务规则、数据模型或关键架构的冲突，应暂停受影响部分，重新确认设计。

### 8.3 如果存在尚未确认的问题，是否可以进入任务拆解？

可以分情况处理：

**Ready：** 关键代码依据充分，可以直接拆解。

**Conditional：** 未知项不影响主要任务边界，可以继续，但要安排验证或处理。

**Blocked：** 未知项会直接改变关键技术方案、实施范围或任务结构，应先解决。

不要求所有信息都完全确定，但不能忽视会导致任务拆解失效的关键未知项。

### 8.4 是否应该把所有结果写入 AGENTS.md？

不应该。

AGENTS 适合保存稳定的项目级协作规则和工程约束。

实施分析结果主要属于当前需求，应该进入 Implementation Context 或相关计划文档。

只有经过确认且具有长期复用价值的项目知识，才考虑维护到 ProjectLevel。

### 8.5 如何避免 AI 的探索成本过高？

建议采用逐层收敛的探索策略：

1. 优先读取已有技术探索结果。
    
2. 根据 SPEC 定位相关模块。
    
3. 先检查入口、调用链及公共能力。
    
4. 对关键不确定项深入追踪。
    
5. 达到任务拆解所需的证据充分度后停止。
    

探索的目标是支撑下一步决策，而不是让 AI 无限制阅读整个仓库。

## 九、阶段完成定义（Definition of Done）

本阶段完成意味着：

**已经基于已评审 SPEC 和当前代码库，识别主要实施设计点对应的现有实现、工程变更及技术依赖；关键判断具有可追溯依据，重要未知项和设计冲突已得到处理或明确标记，分析结果足以支撑下一阶段的任务拆解。**

标准移交内容：

- SPEC 设计点清单。
    
- 代码现状与依据。
    
- SPEC—Codebase 映射。
    
- Engineering Changes 清单。
    
- Risks / Open Issues。
    
- Readiness Conclusion。
    

这些内容可以由 `IMPLEMENTATION_CONTEXT.md` 承载，也可以并入最终实施计划，不要求机械增加文档数量。
