## 一、阶段定位与目标

### 1.1 阶段定位

经过上一阶段，已经明确了：

- SPEC 中需要落实的设计点。
    
- 设计点对应的当前代码实现。
    
- 需要新增、修改、复用、删除或迁移的工程变更。
    
- 相关技术依赖、代码位置和实施风险。
    

但工程变更清单并不等于开发任务清单。

例如，一个「订单超时取消」设计点可能涉及任务调度、领域服务、数据更新、事件通知和测试。

这些工程变更究竟应该一次完成，还是拆成多个可控的开发任务，需要结合实际代码结构、模块依赖和验证方式作出判断。

因此，本阶段的核心目标是：

**以 SPEC 为目标，以代码现状和工程变更为依据，将需要实施的工作组织成可执行、可验证、可审查、可追踪的开发任务集合。**

### 1.2 本阶段需要解决的问题

1. 哪些工程变更需要组合为一个 Task？
    
2. 哪些工作应该独立拆分？
    
3. 如何确定任务的合理粒度？
    
4. 如何避免接口级拆分造成的任务碎片化？
    
5. 如何保证每个任务都具有明确的验收标准？
    
6. 如何确保所有 SPEC 设计点得到覆盖？
    
7. 如何记录尚未确认的任务依赖和技术风险？
    

### 1.3 本阶段的职责边界

**本阶段负责：**

- 确定任务拆解策略。
    
- 根据代码结构组织开发任务。
    
- 定义任务目标、范围和边界。
    
- 初步识别任务依赖。
    
- 定义任务验收标准。
    
- 建立 SPEC—Engineering Change—Task 追踪关系。
    
- 审查任务拆解完整性与合理性。
    

**本阶段暂不负责：**

- 详细分析全部任务依赖和关键路径。
    
- 确定最终实施顺序与开发批次。
    
- 为每个任务规划具体的文件级修改步骤。
    
- 编写代码和执行正式开发。
    
- 生成完整的需求级 Implementation Plan。
    

这些工作分别在后续 `03任务依赖分析与实施排序`、`04需求级实施计划编制` 和 `04Implementation` 中完成。

## 二、开发任务与工程变更的关系

### 2.1 三个层次

实施规划需要区分：

**SPEC Design Item：设计点**

描述目标能力及已确认的技术设计。

**Engineering Change：工程变更**

描述当前代码库为了满足设计目标需要发生什么变化。

**Development Task：开发任务**

描述一组可被 AI 执行、测试和审查的工程工作。

三者之间通常不是一对一的关系。

一个设计点可能对应多个工程变更；一个 Task 也可能覆盖多个紧密相关的工程变更。

### 2.2 为什么不直接把工程变更作为任务？

假设工程变更清单包含：

|Change ID|工程变更|
|---|---|
|EC-01|增加超时判断能力|
|EC-02|扩展订单状态流转逻辑|
|EC-03|新增定时任务调度入口|
|EC-04|复用取消事件通知机制|
|EC-05|补充超时取消测试|

如果机械地把每个 EC 转成 Task，可能出现：

- EC-02 与 EC-04 必须一起实现才能保证业务完整性。
    
- EC-05 中部分测试应随对应功能一起完成。
    
- EC-03 可以作为相对独立的调度入口任务。
    
- EC-01 与 EC-02 可能需要共享领域逻辑。
    

因此更合理的任务组织可能是：

**Task-001：实现超时取消领域能力**

涵盖超时判断、状态流转、事件机制及对应单元测试。

**Task-002：接入现有任务调度框架**

涵盖调度入口、批量扫描、调用领域能力以及调度相关测试。

**Task-003：完成端到端集成验证**

涵盖超时取消链路、重复执行、并发及关键回归场景。

以上仅为示例。实际任务划分必须根据代码结构和可验证边界确定。

**核心原则：工程变更描述需要改变什么，Task 描述如何将相关变更组织成有明确完成标准的工作单元。**

## 三、任务拆解的核心原则

### 3.1 以可验证的工程目标为任务边界

推荐优先按照以下顺序判断任务边界：

1. 可独立验证的业务或技术能力。
    
2. 清晰的模块职责和架构边界。
    
3. 实际代码依赖和修改耦合关系。
    
4. AI 执行时的上下文规模。
    
5. 代码审查与问题定位的便利性。
    

不要默认按照 API、类、文件或数据库表数量拆解。

### 3.2 优先考虑垂直能力拆解

当一项功能需要同时修改 Controller、Service、Repository 和测试时，可以将其组织成一个垂直开发任务。

例如：

**Task：实现订单超时取消领域能力**

任务范围可以包括：

- 调整领域规则。
    
- 修改服务逻辑。
    
- 复用数据访问能力。
    
- 增加对应测试。
    

这样做的优势是：

- 任务有明确的功能目标。
    
- 实现与验证能够在同一任务中完成。
    
- 减少人为拆分导致的无效交接。
    
- AI 可以围绕一个完整目标规划具体编码。
    

但垂直拆解不是唯一方式。

如果底层基础设施需要被多个功能共同使用，或者涉及高风险迁移，也可以先独立实施基础能力。

### 3.3 尊重模块边界

如果任务横跨多个独立部署服务、多个团队负责的模块，或者具有不同发布周期，应考虑分开拆解。

例如：

支付服务的退款能力和订单服务的取消能力，可能通过明确的接口契约衔接。

此时可以分别建立任务，并显式记录接口依赖和集成验证要求。

不能为了让任务表面上具有完整业务功能，就让一个 Task 无限制地跨越多个服务和职责边界。

### 3.4 保持任务粒度适中

任务过大，通常表现为：

- 同时覆盖多个独立功能。
    
- 涉及大量无关模块。
    
- 验收标准复杂且难以一次确认。
    
- AI 容易出现上下文遗漏。
    
- 代码 Review 难以定位问题。
    
- 执行失败后难以确定完成进度。
    

任务过小，通常表现为：

- 单独任务无法形成可验证结果。
    
- 大量任务只是机械地新增文件或修改字段。
    
- 多个任务必须反复修改同一小段代码。
    
- 开发者需要频繁管理任务交接。
    
- 验证成本超过任务本身的价值。
    

**一个合理的 Task 应当能够在可控范围内完成，并留下有意义的验证证据。**

不建议一开始制定固定的文件数量、代码行数或开发时长阈值。这些指标最多用于辅助评估，不能代替工程判断。

### 3.5 测试与实现应协同拆解

不建议默认将所有业务实现和测试完全分开。

例如：

Task-001 实现业务逻辑。

Task-002 才为 Task-001 编写单元测试。

这会导致 Task-001 缺乏独立验收能力。

更合理的方式是：

**每个实现任务包含与其功能对应的必要测试。**

同时可以保留独立的测试类 Task，例如：

- 跨模块集成测试。
    
- 端到端业务链路验证。
    
- 历史数据迁移验证。
    
- 性能与并发验证。
    
- 系统级回归测试。
    

具体拆分取决于验证范围和项目测试基础设施。

## 四、标准执行流程

本阶段建议划分为五个步骤：

### Step 01：确认工程变更覆盖范围

**目标：确保任务拆解有完整、可信的输入。**

读取：

- 已评审 SPEC。
    
- Implementation Context。
    
- 工程变更清单。
    
- 相关代码依据。
    
- 项目工程规范。
    

检查：

- 所有主要 SPEC 设计点是否已经分析。
    
- 各工程变更是否明确来源。
    
- 是否存在未处理的设计冲突。
    
- 是否遗漏数据库、配置、兼容性或测试变更。
    
- 哪些未知项会影响任务边界。
    

若存在直接影响拆解结构的阻塞问题，应先回到上一阶段补充分析。

**产出：已确认的任务拆解输入集合。**

### Step 02：确定任务拆解策略

**目标：选择适合当前项目的任务组织方式。**

常见方式包括：

|方式|适用场景|
|---|---|
|按垂直功能|功能边界明确，可形成完整验证闭环|
|按模块|模块职责清晰，工程边界独立|
|按基础能力|多个任务共同依赖同一底层能力|
|按高风险变更|数据迁移、兼容性、安全等需要独立控制|
|混合拆解|大多数真实项目的常见选择|

建议默认考虑：

**垂直功能为主，模块边界与技术依赖为约束，必要时独立拆分基础能力和高风险工作。**

这不是绝对规则。

例如，一个数据库兼容迁移需要跨多个版本部署，可能应独立分成扩展、迁移、切换、清理等任务。

**产出：任务拆解策略及主要任务分组。**

### Step 03：组织开发任务

**目标：将相关工程变更组合为有明确交付结果的 Task。**

对每一组工程变更，依次判断：

1. 是否具有共同目标？
    
2. 是否属于同一业务能力或技术职责？
    
3. 是否存在紧密的实现耦合？
    
4. 能否定义明确验收标准？
    
5. 是否跨越不应合并的架构边界？
    
6. 修改范围是否便于 AI 执行与审查？
    
7. 是否应该进一步拆分或与相邻任务合并？
    

建议此时形成任务草案。

例如：

|Task|目标|包含变更|
|---|---|---|
|TASK-001|实现订单超时取消领域能力|EC-01、EC-02、EC-04|
|TASK-002|增加订单超时调度入口|EC-03|
|TASK-003|完成超时取消集成验证|EC-05 中跨任务部分|

注意：工程变更和任务之间可以存在多对多关系，但要明确每项变更的主要实施责任，防止不同任务重复修改同一逻辑或遗漏工作。

**产出：开发任务草案。**

### Step 04：定义任务卡

**目标：使每个 Task 成为可理解、可执行、可验收的开发单元。**

每个任务至少应包含以下信息。

#### 任务基本信息

- Task ID。
    
- Task Name。
    
- Objective。
    
- SPEC Reference。
    
- Engineering Change Reference。
    

#### 实施范围

- In Scope：需要完成的工作。
    
- Out of Scope：明确不包含的工作。
    
- Code Area：已确认或预计涉及的模块。
    
- Constraints：关键工程约束。
    

#### 依赖和风险

- 已知前置任务。
    
- 外部依赖。
    
- 可能影响实施的风险。
    
- 需要在任务执行前确认的事项。
    

#### 验收标准

应当是能够验证的结果，而不只是“完成代码”。

例如：

不推荐：

“实现订单超时取消接口。”

推荐：

“超时且处于允许取消状态的订单能够被自动取消；已支付或其他不可取消状态不被错误修改；重复执行不会造成重复业务副作用；相应测试通过。”

如果涉及 API 契约，也需要明确状态码、返回数据及错误场景。

**产出：结构化任务卡。**

### Step 05：任务拆解审查

**目标：检查任务集合是否完整、合理、可执行。**

建议从五个维度进行审核。

**1. 覆盖完整性**

- 是否覆盖 SPEC 中全部必须交付的内容？
    
- 是否有工程变更没有归属任务？
    
- 是否遗漏测试、配置、数据迁移和兼容性工作？
    

**2. 任务边界**

- 是否存在范围过大的任务？
    
- 是否出现无法独立验证的微任务？
    
- 是否有重复或高度重叠的任务？
    
- 是否跨越不合理的架构边界？
    

**3. 工程依据**

- 任务是否建立在真实代码结构上？
    
- 预计修改模块是否有依据？
    
- 是否把未知的代码落点写成确定事实？
    

**4. 验收能力**

- 每个任务是否具有明确的完成标准？
    
- 是否有可执行的验证方式？
    
- 是否遗漏异常、边界或失败路径？
    

**5. 依赖可识别性**

- 任务的主要前置条件是否记录？
    
- 是否有潜在循环依赖？
    
- 是否存在需要进一步分析的跨模块依赖？
    

此处只检查已知依赖是否合理，完整依赖排序放在下一阶段。

**产出：经过审查的** `**TASKS.md**` **初稿。**

## 五、任务拆解的标准产物

### 5.1 推荐产物：TASKS.md

建议采用一个集中管理的任务清单。

基本结构：

```
# Development Tasks

## 1. 基本信息
- 需求名称
- SPEC 引用
- Implementation Context 引用
- 代码基线

## 2. 拆解策略
- 任务拆解原则
- 任务分组依据
- 关键约束

## 3. Tasks
- TASK-001
- TASK-002
- TASK-003

## 4. Traceability
- SPEC → Engineering Changes → Tasks

## 5. Open Issues
- 未解决的任务边界问题
- 待确认的技术依赖

## 6. Review
- 覆盖检查
- 粒度检查
- 验收检查
- 待修正项
```

### 5.2 单任务卡模板

```
## TASK-001：任务名称

### Objective
任务要实现的能力与目标。

### References
- SPEC：SPEC-XX
- Engineering Changes：EC-XX
- Codebase：相关模块及证据

### Scope
**In Scope**
- 需要完成的工作

**Out of Scope**
- 明确不包含的内容

### Dependencies
- 已知前置任务
- 外部依赖或前置条件

### Acceptance Criteria
- [ ] 功能验收条件一
- [ ] 功能验收条件二
- [ ] 关键异常与边界条件
- [ ] 必要测试通过

### Risks / Open Issues
- 风险或待确认问题

### Status
TODO
```

上述任务卡是任务级目标描述，不应在此阶段提前写满文件级编码步骤。

### 5.3 SPEC—Task 追踪矩阵

建议维护如下映射：

|SPEC ID|Engineering Change|Task|覆盖情况|
|---|---|---|---|
|SPEC-01|EC-01、EC-02|TASK-001|已覆盖|
|SPEC-02|EC-03|TASK-002|已覆盖|
|SPEC-03|EC-04、EC-05|TASK-001、TASK-003|已覆盖|

如果某个设计点已经由现有代码完全满足，不需要新开发任务，也应记录验证依据，标记为“现有实现满足”，而不是默默从矩阵中删除。

追踪矩阵的目标是确保：

**SPEC 中每个必须交付的设计点，都能追溯到相应工程变更、开发任务或明确的现状验证结论。**

## 六、AI 辅助任务拆解工作流

### 6.1 AI 的主要职责

AI 可以负责：

- 读取工程变更清单。
    
- 分析变更之间的技术耦合关系。
    
- 提出任务拆解策略。
    
- 生成候选任务集合。
    
- 编制结构化任务卡。
    
- 检查 SPEC 覆盖情况。
    
- 识别过大、过小或重复的任务。
    
- 提出调整建议。
    

开发者重点负责：

- 确认任务边界。
    
- 审核核心业务验收标准。
    
- 判断技术依赖和模块职责。
    
- 审核高风险任务。
    
- 确认拆解是否适合当前开发节奏。
    

### 6.2 推荐的两轮 AI 协作

**第一轮：任务拆解**

让 AI 基于 SPEC、代码现状和工程变更提出任务方案。

强调：

- 不要脱离代码库。
    
- 不要机械地按接口或文件拆分。
    
- 每个任务必须有明确目标和验收标准。
    
- 不要提前进入代码实现。
    
- 对不确定的任务边界明确标记。
    

**第二轮：拆解审查**

使用独立的审查指令检查：

- SPEC 覆盖。
    
- 工程变更覆盖。
    
- 任务粒度。
    
- 重复或遗漏。
    
- 验收完整性。
    
- 依赖与技术风险。
    

根据审查结果修订 `TASKS.md`。

## 七、可复用 Prompt

### Prompt A：生成开发任务

```
你现在负责 03ImplementationPlanning 的
「基于代码库的开发任务拆解」。

输入：
1. 已评审 SPEC：[路径]
2. Implementation Context：[路径]
3. Engineering Changes：[路径或章节]
4. 项目工程规范：[路径]
5. 当前代码库

目标：
基于真实代码现状和工程变更清单，
生成可执行、可验证、可追踪的开发任务。

要求：
1. 先理解 SPEC 的设计目标与实施约束。
2. 优先复用上一阶段已经确认的代码依据。
3. 分析工程变更之间的业务和技术耦合关系。
4. 优先按可验证的功能或技术能力组织任务。
5. 尊重真实架构与模块边界。
6. 不要机械地按接口、类、文件或数据库表拆分。
7. 每个 Task 必须明确：
   - Task ID
   - Objective
   - SPEC / Engineering Change References
   - In Scope / Out of Scope
   - Code Area
   - Known Dependencies
   - Acceptance Criteria
   - Risks / Open Issues
8. 实现任务应包含对应的必要测试。
9. 对跨模块集成、迁移及高风险验证，
   判断是否需要独立任务。
10. 标记未经验证的代码假设。
11. 不要编写代码。
12. 暂不进行最终实施排序。

输出：
- 任务拆解策略
- TASKS.md 初稿
- SPEC—Task 追踪矩阵
- 待确认问题

如果已有工程变更不足以支持合理拆解，

```

### Prompt B：任务拆解 Review

```
请以独立工程审查者的身份，
审核当前 TASKS.md 及其拆解依据。

输入：
- 已评审 SPEC
- Implementation Context
- Engineering Changes
- TASKS.md
- 当前项目代码库

检查维度：

1. SPEC Coverage
   是否覆盖全部必须交付的设计点？

2. Engineering Change Coverage
   是否存在未归属任务的工程变更？

3. Task Granularity
   是否有过大、过小或不合理拆分的任务？

4. Boundary & Coupling
   是否存在重复、职责冲突或不合理跨模块工作？

5. Acceptance Criteria
   各任务是否能通过明确证据验证完成？

6. Engineering Evidence
   任务涉及的代码位置和工程判断是否可信？

7. Dependencies & Risks
   是否遗漏重要前置条件、迁移及技术风险？

输出：
- Findings（按严重程度排序）
- 对应 Task ID / SPEC ID
- 问题依据
- 修改建议
- 未确认事项
- 审查结论

对没有证据支持的判断标记为待验证，
不要直接认定为事实。

请先输出审查结果，不直接修改文件。
```

建议先执行第一轮拆解，再执行第二轮 Review。确认修改建议后更新任务清单。

## 九、质量基线

进入下一阶段前，应满足：

- 已确定合理的任务拆解策略。
    
- 任务基于真实代码现状和工程变更。
    
- 每个 Task 具有明确目标与实施边界。
    
- 每个 Task 具有可验证的完成标准。
    
- 实现任务包含必要的测试要求。
    
- SPEC 设计点存在明确的 Task 或验证映射。
    
- 所有必须实施的工程变更都有任务归属。
    
- 不存在明显重复或职责冲突的 Task。
    
- 任务粒度适合 AI 执行与开发者 Review。
    
- 已记录关键依赖与待确认事项。
    
- 已通过任务拆解 Review。
    

这里不要求任务最终排序已经确定，也不要求任务级详细编码方案已经完成。

## 十、常见误区

### 10.1 直接把 SPEC 章节转成任务

SPEC 的章节是技术方案的文档组织方式，并不等价于工程任务边界。

应先识别工程变更，再根据真实代码结构组织任务。

### 10.2 按接口数量拆分

一个接口可能非常简单，也可能涉及复杂的领域逻辑、事务和数据迁移。

任务粒度不应由接口数量直接决定。

### 10.3 为了任务独立而重复实现公共能力

如果多个任务依赖相同基础能力，应明确公共能力的归属及前置依赖，而不是在多个任务中重复开发。

### 10.4 把测试全部放到最后

这会使大量开发任务无法独立判断是否完成。

应在实现任务中包含必要的测试，并为跨任务验证设置独立工作。

### 10.5 过早写详细代码修改步骤

任务拆解阶段只需要确认目标、范围、代码区域、依赖和验收标准。

具体文件级修改步骤应在任务执行前基于最新代码状态确定。

### 10.6 任务越多越可控

任务太碎会增加交接成本、重复上下文理解和集成风险。

更重要的是任务的边界与验证能力，而不是数量。

### 10.7 任务拆解完成就可以马上开始编码

任务拆解只是形成任务集合。

还需要经过依赖分析、实施排序、整体实施计划和必要的计划审核，才能正式进入受控开发。

## 十一、完成定义（Definition of Done）

本阶段完成意味着：

**基于已评审 SPEC、真实代码库和工程变更清单，已经形成一组目标明确、边界清晰、具有验收标准和初步依赖关系的开发任务，并建立 SPEC—Engineering Change—Task 的完整追踪关系。**

主要产出：

- `TASKS.md` 初稿。
    
- SPEC—Task 追踪矩阵。
    
- 任务拆解 Review 结论。
    
- 关键风险与待确认问题。
