# 04 需求级实施计划编制

> **所属阶段：** `03ImplementationPlanning`
> 
> **前置阶段：** `03任务依赖分析与实施排序`
> 
> **后续阶段：** `05实施计划评审与开发移交`
> 
> **核心输入：** 已评审 SPEC、Implementation Context、TASKS.md、任务依赖关系、实施批次、代码库与项目工程规范
> 
> **核心产出：** `IMPLEMENTATION_PLAN.md`、同步更新的 `TASKS.md`
> 
> **候选 Skill：** `implementation-plan-authoring`（待验证或自建）
> 
> **阶段目标：** 将已经确认的工程变更、任务、依赖关系及实施排序整合成一份可执行、可审查、可维护的需求级实施计划。

---

## 一、阶段定位

### 1.1 什么是需求级实施计划编制？

经过前三阶段，已经完成：

1. **实施现状探索：** 确认 SPEC 与真实代码库之间的差异，识别工程变更。
    
2. **任务拆解：** 将工程变更组织为具有明确边界、验收标准的开发任务。
    
3. **依赖分析与排序：** 确定任务依赖、实施批次、并行条件和阶段性里程碑。
    

但这些结果仍然分散在不同分析过程及任务记录中。

本阶段需要将它们整合为统一的执行基线：

**Implementation Plan（需求级实施计划）。**

它不仅要告诉开发者应该按照什么顺序实施，还要说明：

- 为什么采用该实施顺序？
    
- 每个开发批次完成什么能力？
    
- 任务之间如何交接和集成？
    
- 什么时候可以启动下一阶段？
    
- 如何验证阶段性目标？
    
- 哪些技术风险需要提前解决？
    
- 开发中发生变化如何更新计划？
    

### 1.2 实施计划的核心价值

**1. 形成统一执行入口**

开发者或 AI 不需要每次重新阅读完整 SPEC、重新分析任务依赖和重新决定实施顺序。

通过 Implementation Plan，可以快速了解整体开发安排。

**2. 控制开发范围**

计划明确每个阶段的目标及交付边界，减少 AI 一次性修改过多代码或实施未确认需求的风险。

**3. 支持阶段性验收**

每个 Batch 具有启动条件、交付目标和验证关卡，避免只根据任务数量判断开发进度。

**4. 支持上下文恢复**

当切换 AI 会话、开发分支或接手开发人员时，可以通过计划及任务状态恢复当前实施进度。

**5. 支持变更管理**

实施过程中发现新的依赖或设计问题时，可以明确变更影响，并更新计划，而不是让 AI 静默偏离既定设计。

### 1.3 本阶段的职责边界

**需要完成：**

- 确定整体实施策略。
    
- 整合工程变更与任务清单。
    
- 确认实施批次、里程碑和依赖。
    
- 规划测试、集成与回归验证。
    
- 明确任务执行、Review 和验收的统一规则。
    
- 制定风险处理与计划维护机制。
    
- 生成正式实施计划草案。
    

**不需要完成：**

- 重新设计已经评审的技术方案。
    
- 对每个 Task 生成文件级编码步骤。
    
- 编写正式业务代码。
    
- 执行所有任务的测试。
    
- 代替下一阶段进行计划批准与开发移交。

## 二、输入与前置条件

### 2.1 必要输入

|输入|主要内容|用途|
|---|---|---|
|已评审 SPEC|目标、方案、接口、数据、业务规则|设计基线|
|Implementation Context|代码现状、变更位置、工程变更|工程依据|
|TASKS.md|Task、范围、验收标准、状态|任务来源|
|Dependency Analysis|任务依赖与前置条件|确定顺序|
|Implementation Batches|批次目标与关卡|实施组织|
|Project Context|工程规范、测试约束及环境信息|执行约束|

以上信息不要求分别存放在六个文件中，但应能找到相应的可信来源。

### 2.2 编制前的就绪检查

正式生成计划前，需要确认：

- SPEC 已形成明确的评审基线。
    
- 主要工程变更具有代码依据。
    
- TASKS.md 中各任务具备目标、范围和验收标准。
    
- 关键依赖、实施顺序和批次已有分析结果。
    
- 影响整体实施策略的阻塞性问题已解决。
    
- 项目级工程约束与测试方式已明确，或相关缺口已有处理安排。
    

如果发现输入不完整，应先补齐相关分析。

不应要求 AI 为了生成完整文档而编造任务、代码路径、测试命令或技术决策。

## 三、实施计划编制的核心原则

### 3.1 以既有分析结果为依据

Implementation Plan 主要整合已确认的成果。

不能在生成正式计划时，未经说明重新：

- 拆解全部任务。
    
- 改变任务范围。
    
- 修改硬依赖关系。
    
- 调整已确认的关键技术方案。
    
- 增加 SPEC 范围之外的功能。
    

如果编制过程中发现前置分析存在问题，应提出修订建议，更新对应事实来源后再生成计划。

### 3.2 需求级计划不等于任务级执行计划

需求级计划关注：

- Task 与 Batch。
    
- 全局依赖和顺序。
    
- 阶段目标。
    
- 集成与验收关卡。
    
- 风险和变更控制。
    

任务级计划关注：

- 当前代码最新状态。
    
- 具体文件与方法。
    
- 实现步骤。
    
- 具体测试场景。
    
- 代码修改与验证。
    

因此，Implementation Plan 不需要为全部任务提前生成详细的代码修改方案。

### 3.3 保持单一事实来源

推荐采用以下文档分工：

**SPEC.md**

记录技术设计，作为已评审设计依据。

**IMPLEMENTATION_CONTEXT.md**

记录代码现状、映射和工程变更依据。

**TASKS.md**

管理具体 Task、依赖、验收标准及执行状态。

**IMPLEMENTATION_PLAN.md**

管理实施策略、批次、里程碑、验证关卡与整体风险。

不要在 Implementation Plan 和 TASKS 中重复维护两套完整任务状态。

### 3.4 以可验证交付组织实施

不能仅按技术组件组织实施批次。

每个 Batch 都应明确：

- 要交付的工程能力。
    
- 包含的 Task。
    
- 启动条件。
    
- 批次完成条件。
    
- 必须执行的验证。
    

开发顺序不一定完全等同于代码模块顺序，而应综合考虑依赖、风险和集成验证。

### 3.5 实施计划允许受控演进

计划是经过审核的执行基线，不是永久不变的文档。

允许根据开发过程中发现的真实情况进行调整，但必须区分：

- 任务级实施细节变化。
    
- 任务边界或依赖变化。
    
- 实施批次变化。
    
- 影响 SPEC 的技术设计变化。
    

变更影响越大，需要的审核级别越高。

## 四、标准执行流程

建议分为五个步骤。

### Step 01：汇总前置成果并检查一致性

**目标：建立实施计划的可信输入集合。**

读取并确认：

- SPEC 版本及其评审结论。
    
- 代码基线。
    
- 工程变更清单。
    
- Task 列表及验收标准。
    
- 任务依赖关系。
    
- 实施批次及里程碑。
    
- 风险和待确认事项。
    

重点检查：

1. Task 是否引用同一版本的 SPEC。
    
2. 工程变更与 Task 是否能相互追踪。
    
3. 批次中的 Task 是否真实存在。
    
4. 批次顺序是否满足硬依赖。
    
5. 同一任务是否存在互相冲突的范围描述。
    
6. 是否有尚未解决且会改变实施策略的问题。
    

如发现矛盾，先修订前置产物，不在 Implementation Plan 中隐藏冲突。

**阶段产出：经过一致性检查的实施规划输入。**

### Step 02：确定整体实施策略

**目标：说明整个需求打算采用什么工程落地方式。**

需要综合前面分析，明确：

**1. 组织策略**

例如：

- 先稳定公共契约，再分模块实施。
    
- 按垂直业务能力逐步交付。
    
- 对高风险基础能力先进行技术验证。
    
- 按兼容迁移顺序实施数据库和接口变更。
    

**2. 代码集成策略**

根据项目实际情况明确：

- 任务是否在独立工作区执行。
    
- 采用什么分支或 PR 方式。
    
- 如何控制共享代码的修改冲突。
    
- 任务完成后如何进行集成。
    
- 如何避免多个 AI 代理修改同一工作区。
    

如果项目已有团队流程，应直接遵循，不另行发明。

**3. 质量与验证策略**

明确：

- 每个实现任务的必要自测要求。
    
- AI Review 及人工 Review 的适用条件。
    
- 批次级集成验证节点。
    
- 需求级回归与验收要求。
    

**4. 风险控制策略**

对于数据库迁移、接口兼容、核心状态变更、权限或安全相关任务，需要明确额外检查及确认节点。

**阶段产出：整体实施策略。**

### Step 03：编排开发批次与里程碑

**目标：将任务执行顺序转化为可以管理的阶段性交付计划。**

对每个 Batch 定义：

|字段|说明|
|---|---|
|Batch ID|批次标识|
|Objective|本批次交付目标|
|Tasks|包含的 Task ID|
|Prerequisites|启动条件|
|Deliverables|期望交付能力或产物|
|Verification Gate|必须通过的检查|
|Risks|主要风险|
|Exit Criteria|完成并进入下一批次的条件|

#### 编排要求

- 所有实施任务应具有明确的批次归属或特殊执行安排。
    
- 批次之间的顺序应符合硬依赖。
    
- 任务并行必须有明确条件。
    
- 高风险工作应在适当位置进行验证。
    
- 必要的跨模块集成测试应设置在合理节点。
    
- 批次数量由实际工程目标决定，不强制固定。
    

对于简单需求，可能只有一个实施批次。

对于复杂需求，可以按照基础能力、业务能力、系统集成等不同目标分批。

**阶段产出：Implementation Batches 与 Milestones。**

### Step 04：制定验证、风险和完成标准

**目标：使计划不仅能够指导编码，还能判断实施结果是否满足交付要求。**

#### 4.1 验证策略

至少考虑三个层次：

**任务级验证**

在每个 Task 执行期间完成：

- 必要的单元测试。
    
- 相关代码质量检查。
    
- 任务验收条件检查。
    
- 必要的 AI / 人工 Review。
    

**批次级验证**

当多个任务形成阶段能力时：

- 进行模块集成验证。
    
- 检查接口和数据契约一致性。
    
- 验证批次目标。
    
- 解决阻断性问题。
    

**需求级验证**

所有必要任务与批次完成后：

- 按 SPEC 和需求验收标准核对功能。
    
- 执行相关回归测试。
    
- 检查关键异常和非功能性要求。
    
- 形成整体完成与交付结论。
    

#### 4.2 风险管理

需要记录：

- 风险描述。
    
- 影响的 Task / Batch。
    
- 发生条件。
    
- 潜在影响。
    
- 预防或验证措施。
    
- 风险发生时的处理方案。
    

不能只列出风险名称，而没有具体处理策略。

#### 4.3 整体完成定义

需要明确整个需求什么时候算完成。

例如：

- 所有必须交付的 SPEC 设计点有实现和验证证据。
    
- 必需 Task 已完成。
    
- 集成及回归测试满足要求。
    
- 阻断性问题已解决。
    
- 必要文档、配置及迁移工作完成。
    
- 满足项目交付准入要求。
    

**阶段产出：验证策略、风险措施、整体完成标准。**

### Step 05：生成文档并进行自检

**目标：形成结构统一、可维护的实施计划草案。**

根据标准模板编制 `IMPLEMENTATION_PLAN.md`。

生成完成后检查：

1. 是否与 SPEC 目标一致。
    
2. 是否基于真实代码和已确认的工程变更。
    
3. 是否正确引用 TASKS。
    
4. 是否明确整体实施策略。
    
5. 是否覆盖全部实施批次。
    
6. 批次顺序是否符合硬依赖。
    
7. 是否定义阶段性交付和验证关卡。
    
8. 是否遗漏重要风险与兼容性事项。
    
9. 是否具有明确的计划变更规则。
    
10. 是否能指导开发者选择并启动首批任务。
    

建议此时文档状态设为 `Draft / Pending Review`。

正式计划评审和开发移交在下一阶段完成。

**阶段产出：IMPLEMENTATION_PLAN.md 草案。**

## 五、标准文档关系与维护规则

### 5.1 推荐文档结构

```
docs/changes/<feature>/
├── SPEC.md
├── IMPLEMENTATION_CONTEXT.md    # 可选
├── IMPLEMENTATION_PLAN.md       # 需求级主计划
├── TASKS.md                     # 任务台账
└── tasks/                       # 04阶段按需创建
    ├── TASK-001.md
    └── TASK-002.md
```

目录仅为参考，应遵守项目已有文档管理规范。

### 5.2 文档职责

|文档|维护重点|更新时机|
|---|---|---|
|SPEC|设计决策、接口及业务规则|设计变更时|
|Implementation Context|代码依据与工程变更|关键现状分析失效时|
|TASKS|任务、依赖、验收及状态|任务调整或执行推进时|
|Implementation Plan|实施策略、批次、里程碑、风险|整体实施安排变化时|
|Task Plan|单任务具体实施方案|执行当前 Task 时|

### 5.3 计划变更分级

**Level 1：任务内部调整**

例如修改实际代码落点或任务内部实现顺序。

若不改变 Task 目标和验收标准，只需更新任务执行记录。

**Level 2：任务及批次调整**

例如新增 Task、拆分 Task、修改任务依赖或批次顺序。

需要同步更新 TASKS 和 Implementation Plan，并检查对后续任务的影响。

**Level 3：技术设计变更**

例如修改已评审接口契约、数据模型或核心业务规则。

应先确认 SPEC 变更，再更新任务和实施计划。

## 六、AI 辅助编制方式

### 6.1 推荐执行方式

采用两轮 AI 协作：

**第一轮：计划编制**

让 AI 读取已确认的输入，依据模板生成 Implementation Plan 草案。

重点要求：

- 不自行改变设计。
    
- 不重做任务拆解。
    
- 不编造项目现状。
    
- 不提前生成所有 Task Plan。
    
- 保留引用和依赖关系。
    
- 明确尚未确定的事项。
    

**第二轮：计划一致性自检**

让 AI 对照 SPEC、工程变更、TASKS 与批次安排，检查计划是否存在内容遗漏或内部冲突。

这里的自检只用于发现明显问题，不能替代下一阶段的独立计划 Review。

### 6.2 可复用 Prompt：实施计划编制

```
你现在负责 03ImplementationPlanning 的
「需求级实施计划编制」。

输入：
1. 已评审 SPEC：[路径]
2. Implementation Context：[路径]
3. TASKS.md：[路径]
4. 任务依赖和实施批次：[路径或章节]
5. 项目工程规范：[路径]
6. 当前代码库
7. IMPLEMENTATION_PLAN.template.md：[路径]

目标：
根据已经确认的分析和任务安排，
生成完整、可执行、可审查的需求级实施计划。

执行要求：
1. 阅读全部输入并检查版本与引用一致性。
2. 使用已确认的任务与依赖，不擅自重新拆解。
3. 基于代码现状和工程变更确定整体实施策略。
4. 按现有分析整理 Batch、Milestone 和验证关卡。
5. 明确单任务、批次级和需求级验证要求。
6. 纳入兼容性、数据迁移、外部依赖与关键风险。
7. 保留 SPEC、Engineering Change 和 Task 的引用。
8. 使用提供的 Implementation Plan 模板。
9. 不复制 SPEC 的完整技术设计内容。
10. 不复制 TASKS.md 中全部任务详情及执行状态。
11. 不生成任务级文件修改计划。
12. 不修改业务代码。
13. 不编造类名、文件路径、测试命令或设计决策。
14. 发现前置产物冲突时列出问题，不静默修正。

输出：
- IMPLEMENTATION_PLAN.md（Draft）
- 输入一致性检查结果
- 待确认问题
- 计划编制自检结论

生成后执行自检，但不要自行将计划标记为 Approved。
```

## 七、Skills 使用与沉淀

### 7.1 本阶段候选能力

|能力|用途|初期建议|
|---|---|---|
|`implementation-plan-authoring`|根据前置产物编制实施计划|核心候选 Skill|
|`plan-consistency-check`|检查跨文档的一致性|可内置于主 Skill|
|`milestone-planning`|组织实施批次及关卡|复用上一阶段结果|
|`risk-planning`|整理风险控制与应对策略|作为编制步骤|

以上均为目标能力名称，尚不代表已经找到或安装对应同名 Skill。

### 7.2 推荐封装方式

建议初期只封装一个：

`**implementation-plan-authoring**`

输入：

- SPEC。
    
- Implementation Context。
    
- TASKS。
    
- 依赖分析与实施批次。
    
- 项目规范。
    
- 标准模板。
    

执行流程：

1. 校验输入及版本。
    
2. 检查前置结果一致性。
    
3. 整理实施策略。
    
4. 编排里程碑与验证关卡。
    
5. 制定风险及计划维护机制。
    
6. 生成标准计划。
    
7. 进行内容和引用自检。
    

输出：

- Implementation Plan 草案。
    
- 一致性检查结果。
    
- 待确认事项。
    

后续经过真实需求验证，再考虑将其正式封装为 Skill。

## 八、质量基线

完成本阶段时应满足：

- 使用正确的已评审 SPEC 版本。
    
- 主要工程变更与真实代码依据一致。
    
- 引用的 Task ID 均存在。
    
- 实施策略与项目实际约束匹配。
    
- 实施顺序满足硬依赖。
    
- 所有必须实施的 Task 均被合理安排。
    
- 每个 Batch 具有交付目标和完成标准。
    
- 并行条件及集成风险明确。
    
- 单任务、批次及需求级验证均得到安排。
    
- 高风险变更具有处理或验证措施。
    
- 未解决问题有明确的后续处理方式。
    
- 计划更新及变更规则明确。
    
- 文档通过基础一致性自检。

## 九、常见误区

### 9.1 将 Implementation Plan 写成第二份 SPEC

大量复制架构设计、接口字段及业务逻辑，导致文档重复且容易不一致。

正确做法是引用 SPEC，并聚焦工程实施策略。

### 9.2 将 Implementation Plan 写成完整任务台账

反复复制所有 Task 的详细描述、验收项和状态，增加维护成本。

正确做法是通过 Task ID 引用 TASKS.md。

### 9.3 给每个 Task 提前写详细文件级实现步骤

实际开发时代码可能发生变化，计划容易过时。

正确做法是进入 04Implementation 后，针对当前 Task 生成 Task Plan。

### 9.4 只有开发顺序，没有验证关卡

任务都完成了，但不知道整个功能是否可用。

正确做法是明确每个批次的交付能力与验证标准。

### 9.5 生成计划后不允许调整

实际开发存在不可避免的不确定性。

正确做法是维护计划基线，并实施受控变更。
