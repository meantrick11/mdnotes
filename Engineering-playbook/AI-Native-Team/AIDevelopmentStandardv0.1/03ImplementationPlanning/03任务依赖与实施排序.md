## 一、阶段定位与目标

### 1.1 什么是任务依赖分析与实施排序？

开发任务拆解完成后，虽然已经知道整个需求需要完成哪些工作，但不代表这些任务可以按照清单顺序直接开发。

实际工程中，任务之间可能存在不同类型的依赖：

- 后续任务依赖前置任务提供的数据结构或接口契约。
    
- 多个任务依赖同一个公共组件。
    
- 数据迁移必须满足兼容性和发布顺序要求。
    
- 某些工作可并行实施，但最终需要集成验证。
    
- 高风险技术问题需要在大规模编码之前验证。
    

因此，本阶段需要：

**基于真实代码结构、技术约束和任务边界，分析任务之间的依赖关系，识别关键风险及并行条件，将开发任务组织成有序、可验证的实施批次。**

本阶段主要回答：

1. 哪些任务必须先完成？
    
2. 哪些任务之间存在接口或数据契约依赖？
    
3. 哪些任务可以并行？
    
4. 哪些风险需要提前验证？
    
5. 应该按照什么顺序开发？
    
6. 如何划分阶段性小目标？
    
7. 每个阶段结束时应该验证什么？
    

### 1.2 与上一阶段的区别

|维度|02 任务拆解|03 依赖分析与排序|
|---|---|---|
|核心问题|需要完成哪些 Task？|Task 应如何组织实施？|
|关注重点|任务目标、范围、验收标准|前置依赖、顺序、并行、风险|
|主要活动|拆分和组合工程变更|构建依赖图并编排开发|
|核心产出|`TASKS.md` 初稿|任务依赖图与实施批次|
|阶段边界|不确定最终执行顺序|不编写任务级详细代码计划|

本阶段允许发现任务拆解不合理并返回上一阶段调整。

例如，发现两个任务存在循环依赖，可能说明公共能力归属不清或任务边界需要重新设计。

## 二、理解不同类型的任务依赖

任务依赖不应只有简单的“先做 A，再做 B”。

建议重点识别以下五类依赖。

### 2.1 硬依赖（Hard Dependency）

任务 B 必须等待任务 A 的某项交付完成，才能正确实施或验证。

例如：

- TASK-001：增加新的领域数据模型。
    
- TASK-002：实现基于该模型的业务服务。
    

如果 TASK-002 无法在没有新模型的情况下正确编译或测试，则 TASK-001 是它的硬依赖。

**处理原则：建立明确的前置关系，不应任意并行。**

### 2.2 契约依赖（Contract Dependency）

多个任务依赖共同的数据结构、接口或事件契约。

例如：

- TASK-001：定义支付回调数据契约。
    
- TASK-002：实现支付回调处理。
    
- TASK-003：实现支付结果通知。
    

这里并不意味着 TASK-002 和 TASK-003 一定必须串行。

如果契约已经经过评审、稳定且可以使用 Mock 或 Stub 验证，两者可能并行实施。

**处理原则：区分“依赖契约确定”和“依赖前置实现完成”。**

不能仅因为两个任务存在调用关系，就机械地要求其中一个必须全部完成后另一个才能启动。

### 2.3 资源与代码冲突依赖（Conflict Dependency）

两个任务虽然没有直接的功能前置关系，却可能修改同一批关键文件、数据库结构或配置。

例如：

- 两个任务都修改订单状态流转服务。
    
- 两个任务都调整相同数据库表。
    
- 两个任务都变更同一组部署配置。
    

此类任务可能存在：

- Git 合并冲突。
    
- 行为覆盖。
    
- 不兼容的数据结构调整。
    
- 重复或矛盾的业务逻辑。
    

**处理原则：评估是否需要串行、合并任务或约定清晰的变更边界。**

文件重叠本身不一定构成必须串行的硬依赖，但需要主动控制集成风险。

### 2.4 验证与集成依赖（Verification Dependency）

某些测试或验收任务必须依赖多个功能任务完成。

例如：

订单超时取消端到端验证，需要：

- 超时判断能力。
    
- 取消状态流转能力。
    
- 定时任务调用入口。
    

这些能力可以分别开发、分别单测，但完整业务链路验证需要等待相关任务集成。

**处理原则：明确单任务验证与跨任务集成验证的不同前置条件。**

### 2.5 外部依赖（External Dependency）

任务可能依赖研发团队以外的条件：

- 第三方 API 或测试环境。
    
- 其他团队交付的接口。
    
- 数据库权限或基础设施资源。
    
- 产品或技术负责人确认的设计决策。
    
- 上游系统完成特定版本发布。
    

外部依赖不一定对应本需求中的 Task，但仍然可能阻塞开发。

**处理原则：明确依赖对象、就绪条件及阻塞时的替代工作。**

## 三、依赖分析的基本原则

### 3.1 基于真实工程关系，而不是文档顺序

SPEC 章节顺序、Task ID 顺序都不必然代表开发顺序。

依赖关系应当来自：

- 实际模块调用关系。
    
- 接口和数据契约。
    
- 数据库与迁移机制。
    
- 共享代码与配置。
    
- 构建及测试要求。
    
- 运行时集成关系。
    
- 外部交付条件。
    

例如，数据库变更不一定永远先于业务代码开发。

如果涉及不停机部署，可能需要先进行向后兼容的结构扩展，然后部署双兼容代码、迁移数据，最后清理旧结构。

因此，必须结合系统现状判断依赖。

### 3.2 只把真正必须先完成的条件设为硬依赖

过度建立硬依赖会使任务全部串行执行，降低 AI 并行协作的空间。

分析时应询问：

- B 是否必须等待 A 完整实现？
    
- 还是只需要 A 先确认接口契约？
    
- 是否可以通过 Mock 或 Stub 开发和测试？
    
- 是否可以先完成 B 的独立部分？
    
- 是否存在可隔离的模块边界？
    

但也不能为了提高并行度，忽略共享数据和运行时状态的约束。

### 3.3 优先降低返工风险，而不是单纯追求速度

任务排序不能只考虑哪个任务最容易实现。

还应考虑：

- 哪个任务影响后续最多？
    
- 哪个任务存在最大的技术不确定性？
    
- 哪个任务会决定公共接口或数据结构？
    
- 哪些高风险问题如果发现太晚，会导致大范围返工？
    
- 哪些变更必须提前验证兼容性？
    

**合理的顺序应在技术风险、依赖关系、开发效率与持续验证之间取得平衡。**

### 3.4 每个开发批次都应该具有可检查的目标

实施批次不应只是：

“第一批做三个任务，第二批做四个任务。”

而应该明确：

- 本批次实现什么工程能力？
    
- 包含哪些 Task？
    
- 需要满足哪些前置条件？
    
- 批次完成后能验证什么？
    
- 是否达到下一批次的启动条件？
    

这样才能形成面向阶段性目标的 AI 开发方式。

## 四、标准执行流程

建议采用五步流程：

### Step 01：识别任务前置条件与依赖

**目标：建立各任务的依赖候选集合。**

输入：

- `TASKS.md` 初稿。
    
- SPEC 与技术评审结论。
    
- 工程变更清单。
    
- 相关代码及调用链证据。
    

逐个任务分析：

1. 任务启动需要哪些基础能力？
    
2. 任务依赖哪些接口、数据模型或公共组件？
    
3. 是否存在需要先稳定的技术契约？
    
4. 是否依赖外部资源或其他团队？
    
5. 是否涉及共享文件或配置冲突？
    
6. 完成验证依赖哪些其他任务？
    

记录依赖类型、依据和就绪条件。

建议的依赖记录格式：

|Task|Depends On|类型|原因|就绪条件|
|---|---|---|---|---|
|TASK-002|TASK-001|Hard|需要新增领域模型|模型可使用且基本测试通过|
|TASK-003|TASK-001|Contract|共享接口定义|接口契约已确认|
|TASK-004|TASK-002、003|Verification|需要完整业务链路|两项功能已集成|

这只是示例，实际依赖必须基于真实代码分析。

**阶段产出：任务依赖候选表。**

### Step 02：构建依赖关系图并检查问题

**目标：让任务之间的前后置关系变得清晰、可检查。**

可以使用 DAG（有向无环图）表示必须遵守的任务先后关系。

例如：

```
flowchart TD
    A["TASK-001 领域模型"] --> B["TASK-002 核心业务能力"]
    A --> C["TASK-003 调度入口"]
    B --> D["TASK-004 集成验证"]
    C --> D
```

注意：

- DAG 主要表达硬前置关系。
    
- 契约依赖、文件冲突、外部依赖可以作为补充元数据。
    
- 不应把所有弱关联都画成必须等待的箭头。
    

重点检查：

- 是否存在循环依赖。
    
- 是否存在错误的前置约束。
    
- 是否有遗漏的前置任务。
    
- 是否存在任务边界重叠。
    
- 是否有外部条件未被记录。
    

如果出现 A 依赖 B、B 又依赖 A，应分析：

- 是否存在真正的架构循环？
    
- 是否应该先拆出共享契约？
    
- 是否应该调整任务边界？
    
- 是否可以合并紧密耦合的任务？
    
- 是否误把协作关系当成硬依赖？
    

**阶段产出：经过检查的任务依赖关系。**

### Step 03：识别技术风险与关键实施路径

**目标：确定哪些工作需要优先实施或验证。**

建议从三个维度评估任务。

**1. 依赖影响**

任务是否被多个后续任务依赖？

例如，公共领域模型、核心接口契约、关键基础组件。

**2. 技术不确定性**

是否存在尚未验证的重要技术假设？

例如，第三方 API 能否满足要求、现有并发机制是否适用、历史数据迁移是否可行。

**3. 变更风险**

错误实施是否会造成较大影响？

例如：

- 核心业务状态流转。
    
- 数据一致性。
    
- 权限与安全。
    
- 向后兼容。
    
- 数据迁移及发布回滚。
    

对于高风险且高不确定性的工作，可以考虑安排探索性 Task、技术验证或提前进行集成试验。

这里还应区分：

**关键路径：** 决定整体完成时间的依赖链。在没有可靠工期估计时，只能识别结构上的关键依赖链，不能精确声称哪条是耗时关键路径。

**关键风险路径：** 如果验证失败，会影响大量后续实施工作的任务或技术决策。

两个概念不能直接混为一谈。

**阶段产出：关键依赖、风险优先级及需要提前验证的事项。**

### Step 04：确定实施顺序与开发批次

**目标：把任务依赖转换为可执行的阶段性开发安排。**

推荐综合考虑：

1. 真实硬依赖关系。
    
2. 接口及数据契约稳定性。
    
3. 风险验证优先级。
    
4. 任务之间的代码冲突。
    
5. 单任务验证与跨任务集成机会。
    
6. AI 并行执行的可控性。
    

可以先按硬依赖进行拓扑排序，得到合法的开发顺序，再根据风险和工程成本调整同一层内的任务安排。

#### 开发批次示例

假设需求为订单超时自动取消：

|批次|目标|包含任务|验证关卡|
|---|---|---|---|
|Batch 01|稳定领域能力|TASK-001|领域规则及单元测试通过|
|Batch 02|接入自动执行机制|TASK-002、003|调度与服务调用验证通过|
|Batch 03|验证完整链路|TASK-004|集成、幂等、并发及回归测试通过|

这里的 Batch 不等于固定周期的 Sprint。

它更接近一个可以验收的工程小目标（Milestone）。

**一个 Batch 可以包含一个或多个 Task；每个 Task 可以进一步具有任务级执行计划。**

#### 并行开发的判断标准

只有在以下条件相对明确时，才建议 AI 并行执行：

- 不存在未满足的硬前置条件。
    
- 接口或数据契约足够稳定。
    
- 文件及模块修改冲突可控。
    
- 不需要共享会发生冲突的运行时环境。
    
- 每个任务能够进行独立验证。
    
- 有明确的集成与合并策略。
    

并行不应只根据“任务之间没有箭头”判断。

如果多个 AI 代理直接修改同一工作目录，还需要通过隔离工作区、Git 分支或其他机制控制变更冲突。

**阶段产出：实施顺序、开发批次及可并行任务建议。**

### Step 05：定义阶段性交付与验证关卡

**目标：让每个批次具有明确的完成条件。**

对每个 Batch，建议明确：

- Batch ID 与目标。
    
- 包含的 Task。
    
- 启动前置条件。
    
- 期望交付能力。
    
- 必须完成的测试。
    
- 集成或兼容性检查。
    
- 阻塞风险。
    
- 下一批次的启动条件。
    

例如：

**Batch 01：订单超时取消领域能力**

包含：TASK-001。

完成要求：

- 超时判断业务规则实现。
    
- 已支付等不允许取消状态得到正确保护。
    
- 状态流转满足既定并发要求。
    
- 对应单元测试通过。
    
- 无阻断性 Review 问题。
    

满足这些要求后，可以启动依赖该能力的后续任务。

注意：这里定义的是需求级实施批次的质量门禁，不取代 04 阶段每个 Task 的详细测试与 Review 流程。

**阶段产出：带有验收关卡的实施批次。**

## 五、标准产物与文档组织

### 5.1 本阶段主要更新 TASKS.md

不建议仅为依赖分析再创建一份必须长期维护的独立文档。

可以在 `TASKS.md` 中新增以下内容：

```
# Development Tasks

## 1. Task List
已有开发任务

## 2. Dependency Analysis
- 任务依赖表
- 关键前置条件
- 外部依赖
- 代码冲突风险

## 3. Execution Order
- 推荐实施顺序
- 可并行任务
- 排序依据

## 4. Implementation Batches
- Batch 01
- Batch 02
- Batch 03

## 5. Milestone Gates
- 阶段目标
- 启动条件
- 验证条件

## 6. Risks & Open Issues
- 高风险事项
- 未解决依赖
- 后续确认要求
```

下一阶段生成 `IMPLEMENTATION_PLAN.md` 时，再将实施策略、批次和重要依赖整合进去。

### 5.2 Task 任务卡需要补充的信息

本阶段完成后，建议任务卡增加：

```
### Dependencies
- Hard Dependencies:
- Contract Dependencies:
- External Dependencies:
- Conflict Notes:

### Execution
- Batch:
- Parallelizable:
- Readiness Conditions:

### Verification
- Task Acceptance Criteria:
- Integration Dependencies:
```

对于没有实际依赖的任务，应标记为“无已知依赖”，而不是留空造成歧义。

### 5.3 阶段产出应保持单一事实来源

推荐：

- `TASKS.md` 保存 Task、依赖、状态和批次关联。
    
- `IMPLEMENTATION_PLAN.md` 保存整体策略、实施安排、里程碑与风险决策。
    
- 实际编码阶段通过 Task ID 关联相应执行计划。
    

避免在多份文档中分别维护同一套完整任务状态和依赖表。

## 六、AI 辅助执行方式

### 6.1 AI 的主要职责

AI 可以负责：

- 读取并理解任务列表。
    
- 检查任务之间的技术依赖。
    
- 结合代码库分析调用与数据关系。
    
- 构建依赖关系图。
    
- 识别循环或冗余依赖。
    
- 提出排序与并行建议。
    
- 识别高风险和高不确定性任务。
    
- 规划开发批次和验证关卡。
    
- 对排序结果开展独立 Review。
    

开发者重点审核：

- 核心任务依赖是否真实。
    
- 是否存在被遗漏的架构或数据依赖。
    
- 并行执行是否符合团队协作条件。
    
- 高风险任务是否安排了合理的验证。
    
- 批次目标是否符合实际开发需求。
    

### 6.2 推荐两轮 AI 工作方式

**第一轮：依赖分析与排序**

输入 TASKS、SPEC、Implementation Context 和代码库。

输出：

- 任务依赖矩阵。
    
- DAG。
    
- 高风险工作。
    
- 推荐执行顺序。
    
- 开发批次。
    
- 阶段性验证关卡。
    

**第二轮：实施顺序 Review**

检查：

- 依赖是否真实。
    
- 是否出现无意义的串行。
    
- 是否存在不安全的并行。
    
- 是否遗漏迁移、兼容性和集成问题。
    
- 批次目标是否可验证。
    
- 是否存在更合理的任务边界。
    

如果发现严重任务拆解问题，返回 `02基于代码库的开发任务拆解` 调整任务后，重新进行依赖分析。

```
2. Implementation Context：[路径]
3. TASKS.md 初稿：[路径]
4. 当前项目代码库
5. 项目工程规范：[路径]

目标：
基于真实工程依赖，为开发任务确定合理的
前置关系、实施顺序、开发批次与验证关卡。

执行要求：

1. 读取任务清单，理解目标、范围和验收标准。
2. 基于代码调用链、数据模型、接口契约、
   共享组件及工程约束分析依赖。
3. 区分：
   - Hard Dependency
   - Contract Dependency
   - Conflict Dependency
   - Verification Dependency
   - External Dependency
4. 只有真正必须等待前置实现完成的任务，
   才建立硬前置关系。
5. 对重要依赖给出代码或设计依据。
6. 构建任务硬依赖 DAG，检查循环与冗余依赖。
7. 识别高不确定性、高影响范围的风险任务。
8. 基于依赖、风险、并行条件确定执行顺序。
9. 按可验收工程目标划分 Implementation Batches。
10. 为各 Batch 定义启动与完成条件。
11. 说明哪些任务可以并行，以及并行前提。
12. 不编写代码，不生成任务级详细执行计划。

- Dependency Matrix
- Hard Dependency DAG
- Risk Analysis
- Recommended Execution Order
- Implementation Batches
- Milestone Gates
- Open Issues

如果发现 Task 拆解存在严重问题，
提出重新拆分或合并建议，不擅自改变
```

```
请以独立工程审查者身份，

- Implementation Context

- Implementation Batches

审查维度：

1. Dependency Correctness
   是否存在错误、遗漏或冗余的硬依赖？

2. Contract Readiness
   是否正确区分契约稳定与实现完成？

3. Parallel Safety
   并行任务是否存在共享代码、数据或环境冲突？

4. Risk First
   高风险技术假设是否得到足够早的验证？

5. Migration & Compatibility
   是否考虑数据库、接口及发布兼容性？

6. Verification Gates
   各开发批次是否具有可验证的完成标准？

7. Task Boundary
   是否出现循环依赖或不合理任务边界？

8. Evidence
   关键依赖和排序判断是否具有工程依据？

输出：
- Review Findings，按严重程度排序
- 涉及 Task / Batch ID
- 证据与影响
- 修改建议
- 未确认事项
- Review Conclusion

请先输出审查结果，不直接修改任务文件。
```

## 九、质量基线

进入下一阶段之前，应检查：

### 依赖正确性

- 关键任务依赖具有真实工程依据。
    
- 硬依赖与契约依赖已区分。
    
- 不存在未解释的循环依赖。
    
- 外部依赖已明确记录。
    
- 未将一般调用关系全部认定为必须串行。
    

### 实施顺序

- 顺序满足全部硬依赖。
    
- 高风险和高不确定性事项有合理处理位置。
    
- 数据库及接口兼容性已纳入考虑。
    
- 并行执行条件已明确。
    
- 共享代码与集成冲突风险得到识别。
    

### 开发批次

- 每个 Batch 具有明确的工程目标。
    
- 每个 Batch 包含的任务范围清晰。
    
- 批次启动条件已明确。
    
- 批次完成标准能够验证。
    
- 必要的跨任务集成验证已安排。
    

### 结果质量

- 任务依赖与排序结果经过必要的 Review。
    
- TASKS.md 已同步更新。
    
- 重大不确定项有处理方案。
    
- 后续能够直接据此编制需求级实施计划。

## 十、常见误区

### 10.1 按任务编号直接排序

Task ID 只是任务标识，不代表真正的依赖关系。

应根据技术前置条件建立实施顺序。

### 10.2 数据库任务一定先做

数据库变更是否需要先做，取决于现有系统、兼容性策略和部署方式。

对于涉及在线迁移的系统，可能需要分阶段扩展、迁移和清理。

### 10.3 所有存在调用关系的任务都必须串行

如果接口契约已稳定，并且能够独立开发与验证，相关任务仍可能并行。

### 10.4 只看依赖，不看风险

虽然某项高风险技术验证没有硬前置依赖，也可能值得提前实施，以减少后续大规模返工。

### 10.5 只追求并行数量

并行任务过多可能增加共享代码冲突、环境争用和集成成本。

并行需要符合真实工程条件，不是越多越好。

### 10.6 批次只有任务列表，没有交付目标

这样的批次只是任务分组，无法用于阶段性验收。

应明确批次完成后具备什么能力、需要通过哪些检查。

### 10.7 发现循环依赖后强行排序

循环依赖通常需要重新检查任务边界或技术契约，而不是任意指定 A 或 B 先执行。

本阶段完成意味着：

**已基于真实代码库、技术设计及开发任务清单，建立可信的任务依赖关系，识别关键风险与并行约束，并形成满足前置条件、具有清晰阶段性目标和验证关卡的实施顺序及开发批次。**
