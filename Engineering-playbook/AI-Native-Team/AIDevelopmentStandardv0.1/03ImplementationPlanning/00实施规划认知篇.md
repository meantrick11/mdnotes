# 00 实施规划认知篇

> **所属阶段：** `03ImplementationPlanning`
> 
> **上游阶段：** `02TechnicalDesign`（技术设计与 SPEC 评审）
> 
> **下游阶段：** `04Implementation`（任务级规划与编码实现）
> 
> **核心输入：** 已评审 SPEC、当前项目代码库、项目工程规范、技术评审结论
> 
> **核心产出：** `IMPLEMENTATION_PLAN.md`、`TASKS.md`
> 
> **阶段目标：** 将经过评审的技术方案，结合真实代码库转化为可执行、可验证、可追踪的工程实施计划。

## 一、实施规划的定位与价值

### 1.1 什么是实施规划？

实施规划（Implementation Planning）是技术设计与代码实现之间的衔接阶段。

它并不是简单地把 SPEC 转成 TODO List，而是：

**以经过评审的 SPEC 为目标依据，以真实代码库为实施依据，以项目工程规范为约束，识别实际需要发生的工程变更，并将其组织为具有明确边界、依赖关系、实施顺序和验收标准的开发任务。**

实施规划主要回答六个问题：

|维度|核心问题|
|---|---|
|What|SPEC 中有哪些内容需要落地？|
|Where|现有项目中对应的实现在哪里？|
|Change|哪些代码需要新增、修改、复用或删除？|
|Split|应如何拆分成合理的开发任务？|
|Sequence|任务之间有哪些依赖？应该按什么顺序实施？|
|Verify|如何验证任务完成以及整个需求符合 SPEC？|

核心目标是让开发从「临时决定如何写代码」转向「依据经过审查的计划有序实施」。

### 1.2 为什么 SPEC 通过评审后不能直接编码？

SPEC 解决的是技术方案问题，实施规划解决的是工程落地问题。

即使 SPEC 已经明确接口、数据库表、业务逻辑和架构设计，仍可能缺少以下实施信息：

- 已有代码中哪些能力可以复用？
    
- 哪些类、模块、服务需要修改？
    
- 哪些设计点已经部分实现？
    
- 哪些改动存在隐含的调用链或数据依赖？
    
- 开发任务如何划分才能方便 AI 执行和验证？
    
- 应先修改数据库、领域逻辑还是接口？
    
- 每个任务完成后如何测试？
    
- 多个任务集成后如何确认没有遗漏？
    

如果跳过实施规划，开发过程容易退化为：

一个接口 → 人工描述给 AI → AI 实现 → 人工检查 → 补充遗漏 → 再开发下一个接口。

这种方式的主要问题不是 AI 编码能力不足，而是缺少稳定的任务组织、工程上下文和验证机制。

**实施规划的价值，在于提前明确任务目标、工程变更和验证要求，减少开发者在每次编码对话中重复进行基础决策。**

需要注意：实施规划可以降低遗漏和返工风险，但不能保证 AI 一次性生成的代码完全正确，后续仍然需要测试、Review 和人工验收。

## 二、实施规划必须以真实代码库为基础

### 2.1 三个核心输入

实施规划需要同时依赖三类信息：

**1. SPEC：定义目标**

说明要实现什么，以及已经确定的技术方案。

主要包括：

- 需求范围及验收标准
    
- 接口与数据结构
    
- 核心业务逻辑
    
- 模块与架构设计
    
- 异常和边界处理
    
- 非功能性要求
    
- 技术评审结论
    

**2. Codebase：定义实现现状**

说明项目已经具备什么能力，以及实际需要修改什么。

主要包括：

- 代码目录与模块职责
    
- 核心调用链和数据流
    
- 现有接口和业务实现
    
- 可复用组件与公共能力
    
- 数据访问和事务处理方式
    
- 现有测试及测试基础设施
    
- 模块之间的实际依赖
    

**3. Project Context：定义工程约束**

说明开发必须遵循哪些规范。

例如：

- `AGENTS.md` 或对应 AI 工具的项目规则
    
- 项目架构原则与目录约定
    
- 编码与异常处理规范
    
- 构建、测试、检查命令
    
- 数据库变更规范
    
- 安全、兼容性和发布约束
    

这三类信息缺一不可。

只基于 SPEC 拆解，容易得到脱离项目现实的理论任务。

只基于代码库拆解，则可能遗漏已经评审确定的业务目标和设计要求。

忽略工程规范，则可能生成虽然功能可用、但不符合项目工程要求的实施方案。

### 2.2 先建立 SPEC 与代码现状的映射

在正式拆解任务之前，应当识别：

**SPEC 中的设计目标，在当前项目中对应什么实现现状？**

例如，SPEC 需要增加订单超时取消功能。

|SPEC 设计点|代码现状（假设）|实施判断|
|---|---|---|
|订单超时扫描|已存在通用定时任务框架|复用并扩展|
|订单取消逻辑|已有状态流转服务|扩展现有能力|
|超时配置|尚未实现|新增配置|
|取消事件通知|已有领域事件机制|复用并补充|
|并发控制|已有条件更新机制|验证是否满足需求|

有了这层映射，才能较准确地判断：

- 哪些工作需要新增？
    
- 哪些工作是扩展现有实现？
    
- 哪些设计点已经满足，无需重复开发？
    
- 哪些现有能力需要复用？
    
- 哪些设计假设与真实代码存在差异？
    

**先识别工程变更，再组织开发任务，而不是直接把 SPEC 章节转换成任务。**

### 2.3 与技术设计阶段的代码探索有什么区别？

实施规划不应该重新进行一次完整的项目代码库探索。

在 `02TechnicalDesign` 中，已经为了制定技术方案开展了代码探索、影响分析和方案评估。

其成果应当优先复用。

|维度|02 技术设计|03 实施规划|
|---|---|---|
|核心目的|支撑技术方案决策|支撑开发任务和实施顺序|
|探索方向|架构、影响范围、技术可行性|代码落点、工程变更、依赖和验证入口|
|主要关注|应该如何设计|具体需要改变什么|
|主要产出|SPEC|Task 与 Implementation Plan|
|探索策略|方案驱动探索|SPEC 驱动的定向增量探索|

如果技术设计阶段已经明确相关模块、复用方案和关键依赖，可以直接继承。

但如果设计结束后代码库发生变化，或者尚未确定真实代码落点，就需要补充探索。

这里需要特别注意：

**03 阶段不需要穷尽每个方法、参数和代码行，但必须为任务提供足够可信的工程依据。**

更详细的文件级实施步骤留到 `04Implementation`。

## 三、从设计点到工程任务的转换

### 3.1 区分三个层次

**第一层：SPEC Design Item（设计点）**

描述需要实现的能力及其技术设计。

例如：

支持订单在超时后自动取消。

**第二层：Engineering Change（工程变更）**

描述为满足设计目标，当前项目实际需要发生哪些变化。

例如：

- 扩展订单超时判断能力。
    
- 新增定时任务调度入口。
    
- 复用现有订单状态流转服务。
    
- 完善超时取消的并发控制。
    
- 增加对应测试。
    

**第三层：Development Task（开发任务）**

将工程变更组织为边界清晰、能够验收的执行单元。

例如：

- Task-001：实现订单超时判断及单元测试。
    
- Task-002：基于现有框架增加超时扫描任务。
    
- Task-003：完成订单自动取消业务集成与并发验证。
    

关系如下：

`SPEC Design Item → Engineering Changes → Development Tasks`

这三个层次不一定是一对一关系。

一个 SPEC 设计点可能对应多个工程变更；多个关联工程变更也可能组合成一个开发任务。

### 3.2 什么是合理的任务粒度？

合理的开发任务应当满足：

1. **目标明确：** 知道任务要完成什么。
    
2. **范围清晰：** 知道需要修改什么，以及不应该修改什么。
    
3. **依赖明确：** 知道需要哪些前置条件。
    
4. **可以验证：** 有明确的测试或验收方式。
    
5. **便于审查：** 代码变更范围能够被有效 Review。
    
6. **上下文可控：** AI 能在合理的工作上下文中完成实施。
    

任务拆解不应该机械地按照：

- 一个接口一个任务。
    
- 一个数据库表一个任务。
    
- 一个类一个任务。
    
- 一个文件一个任务。
    

实际项目中，一个业务功能可能需要同时修改接口、Service、Repository 和测试代码。将这些内容组织成一个可验证的任务，可能比拆成多个无法独立验证的微小任务更合理。

反过来，如果任务涉及多个独立业务能力、较大范围的模块修改或高风险数据迁移，则可能需要进一步拆分。

**任务粒度由可执行性、可验证性、依赖关系和代码变更风险共同决定。**

### 3.3 不必要求所有任务完全独立

工程任务通常存在依赖。

例如：

数据库结构调整 → 持久化逻辑 → 业务服务 → API 集成。

因此更实际的要求是：

- 每个任务有清晰的职责边界。
    
- 任务依赖能够显式表达。
    
- 每个任务有与其职责相符的完成证据。
    
- 在完成前置依赖后可以执行。
    

不应为了追求所谓的独立任务，强行重复实现基础能力或制造临时架构。

## 四、实施规划采用两级计划机制

AI-Native 开发中，建议明确区分需求级计划和任务级计划。

### 4.1 需求级实施计划

**归属：** `03ImplementationPlanning`

**规划对象：** 整个需求或一份完整 SPEC。

主要解决：

- 需求需要多少个开发任务？
    
- 每个任务的目标与范围是什么？
    
- 任务之间有什么依赖？
    
- 采用什么实施顺序？
    
- 哪些阶段需要集成验证？
    
- 哪些风险需要提前处理？
    

核心产出：

- `IMPLEMENTATION_PLAN.md`
    
- `TASKS.md`
    

这一层需要明确工程变更范围，但不必为所有 Task 提前规划每一行代码。

### 4.2 任务级执行计划

**归属：** `04Implementation`

**规划对象：** 当前选定的一个 Task。

主要解决：

- 当前相关代码的实际状态是什么？
    
- 需要修改哪些具体文件和方法？
    
- 具体实现步骤是什么？
    
- 有哪些关键边界条件？
    
- 需要增加哪些测试？
    
- 如何验证修改没有破坏已有能力？
    

核心产出：

- `TASK_PLAN.md` 或等价任务执行记录
    
- 代码变更
    
- 对应测试
    
- 验证与 Review 结果
    

对于简单任务，可以不单独创建 Task Plan 文件，而是在任务卡或 AI 执行上下文中维护简短计划。

### 4.3 两级计划的协作关系

整个过程为：

`SPEC → 代码现状映射 → 工程变更 → 需求级计划 → 选择 Task → 任务级计划 → 编码与验证`

需求级计划用于保持整体方向和任务依赖稳定。

任务级计划根据最新代码状态进一步确定具体实施方式。

这种机制既避免了一次性将整个 SPEC 交给 AI 编码，也避免了每实现一个接口都需要开发者重新解释整体背景。

## 五、实施规划阶段的五步工作流

### 01 SPEC 接收与实施现状探索

**目标：明确设计目标与当前工程实现之间的差距。**

主要工作：

- 接收已评审 SPEC 和评审结论。
    
- 复用技术设计阶段的代码探索成果。
    
- 定向探索相关模块、调用链和测试入口。
    
- 建立 SPEC 与代码现状的映射。
    
- 识别需要新增、修改、删除和复用的工程能力。
    
- 识别阻塞性设计问题及实施风险。
    

阶段产出：

**实施现状分析与工程变更清单。**

可作为后续 Implementation Plan 的输入或章节，不强制创建独立文档。

### 02 基于代码库的开发任务拆解

**目标：将工程变更转换为可执行、可验证的 Task。**

主要工作：

- 识别需要完成的工程工作。
    
- 根据功能边界和技术依赖组织任务。
    
- 定义任务目标与实施范围。
    
- 明确前置条件和验收标准。
    
- 建立 Task 与 SPEC 的追踪关系。
    
- 检查任务遗漏、重复和粒度问题。
    

阶段产出：

`**TASKS.md**` **初稿。**

### 03 任务依赖分析与实施排序

**目标：形成合理的任务执行路径。**

主要工作：

- 分析任务之间的技术依赖。
    
- 确定必须先完成的基础工作。
    
- 识别可并行实施的任务。
    
- 评估高风险变更。
    
- 确定实施顺序、开发批次和关键检查点。
    
- 安排必要的集成测试节点。
    

阶段产出：

**任务依赖关系、实施批次与里程碑。**

### 04 需求级实施计划编制

**目标：将已有分析整合为正式的实施计划。**

主要工作：

- 明确整体实施策略。
    
- 整理任务及依赖关系。
    
- 确定开发顺序。
    
- 明确每个阶段的完成标准。
    
- 规划测试与集成验证。
    
- 记录技术风险和实施约束。
    

阶段产出：

`**IMPLEMENTATION_PLAN.md**`**。**

### 05 实施计划评审与开发移交

**目标：确认计划足以支持后续 AI 开发。**

主要工作：

- 检查是否覆盖所有 SPEC 设计目标。
    
- 检查工程变更是否基于真实代码。
    
- 检查任务粒度与边界是否合理。
    
- 检查依赖和实施顺序。
    
- 检查测试、兼容性与验收要求。
    
- 审核关键风险和未解决问题。
    
- 确认首批可执行任务。
    

阶段产出：

**评审通过的实施计划，以及可以进入 04 阶段的开发任务。**

## 六、AI 在实施规划中的职责

### 6.1 AI 应承担的工作

AI 可以主要负责：

- 阅读 SPEC 和技术评审结论。
    
- 定向探索当前代码库。
    
- 建立设计点与现有代码的映射。
    
- 识别工程变更。
    
- 提出开发任务拆解方案。
    
- 分析任务依赖与风险。
    
- 编排实施顺序。
    
- 生成实施计划。
    
- Review 任务拆解和计划质量。
    

AI 的结论应尽可能引用可验证的代码依据，而不是依赖未经检查的推测。

### 6.2 开发者应承担的工作

开发者重点负责：

- 确认需求与设计意图。
    
- 审核工程变更范围。
    
- 决定高风险任务的实施策略。
    
- 确认任务边界和优先级。
    
- 处理设计与代码现状之间的冲突。
    
- 审核整体计划及关键验收要求。
    

开发者不必替 AI 列出每一个需要修改的方法，但需要能够判断 AI 的实施计划是否正确覆盖业务目标、符合工程约束。

**AI 可以负责提出和完善实施路径，开发者负责关键决策和质量门禁。**

## 七、实施规划的标准产物

### 7.1 IMPLEMENTATION_PLAN.md

需求级实施计划，建议包括：

1. 需求与 SPEC 引用。
    
2. 实施目标与范围。
    
3. 代码现状与工程变更概览。
    
4. 实施策略。
    
5. 开发任务与依赖关系。
    
6. 实施顺序与里程碑。
    
7. 测试、集成与验收策略。
    
8. 风险、阻塞项及应对方案。
    
9. 计划评审结论。
    

### 7.2 TASKS.md

开发任务清单，建议每个任务包含：

|字段|说明|
|---|---|
|Task ID|唯一任务标识|
|Name|任务名称|
|Objective|任务目标|
|Scope|实施范围|
|Code Area|预计涉及模块|
|SPEC Reference|对应 SPEC 章节|
|Dependencies|前置任务|
|Acceptance Criteria|验收标准|
|Status|任务状态|

对于简单需求，可以将 TASKS 直接作为 Implementation Plan 中的任务章节。

### 7.3 产物设计原则

- 计划不是代码的替代品，而是执行依据。
    
- 尽量避免重复记录 SPEC 已经明确的技术设计细节。
    
- 保留必要的代码依据和设计追踪关系。
    
- 让任务状态和计划变更可维护。
    
- 保证更换 AI 会话后仍能恢复执行上下文。
    
- 不为了文档数量而创建没有明确用途的文件。

## 八、实施规划阶段的 Skills 能力地图

当前先定义目标能力，不预设所有能力都需要封装成 Skill。

|能力|核心用途|
|---|---|
|`implementation-readiness`|SPEC、代码库和工程条件检查|
|`spec-codebase-mapping`|SPEC 与代码实现映射|
|`engineering-change-analysis`|识别新增、修改、复用、删除的工程变更|
|`spec-to-tasks`|基于代码库进行任务拆解|
|`task-dependency-analysis`|依赖关系与实施排序|
|`implementation-planning`|编制需求级实施计划|
|`plan-review`|实施计划质量评审|

以上为 Skill 候选能力名称，尚不表示已经找到或验证对应实现。

后续每个流程篇需要进一步明确：

- 有哪些现成的 Skill 可复用？
    
- 什么情况下触发？
    
- 需要提供哪些上下文？
    
- 使用什么模板约束产出？
    
- 如何检查 Skill 的输出质量？
    
- 哪些能力值得自行封装？
    
- 是否有更适合使用普通 Prompt 或工具命令的场景？
    

**原则：先把流程跑通并验证有效，再将重复、稳定的工作封装成 Skill。**

## 九、实施规划的质量基线

进入 `04Implementation` 前，应满足以下条件：

- SPEC 和技术评审结论已确认。
    
- 已复用或补充必要的代码库探索。
    
- 主要 SPEC 设计点与当前代码现状存在明确映射。
    
- 关键工程变更已识别。
    
- 必须交付的需求点均已映射到任务或其他明确的交付项。
    
- 各 Task 的目标、边界及验收标准清晰。
    
- 关键任务依赖和实施顺序合理。
    
- 测试、集成与回归工作已纳入计划。
    
- 重要技术风险与设计冲突已得到处理或记录。
    
- 实施计划通过必要的 AI Review 和人工审核。
    
- 首批 Task 具备开发启动条件。
    

这里的目标不是提前消除全部技术不确定性，而是将影响实施的关键未知项显式化，并对其安排验证或处理任务。

## 十、实施规划中容易出现的误区

### 误区一：拿到 SPEC 就直接生成任务

忽视真实代码库，容易重复开发已有能力、遗漏隐藏依赖或规划错误模块。

**正确方式：先建立设计与代码现状的映射，再识别工程变更和开发任务。**

### 误区二：重新完整探索代码库

技术设计阶段已有探索成果，却在实施规划中从零重复分析。

**正确方式：复用已有探索结果，仅针对实施落点、变化和不确定项补充探索。**

### 误区三：任务拆得越细越好

将每个接口、类或文件都拆成独立任务，导致大量任务无法独立验证。

**正确方式：以可执行、可验证的工程目标作为任务边界。**

### 误区四：实施计划写到代码行级别

在需求级规划时提前为所有任务制定详细的代码修改方案，导致计划冗长且容易失效。

**正确方式：需求级计划规划任务与依赖；任务级计划进一步确定具体实现步骤。**

### 误区五：只规划业务代码，不规划测试

任务清单只有接口和 Service 的实现，没有异常、并发、兼容性和集成验证。

**正确方式：将测试与质量要求纳入任务验收标准，并安排必要的跨任务验证工作。**

### 误区六：认为 SPEC 通过评审就不能再调整

开发中发现设计假设错误，却为了维持原方案强行修改代码。

**正确方式：识别偏差，区分实施调整与设计变更；涉及关键设计变化时重新确认并同步更新 SPEC。**

### 误区七：只检查计划是否完整，不检查是否可执行

AI 生成了结构完整的实施计划，但其中的类名、模块、依赖或验收方式没有实际依据。

**正确方式：评审时同时检查 SPEC 覆盖度、代码依据、任务粒度、依赖和验证策略。**

## 十一、本阶段的完成定义（Definition of Done）

实施规划完成并不意味着全部代码实现细节都已确定。

它意味着：

**已评审 SPEC 中需要交付的设计目标，已经基于真实代码库识别出工程变更，并被组织成具有明确目标、范围、依赖、顺序和验收标准的开发任务，形成经过审查、能够指导后续 AI 编码的实施计划。**

最终产出：

- `IMPLEMENTATION_PLAN.md`
    
- `TASKS.md`
    
- 实施计划评审结论
    

进入下一阶段：

`04Implementation`

执行方式：

**选择可执行 Task → 任务级实施计划 → AI 编码 → 自测 → AI Review → 修复与复测 → 任务验收 → 更新计划 → 下一个 Task。**

---

## 十二、核心认知总结

实施规划的核心不是让 AI 生成一份看起来完整的开发计划，而是建立一条可信的工程执行路径：

**SPEC 定义目标 → Codebase 提供现实依据 → Engineering Changes 明确需要修改什么 → Tasks 组织可执行工作 → Implementation Plan 确定顺序与验证方式。**

对于 AI-Native 开发而言，实施规划最重要的价值是：

**让开发者从逐个接口解释实现细节，转向审核和管理具有明确工程依据的任务；让 AI 从被动接受零散编码指令，转向在受控任务边界内进行规划、编码和验证。**
