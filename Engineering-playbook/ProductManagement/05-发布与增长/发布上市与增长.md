# 6 发布上市与增长：上线是起点，不是终点

> 主要来源：[产品发布](https://www.atlassian.com/agile/product-management/product-release)、[产品上市](https://www.atlassian.com/agile/product-management/product-launch)、[上市清单](https://www.atlassian.com/agile/product-management/product-launch-checklist)、[上市时间线](https://www.atlassian.com/agile/product-management/product-launch-timeline)、[上市活动](https://www.atlassian.com/agile/product-management/product-launch-event)、[增长产品管理](https://www.atlassian.com/agile/product-management/growth-product-management)、[产品驱动增长](https://www.atlassian.com/agile/product-management/product-led-growth)。

## 6.1 Release 与 Launch：同一天也不一定是同一件事

产品 **Release** 侧重让新产品或更新能够被客户使用：测试、部署、支持与后续处理。产品 **Launch** 侧重把价值带到市场：定位、目标受众、销售与营销准备、传播和效果观察。两件事可以同时发生，但检查清单不同。

| 关注点 | Release：交付可用能力 | Launch：让市场理解并采用 |
| --- | --- | --- |
| 关键问题 | 功能是否安全、稳定、可用？ | 对谁有价值，如何让他们知道并尝试？ |
| 主要协作 | 研发、测试、运维、支持 | 产品、营销、销售、支持及研发 |
| 常见准备 | 验收、部署、回退、文档、支持方案 | 定位、信息、演示、渠道、销售材料 |
| 后续观察 | 故障、性能、使用与求助情况 | 触达、激活、反馈、留存与业务影响 |

例如，知识库的邀请权限预览已部署，不代表客户知道它能解决“怕邀请错人”的顾虑。产品团队还需要在引导、帮助内容或发布沟通中清楚解释这一价值；同时监控是否真的出现更多首次共同编辑。

### 6.1.1 一个上线后仍然失败的情境

假设权限预览功能稳定上线，邀请点击率也上升了，但共同编辑率没有变化。可能是受邀者没有理解邮件、加入流程太长，也可能是被邀请者根本没有共同任务。技术发布已经完成，但产品结果尚未达到。此时继续扩大宣传，会让更多用户走进同一个断点；应先找出漏斗中新的阻碍。

发布后至少有三条反馈线：**技术质量**（故障与性能）、**使用行为**（能否完成任务）、**客户理解**（他们如何解释体验）。只看其中一条，都容易误判。

## 6.2 用时间线串起团队，而不是只填日期

[上市清单](https://www.atlassian.com/agile/product-management/product-launch-checklist)与[上市时间线](https://www.atlassian.com/agile/product-management/product-launch-timeline)强调提前明确目标、受众、负责人、依赖和发布后反馈。一个简洁的三阶段安排是：

| 阶段 | 应解决的问题 | 典型产物 |
| --- | --- | --- |
| 上市前 | 面向谁、价值主张是什么、各团队准备好了没有？ | 定位、演示、验证结果、支持材料、风险预案 |
| 上市时 | 用户能否顺利发现、理解并使用？ | 发布沟通、产品内引导、渠道协同 |
| 上市后 | 是否触达目标人群、带来预期行为？ | 反馈汇总、指标复盘、下一轮调整 |

[上市活动](https://www.atlassian.com/agile/product-management/product-launch-event)提供演示、故事讲述和互动体验等传播思路。它适合需要集中引起关注的场景；是否举办活动，应由受众和目标决定，而不是把“热闹”当作上市成功。

### 6.2.1 上市清单要覆盖“谁来接住用户”

一个容易遗漏的角色是客户支持。产品发布后，第一批用户的问题可能先到支持团队，而非产品经理。上市前应让支持团队知道目标用户、功能边界、常见误解、问题升级路径和暂不支持的场景；销售也需要知道哪些能力已经可用，哪些仍处于小范围试验。这样传播出去的承诺才能与真实体验一致。

| 检查项 | 只问“完成了吗”还不够 | 更有用的追问 |
| --- | --- | --- |
| 帮助文档 | 文档是否已发布？ | 新用户能否照着完成邀请？ |
| 销售材料 | 是否已制作？ | 是否明确说明适用对象和限制？ |
| 上线监控 | 面板是否存在？ | 出现异常时谁判断、谁行动？ |
| 反馈入口 | 是否建了工单分类？ | 反馈能否回到下一轮产品决策？ |

## 6.3 增长是一组可以学习的实验

[增长产品管理](https://www.atlassian.com/agile/product-management/growth-product-management)把过程写成寻找机会：定义想要的结果，绘制机会，选择重点，设计实验，分析结果，再调整策略。知识库团队可以围绕“邀请 → 受邀者加入 → 首次共同编辑 → 下周继续协作”寻找最大断点。改一个按钮颜色可能提高点击，却未必改善真正的协作结果。

[产品驱动增长（PLG）](https://www.atlassian.com/agile/product-management/product-led-growth)则让用户通过亲身使用感受到价值，由产品体验推动获取、转化与扩展。前提是用户能较快抵达“原来它对我有用”的时刻；否则免费试用只是让更多人更快遇到障碍。

### 6.3.1 把漏斗当作诊断图，而不是成绩单

知识库的增长路径可以写成：访问 → 注册 → 创建第一篇 → 邀请同事 → 首次共同编辑 → 次周回访。每一步的转化率帮助定位哪里流失，但不能直接给出原因。若“注册 → 创建第一篇”流失大，应研究空白页与价值表达；若“邀请 → 共同编辑”流失大，应研究受邀者的任务和进入体验。实验应改变一个明确的障碍，并观察下游结果是否随之改善。

**我的整理**：增长不是不断优化每个百分比。某一步点击率升高，却让后续客户失望，可能损害长期留存。优先看完整价值链，而不是孤立的局部转化。

> **记住**：发布是把能力交到客户手中，上市是让合适的人理解它，增长是验证并扩大持续价值。三者的成功标准不相同。

## 6.4 复盘与自检

上线后一周，你会同时看哪一个技术信号、哪一个用户行为信号、哪一条客户反馈？如果上市声量很大但真正使用的人少，团队能否分清“触达错了人”“价值没说清”和“产品体验没有兑现承诺”？
